## From Humble Boards to Mighty Cluster: My Raspberry Pi Kubernetes Adventure

For a while, I’d been fascinated by Kubernetes. The promises of orchestration, scalability, and declarative infrastructure management were compelling, even if the learning curve looked a little…vertical. Then it hit me – why *not* build my own cluster? And naturally, because the internet is full of people doing neat things with hardware, Raspberry Pi 4s sprang to mind. Three of them, specifically.

This post details that journey - from the initial excitement to the occasional frustration (mostly involving storage), and finally arriving at a working, if somewhat modest, Kubernetes cluster humming away in my home office. **Consider this less a definitive guide and more a chronicle of *my* learning experience.**  Your mileage will vary.

### The Players: Three Raspberry Pi 4s & A Network

First things first – the hardware. I opted for three Raspberry Pi 4 models with 4GB of RAM each (8GB is even better if you can swing it). Each has a quality microSD card (32GB or larger - this will be critical, as we'll see) and enough cooling to avoid thermal throttling. You’ll also need a reliable network; I used wired connections – far superior for stability than relying on patchy Wi-Fi.

**Roles & Responsibilities:**

*   **Master Node (Pi 1):** The control plane of the cluster - managing deployments, pods, and overall state.
*   **Worker Node 1 (Pi 2):** Executes the actual workloads – containers running your applications.
*   **Worker Node 2 (Pi 3):** Another worker node for additional capacity and redundancy.

### Networking: Getting Everyone Talking

Kubernetes requires a functioning network to communicate between components. I chose **Calico** as my Container Network Interface (CNI). Other popular choices like Flannel are viable, but Calico offered the features I needed at this stage including better security policies.  The process looks roughly like this:

1.  **Assign Static IPs:** Each Raspberry Pi needs a fixed IP address on your local network. This prevents configurations from breaking when DHCP leases expire.
2.  **Install Container Runtime (Containerd):** Kubernetes uses a container runtime to manage containers. Docker is still popular, but I chose the leaner and newer Containerd. Follow instructions for your preferred operating system – in my case, Raspberry Pi OS (64-bit).
3.  **Deploy Calico:** This involved using `kubectl` (installed on the master node) along with several YAML manifests provided by the official Calico documentation. The key is getting the Kubernetes API server and other components to discover each other.
4.  **Initial Cluster Setup:** I used *kubeadm* for bootstrapping my cluster, following a standard guide. This process handles certificate generation, token creation, and basic control plane setup.

Networking proved less of a headache than anticipated – but it’s absolutely crucial to have accurate details (IP addresses, DNS settings) during the entire configuration.  Any little mistake here can trigger hours of troubleshooting.

### The Elephant in the Room: Storage

This is where things got…complicated. Kubernetes benefits hugely from persistent storage; without it, all your containers would lose their data when they restart. MicroSD cards are *not* designed for this level of sustained write activity. They wear out quickly and become unreliable. It’s a known issue.

**Initial (Bad) Ideas:**

*   **Directly using microSD storage:** This was my first thought, but quickly abandoned due to the fragility of SD cards in continuous operation.
*   **Network File System (NFS):** A possibility, but I decided against it because performance would be heavily dependent on network conditions and added another point of failure.

**The Solution: NFS from a Separate Server**

Ultimately, I opted for a dedicated Network Storage server sitting entirely outside the Kubernetes cluster. This is a machine – in my case an older desktop - running Ubuntu and configured with an NFS share.  This provided persistent storage that *wasn't* constrained to the limited resources of the Raspberry Pis themselves.

Here’s how it worked:

1.  **Configure the NFS Server:** Set up an NFS export on a relatively high-capacity drive (I used 500GB).
2.  **Create Persistent Volumes:** Defined Kubernetes PersistentVolumes that pointed to this remote NFS share, complete with read/write permissions and storage classes.
3.  **Dynamic Provisioning (Optional):** While I didn't use it in the beginning, implementing dynamic provisioning through a StorageClass would automatically create persistent volumes as needed – a significant convenience for scaling deployments.

This approach did introduce some latency due to network overhead. It’s certainly *not* ideal for performance-critical applications, but for my testing environment and occasional hobby projects, it was an acceptable compromise. **The single most important part here is that your NFS share should be on a drive specifically designated for the task.**

### What's Running? Learning in Miniature

Now, what am I actually using this little Kubernetes cluster *for*? The purpose of building it wasn’t just to have a shiny toy (though that's definitely a perk). It was primarily for learning and experimentation. Here are some things I’ve thrown at it:

*   **A Simple Web Application:** A basic Node.js application deployed as a microservice. This allowed me to get comfortable with deployments, scaling, and rolling updates.
*   **Monitoring Tools (Prometheus & Grafana):** Gathering metrics about the cluster itself - resource usage, container performance – is invaluable for understanding its behavior.
*   **A Lightweight Home Automation Dashboard:**  Connecting a few sensors picked up via MQTT to create a simple display that provides some at-a-glance status of my home systems.

The applications are relatively simple, but it demonstrates the principles of distributed architecture and Kubernetes orchestration in a compact environment. The limitations (especially storage performance) keep deployments realistic – I can’t expect miracles from three little Raspberry Pis!

### Lessons Learned & Future Plans

Building this cluster has been an incredibly rewarding learning experience. It's given me a much more tangible understanding of Kubernetes concepts than any online tutorial could provide.  Here are some lessons:

*   **Storage is King:** Seriously, don’t underestimate its importance and the inherent challenges involved with microSD storage.
*   **Networking is Paramount:** Get it right from the start. Use static IPs and ensure DNS resolution works flawlessly.
*   **Start Small:** Don't try to deploy complex workloads immediately. Begin with simple applications and gradually increase complexity.

Future improvements include:

*   Exploring software-defined storage solutions (e.g., Rook, Ceph) for better local persistence – a significant undertaking!
*   Automating the cluster deployment process using tools like Ansible or Terraform.
