## From Gerrit Gates to GitHub Glory: Our Code Review Journey

For a while, our engineering team of five was firmly in the Gerrit camp. We’d established workflows, understood the nuances, and even built documentation around it. Then, we decided to make a significant shift – migrating entirely to GitHub Pull Requests (PRs) for our code review process. It wasn't a decision taken lightly, but after several months using PRs exclusively, we feel confident that this switch has brought substantial improvements to our productivity and overall development experience.

This post details why we made the move, what we valued about Gerrit, and how GitHub’s approach ultimately proved more effective for our team dynamics. It's a candid breakdown – because honestly, leaving behind aspects of Gerrit was tough!

**(Image: A split image showcasing the Gerrit interface on one side and a clean, modern GitHub PR view on the other.)**

**Why We Were Using Gerrit (and What Was Good About It)**

We initially chose Gerrit for its robustness in controlling access to our codebase. For teams working with highly regulated processes or demanding code quality requirements, Gerrit's fine-grained permissions and approval workflows are a strong selling point.  Specifically, we appreciated:

*   **Strict Approval Process:** Gerrit’s "verify" system offered an extra layer of security before merging changes. It ensured that at least two engineers had signed off on the proposed modifications. While this added rigor, it sometimes led to bottlenecks (more on that later).
*   **Change History & Transparency:**  The history provided by Gerrit was very detailed, showing each change with its approvers and comments in a readily accessible manner. This contributed to a strong sense of transparency within the team. 
*   **Dedicated Review Focus:** The Gerrit interface pushed you directly into code review without distractions. It prevented that tempting “just quickly look at this” mindset which can easily lead to rushed reviews.

**The Growing Challenges with Gerrit**

While those benefits were valuable, several cracks started to show as our team grew and projects became more complex. Here's what we found increasingly cumbersome:

*   **Merge Workflow Complexity:** Gerrit’s branching model (integrated-submit) could be difficult for new team members to grasp, adding a learning curve that often delayed simple changes. The extra steps between pushing a change and landing it in the main branch were significant overhead.
*   **Slow Feedback Loops:**  The required approvals created a noticeable delay in getting feedback on code. While quality was prioritized, this sometimes stalled development speed, particularly when dealing with smaller or experimental changes. That rigidity led to people opening less frequent PRs as they wanted to be sure they'd get the sign-off quickly.
*   **Context Switching:**  Moving between Gerrit and GitHub (for other tasks) introduced a mental burden. It required developers to constantly shift their mindset when reviewing, committing or otherwise working on code. 
*   **Limited Integrations & Discoverability:** While integrations existed, they often felt less streamlined than what we could achieve with GitHub Actions and its broader marketplace of tools. Tracking changes across different platforms was also a chore.

**(Image: A simple diagram contrasting the Gerrit branching model (integrated-submit) to GitHub's simpler branch/PR workflow.)**

**Why We Made The Switch to GitHub Pull Requests**

GitHub’s PR system ticked boxes that were becoming increasingly important for us. It provided flexibility and streamlined our process without sacrificing quality.

*   **Simplified Workflow:**  The standard branching model (feature branches, merge requests) is easier to understand, reducing onboarding time and allowing developers to move more rapidly with their work.
*   **Faster Feedback Cycles:** The optional approval requirement allows for quicker feedback loops for smaller changes or exploratory development. This encourages continuous feedback from multiple engineers on areas ripe for refinement without the formal barrier of dedicated approvals. 
*   **Native Tooling & Integration:**  GitHub’s extensive integrations with other tools (testing frameworks, linters, issue trackers) provided a more cohesive and automated workflow. GitHub Actions has made it remarkably simple to automate checks and build processes.
*   **Improved Collaboration:** The inline commenting features in PRs are simply better—easier to understand the discussion around specific code changes. 
* **Discoverability & Transparency**: It's easier for those outside of our tight knit team (interns, contractors) to grasp what we are working on and how it is progressing.



**What We Miss About Gerrit (Honestly)**

It wasn’t all sunshine and roses moving to GitHub PRs. There were things we genuinely missed:

*   **The Strict Approval Gate:** The inherent rigidity of Gerrit provided a certain level of assurance that every change had been thoroughly vetted by multiple engineers. While we've adapted, there are moments where we miss the extra protection it offered. We’ve addressed this somewhat with required status checks in our GitHub Actions workflow and emphasizing thorough reviews before merging.
*   **The Dedicated Review Focus:**  GitHub PRs can sometimes be overwhelming, given the other features available within the platform. It requires discipline to avoid getting distracted.

**(Image: A testimonial quote from a team member - “The biggest adjustment was learning to stay disciplined during code review in the broader context of GitHub.”) **



**Moving Forward**

Migrating away from Gerrit required a period of adjustment and refinement. However, for our five-person engineering team, the streamlined process, increased collaboration, and tight integrations that GitHub PRs deliver have made it a much more effective platform than what we had before. It's allowed us to move faster while maintaining code quality – ultimately improving both productivity and developer satisfaction.
