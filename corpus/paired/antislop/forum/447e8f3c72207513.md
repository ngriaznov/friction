## Creating Systemd Unit Files for Your Custom Daemon

Let's break down how to create robust systemd unit files for your custom long-running daemon. This guide will walk through common needs – restarting on failure, watchdog timeouts, and choosing the right `Type` setting.

**What is a Systemd Unit File?**

Think of a systemd unit file as a configuration recipe telling systemd how to manage your application (daemon).  It defines dependencies, startup order, execution details, and monitoring behavior. These files are typically located in `/etc/systemd/system/` for globally available services or `~/.config/systemd/user/` for user-specific services.

**Essential Sections & Directives**

Here's a breakdown of common directives:

* **[Unit]**:  Metadata and dependencies.
    * `Description`: Human readable description. (e.g., "My Awesome Daemon")
    * `After`: Defines order. Ensures this unit starts *after* another specified service has started (useful for database dependencies).
    * `Requires`: Similar to `After`, but if the required dependency fails, your daemon also fails.
    * `Wants`:  Similar to `After`, but failure of the wanted dependency doesn't prevent your daemon from running.

* **[Service]**: Core execution instructions.
    * `Type`: Critical for how systemd manages your service (more on this below).
    * `ExecStart`: The command used to start your application.  This is *the* most important directive.
    * `Restart`: Determines when and how to restart the daemon if it exits unexpectedly. `always`, `on-failure`, `on-abort` are typical options.

**Choosing Your `Type` – Simple vs. Notify**

The `Type` setting tells systemd about your application's behavior:

* **`Type=simple`**: The *simplest* option.  Systemd assumes the process launched by `ExecStart` is *your* main process and that it stays alive during the entire service lifetime. This works well for straightforward daemons, but offers limited monitoring capabilities.  It’s often a decent starting point but less reliable.

* **`Type=notify`**:  Your daemon calls `sd_notify(3)` to signal readiness (startup complete) and shutdown.  This allows systemd to accurately track the application's lifecycle. This is *highly recommended* for more sophisticated daemons because it enables better control, dependency ordering, and graceful shutdowns.   You’ll need to compile your daemon with `libsystemd` support to utilize this functionality.

**Restart=on-failure & WatchdogSec – Dealing with Crashes**

* **`Restart=on-failure`**: Automatically restarts the service if it exits with a non-zero exit code (indicating failure).  This is essential for resilience, automatically correcting transient errors.

* **`WatchdogSec=<seconds>`**: Systemd monitors your process and sends signals (SIGTERM) to terminate it after this period *unless* it receives a `sd_notify(3)` signal from the application indicating it’s still alive.  This prevents "frozen" processes from consuming resources indefinitely, but it requires you implement `sd_notify` calls in your daemon to periodically communicate its status (a “keepalive”). Without keepalives, the watchdog will trigger a restart.

**Example Unit File (`/etc/systemd/system/mydaemon.service`)**

```ini
[Unit]
Description=My Awesome Daemon
After=network.target

[Service]
Type=notify  ; Requires daemon support for sd_notify
ExecStart=/usr/local/bin/mydaemon --sd-notify
Restart=on-failure
WatchdogSec=30  ; 30 seconds without a signal triggers restart

# Optional: Define variables to pass to your application (e.g., config location)
EnvironmentFile=/etc/environment/mydaemon

[Install]
WantedBy=multi-user.target
```

**Explanation of the Example:**

* The daemon is launched from `/usr/local/bin/mydaemon` and instructed to support `sd_notify`.  Make sure `--sd-notify` (or similar command line option) is how your application enables this functionality!
*  The service restarts if it fails.
*  The watchdog timeout is 30 seconds; the daemon *must* send a keepalive signal during that time to prevent unexpected restarts.
* `WantedBy=multi-user.target` ensures the daemon starts when the system enters multi-user mode (typical for servers).

**Key Considerations:**

* **Kernel version**: Older kernels may have less feature support.
* **Daemon Implementation**:  If using `Type=notify`, ensure your application is correctly linked against `libsystemd` and implements `sd_notify`.
* **Debugging**: Use `journalctl -u mydaemon` to view service logs for troubleshooting.
* **Reloading:** After making changes, reload systemd: `sudo systemctl daemon-reload`.



By understanding these directives and considerations, you can create robust unit files that ensure your custom daemons run reliably under the management of systemd.
