## Implementing a Simple Bump Allocator with Free List in Embedded C

Okay, let's break down creating a simple bump allocator using a free list for embedded systems where you lack `malloc`/`free`. This is common when space and predictability are priorities over general-purpose allocation flexibility.  This approach is *much* simpler than standard allocators but comes with tradeoffs - mostly fragmentation control.

**The Basics: Why Bump Allocator + Free List?**

Traditional dynamic memory allocation (like using `malloc`) can be complex, involving heaps, metadata tracking, and potentially leading to unpredictable execution times – a nightmare in a hard real-time embedded environment.  Bump allocators are much more predictable because they allocate sequentially from a fixed region of memory ("bump" means moving the allocation pointer).

However, a straight bump allocator only allows allocations that live for the entire program’s lifetime (or until you manually reset it – essentially losing everything allocated before). The free list adds a layer of complexity to reclaim those previously bumped areas.  It provides the *ability* to reuse memory later, albeit with limitations.

**The Implementation Details**

1. **Defining Structures & Regions:**

   ```c
   #include <stdint.h> // For fixed-width integers (important!)

   // Configuration - adjust as needed for your target
   #define HEAP_SIZE 4096  // Total available memory in bytes
   #define MIN_BLOCK_SIZE 16 // Minimum reusable block size after fragmentation
   #define ALIGNMENT 8      // Alignment requirement (dependent on architecture)

   typedef uint32_t BlockHeader; // Could be smaller if you're really tight.

   static uint8_t heap[HEAP_SIZE];
   static uint8_t *allocation_pointer = heap;  // Current allocation position
   static uint8_t *free_list_head = heap; // Start of the free list

   // Structure for a free block header (minimal overhead)
   typedef struct FreeBlock {
       uint32_t size;      // Size of this block, including header
       struct FreeBlock *next;  // Pointer to next free block
   } FreeBlock;
   ```

2. **Allocation Function (`bump_alloc`)**

   This is the core – easy but restrictive.

   ```c
   void* bump_alloc(size_t size) {
       if (size == 0) return NULL; // Prevent zero-sized allocations

       // Ensure proper alignment (important for architecture requirements!)
       uint8_t *aligned_ptr = (uint8_t*)((uintptr_t)allocation_pointer + (ALIGNMENT - ((uintptr_t)allocation_pointer % ALIGNMENT)) % ALIGNMENT);
       size_t aligned_size = size;

        // Check if allocation goes out of bounds.  CRITICAL for safety!
       if (((uintptr_t)aligned_ptr + aligned_size) > ((uintptr_t)heap + HEAP_SIZE)) {
           return NULL; // Allocation fails - not enough space
       }


       void *result = aligned_ptr;
       allocation_pointer = aligned_ptr + aligned_size;

       return result;
   }
   ```

3. **Freeing (Reclaiming) Function (`bump_free`)**

   This is where the free list comes in. This adds complexity, and importantly *requires* you to explicitly `bump_free` memory when it's no longer needed – a stricter discipline than standard allocation.

   ```c
   void bump_free(void* ptr) {
       if (ptr == NULL) return; // Protect against freeing NULL pointers

       // Validate that 'ptr' was allocated by this allocator (safety!)
       if ((uintptr_t)ptr < (uintptr_t)heap || (uintptr_t)ptr >= ((uintptr_t)heap + HEAP_SIZE)) {
           return; // Invalid pointer - crash or handle error appropriately!
       }

       // Create a free block header
       FreeBlock *block = (FreeBlock*)ptr;
       block->size = (uint32_t)(((uintptr_t)allocation_pointer - (uintptr_t)ptr) + sizeof(FreeBlock)); //Calculate the size of this new free block.
       block->next = free_list_head;  // Add to front of the free list

       free_list_head = block;   // Update the list head
   }
   ```

**Putting it Together: Usage Example**

```c
int main() {
    uint8_t *data1 = bump_alloc(1024);  // Allocate 1KB
    if (data1 == NULL) {
        return 1; // Allocation failed!
    }

    uint32_t *array = bump_alloc(sizeof(uint32_t) * 10); // Allocate array of ints

    // ... use allocated memory
    bump_free(data1);  // Explicitly free when done.
    bump_free(array);   // And again.

    return 0;
}
```

**Tradeoffs & Fragmentation Handling (or the Lack Thereof)**

* **Predictability:** The biggest advantage is its simplicity and predictable allocation time – vital for embedded systems where timing matters.
* **No Heap Management Overhead:**  Forget about heap metadata, fragmentation analysis, or internal bookkeeping. This reduces complexity and code size.
* **External Fragmentation:** *This is a significant drawback.* Because you're just "bumping" the pointer, there’s no merging of freed blocks. Imagine freeing many small chunks; they stay as individual free blocks.  Eventually, there might be enough total unused memory but it’s broken up into too many tiny segments to satisfy larger allocation requests.
* **Internal Fragmentation:** Due to alignment requirements (using `ALIGNMENT`), you may waste a few bytes within each allocated block.
* **Limited Flexibility:** You *must* track what is being freed, and if the order of freeing is disrupted your allocations will run into issues.

**Mitigation Strategies (within Limitations)**

While this allocator inherently lacks sophisticated fragmentation control, some basic adjustments can help:

* **Minimum Block Size:** The `MIN_BLOCK_SIZE` helps prevent creating very small free blocks – those are often useless and contribute to fragmentation.  You could potentially split larger freed chunks into multiple smaller ones if it reduces overall slack.
* **Periodic Reset (with Caution):** You *could* reset the entire allocator (`allocation_pointer = heap; free_list_head = heap;`) but this throws away all previously allocated memory. This is a last resort for dealing with severe fragmentation and should be done thoughtfully to avoid data loss.



This simple bump allocator with a free list provides a decent compromise between predictability, simplicity, and basic reuse capability in constrained embedded environments.  Just understand the limitations regarding fragmentation, as more advanced techniques would significantly increase complexity.
