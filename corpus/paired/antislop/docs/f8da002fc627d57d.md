## Building a Simple Webhook Receiver in Node.js with Hookline

Webhooks are essential for connecting your application to other services, enabling automated responses based on external events. They're essentially HTTP callbacks – the other service sends an HTTP request (usually POST) to a defined endpoint in your application when something happens.  Security is *critical* when working with webhooks because they can be exploited if left unprotected.

This tutorial guides you through building a simple webhook receiver using Node.js and Hookline, a powerful middleware library that greatly simplifies the process of verification and handling various webhook formats. We will cover installation, signature verification, response management, and a basic code structure.

**What is Hookline?**

Hookline provides abstractions for dealing with many common webhook providers (GitHub, GitLab, Stripe, etc.). It focuses on handling secret keys, verifying signatures, parsing payloads in different formats (JSON, YAML, XML), and generally streamlining the development of secure and reliable integrations.

**Prerequisites:**

*   **Node.js & npm:** Make sure you have Node.js installed along with its package manager, npm.
*   **Basic understanding of HTTP & JavaScript.**

**1. Setting up Your Project:**

Create a new directory for your webhook receiver and initialize an `npm` project:

```bash
mkdir webhook-receiver
cd webhook-receiver
npm init -y  # Creates a default package.json file
```

**2. Installing Hookline:**

Install the Hookline library using npm:

```bash
npm install hookline
```

**3. Basic Structure and Initializing an Express App:**

Create a basic structure for your application. We’ll use Express.js, a popular Node.js web framework, to handle incoming HTTP requests.

Create `app.js` (or `index.js`) as the entry point of your server:

```javascript
const express = require('express');
const { Hookline } = require('hookline');
const app = express();
const port = 3000; // Or any other preferred port


// This is your webhook secret key - KEEP THIS SAFE!
const secret = 'YOUR_WEBHOOK_SECRET';

// Initialize the hookline instance.  This requires your webhook's secret.
const hookline = new Hookline(secret);


app.use(express.json()); // For parsing application/json
app.use(express.urlencoded({ extended: true })); // For parsing application/x-www-form-urlencoded

// Define a basic route to receive webhooks
app.post('/webhook', async (req, res) => {
  try {
    await hookline.validateHook(req); // This is the *critical* signature verification step.

    const payload = req.body;
    console.log('Received webhook event:', payload);

    // Handle your specific webhook events here based on the 'event' property in the payload
    // For example, you might want to check a property of the incoming data
    // and take different actions accordingly.

    res.status(200).send('Webhook received successfully'); // Send a 200 OK response
  } catch (error) {
    console.error('Error processing webhook:', error);

    if (error instanceof hookline.ValidationError) {
      // Verification failed - unauthorized request!
      res.status(401).send('Webhook signature verification failed');
    } else if (error instanceof Error) {
        // Other errors during handling.  Log for debugging and return a 500 Internal Server Error
       console.error("Unexpected error:", error);
       res.status(500).send("Internal Server Error");
    }

    else{
      //Generic error, best practice is to respond with 400 if it's unexpected.
      res.status(400).send('Webhook processing failed');
    }
  }
});


app.listen(port, () => {
  console.log(`Server listening on port ${port}`);
});
```

**Explanation:**

*   We import `express` and `Hookline`.
*   `secret`: **This is crucial!** This secret key should be provided by the sending service (e.g., GitHub, Stripe) during your webhook setup.  Treat it as a password – keep it confidential!  It’s used to sign the webhook request. *Replace `"YOUR_WEBHOOK_SECRET"` with your actual secret.*
*   `Hookline(secret)`: Initializes the Hookline instance with the provided secret key.
*   We use `express.json()` and `express.urlencoded()` middleware for parsing incoming requests properly.
*   The `/webhook` route is our webhook endpoint.  It's a POST route because webhooks typically send data using HTTP POST requests.
*   `hookline.validateHook(req)`: This performs the signature verification. Hookline automatically calculates the expected signature based on your secret key and compares it to the `X-Hub-Signature` header (or other relevant headers – more about this below).  This is what prevents malicious actors from sending fake webhook requests.
*   If validation succeeds, we log the payload to the console. In a real application, you'd perform actions based on the data in the payload (e.g., updating your database, triggering another process).
*   We respond with a `200 OK` status code to acknowledge that the webhook was successfully received and processed – *this is critical to prevent re-delivery of webhooks*.  The sending service usually expects this acknowledgement.

**4. Important Considerations:**

*   **Secret Management:** Store your secret key securely (e.g., in environment variables) and avoid hardcoding it directly into your source code.
*   **Error Handling:** The example includes basic error handling, but you should implement more robust logging and alerting for production environments.  Always return appropriate status codes to the sender. Returning a 200 means the message was received and successfully handled. Any other response typically signals an issue that triggers retry mechanisms in the sending application.
*   **Webhook Headers:** Hookline automatically detects necessary headers based on provider configurations (GitHub, GitLab, Stripe). However, ensure your server is configured to receive these headers (e.g., `X-Hub-Signature`, `X-Gitlab-Token`).
*   **Payload Parsing:** Hookline offers parsing for different payload formats (JSON, YAML, XML) and supports automatic type conversions. Consult the Hookline documentation for details.
*   **Idempotency:** In some cases, it is necessary to design your webhook processing logic to be idempotent – meaning that if a webhook event is processed multiple times due to temporary network issues, it only has the intended effect once. You can achieve this by tracking processed event IDs and ignoring duplicate requests.
