## Configuring a Reverse Proxy & Lightweight Load Balancer with Wharfgate

Wharfgate is a lightweight, easy-to-configure reverse proxy and load balancer written in Go. It's ideal for smaller setups or when you need something less heavyweight than traditional solutions like Nginx or HAProxy. This guide will walk you through configuring Wharfgate to route incoming traffic to three backend services based on the URL path prefix, effectively distributing requests across different applications behind a single entry point.

**1. Prerequisites:**

* **Wharfgate Installation:**  You'll need Wharfgate installed and accessible. You can download pre-built binaries from the [official GitHub releases page](https://github.com/wharfgate/wharfgate/releases).
    * For example, on Linux: `wget https://github.com/wharfgate/wharfgate/releases/download/vX.Y.Z/wharfgate-linux-amd64` (replace X.Y.Z with the actual version number) and then `chmod +x wharfgate-linux-amd64`.
* **Three Backend Services:** Have three separate services running, each accessible on a specific port (e.g., 8081, 8082, 8083).  These can be anything from simple HTTP servers to complex microservices.  For demonstration purposes, we'll assume these are simple webservers displaying basic HTML pages indicating their service number.
* **Basic Understanding of Networking:** Knowledge of ports and routing concepts will prove helpful.

**2. Understanding the Configuration Approach (Path-Based Routing):**

Wharfgate’s configuration primarily uses YAML files to define how incoming requests should be handled.  We'll utilize “routes” which specify:

* **`pathPrefix`**: The URL path prefix that triggers this route (e.g., `/api`).
* **`backends`**: A list of backend servers where the request will be forwarded. Wharfgate provides basic round-robin load balancing across these backends within a given route.
* **`upstreamName`:**  (Optional, but encouraged for clarity) - Allows grouping of your backend definitions (e.g., `api_servers`).

**3. Sample Configuration File (`wharfgate.yaml`):**

```yaml
listen:
  host: 0.0.0.0  # Listen on all interfaces
  port: 8080      # Wharfgate's listening port

upstreamName: my_services

upstreams:
  app1_servers:
    - host: localhost
      port: 8081
  app2_servers:
    - host: localhost
      port: 8082
  app3_servers:
    - host: localhost
      port: 8083

routes:
  - pathPrefix: /app1/
    upstreamName: app1_servers
  - pathPrefix: /app2/
    upstreamName: app2_servers
  - pathPrefix: /app3/
    upstreamName: app3_servers
  - pathPrefix: /default/ # Fallback route - routes that don't match above will go here.
    upstreamName: app1_servers

# Logging configuration (optional)
logging:
  level: info
```

**Explanation:**

* **`listen`**: Specifies the IP address and port Wharfgate should bind to. `0.0.0.0` means it listens on all available interfaces, making it accessible from anywhere.
* **`upstreamName`:** Used for logical grouping of your backend definitions.  This is purely organizational - Wharfgate doesn’t *require* this but improves readability and future modification.
* **`upstreams`**: Defines the backend servers (your applications). Each entry under `app1_servers`, `app2_servers`, and `app3_servers` specifies the hostname (`localhost` in our example) and port each application is running on.  You can, and often should, expand this to use fully qualified domain names (FQDNs) or IP addresses of your backend servers.
* **`routes`**: Defines how incoming requests are routed. Each route consists of a `pathPrefix` and an associated upstream defined in the `upstreams` section. When a request hits Wharfgate, it checks each route sequentially to see if the requested URL starts with that `pathPrefix`. The first matching route is used to forward the request.
* **`/default/` Route:** This acts as a fallback. If none of the preceding routes match (for example, requests arriving without `/app1`, `/app2`, or `/app3`), they'll be routed to your app1 servers (`upstreamName: app1_servers`).  This ensures that all incoming traffic is directed somewhere.
* **`logging`**: Configures Wharfgate’s logging level.

**4. Running Wharfgate:**

Once you have the `wharfgate.yaml` file, simply run Wharfgate with this configuration:

```bash
./wharfgate -config=wharfgate.yaml
```

(Assuming your binary is named "wharfgate")

This will start Wharfgate and it will begin listening on port 8080 (as defined in the config file).

**5. Testing the Configuration:**

Now, open a web browser or use `curl` to test:

* `http://localhost:8080/app1/`: Should be served by backend service running on port 8081.
* `http://localhost:8080/app2/`: Should be served by backend service running on port 8082.
* `http://localhost:8080/app3/`: Should be served by backend service running on port 8083.
* `http://localhost:8080/default/`:  Should also be served by the app1 servers (port 8081).
* `http://localhost:8080/some-other-route/`: Also should be served through /default route and therefore from port 8081.

**6. Health Checks - Essential for Reliability:**

Wharfgate itself doesn't natively provide sophisticated health checks.  However, integration with a more robust solution is highly recommended in production scenarios. Options include:

* **External Monitoring Tools:** Use monitoring tools (Prometheus, Datadog) to periodically check the status of your backend services and automatically update Wharfgate’s upstream configurations based on their availability.
* **Manual Intervention:** Regularly monitor your backend servers and manually adjust the `upstreams` configuration in `wharfgate.yaml`.  While this is less reliable, it's better than nothing for simple deployments.
* **Consider a Proxy with Native Health Checks (Future Upgrade):** When you need built-in health checks, consider migrating to a reverse proxy like Nginx or HAProxy later.
