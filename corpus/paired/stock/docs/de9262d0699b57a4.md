## Configuring Wharfgate as a Reverse Proxy & Lightweight Load Balancer

Wharfgate is a fantastic choice for setting up a reverse proxy and lightweight load balancer when you need something simple, fast, and configurable without the complexity of full-blown solutions like HAProxy or Nginx. This guide will walk you through configuring Wharfgate to route traffic to three backend services based on URL path prefixes.

**What You'll Need:**

* **Wharfgate Installed:** Download and install Wharfgate from [https://github.com/wharfgate/wharfgate](https://github.com/wharfgate/wharfgate). Installation instructions are platform-specific (Linux, macOS, Windows) on the GitHub repository.
* **Three Backend Services:**  These can be anything: web servers, application instances, API endpoints – as long as they respond to HTTP requests. For this example, let's assume these services are running at:
    * `backend1: http://localhost:8080`
    * `backend2: http://localhost:8081`
    * `backend3: http://localhost:8082`
* **Text Editor:** For creating and editing the Wharfgate configuration file.

**Understanding Wharfgate Configuration**

Wharfgate uses a YAML-based configuration file to define routes, backend servers, and other settings. The core concepts are:

* **Routes:** Define how incoming requests are matched and directed to backends.  They use path prefixes (e.g., `/api/`, `/blog/`) for matching.
* **Backends:** Represent the target services you're routing traffic to.  You specify their addresses (hostname, port) here.
* **Load Balancing:** Wharfgate employs a simple round-robin load balancing algorithm by default.

**Step 1: Creating the Configuration File**

Create a file named `wharfgate.yml` (or any name you prefer). This will hold your configuration. Here’s a sample configuration to get you started:

```yaml
# wharfgate.yml

listen_address: :80  # Listen on all interfaces, port 80
log_level: info      # Set log level (debug, info, warn, error)

backends:
  backend1:
    url: http://localhost:8080
  backend2:
    url: http://localhost:8081
  backend3:
    url: http://localhost:8082

routes:
  /api/:
    backends: [backend1]
  /blog/:
    backends: [backend2]
  /shop/:
    backends: [backend3]
  /*: # Default route - catch-all for anything not matched above.  Consider setting to a specific backend or error page.
    backends: [backend1]
```

**Explanation of the Configuration:**

* `listen_address`: This specifies where Wharfgate listens for incoming requests. `:80` means it will listen on all network interfaces (IP addresses) on port 80 (standard HTTP).  You can change this to a specific IP address and port if needed (e.g., `127.0.0.1:8080`).
* `log_level`: Controls the verbosity of Wharfgate's logs, helpful for debugging.
* `backends`: Defines your backend services.  Each entry assigns a name (e.g., `backend1`) and its corresponding URL. These names are used in the routes section.
* `routes`: This is where you define how requests are routed. Each route consists of:
    * **Path Prefix:** The URL path prefix to match (e.g., `/api/`).  The asterisk (`/*`) acts as a wildcard, matching any request that doesn't match any other defined routes.
    * **`backends`:** A list of backend names to which requests matching the path prefix will be routed. Wharfgate uses round-robin load balancing across these backends.

**Step 2: Running Wharfgate**

Navigate to the directory containing your `wharfgate.yml` file in your terminal and run:

```bash
wharfgate -c wharfgate.yml
```

This will start Wharfgate, loading the configuration from `wharfgate.yml`.  You should see output indicating that Wharfgate is running and listening on port 80 (or whatever you specified in the `listen_address`).

**Step 3: Testing Your Configuration**

Now, test your routing by making requests to different URL paths:

* **`http://localhost/api/something`**: This should be routed to `backend1`.
* **`http://localhost/blog/post`**: This should be routed to `backend2`.
* **`http://localhost/shop/product`**:  This should be routed to `backend3`.
* **`http://localhost/anything-else`**: This will be handled by the default route (`/*`), routing it to `backend1` in this example.

Verify that each request reaches the correct backend service and returns the expected content.

**Important Considerations & Health Checks (Crucial!)**

* **Health Checks:** Wharfgate *does not* have built-in health checks by default.  It simply forwards requests without verifying if a backend is alive and responsive. This means that if a backend goes down, Wharfgate will continue to send traffic to it, potentially causing errors for users.

    **Workaround:** A common workaround is to implement a simple "health check" endpoint on each of your backends (e.g., `/health`). You can then use an external process (like a cron job or monitoring system) to periodically ping these endpoints and temporarily disable the backend in Wharfgate's configuration if it fails. This requires manual intervention or scripting, but is essential for production deployments.  Future versions of Wharfgate may include built-in health check functionality.

* **SSL/TLS:** To enable HTTPS (highly recommended), you’ll need to configure SSL certificates and update the `listen_address` in your configuration file to use port 443 (e.g., `:443`).
* **Error Handling:**  Consider adding error handling to your backends, returning meaningful HTTP status codes when something goes wrong. This will allow Wharfgate to potentially handle errors gracefully or display custom error pages.
* **Advanced Routing:** Explore other routing options within Wharfgate's configuration for more complex scenarios like query parameter-based routing or header-based routing (though these are less common).



This guide provides a basic foundation for using Wharfgate as a reverse proxy and load balancer. Remember to adapt the configuration to your specific needs and environment, and always prioritize implementing health checks for robust production deployments.  The simplicity of Wharfgate makes it ideal for small-to-medium scale applications where you need a lightweight and easy-to-manage solution.
