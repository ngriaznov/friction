## From Gerrit Gates to GitHub Flow: Our Team’s Code Review Journey

For years, our five-person engineering team religiously used Gerrit for code review. It was part of our DNA. We were comfortable with it, even if sometimes we grumbled about its quirks. Recently, however, we made a significant shift and switched entirely to using GitHub Pull Requests (PRs) for all our code reviews. This wasn’t a decision taken lightly; it involved careful consideration, experimentation, and a healthy dose of apprehension.  We wanted to share our experience – the things we miss, the things that are undeniably better, and what you might consider if you're contemplating a similar move.

**Why Gerrit Felt Like Home (and What We’ll Miss)**

Gerrit, for those unfamiliar, is built around a very specific workflow: changes aren't merged directly into the main branch. Instead, they're submitted as "changes" to a central review system. These changes need explicit approval from designated reviewers before they can be integrated ("cherry-picked") into the target branch.  This enforced a strict gatekeeper model that initially felt very safe and controlled.

Here’s what we genuinely appreciated about Gerrit:

* **Explicit Approval:** The clear, binary "Approve/Reject" system left no room for ambiguity. You knew precisely who had signed off on each change. This can be invaluable in highly regulated environments or when dealing with critical codebases.
* **Fine-Grained Control:** Gerrit’s access control was granular. We could define specific review requirements based on file paths, commit messages, and even individual contributors.  This allowed us to enforce coding standards very precisely.
* **Change History & Traceability:** Gerrit's change history was incredibly detailed, providing a robust audit trail for every modification. This was especially useful for debugging and understanding the evolution of specific features.
* **Commit Message Enforcement:** While tedious at times, Gerrit’s mandatory commit message format helped maintain consistency across our codebase.

However, these strengths came with associated costs that accumulated over time.  The strictness became a bottleneck, particularly as the team grew (even just to five people!). The process felt cumbersome and often slowed down development cycles.

**The Lure of GitHub PRs: Simplicity & Collaboration**

GitHub Pull Requests, in contrast, offer a much more fluid and collaborative workflow. Changes are proposed as branches, submitted as PRs, and can be merged after approval – usually with less rigid gatekeeping. This aligns much better with the increasingly common "Gitflow" or similar branching strategies.

The move to GitHub wasn't about abandoning code review entirely; it was about finding a more efficient *way* of doing it.  Here’s what we found significantly improved:

* **Faster Iteration:** The most immediate benefit was speed. Review cycles were noticeably shorter. Smaller, incremental changes could be reviewed and merged much faster without the overhead of Gerrit's formal submission process.
* **Improved Collaboration:** GitHub PRs encourage more casual discussion *within* the review itself.  The inline commenting system is far more intuitive than Gerrit’s change-based discussions. This fostered better communication and a more collaborative coding environment.  We found ourselves having more real-time conversations about code, leading to better solutions overall.
* **Easier Onboarding:** New team members were able to get up to speed much quicker with GitHub's familiar interface and workflow. Gerrit’s learning curve can be steep for those unfamiliar with its specific terminology and processes.
* **Integration with Existing Tools:** GitHub seamlessly integrates with our existing CI/CD pipelines, project management tools (like Jira), and other development utilities.  This reduced friction and streamlined our overall workflow.
* **Reduced Cognitive Load:** Let's be honest: Gerrit had a lot of layers.  GitHub PRs are simply… cleaner. Less to learn, less to manage, and a more straightforward mental model.

**What We Learned & What You Should Consider**

The transition wasn’t flawless. We initially missed the absolute certainty of Gerrit’s explicit approvals. To mitigate this, we implemented stricter branch protection rules on GitHub - requiring at least one approval before merging – which helps recreate some of that safety net.  We also made a conscious effort to enforce code quality through linters and automated tests integrated into our CI/CD pipeline.

Ultimately, the switch to GitHub PRs has been overwhelmingly positive for our team. While we still appreciate some aspects of Gerrit’s rigorous approach, the increased speed, improved collaboration, and simplified workflow have significantly boosted our productivity.  The key takeaway? The “best” tool isn't always about features; it's about finding what works best for *your* team's specific needs and development style. Consider your team size, project complexity, regulatory requirements and be prepared to adapt along the way.
