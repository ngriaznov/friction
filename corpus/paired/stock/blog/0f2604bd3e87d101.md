## From Zero to Tiny K8s: Building a Home Lab with Three Raspberry Pis

The siren song of Kubernetes has been echoing in my ears for quite some time. While cloud-managed services offer a palatable entry point, I yearned for deeper understanding – the kind that comes from wrestling with the complexities firsthand.  So, naturally, I decided to build a small Kubernetes cluster at home using three Raspberry Pi 4s. Let's just say it was an adventure filled with triumphs and frustrations (mostly frustrations involving storage).

**Why Raspberry Pis? Why Kubernetes?**

Raspberry Pis are incredibly accessible. They’re cheap, readily available, and low-power. Building a cluster on them allows you to experiment without breaking the bank or contributing significantly to your electricity bill.  Kubernetes, despite its intimidating reputation, is fundamentally about automating deployment, scaling, and management of containerized applications. Running it locally provides invaluable hands-on experience with concepts like pods, services, deployments, ingress controllers – the building blocks of modern cloud infrastructure.

**The Hardware & Software Landscape**

Here's what I used:

* **Three Raspberry Pi 4 Model B:**  Each with 4GB RAM (8GB would have been ideal, but budget!).
* **MicroSD Cards:** 32GB each - crucial for the OS and some data.
* **Power Supply:** A robust USB-C power supply for each Pi.
* **Ethernet Cables:** Wired networking is *essential*.  Wi-Fi will cripple your cluster’s performance.
* **Raspberry Pi Imager:** For flashing Raspberry Pi OS Lite (64-bit).
* **Kubernetes Distribution:** K3s - a lightweight, certified Kubernetes distribution perfect for resource-constrained environments.

**The Networking Nightmare (and eventual Solution)**

This was my first major hurdle.  Getting three Pis to communicate reliably within the cluster proved trickier than anticipated. 

Initially, I attempted static IP assignments via DHCP reservations in my router. While that got them online, Kubernetes relies heavily on DNS and service discovery.  Without a proper internal network, those features simply wouldn't function as expected.

My solution was **Calico**, a Container Network Interface (CNI). Calico allows you to define network policies and routing rules within your Kubernetes cluster. It also provides IP address management – crucial for assigning IPs to pods dynamically. 

The setup involved:

1. **Installing kubeadm, kubectl, and k3s-helper:**  Following the K3s documentation (https://k3s.io/docs/installation/) I installed these tools on each Pi.
2. **Choosing a Master Node:** One Pi was designated as the control plane (master). The other two became worker nodes.
3. **Joining Workers to the Cluster:** Using `kubeadm join` commands, I added the worker nodes to the master's cluster. This involved generating tokens and ensuring proper DNS resolution.
4. **Installing Calico:** A simple `kubectl apply -f https://raw.githubusercontent.com/projectcalico/k8s-manifests/v3.26.1/calico.yaml` did the trick, though version numbers might change depending on releases.

This finally gave me a functioning internal network where pods could communicate with each other and services were discoverable.  It was a huge relief!

**The Storage Saga: MicroSD Card Limitations & NFS to the Rescue**

Kubernetes needs persistent storage – places to store data that survives pod restarts. This is where my idyllic Raspberry Pi cluster started hitting some serious roadblocks. 

MicroSD cards are *not* designed for the constant read/write cycles inherent in Kubernetes workloads. I quickly experienced performance bottlenecks and, more worryingly, card corruption.  Directly mounting MicroSD cards as persistent volumes inside pods was a recipe for disaster.

My initial attempts involved trying to use Longhorn, a distributed storage system. However, it proved too resource-intensive for my little Pis. It simply bogged down the entire cluster.

The solution? **Network File System (NFS)**. I set up an NFS server on a separate NAS device in my home network and configured Kubernetes to use it as a persistent volume provider. 

Here's how:

1. **Configuring the NFS Server:**  This involved exporting directories from the NAS, ensuring appropriate permissions, and configuring firewall rules.
2. **Creating a Persistent Volume Claim (PVC):** This is where you define your storage requirements – size, access mode, etc. The PVC then dynamically provisions a persistent volume backed by the NFS share.
3. **Using the PV in Pods:**  Pods can then request to use this pre-provisioned persistent volume to store their data.

While NFS isn't as sophisticated as distributed storage solutions like Longhorn or Ceph, it provided a stable and relatively performant solution for my home lab needs, avoiding MicroSD card carnage. It does mean I’m reliant on the NAS being available, but that’s an acceptable trade-off for now.

**What Am I Actually Running?  A Tiny Home Lab Ecosystem**

Now that I had a (mostly) stable Kubernetes cluster, it was time to put it to work! Here's what I ended up deploying:

* **Portainer:** A web UI for managing Kubernetes clusters. Makes visualizing and interacting with the cluster much easier than just using `kubectl`.
* **Traefik Ingress Controller:** Handles external access to my services – exposes them via a reverse proxy.
* **Home Assistant:** My home automation hub, running in a pod.  This was the primary motivator for building the cluster - having Home Assistant reliably deployed and managed by Kubernetes is fantastic.
* **Plex Media Server:** A containerized Plex server for streaming media to my devices.
* **Grafana & Prometheus:** For monitoring resource usage and application health within the cluster.  Essential for understanding what’s going on inside this little ecosystem.

**Lessons Learned (and Future Plans)**

Building a Kubernetes cluster with Raspberry Pis has been an incredibly rewarding learning experience. Here's what I've gleaned:

* **Networking is Paramount:** Don’t skimp on it! Wired connections and a CNI like Calico are essential for stability.
* **Storage Solutions Matter:** MicroSD cards are not persistent storage solutions. Explore alternatives like NFS or, if you have the resources, distributed storage systems.
* **Resource Constraints are Real:**  Kubernetes is powerful, but Raspberry Pis aren't powerhouses. Optimize your deployments and be mindful of resource usage.
* **K3s is a Winner:** It’s lightweight and easy to manage – perfect for this use case.

Future plans include experimenting with more advanced storage solutions like Rook (Ceph) - assuming I can get my little Pis to handle the load.  I also want to explore service mesh technologies like Istio to add another layer of complexity and understanding.



Building a home Kubernetes cluster isn’t about running production-grade workloads; it's about learning, experimenting, and gaining a deeper appreciation for the technology that powers modern cloud infrastructure. And honestly, seeing my Home Assistant pod reliably deployed and managed by Kubernetes? That’s pretty satisfying.
