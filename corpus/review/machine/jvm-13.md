This is a solid, well-scoped addition — the new `OrderEventProducer` and its wiring into `OrderService.confirmOrder()` are easy to follow, and I appreciate that the retry and DLQ topic configuration lives in `application.yml` rather than being hardcoded, which will make tuning this in prod much easier without a redeploy.

A few things I'd want addressed before merging:

The producer factory config sets `acks=1` rather than `acks=all`. For order-confirmation events specifically, which downstream services (billing, fulfillment) presumably treat as the trigger for real-world side effects, I'd want the stronger durability guarantee — `acks=1` only waits for the leader to write the record, and a leader failure right after that ack but before replication means the event can be lost even though the producer believes it succeeded. Given this is a low-volume, high-importance event stream (order confirmations, not clickstream telemetry), the latency cost of `acks=all` should be negligible here.

`OrderEventProducer.publish()` catches `KafkaException` and logs it but then returns normally rather than propagating anything to the caller. That means if publishing fails, `OrderService.confirmOrder()` still returns success to the API caller, and the order is confirmed in the database with no corresponding event ever reaching downstream consumers — silent data loss from the consumer's perspective. I'd either let the exception propagate so the whole operation can be retried/rolled back, or if fire-and-forget is intentional, at minimum increment a metric so this is observable rather than only visible in logs.

The retry topic naming (`order-events-retry-0`, `order-events-retry-1`, `order-events-retry-2`) followed by a DLQ topic is a reasonable pattern and matches what I'd expect from `RetryTopicConfiguration`. Nice touch including the max-retry exhaustion handler that writes to `order_events_failed` table in addition to the DLT — gives you a queryable record without needing to consume the DLQ topic to see what's failing.

Test coverage on the retry/backoff path looks thin — I see a test that the producer sends successfully and one that it handles a `KafkaException` at the mock level, but nothing exercising the actual retry topic routing via an embedded or Testcontainers Kafka. Given this is the trickiest part of the change to get right, I'd want at least one integration test asserting a message actually lands on `order-events-retry-0` after a simulated consumer failure, using `@EmbeddedKafka` or a Testcontainers Kafka instance, before merging.
