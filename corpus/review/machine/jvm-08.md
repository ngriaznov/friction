This works correctly but it's going to make your test suite painfully slow as it grows, so I'd push back on the container lifecycle before anything else.

Every `@Test` method in `OrderRepositoryIntegrationTest` is annotated with its own `@Container` field pointing at a fresh `PostgreSQLContainer`, started and torn down per test via JUnit's lifecycle rather than shared across the class. With eleven test methods in this class alone, that's eleven container starts, each one paying Postgres's boot cost (a few hundred milliseconds to a couple of seconds depending on the machine) before the actual assertion runs. Multiply that across however many other integration test classes follow the same pattern and your CI integration stage is spending most of its wall-clock time booting and discarding Postgres instances rather than running test logic.

The standard fix is a static container shared across the whole test class (or better, the whole test run) via a singleton container pattern: declare the `PostgreSQLContainer` as a `static` field, start it once in a static initializer or `@BeforeAll`, and never call `stop()` — let Testcontainers' Ryuk cleanup handle teardown when the JVM exits. If you're worried about test isolation because you're sharing one database instance across tests, that's a legitimate concern, but the answer is to reset state between tests (delete rows in `@AfterEach`, or better, wrap each test in a transaction that's rolled back — `@Transactional` on the test class works here since Spring's test framework rolls back by default) rather than paying for a new container per method.

If you want to go further and share the container across multiple test classes in the module, a base class with a static container and a `@DynamicPropertySource` registering the JDBC URL is the common pattern — several of your other integration test classes (`PaymentRepositoryIntegrationTest`, `InventoryRepositoryIntegrationTest`) look like they'd benefit from being consolidated onto the same shared instance rather than each maintaining a near-identical container declaration.

Smaller note: `withReuse(true)` is set on the container but Testcontainers reuse also requires `testcontainers.reuse.enable=true` in `~/.testcontainers.properties` on the machine running the tests — if that's not set in CI, the flag is silently a no-op and you're back to a fresh container each run anyway. Worth confirming CI actually has it enabled, otherwise this setting is dead configuration.
