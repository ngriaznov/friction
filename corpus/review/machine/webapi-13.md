This PR replaces the `/v1/shipments` list endpoint's offset-based pagination with cursor-based pagination, touching the handler in `internal/api/shipments.go`, the query builder in `internal/store/shipments_query.go`, and adding a new `Cursor` encode/decode helper in `internal/api/cursor.go`. It also updates the OpenAPI spec and the two existing integration tests that asserted on `page`/`page_size` query params.

Good call moving off offset pagination for this endpoint specifically — shipments is exactly the kind of high-write, frequently-paginated table where the old approach was going to bite someone eventually, and the PR description's benchmark numbers (P99 dropping from ~800ms to ~40ms at high offsets) make the motivation concrete rather than theoretical. The keyset query in `shipments_query.go` using `(created_at, id) > (?, ?)` as a compound cursor to break ties on equal timestamps is the right pattern and I'm glad it's not just ordering by `id` alone, since `created_at` is the actual field clients probably want to sort by.

A few things before this merges. `cursor.go` encodes the cursor as base64 of a plain JSON struct (`{"created_at":..., "id":...}`) with no signature or encryption. That means the cursor is fully readable and, more importantly, forgeable by any client — someone can hand-craft a cursor with an arbitrary timestamp to skip straight to any point in the dataset, which may not matter for shipments specifically but is worth a deliberate decision rather than an implicit one; at minimum I'd add an HMAC over the encoded payload so a tampered cursor is rejected rather than silently accepted, since accepting an attacker-chosen `(created_at, id)` pair as-is could be used to probe ID ranges you didn't intend to expose ordering over.

Second, backward compatibility: this PR removes the `page`/`page_size` query params entirely rather than accepting both during a transition period. If any existing integrations depend on the old params, they'll now get whatever the new default cursor behavior is instead of an error, since I don't see validation that rejects unrecognized query params — worth confirming whether this API has external consumers and, if so, whether a deprecation window is needed instead of a hard cutover in one release.

Third, smaller: `Cursor.Decode` returns a zero-value struct on any parse error instead of a distinguishable error, so a malformed cursor currently gets treated as "start from the beginning" rather than a 400. That's probably not what you want — a client with a corrupted or stale cursor should get a clear error, not silently restart pagination.

The test updates look reasonable, though I'd like to see one more case: a cursor pointing at the last page returning an empty `next_cursor` (or however you're signaling end-of-results) rather than a cursor that loops back or errors.

Solid direction, needs the cursor integrity issue addressed and a decision on the compat question before I'd approve.
