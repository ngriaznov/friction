This modal component is close, and I appreciate that you're already handling `Escape`-to-close and a backdrop click listener, but the focus management has a few gaps that matter a lot for keyboard and screen-reader users, so I'd treat this as a request-changes rather than a nit-level review.

The biggest issue: there's no focus trap. Right now, once the modal opens, `Tab` and `Shift+Tab` continue to cycle through the entire page's focusable elements, including whatever sits behind the modal (which you've correctly dimmed with a backdrop, but dimming doesn't remove it from the tab order). A sighted mouse user won't notice, but a keyboard user tabbing through the form fields inside your modal will eventually tab straight out of it and onto a nav link in the page behind, with no visual indication of what happened. You need to either roll your own trap — capture `Tab` on a `keydown` listener attached while the modal is open, query all focusable elements within the modal container, and wrap focus at the first/last — or, honestly, just use `focus-trap-react` or Radix/Headless UI's dialog primitive instead of hand-rolling this. Given how many edge cases a correct trap has (disabled elements, elements with `tabindex="-1"`, nested modals, dynamically added content), I'd lean toward not reinventing this.

Second, initial focus placement: on open, focus should move to the modal itself or to the first meaningful interactive element inside it (commonly the close button, or the first form field, depending on the modal's purpose). Right now nothing calls `.focus()` on open, so focus stays wherever it was on the trigger button, and a screen reader user gets no indication that a dialog has appeared and taken over the page. Add a `useEffect` that runs on open and focuses either a ref to the dialog container (with `tabIndex={-1}` so it's programmatically focusable) or the first interior control.

Third, and this one's easy to miss: when the modal closes, focus needs to return to whatever triggered it — typically the button that opened the modal. Store a ref to `document.activeElement` at the moment the modal opens, and call `.focus()` on it in your close handler. Without this, closing the modal silently drops focus to `<body>`, and a keyboard user has to tab all the way back through the page to find where they were.

On markup: I don't see `role="dialog"` or `aria-modal="true"` on the container, nor `aria-labelledby` pointing at the modal's heading. Add all three — screen readers rely on `role="dialog"` plus `aria-modal="true"` to announce that background content is inert, and without `aria-labelledby` the dialog has no accessible name at all.

Smaller items: the backdrop click handler closes the modal on any click inside the backdrop element, which is correct, but double-check it's not also firing when a click starts inside the modal and the mouseup happens to land on the backdrop during a text selection drag — a common false-positive with naive backdrop click detection. Comparing `event.target === event.currentTarget` handles this correctly and it looks like you're already doing that, so that part's fine.

Once the focus trap, initial focus, return focus, and ARIA attributes are in, this is good to go. The rest of the implementation — portal rendering via `createPortal`, body scroll lock — all look correct as written.
