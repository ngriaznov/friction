This PR adds zero-copy deserialization for the binary sensor-frame protocol in `src/codec.rs`, replacing the previous approach (parse into an owned `Frame` struct field-by-field, copying each value out of the receive buffer) with a `zerocopy`-derived view type that reinterprets a validated byte slice directly as `&FrameView`, avoiding the copy for the hot decode path. The motivation given — this runs on every inbound packet on a link that's apparently pushing a meaningful packet rate — is a legitimate reason to want this, and the general approach is right for the problem.

The `#[derive(FromBytes, KnownLayout, Immutable)]` on `FrameView` and the use of `FrameView::ref_from_bytes` rather than a manual transmute is the correct way to do this in current `zerocopy` — it gets you the alignment and size validation the derive macro generates instead of hand-rolling `unsafe` pointer casts, which is exactly what I'd want to see for this kind of change, so no concerns about the soundness of the transmute mechanism itself.

Two things I'd want addressed before merging. First, `FrameView`'s field layout is defined by the struct's declared field order plus `#[repr(C)]`, which is correct for controlling layout, but there's no static assertion tying the struct's `size_of` to the wire format's documented frame size (referenced elsewhere as a constant, `FRAME_SIZE_BYTES`, in `src/proto/spec.rs`). If someone adds a field to `FrameView` later, or the wire format changes and this struct isn't updated to match, `ref_from_bytes` will still succeed as long as the byte slice is long enough and correctly aligned — it validates against its own layout, not against the protocol's independent definition of what a valid frame looks like. A `const _: () = assert!(core::mem::size_of::<FrameView>() == FRAME_SIZE_BYTES);` would catch a drift between the two at compile time instead of it manifesting as silently misinterpreted fields at runtime, which for a sensor protocol could mean happily decoding garbage as a plausible-looking but wrong reading rather than erroring.

Second, and this is the more important one: multi-byte numeric fields in `FrameView` are plain `u16`/`u32`/`f32` rather than the endian-explicit wrapper types `zerocopy` provides (`U32<byteorder::BigEndian>` and friends). Since this is reinterpreting bytes off the wire directly rather than going through an explicit decode step, the struct's field types are now implicitly assuming the wire format's byte order matches the host's native order. That's fine on the current target if the wire format happens to be little-endian and this only ever runs on little-endian hosts, but it's an assumption baked silently into the type rather than stated anywhere, and it will silently produce wrong values (not a crash, not an error — just wrong numbers) if this code is ever built for a big-endian target or the wire format's endianness was assumed rather than confirmed against the protocol spec. I'd switch the multi-byte fields to the explicit-endian wrapper types zerocopy provides for exactly this situation, which costs nothing at runtime on the matching-endian case and makes the assumption correct-by-construction rather than implicit.

The zero-copy mechanism itself is sound and this is a reasonable place to spend the added type complexity given the packet rate involved. I'd want the size assertion and the explicit endianness handling in before merge — both are the kind of gap that produces quietly wrong data rather than a loud failure, which is the worse failure mode for a protocol decoder.
