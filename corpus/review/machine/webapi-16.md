This PR adds a Redis read-through cache in front of the product catalog service (Go, using `go-redis/v9`), touching `internal/catalog/repository.go` where `GetProduct` and `ListProductsByCategory` now check Redis before falling back to Postgres, plus a new `internal/cache/redis.go` wrapper and config additions for TTL and Redis connection settings.

The read-through pattern itself is applied correctly — check cache, on miss query Postgres, populate cache, return — and wrapping the Redis client in your own small interface in `redis.go` rather than passing the raw client around the codebase is good for testability. A few things I'd want addressed before merge.

`ListProductsByCategory` caches its result under a key built from `fmt.Sprintf("category:%s:products", categoryID)` with no encoding of pagination or sort parameters, but looking at the handler, this method does accept a `limit`/`offset` pair that varies per call. As written, whichever combination of limit/offset happens to populate the cache first for a given category will be served back to every subsequent caller regardless of what they actually asked for, since the cache key doesn't vary with those parameters. This will produce wrong results, not just stale ones. The cache key needs to include limit, offset, and sort order, or you need to cache only the full unpaginated set and paginate in application code after reading from cache.

Second, on invalidation: I don't see any cache invalidation when a product is updated or deleted elsewhere in the codebase — is that out of scope for this PR, or is the plan to rely purely on TTL expiry? If updates go through a different code path (an admin service, a different repo, an async worker), stale product data — price, availability — could be served for up to the full TTL after a change, which for a catalog service directly affects what customers see before checkout. Worth at least a comment or a follow-up ticket link explaining the intended staleness tolerance, since "how stale is acceptable" is a product decision, not just an engineering one.

Third, smaller: `redis.go`'s `Get` method returns the zero value with a nil error when the key doesn't exist (I think it's swallowing `redis.Nil` internally), which means callers in `repository.go` can't distinguish "not in cache" from "cached empty result." Right now that's probably fine since the callers always fall through to Postgres on a zero value, but it's a foot-gun for the next feature that wants to legitimately cache "this ID doesn't exist" as a negative cache entry — I'd have `Get` return `(value, found bool, err error)` instead.

Also, no circuit breaking or fallback if Redis itself is unreachable — does `Get` returning an error cause the whole request to fail, or does it fall through to Postgres? A quick read suggests errors propagate up rather than being treated as a cache miss, which means a Redis outage takes the catalog service down with it even though Postgres alone would be sufficient to serve (slower) responses. I'd treat Redis errors as cache misses (log them, maybe emit a metric) rather than hard failures, so the cache is a pure performance optimization and not a new availability dependency.

Good direction overall, but the pagination cache-key bug is a real correctness issue I'd block on, and the Redis-unavailable behavior is close behind since it changes your availability profile in a way that's probably unintentional.
