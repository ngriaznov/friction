This PR adds GraphQL subscriptions for order status changes using Strawberry's `@strawberry.subscription` support over websockets, with a new `subscriptions.py`, a Redis pub/sub bridge in `pubsub.py` that the order-status-update code path publishes to, and a small change to `main.py` wiring up the ASGI websocket route.

Nice addition and the Redis pub/sub bridge is a sensible choice here rather than trying to fan out in-process, since this presumably runs behind multiple app instances. The subscription resolver's use of an async generator that yields parsed `OrderStatusEvent` objects reads cleanly, and I like that you're validating the `order_id` argument against the requesting user's permissions before subscribing rather than filtering after the fact — that's the right place to enforce that check.

Couple of things I'd want addressed. In `pubsub.py`, the Redis subscription is created with `pubsub.subscribe(channel)` but I don't see it ever unsubscribing or closing the connection when the client disconnects — the async generator in `subscriptions.py` has a `try`/`finally` around the yield loop, but the `finally` block only breaks out of the local loop, it doesn't call `pubsub.unsubscribe()` or return the connection. Over time, with clients connecting and disconnecting from the websocket without a clean GraphQL-level unsubscribe (mobile clients going to background, network blips), you'll accumulate orphaned Redis subscriptions and connections. Worth confirming this against a manual disconnect test — kill the websocket mid-subscription and check Redis's `CLIENT LIST` afterward.

Second, minor but worth a comment: events published to Redis are plain JSON with no schema versioning field. If the order status event shape changes later, older long-lived subscriptions (if any survive a deploy) or a rolling deploy where publisher and subscriber briefly run different versions could produce parse failures. A `version` field in the payload, even unused today, is cheap insurance.

Third, is there a cap on concurrent subscriptions per connection or per user? A client could open many subscriptions to different order IDs; not necessarily a problem at current scale but worth at least a TODO if there's no limit today.

The core approach is right and this is close. I'd want the disconnect cleanup verified before merging, but nothing here blocks getting a fix out quickly once that's confirmed — approving with that one item to close out.
