Reviewing a FastAPI file upload endpoint for user avatars: it accepts a `UploadFile`, reads the filename from the client, joins it onto a base uploads directory with `os.path.join(UPLOAD_DIR, file.filename)`, and writes the bytes to disk.

This has a path traversal vulnerability that needs fixing before this goes anywhere near production. `file.filename` is fully client-controlled, and `os.path.join` does not sanitize `..` segments — a filename like `../../etc/cron.d/evil` (or on the deployment target, wherever a write would land somewhere sensitive) will be joined literally, and the resulting path can escape `UPLOAD_DIR` entirely. At minimum, strip the filename down to its basename with `os.path.basename(file.filename)` before joining, but I'd go further and not trust the client-provided filename at all for the on-disk name — generate your own (a UUID, or a hash of the content) and store the original filename separately as metadata if you need to show it back to the user later. That sidesteps not just traversal but also filename collisions and weird characters/encoding issues across filesystems.

Second issue: there's no size limit. The handler reads the whole upload into memory with `await file.read()` before writing it out, and nothing caps `Content-Length` or streams-and-aborts past a threshold. A client can upload an arbitrarily large file and either exhaust memory or fill disk. FastAPI's `UploadFile` is backed by a `SpooledTemporaryFile` so small files stay in memory and larger ones spill to disk automatically, which helps with the memory side, but you still want an explicit size cap enforced (check `Content-Length` up front and reject early, and/or read in chunks and abort once you exceed the limit, since `Content-Length` can be absent or wrong for chunked transfer encoding).

Third, smaller: there's no content-type or extension validation, so anything can be uploaded as an "avatar," including executable content if this directory is ever served directly by the web server rather than through your app — worth confirming `UPLOAD_DIR` isn't inside a statically-served path, and if avatars are served back to users, consider validating it's actually a decodable image (e.g., via Pillow's `Image.open` plus `.verify()`) rather than trusting the declared content type, which is also client-supplied and easy to spoof.

The endpoint's structure and use of `UploadFile` is otherwise fine and idiomatic FastAPI — this is really about the three trust boundary issues above, and I'd want at least the path traversal and size limit fixed before merging.
