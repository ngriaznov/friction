The snippet was a Go REST handler using `sqlx` that implements offset/limit pagination over a `products` table — `SELECT * FROM products ORDER BY id LIMIT $1 OFFSET $2` — and the author reported that items were showing up twice across pages or getting skipped entirely when clients paginated through results while writes were happening concurrently, and separately that page 200+ was noticeably slower than page 1.

Both symptoms trace back to the same root cause plus one more. The duplication/skipping is because `ORDER BY id` without a uniqueness guarantee combined with concurrent inserts and deletes shifts the offset window between requests — if a row is deleted from an earlier page after the client fetched page 1 but before fetching page 2, everything shifts left by one and the client either re-sees a row or misses one. This isn't a bug in your SQL, it's an inherent property of offset pagination against a mutating table, and no amount of tuning the query fixes it. If `id` is a sequential and unique primary key here (looks like it, given the ordering) the actual fix is to switch to keyset/cursor pagination: instead of `OFFSET`, carry the last-seen `id` from the previous page and query `WHERE id > $last_id ORDER BY id LIMIT $1`. That's also stable under concurrent writes because it's anchored to a value, not a position.

The slowness at high offsets is the well-known cost of `OFFSET` in Postgres (I'm assuming Postgres from the placeholder syntax) — the database still has to scan and discard all the skipped rows before it can start returning the requested page, so cost grows roughly linearly with the offset regardless of the index on `id`. Keyset pagination fixes this too, since `WHERE id > $last_id` can seek directly via the index instead of scanning from the start.

One more thing while you're touching this: `SELECT *` means every column addition to the table silently flows into the API response, and it also defeats a potential covering index if you later want one. Enumerate the columns you actually serialize.

I'd treat this as "needs rework" rather than a tweak — cursor pagination is a bit more API surface (you're returning an opaque cursor token instead of a page number) but it's the correct fix for both problems you're seeing, and retrofitting it later after clients depend on page numbers is more painful than doing it now.
