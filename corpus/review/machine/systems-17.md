This PR adds an SSE2/AVX2 fast path to the JSON string-scanning routine in `src/parse/string.rs`, using `std::arch::x86_64` intrinsics to find the next quote or backslash sixteen or thirty-two bytes at a time instead of the current byte-by-byte loop, with a scalar fallback for non-x86_64 targets and for tails shorter than a full vector width. I appreciate that this is scoped to just the string-scanning hot path rather than trying to SIMD-ify the whole parser in one go, but I don't think this is safe to merge as written.

The AVX2 path is reached through a `#[target_feature(enable = "avx2")]` function that's called unconditionally from the dispatch function whenever `cfg!(target_arch = "x86_64")` is true — there's no runtime `is_x86_feature_detected!("avx2")` check anywhere in the diff. `target_arch = "x86_64"` tells you the compile target, not what the CPU running the binary actually supports; plenty of x86_64 hardware still in service doesn't have AVX2 (some older cloud instance types, some embedded/industrial x86 boards), and running an AVX2 instruction on a CPU without it is `SIGILL`, not a graceful failure. This needs to detect the feature at runtime and fall back to the SSE2 path (which is a safe baseline for x86_64 since it's part of the ABI baseline) or the scalar path when AVX2 isn't present. This is the actual blocker — everything else here is secondary.

Second, I want to see the safety comment on the `unsafe fn` that wraps the intrinsics actually justify why the loads are sound — right now it says only `// SAFETY: uses AVX2 intrinsics`, which restates what the code does rather than justifying it. The real invariant that needs stating and upholding is that `_mm256_loadu_si256` is used (unaligned load) rather than the aligned variant, so alignment isn't the concern, but the pointer arithmetic advancing through the buffer needs to never read past the end of the underlying allocation — worth spelling out how the tail-handling guarantees that (I think it does, via the length check before entering the vectorized loop, but it should say so).

Third, no benchmark is included, which for a PR whose entire point is performance feels important — SIMD string scanning can be a significant win, but it can also be a wash or even a regression for typical JSON with mostly short strings, where the fixed cost of setting up vector registers and handling the tail dominates over the byte-by-byte loop's simplicity. I'd want numbers across a range of realistic payloads (short keys, long string values, mixed) before this is worth the added `unsafe` surface and platform-specific code path at all.

I'd like to see this land eventually — the direction is reasonable and JSON string scanning is a legitimate SIMD target — but the missing runtime feature detection is a correctness bug that will crash real users on real hardware, so this needs another pass before merge.
