This PR replaces the old single-stage `Dockerfile` (which was building on `python:3.10` full image, installing everything as root, running `python manage.py runserver`) with a multi-stage build targeting `python:3.10-slim`, adding a non-root user, and switching the entrypoint to gunicorn. Directionally this is exactly the right change and I'm glad to see it — but there are enough issues in the execution that I don't think this should merge as-is.

Start with what's working well: separating the builder stage (which installs `build-essential`, compiles `psycopg2` and `Pillow` from source, and runs `pip install`) from the runtime stage is the correct pattern for keeping the final image lean, and you're copying only the installed site-packages plus the app code into the final stage rather than the whole builder filesystem. The switch from the Django dev server to `gunicorn --workers 3 --bind 0.0.0.0:8000 config.wsgi` is the single most important change in this PR and it's done correctly, including binding to a real WSGI entrypoint rather than something ad hoc.

Now the problems, roughly in order of severity.

`RUN python manage.py collectstatic --noinput` is running inside the Dockerfile build itself, before the final `USER appuser` switch, which means static files get collected and owned by root inside the image layer. That's not immediately broken since the container itself runs the app fine, but if you ever mount a volume over `STATIC_ROOT` for serving via an external CDN sync step, or if anything downstream tries to write to that directory as the non-root user, you'll hit a permissions error. More importantly, `collectstatic` at build time requires `DJANGO_SETTINGS_MODULE` and typically a working (or at least non-fatal) database connection depending on what apps are installed and what they do in `AppConfig.ready()` — baking that into the image build means your CI build step now has an implicit dependency on settings/secrets being available at build time, which is a layering violation. The more common pattern is to run `collectstatic` as a separate step in the deploy pipeline (or in an init container in Kubernetes) rather than inside the image build, specifically so the image itself stays environment-agnostic and doesn't need `SECRET_KEY` or database credentials present just to build.

Related to that: I see `ARG DJANGO_SECRET_KEY` and `ENV DJANGO_SECRET_KEY=$DJANGO_SECRET_KEY` in the builder stage, presumably to satisfy `collectstatic`'s settings import. Build args get baked into the image's layer history and are visible to anyone with `docker history` access to the image, even though they don't persist into the final stage's environment directly (multi-stage does help here since ARG scope doesn't carry to the final stage automatically) — but the value still sits in the builder stage's layer cache and, depending on your registry/CI setup, cached builder-stage layers may be pushed or retained. Don't pass secrets as build args at all; use a Django settings module that tolerates a missing or dummy `SECRET_KEY` during `collectstatic` (Django's own docs cover a pattern for this), or move `collectstatic` out of the build entirely as suggested above.

The non-root user setup itself (`RUN groupadd -r appuser && useradd -r -g appuser appuser`, then `USER appuser` before `CMD`) is correctly ordered relative to the `CMD`, but the `chown` for `/app` only covers the app directory, not `/app/staticfiles` if that's a separately mounted volume path in production — worth double-checking against how the Kubernetes manifests actually mount static storage, since a mismatch here would produce permission-denied errors only in the deployed environment, not locally.

`HEALTHCHECK` is missing entirely — for a service being fronted by an orchestrator that's about to depend on health status (given the accompanying Helm chart changes referenced in the PR description), add one hitting a lightweight health endpoint rather than relying solely on the orchestrator's own probes, or at minimum make sure the same endpoint is used consistently.

Nit-level: the final stage still has `apt-get` cache files present because `apt-get clean && rm -rf /var/lib/apt/lists/*` isn't chained into the same `RUN` as the `apt-get install` in the runtime stage (it only appears in the builder stage) — since the runtime stage does still run a small `apt-get install` for `libpq5` and a couple of runtime-only shared libraries, that layer is carrying apt cache weight it doesn't need to.

To summarize: the architectural direction is right and most of the individual pieces (multi-stage, non-root user, gunicorn) are implemented correctly in isolation, but the `collectstatic`-at-build-time-with-a-secret-key issue is a real problem that I'd want resolved before merge, not just noted for later — it's exactly the kind of thing that quietly leaks a secret into a cached image layer and gets discovered during a security audit six months from now. Please move `collectstatic` out of the image build, and let's talk about how static files get delivered to the running containers instead.
