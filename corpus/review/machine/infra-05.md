There are a few bugs here that will actually bite you, not just style nits, so I'd hold off running this against production backups as-is.

The core problem: your `find $BACKUP_DIR -mtime +$RETENTION_DAYS -exec rm {} \;` isn't quoting `$BACKUP_DIR`, and more importantly there's nothing constraining `find` to files — if `$BACKUP_DIR` ever resolves to something unexpected (unset variable, typo, a failed mount that leaves the directory empty and `find` walking up to a parent), you're one bad expansion away from `rm`-ing outside the backup tree. Given the script doesn't `set -u`, an unset `$BACKUP_DIR` would silently expand to an empty string, and `find "" -mtime ...` behaves in surprising ways depending on your `find` implementation. Add `set -euo pipefail` at the top — right now a failed `tar` in the middle of the script won't stop execution, it'll just fall through to the rotation step and delete old backups even though the new one never got created, which is close to worst-case behavior for a backup script specifically.

Second, `tar czf $BACKUP_DIR/backup-$(date +%Y%m%d).tar.gz /var/lib/app/data` — no quotes around the tar destination path, and you're building the filename with just a date, no time component, so if this ever runs twice in a day (manual re-run after a failure, cron misfire) the second run silently clobbers the first. I'd add `%H%M%S` or check for existing files before overwriting.

Third, there's no verification step after the `tar` completes — no `tar tzf` to confirm the archive is readable, no checksum written alongside it. A backup script's entire job is producing something restorable; right now you'd only find out an archive was corrupt at restore time, which is the worst possible moment to learn that.

Fourth, the S3 upload with `aws s3 cp` has no retry or error handling — if that command fails (network blip, credential expiry), the script currently continues to the rotation step and deletes the local copy of a backup that never made it offsite, per the `rm $BACKUP_DIR/backup-*.tar.gz` a few lines later that isn't gated on upload success. Check the exit code of the `aws s3 cp` call explicitly and skip local deletion if it failed.

Smaller stuff: quote all your variable expansions throughout (`$BACKUP_DIR`, `$RETENTION_DAYS`, the constructed filename) — right now nothing in this script would survive a path with a space in it. And consider `mktemp` for any intermediate files instead of writing directly into `$BACKUP_DIR`, so a failed run doesn't leave a half-written archive that the rotation logic might later try to process.

The overall shape — tar, upload, rotate — is the right structure, it just needs `set -euo pipefail`, quoting, and success-gating between each step before I'd trust it unattended on a cron.
