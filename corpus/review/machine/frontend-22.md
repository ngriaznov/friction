Went through the memoization pass across the analytics dashboard components — this PR wraps roughly a dozen components in `React.memo` and adds `useCallback`/`useMemo` in several parent components that pass props down to them. The motivation (reducing re-render cost on a dashboard that re-renders frequently due to a polling data source) is legitimate, but I think a meaningful chunk of this PR is adding complexity without adding benefit, and a couple of spots are actively counterproductive.

Let's start with what's working: `MetricCard`, wrapped in `React.memo` here, receives simple primitive props (a number, a string label, a trend direction enum) and is rendered many times in a grid — that's a textbook case where memoization pays off, since primitive props compare cheaply with reference/value equality and the component itself does some non-trivial formatting work in render. Same story for `ChartLegend`. Good calls on both.

Where I'd push back: `DashboardHeader` is wrapped in `React.memo`, but it only ever renders once per page — it's not in a list, doesn't re-render due to polling (its props come from route params, not the polled data), and has no expensive render logic, just some JSX and a couple of static labels. Memoizing a component that already rarely re-renders and is cheap when it does adds the cost of a props comparison on every render for no corresponding benefit. `React.memo` isn't free — it does a shallow prop comparison every render — so applying it reflexively to components that don't actually re-render often or expensively is a net negative, however small. I'd remove it here.

More concerning: to make `React.memo` on `RevenueChart` actually effective, the PR wraps the `onDataPointClick` callback passed to it in `useCallback` in the parent — but the dependency array for that `useCallback` includes `filters`, which is a new object literal recreated on every parent render (built inline as `{ dateRange, region, category }` directly in the JSX rather than sourced from stable state or memoized itself). Since `filters` is a new reference every render, the `useCallback` recomputes every render anyway, which means the `useCallback` wrapper does nothing to help `RevenueChart`'s memo comparison — the callback prop still changes reference every time, defeating the memoization it was added to support. This is a common pattern where people add `useCallback` without realizing the fix needs to go one level further up, to whatever's producing a fresh `filters` object each render. Either memoize `filters` itself with `useMemo`, or derive it from stable primitive state values directly in the dependency array instead of building a fresh object.

I'd also ask for actual before/after profiling data on this PR, ideally via the React DevTools profiler, showing the render counts or render time changes for at least the top three or four components you're claiming benefit from this. Blind memoization is a common enough anti-pattern that I'd rather see the numbers than take the optimization on faith, especially since a couple of the changes as currently written aren't actually achieving what they're meant to (per the `filters` issue above).

To be clear, I'm not against this PR's goal — dashboard re-render cost from polling is a real, worth-fixing problem — but I'd want the `DashboardHeader` memo removed, the `filters` object stabilized so the `RevenueChart` memoization actually works, and some profiling evidence attached before merging. Happy to re-review quickly once those are in; this shouldn't take long to fix given the underlying components are already solid.
