The query itself is correct, but the pagination strategy is going to degrade badly as this table grows, and I think that's worth addressing now rather than after someone complains about page 400 of the audit log taking eight seconds to load.

`findByTenantIdOrderByCreatedAtDesc(tenantId, pageable)` uses Spring Data's standard `Pageable`, which under the hood does `LIMIT ? OFFSET ?`. For early pages that's cheap, but offset pagination requires the database to scan and discard every row before the offset — by the time a user (or, more likely, an internal job walking the whole audit log) reaches page 500 at 50 rows per page, Postgres is scanning and throwing away 25,000 rows just to return the next 50. On a table that's going to accumulate audit records indefinitely, this gets worse every day it's in production, not just with usage growth.

For an append-only, timestamp-ordered table like this, keyset pagination (a.k.a. seek pagination) is the standard fix: instead of an offset, the client passes the last-seen `createdAt`/`id` pair from the previous page, and the query becomes `WHERE tenant_id = :tenantId AND (created_at, id) < (:lastCreatedAt, :lastId) ORDER BY created_at DESC, id DESC LIMIT :size`. That's a single index range scan regardless of how deep into the table you are. It does mean giving up arbitrary "jump to page N" navigation and random total-count display, which is a real UX tradeoff — worth confirming with whoever owns this endpoint's consumers whether that's acceptable before committing to the rewrite, since if this is purely an internal export job walking sequentially, keyset pagination is a strict win with no downside.

If you want a smaller, incremental version of the fix without redesigning the API contract yet: at minimum confirm there's a composite index on `(tenant_id, created_at)` — I don't see one in the migration you included, and without it, even the current offset query is doing a filter-then-sort rather than an index-ordered scan, which is a separate and more urgent problem than the offset cost itself.
