An intrusive doubly-linked list for an LRU cache is a reasonable choice — it gets you O(1) move-to-front without a second allocation per node — but the raw-pointer plumbing here has a few issues I'd want fixed before trusting it with real traffic.

The biggest one: `unlink` sets `node.prev` and `node.next` to null after splicing the node out, but `remove_lru` (which pops the tail) doesn't null out the removed node's pointers before it's handed back to the caller as an owned `Box`. If the caller ever inspects `prev`/`next` on that box before reinitializing it — and your own `reinsert_at_front` does exactly that, briefly, before overwriting them — you're reading dangling pointers into freed-adjacent nodes for a few instructions. It happens to work today because `reinsert_at_front` overwrites both fields before dereferencing either, but that's fragile: the next person to touch this code (including you in six months) can easily add a debug print or a stray field read in between and get UB. I'd add an explicit `debug_assert!(node.prev.is_null() && node.next.is_null())` at the top of `reinsert_at_front` so a violation gets caught immediately rather than manifesting as an intermittent crash.

Second, the list stores `*mut Node<K, V>` for `prev`/`next` and separately keeps ownership in a `HashMap<K, Box<Node<K, V>>>`. That's a legitimate pattern, but it means the raw pointers into the list are only valid as long as the `Box` isn't moved or reallocated by the map, and `HashMap` never moves its values on insert/resize by contract, so this is fine — but it's exactly the kind of invariant that deserves a comment, because it's not obvious from reading `Node` in isolation, and it's the sort of thing that breaks silently if someone later switches the backing map to something that does move values.

Third, `Node::new` returns a raw pointer obtained via `Box::into_raw` and there's no corresponding `Drop` for the list that walks it and reconstitutes boxes to free them — right now cleanup relies entirely on the `HashMap`'s own `Drop`, which is correct today since the map owns the boxes, but if that ownership model ever changes this becomes a leak with no compiler warning to catch it. Worth a comment stating explicitly "the map owns all nodes; the list holds only borrowed raw pointers and must never be the thing that frees them," so the invariant is documented where someone would look for it.

Smaller stuff: `unsafe impl Send for LruCache` is present but I don't see the corresponding `Sync` impl or a justification for why `Send` alone is sufficient given the raw pointers — if this is only ever accessed from one thread at a time behind an external mutex, say so in a comment; if it's meant to be used concurrently without external locking, it isn't safe as written and needs actual synchronization.

None of this is unfixable, and the overall structure is sound — I'd just want the invariants written down as comments or `debug_assert!`s so the unsafety is locally checkable rather than relying on nothing-moved-yet coincidences holding forever. Please address the null-out-before-reuse issue and document the ownership split before merging.
