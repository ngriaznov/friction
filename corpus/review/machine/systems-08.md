Writing a `shared_ptr` clone as a learning exercise is a great way to actually understand refcounting, but there are two bugs here that would matter in real use, plus the usual thing everyone forgets the first time through.

The increment/decrement of the control block's refcount uses `int refcount` with plain `++`/`--`, not `std::atomic<int>`. If this type is ever shared across threads — and the whole point of `shared_ptr` is usually that it can be — two threads copying or dropping the same pointer concurrently will race on that increment, and you'll get a refcount that's wrong in either direction: too high leaks the object, too low frees it while something still holds a "valid" copy, which is a use-after-free. `std::shared_ptr` itself guarantees the control block operations are thread-safe (the pointed-to object's mutation isn't, but the refcounting is) specifically because this is such an easy trap; I'd make yours atomic too, or clearly document in the class that it is not thread-safe if that's an intentional scope cut.

Second, there's no handling for self-assignment in `operator=`. As written, `this->ptr = other.ptr; this->ptr->refcount++;` followed by decrementing the old refcount — if `other` and `*this` share the same control block (or in the pathological case, are literally the same object), you increment then decrement the same counter, which happens to net out correctly for the shared-control-block case, but if the order were ever flipped (decrement-then-increment, which is the more common way people write this to "release old, then acquire new") a self-assignment would drop the refcount to zero and free the object out from under itself before the increment ever runs. It works today by luck of ordering; I'd add an explicit self-assignment guard (`if (this != &other)`) so correctness doesn't depend on remembering which order the two operations happen in.

The move constructor and move assignment look correct — you null out the source's raw pointer after transferring ownership, which is the detail people most often miss. Good.

Given this is a learning exercise rather than something meant to replace `std::shared_ptr` in production, I wouldn't block on making it a full drop-in (no `weak_ptr` equivalent, no custom deleter support, no `make_shared`-style single-allocation optimization) — but I would fix the self-assignment case and either make the refcount atomic or document clearly that this type is single-threaded only, since that's the kind of gap that bites you exactly when you've forgotten you cut the corner.
