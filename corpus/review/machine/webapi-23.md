This PR adds query complexity limiting to the Python GraphQL API (Ariadne), introducing a cost-per-field convention via a `@cost(complexity: N, multiplier: "field")` schema directive and a validation rule registered in the Ariadne setup that rejects queries above a configured threshold before execution.

Good defensive addition, and using a schema directive to declare cost per field rather than a separate out-of-band config file keeps the cost annotations next to the fields they describe, which will make them much easier to keep accurate as the schema evolves — a real strength of this approach over a lot of the complexity-limiting setups I've seen.

Two things worth a look before merging. The multiplier directive is applied to list-returning fields (`orders(first: Int): [Order]`) using the `first` argument to scale cost, which is correct in principle, but the default cost when `first` is omitted isn't addressed — if a client omits `first` entirely, does the field fall back to some assumed worst-case multiplier, or does it get treated as multiplier 1? A quick look at the validation rule suggests the latter, which would let a query that omits the limit argument (relying on whatever server-side default page size applies at execution time) sail through complexity validation as if it only returned one item, while actually returning however many the resolver's default happens to be. I'd have the directive require an explicit worst-case multiplier for any field where the argument is optional, rather than defaulting to the friendliest case.

Second, smaller: the threshold itself (mentioned in the PR description as 10,000) is a single global constant with no per-client or per-auth-tier variation. That's a fine starting point, but if there's any plan to offer different rate/complexity tiers to different API consumers later, it'd be worth threading the limit through as a value resolved from the request context now rather than a hardcoded constant, just to avoid a second migration through all the call sites later.

Nothing here is a blocker — this is a net positive addition and the directive-based design is the right call. Approving, with the optional-argument default-cost gap as the one thing I'd actually want fixed rather than deferred, since it's the kind of edge case that undermines the whole point of the feature if left as-is.
