This PR adds a `p99-latency` and `error-budget-burn` alert group to `monitoring/prometheus/rules/api-slo.yml`, plus a companion Grafana dashboard JSON for visualizing both. Nice work overall — this is clearly modeled on a proper SLO/error-budget approach rather than an arbitrary static threshold, and using multi-window burn-rate alerts (1h/6h fast-burn and 24h/3d slow-burn, per the Google SRE workbook pattern) rather than a single flat threshold is the right way to do this; it avoids the classic problem of either paging on every blip or missing slow sustained degradation.

The burn-rate math itself checks out — `(1 - (sum(rate(http_requests_total{status!~"5.."}[1h])) / sum(rate(http_requests_total[1h])))) > (14.4 * (1 - 0.999))` for the fast-burn window matches the standard formula for a 99.9% SLO target with a 14.4x burn multiplier, and the annotations correctly note which error budget percentage each alert consumes.

Two things worth double-checking before merge:

The `error-budget-burn` group's `slow_burn` alert uses a 3-day window (`[3d]`) — Prometheus's default retention and your `rate()` evaluation over that range depend on your scrape interval and retention settings actually covering 3 days of data at query time. If your Prometheus instance has a shorter retention or is federated in a way that doesn't preserve raw samples that far back, this rule will silently produce `NaN`/no-data rather than erroring, and you won't notice until you go looking for why the slow-burn alert never fires. Worth confirming retention covers this, or documenting the assumption in a comment near the rule.

The Grafana dashboard JSON has the datasource UID hardcoded (`"uid": "prometheus-prod-1"`) rather than using a templated `${DS_PROMETHEUS}` variable. That'll work fine in the environment it was exported from but will silently point at nothing (or the wrong datasource) if this dashboard is provisioned into a different Grafana instance via the dashboard-as-code pipeline referenced elsewhere in the repo. Minor, but worth fixing since dashboards get copied across environments more often than people expect.

Everything else — the runbook links in the alert annotations, routing fast-burn to the paging receiver and slow-burn to a ticket-only receiver, and the `for:` durations lining up with the burn-rate methodology — is well done. Approving with the one request to fix the hardcoded datasource UID before merge; the retention question is worth a quick confirmation but I wouldn't block on it.
