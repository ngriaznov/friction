This PR introduces a dedicated `ServiceAccount` and scoped `Role`/`RoleBinding` for the `reporting` service (replacing its previous use of the namespace's `default` service account), and switches its database credential from a plain `Secret` to a Bitnami Sealed Secret. Good change on both fronts — running workloads under `default` with no explicit RBAC is a common footgun since it tends to accumulate permissions over time as other things get bound to it, and Sealed Secrets means the encrypted blob can live safely in git rather than needing to be applied out-of-band.

The `Role` grants `get`, `list`, `watch` on `configmaps` and `secrets` scoped to the `reporting` namespace, which matches what the service actually needs per the PR description (it reads a couple of ConfigMaps for feature flags and needs to read its own sealed-then-unsealed secret). Scoped to a `Role` rather than a `ClusterRole` is the right call here since there's no indication this service needs cross-namespace access.

One thing worth a second look: the `Role` grants `list`/`watch` on `secrets` at the resource-kind level rather than scoped to a specific named secret via a `resourceNames` field. That means this service account can list and watch every Secret in the `reporting` namespace, not just its own — if any other workload later gets deployed into this same namespace with its own secrets, `reporting`'s service account would be able to read those too. Since Kubernetes RBAC does support `resourceNames` for exactly this kind of narrowing, I'd add that here scoped to the one or two secrets this service actually needs, rather than namespace-wide secret access.

The SealedSecret's `spec.encryptedData` looks correctly generated via `kubeseal`, and the accompanying comment noting which cluster's controller public cert was used to seal it is a nice touch for future maintainers.

Small note: the `RoleBinding` subject references the ServiceAccount by name correctly, and `automountServiceAccountToken` isn't explicitly set to `false` — worth considering whether this pod actually calls the Kubernetes API at all beyond what's needed for the mounted secret/configmap (which doesn't require API access, just volume mounts); if it doesn't call the API directly, disabling auto-mount is a small additional hardening step.

Approving — the `resourceNames` scoping on secrets is worth doing but isn't a blocker given this is already a meaningful improvement over the previous `default` service account setup.
