Reviewed the new `InventoryReservationIntegrationTest` suite along with the reservation-flow changes it covers. The scenario coverage is good — happy path reservation, expiry-driven release back to available stock, and the concurrent-reservation race where two requests compete for the last unit are all exercised, and that last one in particular is the case I'd have specifically asked for if it weren't already here, since that's where this kind of feature usually breaks in production.

A structural concern: this test class starts its own `PostgreSQLContainer` and `KafkaContainer` rather than reusing the shared containers already defined in `AbstractIntegrationTest`, which every other integration test in this module extends. I'd guess this was because the reservation flow needed a Kafka container and the base class only wires up Postgres, but the fix should be adding Kafka to the shared base class (behind a flag or as a second abstract class, `AbstractKafkaIntegrationTest`, if not every suite needs it) rather than this test standing up a fully parallel container set. As written, CI now boots two separate Postgres instances and two separate Kafka instances across the suite whenever this test class runs alongside the others, which adds real time to the pipeline for no isolation benefit.

The expiry test (`shouldReleaseStockWhenReservationExpires`) uses `Thread.sleep(6000)` to wait past the 5-second reservation TTL configured for the test profile. That works but it's a real six-second tax on every CI run of this class, and it's the kind of sleep-based test that becomes flaky the moment the TTL value or scheduler cadence changes elsewhere. If the expiry sweep is driven by a scheduled job, consider exposing a way to trigger it synchronously in the test profile (a manually-invokable `@Component` method rather than only the `@Scheduled` trigger) so the test can call it directly instead of waiting out the clock.

The concurrency test uses two threads calling `reservationService.reserve()` simultaneously via `CompletableFuture.allOf`, then asserts exactly one succeeded and one got `InsufficientStockException` — good test, but it's asserting on application-level behavior only. Given the whole point of this test is proving the race is handled correctly, I'd also assert directly on the row in `inventory_stock` afterward to confirm the reserved count didn't get corrupted by a lost update, rather than trusting the service-layer exception alone to prove the database ended up consistent.

Solid suite overall, good instinct to test the race condition — the container consolidation and the sleep-based expiry test are the two things I'd want addressed before merging, the rest are minor.
