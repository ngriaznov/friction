The overall approach — a `processed_webhook_events` dedup table keyed on the provider's `event_id`, checked before processing each payment webhook consumed from the `payment-webhooks` topic — is the right pattern for this problem, and I like that you're storing the dedup record in the same database transaction as the actual payment state update rather than in a separate cache, since that's what makes the dedup check atomic with the effect it's guarding.

There's a race condition in `PaymentWebhookConsumer.handle()` as written, though. The flow is: check `processedEventRepository.existsByEventId(eventId)`, and if false, process the payment update and then `processedEventRepository.save(new ProcessedEvent(eventId))`. Between the `existsByEventId` check and the `save`, if two instances of this consumer somehow process the same event concurrently — which can happen during a rebalance where, briefly, delivery isn't strictly single-consumer, or if this ever runs with more than one thread per partition — both can pass the exists-check before either has saved, and you're back to double-processing the exact case this table exists to prevent. The fix is to rely on the database's unique constraint rather than the read-then-write check: put a unique index on `event_id` (I see one already exists, good), and instead of pre-checking, just attempt the insert first and catch the constraint violation as your "already processed, skip" signal. That collapses the check-then-act race into a single atomic operation the database enforces for you.

Second, related: `save()` happens after the payment state update within the same `@Transactional` method, which is correct for atomicity, but I don't see what happens if the payment update logic itself is not idempotent when retried after a partial failure. If the process crashes after updating payment state but before the transaction commits (so the dedup row never gets written), Kafka will redeliver the event on restart since the offset wasn't committed either — and since both operations are in the same transaction, this should actually be fine on retry precisely because the whole transaction rolls back together. Worth a comment in the code explaining this invariant explicitly, since it's easy for a future change to accidentally split the payment update and the dedup insert into separate transactions without realizing why that would reintroduce the exact bug this table was built to prevent.

Smaller: no retention or cleanup policy on `processed_webhook_events` that I can see — this table grows forever. A scheduled job purging entries older than some window (a few days past your consumer's max plausible redelivery lag) would keep it from becoming an unbounded table.

The insert-first-catch-violation fix is the one I'd actually block on; the rest are worth doing but not blocking.
