The tokio TCP proxy structure — a task per connection, `tokio::io::copy_bidirectional` shuttling bytes between the client and upstream sockets — is a reasonable starting point, but I don't think it actually gives you the backpressure you're asking about, and there's a resource issue worth fixing alongside it.

`copy_bidirectional` already does the right thing internally: it won't read more from one side than it can currently write to the other, because it's driven by each socket's own readiness and buffer state, so you get backpressure "for free" in the sense that a slow downstream naturally throttles reads from the fast side. What you don't have is any bound on the number of concurrent connections — `TcpListener::accept()` in a loop spawning a new task per connection with no semaphore or connection-count limit means a burst of incoming connections (or a deliberate connection-exhaustion attack, if this proxy is internet-facing) can spawn an unbounded number of tasks, each holding its own socket buffers, until the process runs out of file descriptors or memory. I'd wrap the accept loop with a `tokio::sync::Semaphore` sized to your target max-concurrency, acquiring a permit before spawning each task and holding it for the task's lifetime, so `accept()` effectively pauses (or you queue/reject) once you're at capacity instead of unconditionally spawning.

Also worth checking: what happens to the semaphore permit and any partially-copied bytes if `copy_bidirectional` returns an error, versus finishing cleanly. From what's posted, both paths just log and return, which is fine, but make sure the permit's `Drop` is what releases it (rather than an explicit release call that could be skipped on an early return) — using the RAII guard rather than manual release is the safer pattern here and it looks like you're already doing that, just flagging it as the thing to double check if you refactor this later.

That's really the one substantive gap — bound your concurrency — the copy mechanism itself is fine as-is.
