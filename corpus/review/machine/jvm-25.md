Went through this end to end since it touches test infrastructure used by nearly every integration test in the repo. Consolidating the five near-duplicate base classes (`PostgresIntegrationTest`, `KafkaIntegrationTest`, `PostgresKafkaIntegrationTest`, `RedisIntegrationTest`, and the module-local `OrderServiceIntegrationTestBase` that reimplemented most of `PostgresKafkaIntegrationTest` independently) into a single composable `AbstractIntegrationTest` with opt-in container traits is a genuinely good piece of infrastructure work, and it's overdue — I've seen at least two of the old base classes drift out of sync with each other on Postgres image versions before this change.

The trait-based approach — `@IntegrationTest(containers = {POSTGRES, KAFKA})` on the test class, with a static registrar picking which `GenericContainer`s to start based on the annotation — is a clean design. It keeps the container-selection declarative at each test class rather than forcing inheritance from whichever combination happens to match, which was the actual root cause of the duplication you're removing. And using a single shared `Network` across all containers started for a given test class, rather than each container getting its own default network, fixes a latent bug where cross-container hostname resolution (Kafka's advertised listeners reaching Postgres by container name) was working by accident in some of the old base classes and not others.

A few things I'd want addressed before merging, given how many downstream test files this touches:

The migration script (`migrate_test_bases.py`) that rewrites existing test classes to the new annotation-based form is not included in this PR, only the end state — 340 files already converted. If a test file gets added on a branch that's based off `main` before this merges, and that branch also touches one of the five old base classes, the merge conflict resolution is going to be manual and error-prone without the script to lean on. I'd either include the migration script in the PR (even if it's a one-time-use tool, keep it in `scripts/` for reference) or, if it's already been discarded, at least document the mechanical transformation rules in the PR description for anyone resolving a conflict by hand in the next couple of weeks.

Container startup ordering: `AbstractIntegrationTest`'s static initializer starts all requested containers in the order they appear in the `containers` array on the annotation, sequentially, rather than in parallel. For a test class requesting `{POSTGRES, KAFKA, REDIS}`, that's three sequential container boots adding to setup time that used to be somewhat parallelized in `PostgresKafkaIntegrationTest`'s old constructor (it used two threads to start Postgres and Kafka concurrently). Worth starting all requested containers concurrently via `CompletableFuture.allOf` rather than sequentially — this is exactly the kind of regression that's easy to miss because each individual test still passes, it just makes the whole suite slower in aggregate.

One test-suite-level item: I spot-checked a handful of the 340 converted files and the annotation-based versions look like faithful mechanical translations, but `PaymentReconciliationIntegrationTest` and `RefundProcessingIntegrationTest` both lost a `@DirtiesContext` that was present on their old base class usage. If that annotation was load-bearing (forcing a fresh Spring context between these specific tests because they mutate shared singleton state), dropping it silently during the mechanical conversion could introduce order-dependent flakiness that won't show up until these tests run in a different order than they have been — worth specifically re-verifying those two rather than trusting the conversion was uniform across all 340 files.

Overall this is the right infrastructure investment and I want it to land, but I'd fix the sequential container startup and get eyes specifically on the two files that lost `@DirtiesContext` before merging — the rest of the conversion looks solid from what I sampled.
