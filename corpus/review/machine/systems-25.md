This PR adds a custom `Allocator` trait implementation (the unstable `allocator_api` feature) backing the arena crate's `Bump` type, letting `Vec`, `Box`, and friends allocate directly out of the arena via `Vec::new_in(&bump)` instead of the crate's existing bespoke `bump.alloc(value)` API. Nice ergonomic win if it lands cleanly, since it lets arena-allocated collections use the standard library's own types instead of the crate reinventing a parallel `BumpVec`, which I know from the issue tracker was a long-standing complaint about this crate.

The `alloc` and `alloc_zeroed` methods on the `Allocator` impl correctly forward to the arena's existing bump-pointer logic and respect the requested `Layout`'s alignment, which I checked against the existing hand-written `bump.alloc::<T>()` path and the two produce the same offsets for a handful of alignment/size combinations I traced through by hand. Good.

The part I'd want changed before merging: `deallocate` is implemented as a no-op, which is correct for a bump allocator in the general case — you can't reclaim arbitrary interior allocations without a free list, and adding one would defeat the point of a bump allocator — but there's a missed opportunity and a subtle risk here that are worth addressing together. The opportunity: if the deallocated pointer happens to be the most recently allocated block (i.e., it's sitting exactly at `current - layout.size()`), you can actually roll the bump pointer back, which is a real and common optimization for exactly the "allocate a scratch `Vec`, push some things, drop it" pattern that `Allocator` trait usage encourages. Worth adding that check — it's a few lines and meaningfully reduces waste for the pattern this PR is explicitly trying to make more ergonomic. The risk: because `deallocate` is a true no-op, `Vec::shrink_to_fit` and similar operations that reallocate-and-copy under the assumption that the old allocation becomes reusable space will work correctly (nothing unsound happens) but will silently waste arena space on every call, since the old block is never reclaimed and the new one is bump-allocated fresh. That's not a bug, but it's a footgun for exactly the audience this PR is aimed at — people used to `Vec`'s normal allocator behavior who won't expect their arena to grow unboundedly from a pattern that's normally free. I'd flag this prominently in the trait impl's doc comment, since it's the kind of thing that's easy to hit by just calling ordinary `Vec` methods without realizing they interact differently with a bump allocator.

Also: this depends on the unstable `allocator_api` feature, meaning both this crate and anyone consuming this trait impl now needs nightly Rust. That's a real cost worth stating explicitly in the changelog and README rather than only in the PR description, since it changes the MSRV story for every downstream user who wants this specific integration, even though the crate's existing `bump.alloc()` API presumably stays available on stable and this is additive.

I'd merge this once the doc comment calls out the shrink/no-reclaim footgun clearly, and I'd strongly encourage adding the last-allocation rollback optimization in this same PR since it directly addresses the case this feature is mostly going to be used for. The nightly-only caveat just needs to be visible in user-facing docs, not code changes.
