Went through the TypeScript strict-mode migration for `src/utils/`. This is a good, disciplined pass — turning on `strict` incrementally per-directory via a `tsconfig` override rather than flipping it globally is the right way to do this on an existing codebase, and I appreciate that the diff is scoped tightly to just the utils folder plus its existing test files rather than sprawling into unrelated areas.

A few of the fixes are the kind I'd want a second look at rather than rubber-stamp, since strict-mode migrations are exactly where non-null assertions tend to get sprinkled in as the path of least resistance rather than actually fixing the underlying type issue. In `parseQueryString.ts`, the change from an implicit `any` to explicit typing added three uses of the non-null assertion operator (`!`) on `match[1]`, `match[2]`, and `params.get(key)`. The first two are probably fine, since they follow a regex `.exec()` call where the capture groups are guaranteed to exist given the pattern, but I'd still prefer a comment explaining why, since a future edit to that regex could silently invalidate the assumption and TypeScript won't catch it. The third one, `params.get(key)!`, is more concerning — `URLSearchParams.get()` legitimately returns `null` when the key isn't present, and asserting it away rather than handling the `null` case looks like it's papering over a real possibility rather than an impossible one. Worth checking whether the caller actually always has that key present (in which case a comment justifying the assertion is enough) or whether this needs an actual null check with a fallback.

`formatCurrency.ts` and `debounce.ts` both look clean — proper generic typing on `debounce<T extends (...args: any[]) => void>`, no assertions, and the return type changes look correct against how these are actually called elsewhere (I spot-checked a few call sites).

One structural note: `strictNullChecks` being on now means several functions in `arrayHelpers.ts` that previously accepted `T[] | null | undefined` loosely now have explicit union types threaded through, which is good, but a couple of call sites elsewhere in the app (outside this PR's scope, in `src/components/OrderList.tsx`) are presumably still passing values that could be `undefined` into these newly-strict signatures. Since those files aren't part of this PR's `tsconfig` override yet, this won't show up as a build error until they're migrated too — just flagging that there may be a wave of follow-up type errors surfacing in adjacent files as the strict boundary expands, which is expected and fine, just worth having on the radar for whoever picks up the next directory.

Test coverage for the changed functions looks adequate — I don't see new tests added specifically for the type-narrowing changes, but the existing test suite for utils passes according to the CI check, and the changes here are type-level rather than behavioral in most cases, so I don't think new tests are strictly required for this PR.

Approving, with a request to either justify or fix the `params.get(key)!` assertion in `parseQueryString.ts` before merge — that one specifically looks like it could hide a real bug rather than just satisfying the compiler.
