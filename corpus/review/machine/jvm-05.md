I'd hold off on merging this as-is — the exception handling here is going to make production incidents much harder to diagnose than they need to be.

The `@ControllerAdvice` has a single `@ExceptionHandler(Exception.class)` that catches everything — validation failures, `EntityNotFoundException`, `DataIntegrityViolationException`, and genuine bugs — and returns the same generic 500 with the message `"Something went wrong"`. That means a client sending a malformed request gets the same response as a database outage, which makes it impossible for API consumers to distinguish "fix your request" from "retry later" from "this is broken, page someone." At minimum split this into a few targeted handlers: `MethodArgumentNotValidException` and constraint violations should map to 400 with field-level detail, `EntityNotFoundException` (or whatever your custom not-found type is) to 404, and only truly unexpected exceptions should fall through to the catch-all 500.

Related: the catch-all handler logs at `WARN` with `ex.getMessage()` only, not the stack trace. For anything that reaches this handler unexpectedly, you want `ERROR` level with the full exception logged (`log.error("Unhandled exception", ex)`), otherwise you'll be debugging production issues with a one-line message and no idea where in the call stack it originated.

There's also a correctness issue, not just a taxonomy one: `DataIntegrityViolationException` gets caught by the generic handler and turned into a 500, but in `OrderService.createOrder` that exception is thrown specifically when a duplicate order reference hits the unique constraint — that's a client error (409 Conflict, "this order already exists"), not a server error. Right now legitimate duplicate-submission retries from the frontend surface as 500s and presumably get retried again, which won't help.

Smaller: the response body is a bare string wrapped in `ResponseEntity<String>`. Even a minimal `{"error": "...", "timestamp": "..."}` shape would be more useful to API consumers and easier to extend later without a breaking change to every handler at once.

I know the goal here was probably just "stop leaking stack traces to clients," and that part is achieved, but the current shape trades one problem for a worse one. Happy to pair on splitting this into a few handlers if useful — it's mostly mechanical once the exception hierarchy is sorted out.
