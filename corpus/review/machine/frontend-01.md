There's a real bug here, so let me start with that before getting into style: `useFetch` as written is vulnerable to a classic race condition. You fire the request inside `useEffect`, store the response in state with `setData`, but nothing stops a stale response from a previous `url` value overwriting a newer one if the earlier request happens to resolve after the later one. This is the single most common bug in hand-rolled data-fetching hooks, and it's exactly why libraries like React Query and SWR exist, but if you want to keep this hand-rolled, it's fixable in a few lines.

The standard fix is a cancellation flag scoped to each effect run. Inside the `useEffect`, declare a local `let cancelled = false`, and in the cleanup function returned from the effect, set `cancelled = true`. Then, right before each `setData`/`setError`/`setLoading` call inside the `.then`/`.catch`, check `if (!cancelled)`. Because the closure captures the flag from that specific effect invocation, a response belonging to an abandoned request can no longer clobber state. Alternatively — and I'd actually recommend this over the boolean flag — use `AbortController`. Create one per effect run, pass its `signal` to `fetch`, and call `controller.abort()` in the cleanup. This has the added benefit of actually canceling the in-flight network request instead of just ignoring its result, which saves bandwidth and avoids doing pointless work when a user types quickly into a search box that drives this hook.

Second issue: your dependency array is `[url]`, but the effect body also references `options`, which you're passing in as a fresh object literal on every render from the calling component (`useFetch(endpoint, { headers: authHeaders })`). Since `options` isn't in the dependency array, ESLint's `react-hooks/exhaustive-deps` rule should already be flagging this, and if it isn't, turn that rule on. Even if you add `options` to the array, though, you'll get an infinite loop because the object reference changes every render. You have two reasonable options: either serialize the parts of `options` that matter (e.g., `JSON.stringify(options)` as a dependency, which is hacky but works for small option objects), or require callers to memoize the object with `useMemo` before passing it in, and document that requirement clearly. I'd lean toward the latter — pushing memoization responsibility onto the hook itself tends to paper over problems rather than fix them, and callers who don't memoize will hit stale-closure bugs elsewhere too.

On the loading state: right now you initialize `loading` to `true` unconditionally, which means a component that calls `useFetch` with a `url` of `null` (a common pattern for "don't fetch yet") will render a permanent loading spinner because the effect bails out early on a null URL without ever setting `loading` back to `false`. Guard the early return so it also resets loading, or better, don't set `loading: true` until you've confirmed there's actually a URL to fetch.

A smaller thing: you're catching errors with a bare `catch (err) { setError(err) }`, but you're not distinguishing an aborted request from a genuine failure. If you adopt `AbortController`, an aborted fetch throws a `DOMException` named `AbortError`, and you almost certainly don't want to surface that to the UI as a user-facing error — it just means a newer request superseded it. Add a check like `if (err.name !== 'AbortError') setError(err)`.

On naming and shape: returning `{ data, loading, error }` is a fine, conventional shape, and I wouldn't change it. Consider adding a fourth field, something like `refetch`, exposed as a stable callback via `useCallback`, since callers frequently need to manually re-trigger a fetch (after a mutation, for instance) without changing the URL. Without it, people will end up appending a fake cache-busting query param just to force the effect to re-run, which is a smell you can head off now.

Performance-wise, this is fine for a handful of call sites, but if this hook gets used in a list where each row calls `useFetch` independently, you're going to fire one request per row with no shared cache and no deduplication of identical URLs requested concurrently. That's not a bug, just a scaling limit worth knowing about before this pattern spreads through the codebase.

Overall the shape of the hook is reasonable and the instinct to abstract fetching behind a hook is right, but the race condition needs fixing before this ships anywhere with rapid consecutive updates (search-as-you-type, filters, tabs), and the missing `options` dependency will bite the first person who passes headers or a request body through it. I'd request changes rather than approve as-is, though none of this is a big rewrite — probably 20 minutes of work.
