Reviewed the introduction of React Query to replace the hand-rolled `useApi` hooks across the dashboard section. This is a good direction and the query key structure is thoughtfully designed, but there are a handful of things worth fixing before this pattern gets copied to the rest of the app, since that's clearly the intent given the PR description mentions this is meant to be the template going forward.

Query keys are structured as arrays with a consistent hierarchy — `['orders', 'list', filters]`, `['orders', 'detail', orderId]` — which is exactly the pattern React Query's own docs recommend for enabling targeted invalidation, and I can see it's being used correctly in the mutation's `onSuccess` handler, which invalidates `['orders', 'list']` broadly rather than needing to know every specific filter combination that might be cached. Good.

One real issue: `staleTime` isn't set anywhere, so it defaults to `0`, meaning every component mount (including ones caused by navigating away and back, or a parent re-render that remounts a query-consuming child) triggers a background refetch. For data like the order list, which doesn't need to be second-by-second fresh, that's a lot of unnecessary network traffic. Consider setting a sensible `staleTime` — even something modest like 30 seconds — either per-query or via the `QueryClient` defaultOptions, rather than accepting the zero-staleness default everywhere.

Second: I see `useQuery` called with `refetchOnWindowFocus` left at its default (`true`) across the board, including for a query that hits a genuinely expensive backend aggregation endpoint (`['dashboard', 'revenue-summary']`, which per a comment in the API route takes several seconds to compute). Refetching that every time the browser tab regains focus seems like an unnecessary load on that endpoint for marginal freshness benefit. Worth setting `refetchOnWindowFocus: false` specifically for expensive queries like that one, even if the default stays on elsewhere.

Third, and this is the one I'd actually block on: the migration replaced the old `useApi` hooks' error handling, which surfaced errors through a consistent app-wide toast notification, with each component now handling `isError`/`error` from `useQuery` independently, and about half the migrated components don't render anything on error at all — they just show a permanent loading spinner or blank space if the query fails, because the JSX only branches on `isLoading` and the success case. A consistent error-handling story matters more once this becomes the template for the rest of the app; I'd suggest either wiring a global `onError` handler via `QueryClient`'s `queryCache` config to restore the toast behavior automatically for all queries, or requiring every migrated component to explicitly handle the error case, but right now it's an inconsistent mix of both approaches within the same PR.

Smaller items: `QueryClientProvider` is instantiated with `new QueryClient()` directly inside the `_app.tsx` component body rather than outside the component or in a `useState` initializer, which means a new `QueryClient` (and therefore a fresh, empty cache) gets created on every re-render of `_app`. This is a well-known React Query gotcha and should be `useState(() => new QueryClient())` or a module-level singleton instead.

Solid direction overall, and the query key design is the hardest part to get right long-term, so I'm glad that's solid. I'd want the `QueryClient` instantiation bug and the inconsistent error handling fixed before this becomes the pattern other PRs copy, since both will multiply in cost the longer they sit unaddressed.
