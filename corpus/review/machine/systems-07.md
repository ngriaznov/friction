Thanks for posting the whole module rather than just the hot function — it makes it much easier to see where the TTL cache's actual bottleneck is likely to be, which I don't think is where you're expecting.

The design is `Arc<Mutex<HashMap<K, (V, Instant)>>>` with a background thread that wakes every second, takes the lock, and walks the entire map evicting anything past its TTL. Functionally this works, and I don't see a correctness bug in the eviction logic itself — the `Instant::now() > expires_at` comparison is right, and you're correctly using `Instant` rather than `SystemTime` so you're immune to clock adjustments. But there are three things I'd change before calling this production-ready for anything with meaningful throughput.

First, and most important: every single read (`get`) takes the same `Mutex` that writes and the eviction sweep use. That means a cache that's supposed to speed up a read-heavy workload serializes all reads behind one lock, and worse, a read can block for the full duration of an eviction sweep over a large map. For a read-mostly cache this is the wrong tool — `RwLock` gets you concurrent readers, or better, something like `dashmap::DashMap` gives you sharded locking so unrelated keys don't contend at all. Given you mentioned this sits in front of a database call on a hot path, I'd treat this as the change to make first; it's very likely the actual source of latency spikes under load, more so than anything about the eviction strategy.

Second, the eviction thread walks the whole map every second regardless of how many entries have actually expired, which is O(n) work on a timer independent of cache activity. For a small map this is nothing, but if this cache is meant to scale to a large number of entries, a lazy-expiration approach (check-and-evict-on-access, plus a much less frequent or size-triggered sweep for entries that are never touched again) does less wasted work. Whether this matters depends on your actual `n`, which you didn't mention, so take this as a "worth measuring" rather than a must-fix.

Third, the eviction thread is spawned with `thread::spawn` in `Cache::new` and there's no way to stop it — the `Arc<Mutex<HashMap>>` is cloned into the thread's closure, so even after every other reference to the cache is dropped, that background thread keeps the map alive forever and keeps running its sweep loop. This is a real resource leak if `Cache::new` is ever called more than once per process (tests are the obvious place this bites — every test that constructs a cache leaks a thread that outlives the test). I'd add a shutdown mechanism: either hold a `Weak` reference in the background thread and exit the loop once upgrading it fails (this is the cleanest option and requires no explicit shutdown call), or add an explicit `Drop` impl on `Cache` that signals the thread via an `AtomicBool` or a channel and joins it.

Smaller things: `get` returns `Option<V>` by cloning the value out from behind the lock, which is correct but means `V` needs to be cheap to clone or this itself becomes a cost center — if `V` is something like a large struct or a `Vec`, wrapping it in an `Arc<V>` internally so clones are just a refcount bump would help. And the TTL is a single fixed `Duration` for the whole cache rather than per-entry, which is fine if that matches your use case, but worth calling out explicitly in the doc comment since "TTL cache" often implies per-entry TTLs to readers coming in cold.

To summarize: I'd want the Weak-reference shutdown fix and a plan for the reader contention (RwLock at minimum, sharding if you can justify the complexity) before merging. The eviction-sweep efficiency and the Arc<V> question are worth a follow-up but aren't blockers on their own.
