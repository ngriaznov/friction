This PR adds read-replica support to the Go service's database layer, introducing a `DB` wrapper in `internal/db/db.go` that holds a primary `*sql.DB` and a slice of replica `*sql.DB` connections, with a simple round-robin `ReadConn()` method and `WriteConn()` returning the primary. Repository methods across the codebase are updated to call one or the other depending on whether they read or write.

Reasonable feature to add and the wrapper approach — rather than threading replica selection logic through every call site — keeps the blast radius contained to the `db` package and the call-site updates, which are mostly mechanical (`db.ReadConn()` instead of `db.conn` for `SELECT`s). The round-robin selection is simple and appropriate for this scale; no objection to not doing anything fancier like latency-aware routing yet.

The main thing I'd want addressed is replication lag, which this PR doesn't appear to account for anywhere. Several of the updated call sites are in patterns like: a handler calls `CreateOrder` (write, goes to primary), then immediately calls `GetOrder(id)` (now routed to a replica) to return the created resource in the response. Replica lag of even a few tens of milliseconds — routine on most managed Postgres/MySQL replica setups — means this read can miss the just-written row and return a 404 or stale data for a request that, from the client's perspective, should obviously see its own write. This is the classic read-your-writes problem that shows up immediately once replicas are introduced, and it's worth checking every updated call site for this pattern, not just the order-creation one I happened to notice — I'd specifically look at anything that writes and then reads back in the same handler.

The two ways to handle this: route "read after write within the same request" back to the primary (simplest, and you likely already have the request-scoped context to make that decision — a flag on the context that gets set after any write and checked before choosing read vs. primary), or accept eventual consistency for those paths and change them to construct the response from the data you already have in memory after the write, rather than re-querying at all. I'd lean toward the latter where practical since it also saves a round trip, but either is fine as long as it's a deliberate choice per call site rather than the current default of "reads always go to a replica regardless of what just happened in this request."

Smaller: `ReadConn()`'s round robin uses a package-level `atomic.Uint64` counter with no health checking — if one replica falls behind or goes unreachable, it stays in rotation and a fraction of reads will fail or return stale data indefinitely rather than being routed around. Not necessarily needed for a first version, but worth a follow-up ticket at minimum, and worth calling out in the PR description so it's a known gap rather than a surprise later.

I'd request changes here specifically because the read-after-write pattern seems present in at least one call site already, which means this PR as written would introduce a real correctness regression on merge, not just a hypothetical future risk.
