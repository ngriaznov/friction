This is a textbook N+1 setup. `Author` has a `@OneToMany(mappedBy = "author")` collection of `Book`, and your endpoint loops over `authorRepository.findAll()` and calls `author.getBooks().size()` inside the DTO mapper. With lazy loading (the correct default, don't change it) that's one query for the authors and then one additional query per author to fetch their books — fine for ten authors, a real problem for ten thousand.

Fix it at the query level, not by making the association eager. Add a repository method with `@Query("select distinct a from Author a left join fetch a.books")` or, if you want it more targeted, use a `@EntityGraph` on the specific finder you're calling from this endpoint. Don't flip `fetch = FetchType.EAGER` on the entity itself — that just moves the N+1 problem to every other place `Author` gets loaded, including ones where you don't need the books at all.

Two smaller notes: `getBooks()` returning the raw entity collection out of `Author` means callers can mutate it directly and it'll get flushed on the next transaction commit, which is probably not intended for a read endpoint. Consider returning `Collections.unmodifiableList(books)` or, better, only ever exposing books through the DTO. Also worth double-checking `equals`/`hashCode` on `Book` if it's ever put in a `Set` — with a lazy proxy involved, using the JPA-generated `@Data` equals from Lombok can throw off proxy comparisons; a stable business-key-based implementation is safer than the default identity-based one Lombok gives you here.
