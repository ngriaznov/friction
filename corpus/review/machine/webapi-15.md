This PR reworks the FastAPI auth layer to support two credential types on the same endpoints — existing JWT bearer tokens for the web app, and a new API key scheme (a static, database-backed key sent via an `X-API-Key` header) for server-to-server integration partners. It touches `app/auth/dependencies.py`, adds `app/auth/api_key.py`, changes the `Depends(get_current_user)` signature used across roughly fifteen route files, and adds an `api_keys` table migration.

This is a meaningful surface area to change and I want to go through it carefully since auth bugs are disproportionately costly compared to most other bugs.

Structurally, the approach of introducing a `CurrentPrincipal` union type that both auth paths resolve to, and having a single `get_current_principal` dependency that tries JWT first and falls back to the API key header, is reasonable and keeps the fifteen call sites from needing to know which auth method was used. Good instinct to centralize that rather than duplicating the branching logic per route.

Now the issues, roughly in order of severity. In `api_key.py`, the lookup does `ApiKey.objects.get(key=raw_key)` — I'm reading this as SQLAlchemy given the rest of the codebase, so `db.query(ApiKey).filter(ApiKey.key == raw_key).first()` — comparing the raw incoming key directly against a plaintext column. Storing API keys in plaintext in the database means a database read (backup leak, replica misconfiguration, insider access, SQL injection elsewhere in the app) directly yields credentials usable against your API, with none of the defense-in-depth you presumably already apply to passwords. API keys should be hashed at rest the same way passwords are — a fast hash like SHA-256 is actually fine here (unlike passwords, API keys are high-entropy and not subject to offline brute force in the same way, so you don't need bcrypt's deliberate slowness), but plaintext storage is the part that needs to change. Store `sha256(raw_key)` and look up by the hash; when issuing a new key, show the raw value to the user exactly once and never again.

Second, `get_current_principal`'s fallback logic: it tries to decode the `Authorization` header as a JWT first, and if that raises any exception at all — not just "header missing," but any decode failure including a malformed or expired token — it silently falls through to checking `X-API-Key`. If both headers happen to be present (a client bug, a proxy that adds a stale cached auth header, a copy-pasted curl command with leftover state), an expired or invalid JWT won't produce a 401 the way a caller would expect; it'll just silently succeed via the API key path if one happens to be present, or fail with an error message that only mentions the API key check, hiding the real problem. I'd make the two paths mutually exclusive based on which header is present rather than "try JWT, catch everything, fall back," so a present-but-invalid JWT always fails loudly regardless of what else is on the request.

Third, rate limiting and scoping: the PR doesn't appear to change anything about per-key rate limits or scopes/permissions — is that intentional for this PR (auth mechanism first, authorization/limits later) or an oversight? If server-to-server partners are meant to have different rate limits than interactive users, that's worth deciding explicitly now rather than after the first partner integration ships and needs different treatment retroactively.

Smaller items: the migration adds `api_keys.key` as the plaintext column mentioned above with a unique index on it — once you switch to hashing, make sure the index moves to the hash column, and add a `revoked_at` nullable timestamp now rather than needing a follow-up migration, since key revocation is going to come up almost immediately once partners are live. Also, none of the fifteen updated route files got new tests specifically exercising the API-key path — the existing JWT tests were left as-is, which is fine, but I'd want at least a handful of new tests covering: valid key, revoked key, malformed key, and the both-headers-present ambiguity case above, since that's precisely the kind of case that's easy to get wrong silently.

I'd request changes here — the plaintext key storage is the one I consider a blocker, the JWT/API-key fallback ambiguity is close behind, and the rest are worth resolving before merge but wouldn't hold it up on their own.
