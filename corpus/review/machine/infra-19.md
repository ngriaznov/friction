This adds `scripts/cleanup-logs.sh`, intended to run nightly via cron on the app servers to delete application logs older than 30 days from `/var/log/myapp/`. A few things need fixing before this runs unattended in prod.

The core delete command is `find /var/log/myapp/*.log -mtime +30 -delete`. Two problems with this line specifically: first, `/var/log/myapp/*.log` gets shell-expanded before `find` ever sees it, so if there are zero matching files at the time the script runs (log rotation already cleaned everything, say), the glob expands to the literal string `/var/log/myapp/*.log` and `find` will error out trying to stat a path that doesn't exist — not catastrophic, but it means the script's exit code will be non-zero on a day with nothing to clean, which will look like a failure in whatever's monitoring the cron job's exit status. Better to pass the directory and a `-name '*.log'` filter to `find` directly: `find /var/log/myapp -name '*.log' -mtime +30 -delete`, which handles the empty case gracefully.

Second, and more important: there's no validation that `/var/log/myapp` actually exists and is the directory you think it is before the `find ... -delete` runs. If this script is ever run on a host where that path doesn't exist yet (new server provisioning order, a typo'd variable if this gets parameterized later), depending on shell behavior this could be a no-op — fine — but the script doesn't currently guard against a mistyped path pattern doing something more destructive. Given this script runs as root via cron (per the crontab entry included in the PR), I'd want an explicit check like `[ -d "$LOG_DIR" ] || { echo "log dir missing" >&2; exit 1; }` before any `find -delete` runs, as cheap insurance.

The crontab entry redirects both stdout and stderr to `/dev/null` (`0 3 * * * /opt/scripts/cleanup-logs.sh > /dev/null 2>&1`). That means if `find` ever does error out, or if the disk is full and `-delete` starts failing, there's no record of it anywhere. At minimum route stderr to a log file or your existing syslog/journald setup so a failure isn't silent.

Nit: no `set -euo pipefail` at the top of the script itself, which combined with the above means a failure partway through wouldn't necessarily be visible even if you do capture output, depending on what "partway through" means here since there's really only one significant command. Still worth having as a habit for any script that runs unattended and modifies the filesystem.

The 30-day retention constant is hardcoded rather than a variable at the top of the script — small thing, but if ops ever wants to tune retention without editing the `find` invocation itself, having `RETENTION_DAYS=30` declared up top and referenced as `-mtime +$RETENTION_DAYS` is friendlier to change later.

Requesting changes — mainly the glob-vs-find-filter issue and getting error output somewhere visible instead of `/dev/null`. Both are quick fixes.
