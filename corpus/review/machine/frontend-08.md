Small hook, small review. The `useDebouncedValue` implementation itself is correct — `setTimeout` in a `useEffect`, cleared in the cleanup function, dependency array includes both `value` and `delay`. That's the right shape and I wouldn't change the core logic.

Two things worth fixing before merging. First, in the search input component that consumes this hook, you're calling the debounced search API request directly inside the same `useEffect` that watches the debounced value, but you're not guarding against the component unmounting mid-request or a newer debounced value superseding an in-flight one — the same race condition that shows up in most fetch-on-effect code. Since search-as-you-type is exactly the scenario debouncing is meant to protect against overlapping requests for, and debouncing alone doesn't guarantee ordering of responses (a fast network can still return an older query's results after a newer one), add either an `AbortController` tied to the effect's cleanup or a `cancelled` flag, same pattern as any other fetch effect.

Second, minor but worth calling out: `delay` defaults to `500` inside the hook itself via a default parameter, which is fine, but it's called with a literal `300` at every call site in this codebase per a quick search, so the default is dead code nobody actually exercises. Either standardize on the actual value you want everywhere and drop the parameter, or keep it configurable and vary it meaningfully somewhere — right now it's configurable in name only.

Everything else — naming, hook placement, dependency array — is clean. Approving with those two nits; neither is a hard blocker for merging as long as there's a follow-up for the abort handling.
