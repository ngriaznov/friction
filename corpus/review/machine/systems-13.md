This PR adds an `io_uring`-backed reactor as an alternative to the existing epoll-based one, gated behind a `uring` feature flag, touching `src/reactor/mod.rs`, the new `src/reactor/uring.rs`, and `src/net/tcp.rs` to route through whichever reactor is active. Big undertaking, and the fact that it's feature-gated rather than replacing epoll outright is the right call for something this invasive — I don't think we should be forcing this on every user until it's had real production mileage.

What's good: the submission-queue/completion-queue bookkeeping in `uring.rs` correctly tracks in-flight operations by user_data token in a slab, and the completion loop drains the CQ fully before returning control to the executor rather than processing one entry per wake, which matters a lot for `io_uring` throughput. The buffer-lifetime handling for reads — keeping the target buffer pinned and alive in the slab entry until the corresponding CQE arrives — looks correct on inspection; that's the part of io_uring integration most implementations get wrong (submitting a buffer pointer and then letting the buffer move or drop before the kernel writes into it), so I want to call out that it's handled carefully here.

Now the concerns, roughly in order of how much I'd want addressed before merge:

The PR doesn't check the kernel version or probe for the specific opcodes it uses (it submits `IORING_OP_RECV`/`IORING_OP_SEND` directly) before falling back. On kernels older than roughly 5.6 for the ring itself, and later for some of the specific opcodes and flags used here, this will either fail to initialize the ring or silently misbehave. I'd want a capability probe at startup — `io_uring_setup` with a `probe` call, or a documented minimum kernel version enforced at init with a clear error — rather than discovering this in production on an older kernel where the failure mode might not be an obvious error.

Second, error handling on the submission side is inconsistent: `submit_read` propagates `io_uring::squeue::PushError` when the SQ is full, but `submit_write` on the same condition just calls `.unwrap()`. Under real backpressure (SQ full because the kernel hasn't drained completions fast enough) that unwrap will panic the whole reactor thread. Given the read path already does this correctly, this looks like an oversight rather than an intentional difference — please align them, propagating the error and letting the caller retry or apply backpressure the same way both paths do.

Third, there's no test exercising SQ-full backpressure or CQE overflow (the ring's completion queue itself has a bound, and the kernel sets a flag when entries are dropped due to overflow — I don't see that flag being checked anywhere in the completion loop). Given how central these two failure modes are to `io_uring` correctness under load, and how easy they are to never hit in a light dev-machine test but common in production, I'd want at least one test that artificially shrinks the ring size to force both conditions.

Smaller things: the new `uring` feature isn't documented in the crate-level docs or the README's feature table, and `Cargo.toml` pins `io-uring = "0.6"` without an upper bound, which given how actively that crate's API has moved between minor versions historically feels like it'll break someone's build eventually — I'd pin more precisely or at least note the intended MSRV-compatible range in a comment.

I think the core is close, and I don't want to hold this hostage to a full production-hardening pass in one PR — but the unwrap-on-backpressure in `submit_write` is a crash bug waiting to happen under exactly the load conditions this feature exists to handle well, so that one I'd treat as a blocker. Kernel probing and the CQE-overflow test I'd want before we flip this on by default for anyone, but I'm fine with them landing as fast-follow PRs if you'd rather keep this one focused. Nice work overall on a genuinely hard piece of systems code.
