This PR adds the `modules/gke-cluster` Terraform module provisioning a regional GKE cluster with two node pools (a general-purpose pool and a spot-instance pool for batch workloads), plus Workload Identity binding for the cluster's service accounts. This is a substantial module and mostly well thought out, but there are a handful of issues I'd want resolved before this becomes the template other environments build from.

Starting with what's good: provisioning a regional cluster (`location = var.region` rather than a single zone) is the right default for anything meant to survive a zonal outage, and separating node pools by workload type — with the spot pool tainted (`taint { key = "cloud.google.com/gke-spot", value = "true", effect = "NO_SCHEDULE" }`) so only workloads with a matching toleration land there — is exactly the pattern you want for cost control without accidentally scheduling stateful or latency-sensitive work onto preemptible nodes. Workload Identity is correctly wired via `workload_identity_config` on the cluster and the `iam.workloadIdentityUser` binding on each GCP service account referenced by the module's `var.workload_identity_bindings` map, which is the right way to hand GCP permissions to specific Kubernetes service accounts without static key files.

Now the issues.

The `google_container_cluster.this` resource has `remove_default_node_pool = true` and `initial_node_count = 1`, which is the well-known pattern for avoiding GKE's mandatory default node pool — good — but the cluster resource itself doesn't set `deletion_protection`, which as of recent provider versions defaults to `true` for the `google_container_cluster` resource specifically, meaning a `terraform destroy` against this cluster would fail until that's explicitly disabled first. That's arguably a feature, but if it's not intentional here, worth an explicit `deletion_protection = var.enable_deletion_protection` variable so environments can opt in or out deliberately rather than discovering the behavior by surprise during a teardown.

Networking: I don't see `private_cluster_config` set at all, which means by default this provisions a cluster with publicly routable node IPs and a public control plane endpoint. Given the module is going to back a production environment (per the PR description, this replaces a manually-clicked-together cluster), I'd expect at minimum `enable_private_nodes = true`, and ideally `enable_private_endpoint` scoped with `master_authorized_networks_config` restricting control-plane API access to your VPN/bastion CIDR rather than the whole internet. As written, the GKE control plane API is reachable from anywhere with valid credentials, which is a meaningfully larger attack surface than it needs to be.

The spot node pool's `autoscaling` block has `min_node_count = 0` and `max_node_count = 20`, which is fine, but the general-purpose pool's autoscaling has `min_node_count = 3` with no explanation of why 3 specifically — if that's meant to guarantee quorum for some in-cluster stateful component (etcd-backed operator, say), a comment would help; if it's arbitrary, it's worth revisiting since 3 nodes minimum is a real cost floor that should be a deliberate choice, not a copy-pasted default.

`node_config.oauth_scopes` on both pools is set to `["https://www.googleapis.com/auth/cloud-platform"]` — the broadest possible scope, giving every node (and by extension anything running on it with node-level credential access, absent Workload Identity enforcement) full API access to the project. Given you've already gone to the trouble of setting up Workload Identity correctly, the node-level OAuth scope should be minimized rather than left maximal — the whole point of Workload Identity is that workloads shouldn't need to fall back to node credentials at all, so leaving the broad scope in place undermines part of what Workload Identity is meant to prevent (a workload that somehow reaches the node metadata server directly still gets full project access). I'd narrow this to the minimum GKE requires (logging, monitoring, and storage read-only for pulling images) unless there's a specific reason a broader scope is needed.

Smaller items: no `maintenance_policy` block, meaning GKE will pick its own maintenance window — worth setting explicitly so cluster upgrades don't land during your peak traffic hours. And `release_channel` isn't set, which means the cluster follows whatever GCP's default is rather than an explicit choice between `RAPID`/`REGULAR`/`STABLE` — for a production module I'd want that pinned explicitly and documented, since it directly affects how aggressively Kubernetes minor versions get auto-upgraded under you.

One more structural note: the module's `outputs.tf` exposes the cluster's `endpoint` and `ca_certificate` as regular (non-sensitive) outputs. The CA certificate isn't secret, but I'd still mark it `sensitive = true` defensively along with anything that could be used in combination with other leaked values to reconstruct connection details — cheap to do, no downside.

To sum up: the workload identity setup, regional cluster choice, and tainted spot pool are all well done and show real GKE experience. But the private cluster networking gap and the maximal node OAuth scope are both things I'd want fixed before this becomes the module every environment inherits from — they're the kind of defaults that are easy to carry forward unnoticed once a few environments are already built on top of this module. Requesting changes on those two; happy to re-review quickly once addressed since everything else here is solid.
