This PR adds a `deploy` stage to `.gitlab-ci.yml` that runs `kubectl apply -k overlays/production` against the cluster after the existing `build`/`test` stages pass, using a `kustomize` overlay structure introduced alongside it under `k8s/overlays/`. The kustomize base/overlay split itself is reasonable — `k8s/base` holding the common Deployment/Service/ConfigMap and `overlays/staging` / `overlays/production` patching replica counts and resource limits is a clean way to avoid duplicating full manifests per environment.

A few things need attention before this goes live against production, though:

The deploy job has no `environment:` block defined. GitLab's environment tracking is what gives you the deployment history, the ability to see what's currently deployed where, and — more importantly for this specific pipeline — the ability to gate production deploys behind a manual approval or a protected environment rule. Right now, per the `rules:` block, this job runs automatically on every push to `main` with no manual gate. For a production deploy, I'd expect at minimum `when: manual` or a protected environment requiring an approving reviewer, not an automatic apply on merge. As written, merging any PR to `main` immediately applies to production with no human checkpoint between merge and live traffic.

The job authenticates to the cluster using `KUBE_CONFIG` decoded from a base64 CI/CD variable and written to a temp file via `echo $KUBE_CONFIG | base64 -d > kubeconfig`. That's a workable pattern, but the temp file isn't being cleaned up in an `after_script`, so if the runner reuses the same workspace across jobs (depends on your runner's executor and whether it's ephemeral per job), that decoded kubeconfig could linger on disk longer than intended. Also worth checking: is `$KUBE_CONFIG` masked and protected in the GitLab CI/CD variable settings? If it's not marked "protected," it'd be exposed to jobs running on non-protected branches too, which given this variable grants cluster access is a bigger deal than a typical leaked variable.

`kubectl apply -k` with no `--dry-run` verification step beforehand and no diff review means the first time anyone sees what's actually about to change in the cluster is after it's already applied. Consider adding a `kubectl diff -k overlays/production` step (or `kustomize build | kubectl diff -f -`) as a separate job that runs on the merge request itself, before merge, so reviewers can see the actual resource diff rather than just the YAML diff in the MR — those aren't always the same thing once kustomize patches are involved.

No rollback mechanism referenced anywhere in this pipeline — worth at least documenting (even if it's a manual `kubectl rollout undo` runbook for now) what happens if this deploy job succeeds but the new version is broken.

I'd request changes here, mainly on the missing manual gate / protected environment for the production job — that's the one I consider a real risk given the automatic trigger on merge to main. The kustomize structure and job organization otherwise look sound.
