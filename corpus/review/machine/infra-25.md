This PR adds a `HorizontalPodAutoscaler` for the `image-processor` Deployment, targeting 70% average CPU utilization with `minReplicas: 2` and `maxReplicas: 10`, and adjusts the Deployment's `resources.requests.cpu` from `100m` to `500m` to give the HPA a more realistic baseline to scale against.

The reasoning in the PR description for bumping the CPU request is good — HPA percentage-based scaling is only meaningful relative to the request value, and `100m` was apparently set arbitrarily low when the Deployment was first written, which would have made the HPA's 70% threshold trigger scale-out far too aggressively relative to actual load. Raising it to something that reflects real observed usage (the PR links a Grafana panel showing steady-state CPU around 350-400m under normal load) is exactly the right way to arrive at that number rather than guessing.

One thing worth checking: `behavior.scaleDown.stabilizationWindowSeconds` isn't set, so it falls back to the Kubernetes default of 300 seconds, which is probably fine, but given this is an image-processing workload that likely has bursty, uneven load (batch uploads rather than steady traffic), you might want a longer stabilization window to avoid scaling down right before the next burst arrives and then immediately scaling back up. Not a blocker, just worth confirming the default matches the actual traffic pattern rather than being left unexamined.

Also worth a quick look: `maxReplicas: 10` — is that backed by a check that the cluster/node pool has headroom for 10x this pod's resource footprint at once, and that whatever this service talks to downstream (a queue, another service, a database connection pool) can handle 10 concurrent instances without hitting a connection limit? Nothing in the PR suggests this was checked, and it's an easy thing to overlook until the first time the HPA actually scales all the way up.

Small nit: the HPA doesn't set memory-based scaling alongside CPU, which is fine if this workload is genuinely CPU-bound (plausible for image processing), just flagging in case it turns out this workload is actually more memory-constrained under real load.

Approving — the CPU request fix is well-justified with real data, and the HPA config itself is standard and correctly formed. The stabilization window and downstream capacity questions are worth a quick sanity check but don't need to hold up this PR.
