This PR reworks the thread pool in `src/threadpool.cpp`/`threadpool.h` from a single shared task queue guarded by one mutex to a work-stealing design — each worker thread owns a local deque, pushes new work to the front of its own deque, pops from its own front when idle, and steals from the back of another thread's deque when its own is empty. This is a substantial rewrite and a well-chosen one for the stated problem (contention on the single shared queue under many short-lived tasks submitted from multiple threads), and the overall architecture matches the standard work-stealing design closely enough that I don't have concerns about the high-level shape.

The local-deque push/pop-front-steal-from-back split is implemented correctly as far as I traced it, and importantly you're using a genuinely lock-protected deque per worker (a small spinlock around each `std::deque`) rather than attempting a fully lock-free Chase-Lev deque. I want to explicitly say I think that's the right call for this PR even though lock-free work-stealing deques exist and get cited in a lot of the literature on this — a correctly-locked simple deque with low contention (since each thread mostly touches its own) is much easier to verify correct than a lock-free Chase-Lev implementation, and the performance difference at this pool's expected task granularity is unlikely to matter. If profiling later shows the per-deque lock is actually hot, that's a good problem to have and a well-scoped follow-up, not something to solve preemptively here.

A few things I'd want addressed:

The victim-selection strategy for stealing is a fixed round-robin starting from `(my_index + 1) % num_workers`, always in the same order for every stealing attempt. Under sustained imbalance this means the same worker tends to get hit first by every other idle thread simultaneously, which can itself become a point of contention on that one worker's deque lock right when it's least helpful (it's already probably busy since it wasn't the one that ran dry). A randomized starting point per steal attempt, or at least a per-thread starting offset seeded independently, would spread stealing attempts more evenly. This isn't a correctness issue, just a fairness/contention one, and I'd want it addressed before this is under real load rather than treated as a later optimization, since it's a small change now versus a harder-to-diagnose "some workers seem to run hot" report later.

Second, task submission from outside the pool (i.e., an external thread calling `ThreadPool::submit`, not a worker thread submitting a task from within a running task) currently pushes onto worker 0's deque unconditionally rather than round-robining across workers or picking the least-loaded one. That reintroduces exactly the kind of imbalance work-stealing is meant to smooth out, just concentrated at the entry point instead of during steady-state execution — worker 0 becomes a hot spot for every externally-submitted task before stealing has a chance to redistribute it. Round-robining external submissions across workers (even naively, with an atomic counter mod worker count) would be a straightforward fix.

Third, shutdown: `~ThreadPool` sets a stop flag and joins all worker threads, but I don't see it verifying that all workers' deques are actually empty first, or documenting what happens to tasks still queued at shutdown time (dropped silently, run to completion, or something else). Given the previous single-queue implementation apparently drained the queue before stopping (based on the removed code in this diff), this looks like an unintentional behavior change rather than a deliberate one — worth confirming which behavior you want and making it explicit, since "tasks silently dropped at shutdown" versus "shutdown blocks until all queued work completes" are very different contracts for callers to design around.

This is a well-executed rewrite of a genuinely tricky piece of concurrent code, and I don't have soundness concerns about the locking itself. I'd want the shutdown-draining behavior clarified and fixed if it's a regression, and I'd like to see the external-submission hot-spot addressed before merge; the steal-order randomization I'd be fine taking as a fast follow if you'd rather keep this PR from growing further.
