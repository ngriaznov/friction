This PR rips out `clap` in favor of a hand-rolled argument parser in the new `src/cli/args.rs`, motivated per the description by wanting to shave startup time and binary size for a CLI tool that's invoked very frequently in scripts (the numbers cited are around 4ms of clap's derive-macro-generated parsing overhead and roughly 300KB of binary size, which — for a tool run thousands of times in CI pipelines, as this one apparently is — is a real and reasonable thing to want to cut). I want to take the motivation seriously rather than dismiss it, but I have real reservations about doing this by hand.

What's implemented covers the common cases: positional arguments, `--flag`/`-f` short and long forms, `--key=value` and `--key value` forms, and a `--help` generator that's built from struct field doc comments via a small proc macro you've also added. That's a meaningful amount of the surface area clap covers, and the tests do exercise a good spread of the parsing table.

What's missing that I'd want addressed or explicitly scoped out before this replaces clap everywhere: there's no handling for combined short flags (`-abc` as shorthand for `-a -b -c`), which several of this tool's existing subcommands' documented usage examples rely on — I checked the current `--help` output on `main` and at least `pack -xvf` is a documented invocation that this parser would not accept. That's a user-facing regression, not just missing polish. There's also no support for `--` to terminate flag parsing and treat everything after as positional, which matters for the subcommand that shells out to another program and forwards arguments (`run -- cargo build --release` currently works and needs to keep working). And error messages on invalid input are currently a bare `Err(ArgError::Unknown(String))` with no suggestion-based "did you mean" behavior, which clap's default error output includes and which show up in this tool's own existing tests as expected output — those tests are presumably currently failing or have been weakened, and I'd want to see which.

Beyond the missing features, my bigger-picture concern is maintenance cost: clap's parsing rules around interspersed positional/optional arguments, negative-number-looking positionals, and multi-value flags have a lot of accumulated edge-case handling from years of bug reports across a huge number of real-world CLIs. Reimplementing that surface area means this project now owns all of those edge cases going forward, tested only as well as our own test suite covers them, versus a shared dependency reviewed by many more eyes. If the 4ms/300KB is the real driver, it might be worth first checking whether `clap`'s `cargo` feature flags are fully disabled and whether the `derive` macro overhead specifically (versus builder-style clap, which is lighter) is actually necessary, since that alone sometimes closes most of the gap without dropping the dependency.

I don't think this should merge yet — the combined-short-flags and `--` terminator gaps are behavior regressions against currently-documented usage, not just missing nice-to-haves, and I'd want those closed or explicitly and visibly deprecated before this replaces clap as the tool's parser. If after that the size/speed win is still real and worth owning the maintenance burden, I'm not opposed to the direction in principle.
