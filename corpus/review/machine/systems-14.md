This PR replaces the raw `Connection*` ownership in `src/net/connection_pool.cpp` and `src/net/connection.h` with `std::unique_ptr<Connection>`, removing the manual `delete` calls scattered across the three call sites that previously closed connections. Good change, and the diff is pleasantly minimal for what it accomplishes — you didn't try to also refactor the pool's locking or API surface in the same PR, which keeps this reviewable.

I checked the three sites where `delete conn` used to appear (`ConnectionPool::evict`, `ConnectionPool::~ConnectionPool`, and the error path in `ConnectionPool::acquire` when the handshake fails) and all three are now correctly just letting the `unique_ptr` go out of scope or explicitly `.reset()`, with no remaining raw `delete` anywhere in the touched files. The move semantics in `ConnectionPool::release` — moving the `unique_ptr` back into the pool's free list rather than copying a raw pointer — are correct, and the fact that `Connection` itself is non-copyable was already enforced before this PR, so there's no risk of the old raw-pointer-copy bugs resurfacing through a back door.

One thing to double check rather than a request for changes: `Connection::~Connection` closes the underlying socket fd, and previously that only ran when something explicitly called `delete`. Now it runs implicitly whenever a `unique_ptr<Connection>` is destroyed, including if an exception unwinds through a function holding one on the stack. I don't see anything in this codebase that throws in the paths that touch connections, but worth a quick sweep — if any exception can propagate through code holding one of these by value or reference, the destructor ordering guarantees you get from `unique_ptr` are actually stronger/safer than what existed before, so this should only be a win, but it's the kind of behavior change worth confirming rather than assuming.

Very minor style note: a couple of the function signatures still take `Connection*` as a parameter (e.g. `bool is_healthy(Connection* conn)`) even though callers now always pass `.get()` on a `unique_ptr`. That's fine and idiomatic — non-owning raw pointer parameters are the correct way to pass a "borrowed" reference without transferring ownership — but a `Connection&` instead of `Connection*` there would make the "never null, never owning" contract explicit in the type rather than by convention, if you want to tighten it further. Not blocking.

This is exactly the kind of ownership cleanup that pays for itself the first time someone adds a new error path and doesn't have to remember to add a matching `delete`. Approving.
