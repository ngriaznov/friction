This PR adds an Istio `VirtualService` and `DestinationRule` pair for the `checkout` service to enable a canary rollout, splitting traffic 90/10 between the `stable` and `canary` subsets based on pod labels, plus a header-based override so internal QA traffic can force-route to the canary regardless of the weighted split. The overall approach is sound and the header-match rule (`match: - headers: x-canary-route: exact: "true"`) placed before the weighted-split route in the `http` list is correctly ordered, since Istio evaluates `http` route rules in order and the first match wins — if that block were after the weighted split it would never be reached.

A few things to look at before merging:

The `DestinationRule`'s subset selectors key off `version: stable` and `version: canary` pod labels, but I don't see this PR touching the Deployment manifests to confirm those labels actually exist on the corresponding pods yet. If the canary Deployment doesn't carry `version: canary` as a pod label, Istio's subset selector will match zero pods and any traffic routed to that subset will fail with a 503 (`no healthy upstream`) rather than falling back to `stable`. Worth confirming the Deployment PR (if it's separate) lands together with this, or that it's already merged — as written, merging this VirtualService ahead of the labeled Deployment would send 10% of checkout traffic into a black hole.

No `retries` or `timeout` policy set on the `HTTPRoute` block. Not necessarily wrong — maybe the defaults are intentional — but for a payment-adjacent service like checkout, I'd expect an explicit retry policy (with `retryOn` scoped to safe conditions like `connect-failure,refused-stream` rather than blanket retrying on `5xx`, which could double-charge a customer if the original request actually succeeded server-side but the response was lost) to be a deliberate decision made in this PR rather than left to whatever Istio's mesh-wide default happens to be.

The `DestinationRule`'s `trafficPolicy.outlierDetection` block isn't set at all. For a canary rollout specifically, this is worth having — if the canary subset starts erroring, outlier detection would eject unhealthy canary pods from the load-balancing pool automatically, which is a meaningful safety net on top of (or in place of, if you're watching metrics manually) a human noticing and rolling back. Given canary rollouts are exactly the scenario outlier detection exists for, I'd want this in before the first real canary run rather than added reactively after a bad canary causes visible customer impact.

One question rather than a blocking issue: is there a plan to automate the weight shift (10% → 50% → 100%) via Flagger or Argo Rollouts, or is this expected to be edited by hand for each stage of the rollout? If it's manual, a comment in the PR description or a runbook link would help whoever's on call during the rollout know what "advancing the canary" actually means operationally.

Good use of the header-based override for QA — that's a nice detail that a lot of first canary setups skip, and it'll make testing the canary path much easier without waiting on the traffic-split percentage to naturally route a QA request there.

Mixed verdict: I'd want the pod-label dependency confirmed and the outlier detection added before this goes live, but the routing logic itself is correct and well-organized. Requesting changes, mainly on those two points.
