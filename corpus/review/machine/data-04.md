The incremental logic itself is standard and fine — `{% if is_incremental() %} WHERE updated_at > (SELECT MAX(updated_at) FROM {{ this }}) {% endif %}` is the textbook pattern and there's nothing wrong with reaching for it here for the `fct_shipments` model.

My concern is specifically about late-arriving facts, which you mentioned in the PR description as a known open question, so I'll focus there. Filtering strictly on `updated_at > max(updated_at) from this` works cleanly when source rows are only ever inserted once and never touched again, but shipment records are exactly the kind of thing that gets corrected days later — a carrier updates a delivery timestamp, a warehouse fixes a quantity — and when that correction lands, its `updated_at` will indeed be newer than your watermark, so the row gets picked up. The problem is what happens next: are you using `unique_key` with an `incremental_strategy` of `merge` (or `delete+insert`), or just appending? If this is a plain append-only incremental model, a corrected row shows up as a second, contradictory record rather than replacing the original, and every downstream aggregate built on `fct_shipments` silently double-counts or diverges from source. Worth confirming `unique_key` is set to `shipment_id` and the strategy is explicitly `merge`, not left at the adapter default, since that default varies across warehouses.

I'd also suggest widening the incremental window with a small lookback buffer — something like `updated_at > (SELECT MAX(updated_at) FROM {{ this }}) - interval '3 days'` — as cheap insurance against clock skew or late-committing transactions in the source system landing just outside the exact watermark. Small change, meaningfully reduces silent data loss risk.
