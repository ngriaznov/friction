The `@Cacheable` addition on `ProductLookupService.getProduct(sku)` backed by Redis will solve the latency problem it's aimed at, but I don't think this can merge without addressing invalidation, because right now the cache and the database can silently disagree with no path back to consistency.

`updateProduct()` in the same service writes the change to Postgres but has no corresponding `@CacheEvict` or `@CachePut` on the `products` cache. Once a product is cached, any update to its price, name, or availability is invisible to callers hitting the cached path until the entry's TTL (300 seconds, per the `RedisCacheConfiguration`) expires on its own. For a product catalog where price accuracy matters — and I'd assume it does — a five-minute window of serving stale prices after every edit is a real problem, not a cosmetic one. Add `@CacheEvict(value = "products", key = "#product.sku")` on `updateProduct`, and the same for `deleteProduct`, which has the identical gap.

Second, `getProduct` caches on the `sku` alone via the default key generator, but the method signature takes `(String sku, String locale)` and returns locale-specific product copy. As written, the cache key only reflects `sku`, so the first locale to populate the cache for a given SKU determines what every subsequent request sees regardless of the `locale` argument — a request for the German product page could get served the English cached entry. This needs an explicit `key = "#sku + '-' + #locale"` (or a `@Cacheable(key=...)` SpEL expression referencing both params) rather than relying on the default key generator, which only appears to be keying on the first argument here based on how the cache hit is behaving in the linked bug report.

Smaller: no `sync = true` on the `@Cacheable` annotation. Under a cache-miss stampede (TTL expiry during a burst of concurrent requests for the same popular SKU), every one of those requests will independently hit the database rather than one request populating the cache while the others wait for it. For a service that's presumably adding this cache because the database path is expensive enough to want to avoid, `sync = true` is a small change that meaningfully reduces load during exactly the moments the cache is supposed to be protecting you.

I'd want the eviction gap and the locale key-collision fixed before merging — as it stands this could serve stale or wrong-locale prices to customers, which is a worse outcome than not caching at all.
