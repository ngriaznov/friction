This is a reasonable first pass, but I'd stop short of shipping it against a 200M-row table as written. The `ROW_NUMBER() OVER (PARTITION BY customer_id, order_date ORDER BY updated_at DESC)` approach is the right general idea for deduplicating `orders`, and wrapping it in a CTE before filtering `WHERE rn = 1` is clean and readable — no complaints on correctness there, assuming `updated_at` really is monotonic and never null. Worth double-checking that null `updated_at` rows don't silently sort last and win ties you didn't intend.

The performance concern is the partition key. `customer_id, order_date` is fine for correctness but if `order_date` has low enough cardinality per customer you're building large windows that Postgres has to sort in full before it can hand out row numbers, and on 200M rows that sort is going to spill to disk unless `work_mem` is generously bumped for this session. I'd want to see the query plan before merging — specifically whether it's doing a `WindowAgg` over a full sort versus using an index that already gives you the ordering. An index on `(customer_id, order_date, updated_at DESC)` would let Postgres avoid the explicit sort entirely.

Also consider whether you actually need every column carried through the CTE — projecting only the primary key plus `rn` before joining back to the base table for a final select is usually cheaper than dragging every column through the window computation. Minor naming nit: `rn` is fine in a CTE this small, but `dedup_rank` reads better to the next person who inherits this.

Net: logic is sound, but get an `EXPLAIN ANALYZE` on real data before calling it done.
