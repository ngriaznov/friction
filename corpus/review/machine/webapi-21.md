This PR standardizes error responses across the FastAPI app to follow RFC 7807 (`application/problem+json`), adding a global exception handler in `app/errors.py`, a `ProblemDetail` Pydantic model, and converting roughly twenty scattered `raise HTTPException(status_code=..., detail="...")` call sites to raise typed domain exceptions (`NotFoundError`, `ValidationError`, `ConflictError`, etc.) that the new handler translates into the standard shape. Sizable PR, touches most of the route modules plus the new error module, so I went through it in full rather than spot-checking.

This is a good change to make and the direction is right — a consistent, machine-parseable error shape across the API is worth the churn, and RFC 7807's `type`/`title`/`status`/`detail`/`instance` fields are a sensible standard to converge on rather than inventing a custom shape. I like that the domain exceptions carry a `type_uri` class attribute so the mapping from exception class to `problem+json` `type` field is declared once at the exception definition rather than scattered across handler logic.

A few things worth addressing before merge, and one design question I'd want answered rather than just noted.

The design question first: the global handler in `errors.py` catches `Exception` as a final fallback and returns a generic 500 `ProblemDetail` — good, that's the right safety net — but I noticed it includes `str(exc)` in the `detail` field for unhandled exceptions, which means any uncaught internal error (a `KeyError`, a database driver exception, whatever) has its Python exception message surfaced directly to API clients. That's a real information disclosure risk — stack details, internal identifiers, sometimes even fragments of SQL, ending up in a public API response. For the generic fallback specifically, `detail` should be a static, non-specific message, with the actual exception logged server-side (ideally with a correlation/request ID that's also included in the client-facing response so support can find the matching log entry). The typed domain exceptions with intentional, reviewed messages are a different story and are fine to pass through as-is.

Second, backward compatibility: existing clients of this API presumably parse the current error shape (looks like `{"detail": "..."}` from FastAPI's default, based on what's being replaced). This PR changes the response body shape and, from what I can see, the `Content-Type` header too (`application/problem+json` instead of `application/json`), with no versioning or transition period — is there an API version boundary this rides along with, or does this ship to all clients immediately on deploy? If there are external consumers, a strict `Content-Type` change in particular can break clients that check it rather than just parsing the body permissively. Worth confirming this is understood and intentional, not just an oversight of scope.

Third, a few of the converted call sites lost information in translation. `orders.py`'s old `HTTPException(404, detail=f"Order {order_id} not found")` became `raise NotFoundError()` with no context, and the handler's generic mapping for `NotFoundError` produces a `detail` string that doesn't mention which resource or ID was missing. That's a regression in error usefulness for API consumers debugging their own integration — the new exceptions should generally accept a context message or structured extension members (RFC 7807 explicitly allows extension members beyond the five standard fields) so callers can still get "order abc123 not found" rather than a generic "not found."

Smaller items: the new `ProblemDetail` model doesn't set `instance` (meant to be a URI identifying this specific occurrence) anywhere — either populate it with the request path plus a request ID, or drop the field rather than leaving it always null, since a field that's always absent invites consumers to write code against a shape you're not actually providing. And a few of the ~20 converted sites (I counted three in `webhooks.py`) still raise `HTTPException` directly rather than the new domain exceptions — either intentional exclusions worth a comment, or leftover from an incomplete pass.

Good initiative and the core design is right; I'd want the information-disclosure issue in the generic handler fixed before merge, the compatibility question answered explicitly, and the lost-context regressions in the converted call sites addressed, ideally as part of this PR rather than a follow-up given how easy it is to lose track of which sites still need the context added back.
