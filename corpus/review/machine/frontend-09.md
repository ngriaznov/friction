The core issue you're describing — the whole app re-rendering on every keystroke in a settings panel — is almost certainly caused by how this `AppStateContext` is structured, and the fix here is a common one for Context API misuse rather than anything exotic.

You've put essentially the entire application state into a single `AppStateContext.Provider value={state}`, where `state` is one big object containing user session data, UI preferences, notification counts, and the current form draft someone's typing into. Every consumer that calls `useContext(AppStateContext)` re-renders whenever any part of that object changes, because React's context propagation doesn't do partial subscriptions — a consumer either re-renders on any change to the provided value or it doesn't subscribe at all. So a keystroke updating `state.settingsDraft.displayName` re-renders every component anywhere in the tree that reads from this context, including a sidebar nav that has nothing to do with settings.

The fix is to split this into multiple, narrower contexts along lines of "what changes together." Session/user data that's essentially static after login is a good fit for one context. UI preferences that change occasionally (theme, sidebar-collapsed) can be another. But form draft state that changes on every keystroke almost certainly shouldn't live in Context at all — that's exactly the kind of high-frequency, narrowly-scoped state that belongs in local component state (or a form library like `react-hook-form`, which is designed specifically to avoid the free re-render problem via uncontrolled inputs and refs) rather than broadcast through a context that other unrelated parts of the tree are subscribed to.

If splitting contexts isn't feasible in one pass, an interim mitigation is wrapping expensive consumers in `React.memo` and making sure the values/callbacks you pass down are stable (`useMemo`/`useCallback`), but that only helps components that receive props derived from context, not components calling `useContext` directly — those re-render regardless of memoization, because `memo` doesn't prevent a context consumer's own re-render, only re-renders triggered by parent prop changes. This is a common point of confusion, and it looks like the codebase is already tripping over it: I see `React.memo` wrapped around `<SettingsPanel>` in this diff, but `SettingsPanel` itself calls `useContext(AppStateContext)` internally, so the memoization does nothing for it.

For anything beyond occasional, coarse-grained global state, I'd also seriously consider whether this whole area is better served by a proper state manager (Zustand, Jotai, Redux with reselect) that supports selector-based subscriptions, since that solves this exact class of problem structurally rather than requiring you to manually partition contexts and remember the memoization caveats every time new state gets added. That's a bigger conversation than this PR, but worth raising given how much of this codebase seems to route through a single context already.

Short-term, I'd request splitting the settings draft out of `AppStateContext` before merging, since that's the piece actively causing the reported performance problem; the broader context/state-manager conversation can be a follow-up.
