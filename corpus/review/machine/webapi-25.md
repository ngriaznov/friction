This PR adds a circuit breaker around calls to a downstream pricing service from the Go order-service, using `sony/gobreaker`, wrapping the existing `pricingClient.GetPrice` calls in `internal/pricing/client.go` with a breaker configured with a failure-ratio threshold, a 30-second open-state timeout, and a fallback that returns a cached last-known price when the breaker is open. Also adds Prometheus metrics for breaker state transitions.

This is a substantial and welcome addition given that (per the PR description) the pricing service has caused two cascading incidents in the past quarter, and circuit breaking around it is exactly the right response. I want to go through the configuration and fallback behavior carefully though, since a circuit breaker that's misconfigured can be worse than no circuit breaker at all — it can mask a real outage as degraded-but-functioning when it should be surfacing loudly, or it can trip on noise and take a healthy dependency out of rotation unnecessarily.

First, the fallback: when the breaker is open, `GetPrice` returns a cached price read from a local in-memory map that's populated opportunistically on successful calls, with no TTL or staleness indicator surfaced to the caller. For a pricing service specifically, serving a stale price during checkout is a business-correctness issue, not just a degraded-UX one — a customer could be charged a price that's meaningfully out of date if the outage is long enough. I'd want to see either a maximum staleness the cached fallback is allowed to serve before it instead fails the request outright (falling back to "we can't process this order right now" rather than a wrong price), or, if serving a stale price is genuinely acceptable business-wise up to some bound, that bound should be an explicit configured value rather than "however old happens to be in the map," and the response should carry a flag so calling code (and ultimately the checkout flow) can decide whether to proceed or ask the customer to retry.

Second, the breaker's `ReadyToTrip` function trips based on a failure ratio over a rolling window (looks like `gobreaker`'s default `Settings.ReadyToTrip`, which trips at a 60% failure ratio with a minimum of 5 requests), but this order service's request volume to pricing varies enormously by time of day — the PR doesn't adjust the minimum-requests threshold or window size to account for that. During low-traffic periods, 5 requests is a small enough sample that a handful of transient blips (a couple of slow responses crossing your timeout) could trip the breaker over genuinely healthy service, causing customers to see stale pricing unnecessarily. I'd want to see this tuned against actual traffic patterns rather than left at the library default, and ideally validated against a staging load test or the historical incident data mentioned in the PR description, since you presumably know what failure pattern preceded the two prior incidents and can check whether this configuration would have actually caught them without over-tripping on normal noise.

Third, half-open state behavior: `gobreaker`'s default allows a single trial request through in half-open state before deciding whether to close or re-open. That's reasonable, but I don't see any jitter or staggering if this order-service runs multiple replicas — if pricing recovers and all replicas' breakers happen to be in a similar timing phase (plausible if they all tripped around the same incident), you could get a thundering-herd of simultaneous half-open trial requests hitting the just-recovered service at once, which is a milder version of the exact problem this PR is trying to prevent. Given the 30-second fixed open-state timeout is identical across replicas with no jitter, I'd add a small random jitter to the open-state duration per replica.

The Prometheus metrics addition is good and exactly what I'd want to see alongside a circuit breaker — being able to see state transitions on a dashboard during an actual incident is valuable and it's easy to forget to add when focused on the breaker logic itself. One addition: consider also emitting a metric or log line specifically when the fallback path serves a cached price, separate from the breaker-state metric, since "how many customers saw a stale price during this incident" is a different and important question from "was the breaker open."

Overall this is the right feature and mostly well-built, but given that a pricing correctness issue during an outage could be worse for the business than the outage itself, I'd request changes on the staleness bound before merging, and would strongly encourage tuning the trip threshold against real traffic data rather than shipping with library defaults given how much this specific dependency has already cost in incidents.
