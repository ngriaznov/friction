Migrating this product page from `getServerSideProps` to the App Router is the right call given you mentioned wanting streaming and partial prerendering down the line, and the overall structure of the new `page.tsx` is close to correct, but there are a few App Router-specific traps here worth fixing.

First, `page.tsx` is marked with `'use client'` at the top, but the only reason given is that you're using `useState` for a quantity selector further down in the tree. Don't make the whole page a client component for that — keep `page.tsx` as a server component (drop the directive), do the data fetching there with a plain `async function`, and extract just the quantity selector into its own small client component that receives the fetched product data as props. As written, you've opted the entire page — including the parts that don't need interactivity, like the product description and reviews list — out of server rendering, which defeats a good chunk of the reason to migrate off `getServerSideProps` in the first place.

Second, the data fetching itself uses `fetch(url, { cache: 'no-store' })` unconditionally, which is the direct equivalent of the old SSR-per-request behavior, and that's a legitimate choice if this data genuinely needs to be fresh on every request. But if product data doesn't change every second, consider `next: { revalidate: 60 }` (or whatever interval makes sense) instead, so you get ISR-style caching rather than paying full SSR cost on every hit. Worth a deliberate decision rather than defaulting to `no-store` out of caution.

Third, error handling: the old `getServerSideProps` had a `try/catch` that redirected to a 404 page on a missing product. In the App Router version, that logic is gone — a missing product just results in the fetch returning a 404 status that isn't checked, so the page will try to render with `undefined` data and presumably throw somewhere downstream. Use `notFound()` from `next/navigation` when the fetch indicates the product doesn't exist; that's the idiomatic replacement and it'll render your `not-found.tsx` boundary correctly, including the right HTTP status code.

Fourth, you dropped the `getServerSideProps`-era `res.setHeader('Cache-Control', ...)` call with nothing corresponding to it. If that header mattered for a CDN in front of this, you need the App Router equivalent, which is generally handled through the `revalidate` export or `fetch` cache options rather than manual headers — but confirm that's actually equivalent to what you had before, since the semantics aren't identical.

Smaller note: `generateMetadata` is missing entirely, and the `<title>`/`<meta>` tags that used to be set via `next/head` in the old pages-router version have no replacement here. That's not a bug that breaks the build, but it is a regression — the page will lose its per-product title and description in search results and social previews until `generateMetadata` is added.

The bones of the migration are right, and I don't think any of this requires rethinking the approach, just tightening up the client/server boundary and restoring the error and metadata handling that got dropped in translation.
