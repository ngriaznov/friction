Reviewed the error boundary plus Sentry wiring across the app shell. This is a well-scoped addition and mostly ready to merge — a few things to tighten up first.

The top-level `AppErrorBoundary` class component correctly implements `getDerivedStateFromError` and `componentDidCatch`, and the fallback UI it renders is reasonable (a friendly message plus a reload button, rather than a raw stack trace shown to end users). Good instinct wrapping it around the router outlet rather than around individual pages, since a boundary that's too granular tends to produce a confusing experience where one broken widget takes down its section but the rest of the chrome around it looks fine and inconsistent.

One gap: there's only one error boundary in the whole app, at the very top. If a non-critical widget somewhere deep in a page throws — say, a sidebar recommendation carousel — the entire page unmounts and the user sees the generic fallback instead of just losing that one widget. Given this app has several genuinely optional, non-critical UI regions (the recommendations carousel, the "recently viewed" strip), I'd add narrower boundaries around those specifically, so a failure there degrades gracefully instead of nuking the whole page. Not necessary for boundaries around every component — that's overkill — but a second tier around known-risky, non-essential widgets is worth it.

On the Sentry integration itself: `Sentry.init()` is called in `_app.tsx` with `tracesSampleRate: 1.0`. That's fine for initial rollout to catch issues, but 100% trace sampling in production will generate a lot of volume and cost once traffic is real; I'd want to see this either environment-gated (lower in production, full in staging) or explicitly called out as an intentional temporary setting with a follow-up ticket to tune it down after you've had a chance to look at real data.

`componentDidCatch` calls `Sentry.captureException(error, { extra: errorInfo })` — correct, and good that `errorInfo.componentStack` is included, since that's often the difference between a debuggable and undebuggable error report. I'd also suggest tagging these captures with something like `{ tags: { boundary: 'app-root' } }` once you add the narrower boundaries mentioned above, so Sentry issues are attributable to which boundary caught them rather than all bucketing under one generic signature.

One thing I didn't see: no test for the error boundary itself. A simple test that renders a component known to throw inside the boundary and asserts the fallback UI renders (rather than the app crashing or the test failing due to an uncaught error) would catch regressions here cheaply, and error boundaries are exactly the kind of code that silently stops working if someone refactors `componentDidCatch` incorrectly later, since the failure mode looks correct until an error actually happens in production.

Nothing here blocks merging in my view except I'd like the sampling rate question answered explicitly rather than left as a default — either confirm it's intentional for now with a tracked follow-up, or dial it down before this goes to production traffic.
