The poster shared a Go HTTP handler, written against the standard library plus `gorilla/mux`, that receives Stripe webhook events, and asked why they were occasionally processing duplicate events or missing the signature check under load. This deserves a fairly thorough answer since there are several compounding issues.

First, and most seriously: the signature verification is happening after the JSON body has already been decoded with `json.NewDecoder(r.Body).Decode(&event)`, and the raw bytes used for the HMAC comparison are reconstructed by re-marshaling the decoded struct with `json.Marshal(event)` rather than using the original request bytes. This is wrong in a way that matters for security, not just style: Stripe signs the exact bytes it sent over the wire, and Go's JSON marshaling is not guaranteed to round-trip byte-for-byte (field ordering, whitespace, and how you handle unknown fields all differ). In practice this means legitimate webhooks can fail verification unpredictably, and more importantly, an attacker who understands your re-marshal behavior might be able to craft a payload whose re-encoded form matches a stolen or brute-forced signature more easily than the original. You should read the full body with `io.ReadAll(r.Body)` first, run `webhook.ConstructEvent(payload, sigHeader, endpointSecret)` from Stripe's own Go SDK against those exact bytes, and only decode into your event struct afterward. Don't hand-roll the HMAC comparison either — the SDK's `ConstructEvent` already does a constant-time compare, and hand-rolled `==` string comparisons on MACs are vulnerable to timing attacks even though the practical exploitability against a webhook endpoint is debatable.

Second, on duplicates: Stripe explicitly documents that webhooks are delivered at-least-once and that consumers must be idempotent. Your handler processes `event.Type == "payment_intent.succeeded"` by directly calling `fulfillOrder(event.Data.Object)` with no dedupe check. You need to persist `event.ID` (Stripe's idempotency key for the event itself) somewhere durable — a unique constraint on an `processed_events` table works well — and check-and-insert that ID before doing any side-effecting work, ideally inside the same transaction as the fulfillment write so a crash between "recorded" and "fulfilled" can't silently drop the order. Right now, any retry from Stripe (which happens routinely on 5xx or timeout) will double-fulfill.

Third, smaller but worth fixing: you return `http.StatusOK` before the fulfillment logic finishes, using a goroutine to do the work "for speed." That inverts the reliability guarantee Stripe's retry mechanism gives you — if `fulfillOrder` fails, Stripe will never know because you already returned 200, so you lose the automatic retry entirely and now depend on your own goroutine's error handling being perfect, which it isn't (the error is just logged with `log.Println`). Do the work synchronously within the timeout budget (Stripe waits several seconds) and return a 5xx if it fails so Stripe retries; only offload to a queue if fulfillment is genuinely slow, and if you do that, make the enqueue step itself idempotent and durable (write to the DB in the same transaction as the dedupe insert, then have a separate worker consume it) rather than firing an unsupervised goroutine per request.

Smaller notes: the handler doesn't check `r.Method != http.MethodPost` explicitly (mux routing probably covers this, but worth confirming), and there's no size limit on the body read, so a malformed or malicious request with an enormous payload will be fully buffered into memory — wrap the reader in `http.MaxBytesReader` before reading.

I'd block this from shipping as-is because of the signature verification bug and the missing idempotency; the async-fulfillment issue is a close second.
