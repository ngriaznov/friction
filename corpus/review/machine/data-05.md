There's a data leakage bug here that needs to be fixed before this model is trustworthy, so I can't sign off as-is even though the surrounding pipeline structure is otherwise nicely organized.

The problem is in how `category_mean_encode` is being applied. You compute `df.groupby('merchant_category')['is_fraud'].mean()` and map it back onto the full dataframe before calling `train_test_split`. That mean is computed using every row in the dataset, including the ones that end up in your test split. So each test row's `category_mean_encoded` feature is partially derived from its own label (and its neighbors' labels), which means the test set is no longer a clean holdout — you're leaking target information across the split boundary. In practice this tends to show up as suspiciously strong test AUC that doesn't hold up in production, and it's one of the more common ways fraud models look great in evaluation and then underperform once deployed against genuinely unseen data.

The fix is to compute the encoding only on the training fold, then apply that mapping to the validation/test folds, falling back to a global prior (e.g. overall fraud rate) for categories that didn't appear in training. If you're using scikit-learn, `category_encoders.TargetEncoder` (or the newer `sklearn.preprocessing.TargetEncoder` if you're on a recent version) handles this correctly out of the box with proper cross-fitting, and swapping to it would also resolve the leakage without you having to hand-roll the fold-aware logic yourself. If you do want to keep the manual implementation, move the `groupby().mean()` computation to after the split and fit it only on `X_train`.

Two smaller notes while I'm in here: `train_test_split` isn't stratified on `is_fraud`, and given fraud is presumably a small minority class, an unstratified split risks meaningfully different fraud rates between train and test purely from sampling variance — add `stratify=y`. Also the pipeline drops rows with any null via `df.dropna()` before feature engineering, which for a fraud dataset could be silently removing a disproportionate share of the positive class if missingness correlates with fraud (it often does, since fraudulent transactions frequently have incomplete profile data) — worth checking the drop rate by class before accepting that as safe.

Once the leakage is addressed I'm happy with the rest: the pipeline structure using `ColumnTransformer` is clean, and the choice of `LightGBM` with early stopping on a proper validation set is reasonable for this problem.
