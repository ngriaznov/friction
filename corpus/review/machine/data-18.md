Went through the new `fraud_features` module carefully since this feeds a live scoring path, and while the feature ideas themselves are good — velocity counts over multiple windows, device-fingerprint reuse rate, distance-from-last-transaction — there are a few issues around training/serving consistency that I think are serious enough to hold this PR on.

The core problem is that `compute_velocity_features()` in `features/velocity.py` is written against a full historical DataFrame — it does a `groupby("account_id")` over the entire batch and computes rolling counts using `.rolling("24h")` on a sorted-by-time index. That's correct and reasonably efficient for the offline training path where you have the full history available. But the PR also wires this same function into the real-time scoring path in `scoring/pipeline.py`, where at inference time you only have the single incoming transaction plus whatever's fetched from the feature store, not a full historical batch to run a `groupby` over. Right now, calling this function at serving time with a single-row frame will produce degenerate rolling windows — every count comes back as zero or one, regardless of the account's actual recent activity — because there's no history in scope for the rolling computation to operate over. That's a silent training/serving skew: the model will have learned that velocity features carry real signal, and at serving time those features will be uninformative, which likely shows up as depressed real-time fraud catch rates without any errors being raised.

The fix isn't just to duplicate the logic for the streaming case — that reintroduces the risk of the two implementations drifting apart, which is the same class of bug in a different shape. Since you already have a feature store dependency listed (I see the `feast` import in `scoring/pipeline.py`), the velocity aggregates should be computed once, incrementally, as transactions land, and materialized into the feature store so both training (via point-in-time correct historical retrieval) and serving (via online lookup) pull from the same underlying computation. That's a bigger change than this PR currently attempts, so at minimum I'd want an explicit test that exercises the scoring path end-to-end with a cold single-transaction input and asserts the velocity features come back non-degenerate, so this gap is at least visible and documented rather than silent.

Separately, `device_fingerprint_reuse_rate` divides `distinct_accounts_per_device` by `total_transactions_per_device` with no guard against the denominator being zero for a first-seen device — I'd expect that to throw or produce NaN/inf on a brand-new device, which given fraud rings frequently use fresh devices is exactly the input distribution where you most need this feature to behave predictably rather than error out or return garbage.

Smaller items: the module has no unit tests at all despite being feature logic that directly drives a fraud model's inputs — even basic tests asserting known inputs produce expected feature values would catch regressions in future edits. Also, several functions accept a bare `pd.DataFrame` with no schema validation on the columns they expect, so a silent upstream rename would fail deep inside a rolling computation with an unhelpful KeyError rather than a clear "expected column X" message at the function boundary.

I want to be clear the modeling instinct behind these features is good and the offline computation logic in isolation looks correct where I traced it. But the training/serving skew risk here is the kind of bug that's expensive to discover after the fact — it degrades model performance without throwing any errors — so I'd like to see either the feature-store-backed approach or at minimum the cold-start test and a documented limitation before this merges.
