This was a fairly large chunk of a Go GraphQL server built with gqlgen, specifically the resolver for a `createInvoice` mutation plus the generated server's panic-recovery setup, and the author's question was "we're getting 200 OK responses with null data and no error message when something goes wrong internally, and I can't figure out why the client sees nothing useful." Given how much is going on here, I'll go through it in the order I'd actually debug it.

The core issue is in how errors are being produced inside the resolver. In several places, instead of returning `nil, gqlerror.Errorf(...)` or wrapping with `graphql.AddError(ctx, ...)`, the code does things like `log.Println(err); return nil, nil` — swallowing the error and returning a nil result with a nil error. gqlgen (like any GraphQL server) treats a nil error as success, so the response comes back as valid GraphQL with `data: { createInvoice: null }` and no `errors` array at all, which from the client's perspective is indistinguishable from "the mutation legitimately returned null." That's exactly the symptom you're describing. Every early-return-on-failure path in this resolver needs to actually propagate the error, not just log it: `return nil, fmt.Errorf("creating invoice: %w", err)` at minimum, or better, use `gqlerror.Errorf` with an extension code (e.g. `INVALID_INPUT`, `NOT_FOUND`) so the client can branch on error type rather than parsing message strings.

Second, the panic recovery. You've set a custom `RecoverFunc` on the gqlgen server that does `return fmt.Errorf("internal error")` for any recovered panic, which is reasonable as a last line of defense, but I noticed at least one spot in the resolver — the type assertion `input.Amount.(int64)` on a value that comes from a `map[string]interface{}` — that will panic on any non-integer numeric input (JSON numbers over the wire can decode as `float64` depending on your scalar handling) rather than returning a typed error. Relying on the global recover for something this predictable means every one of those hits becomes an opaque "internal error" with a 500-style GraphQL error and no logged stack trace tied to a request ID, which makes production debugging much harder than it needs to be. I'd handle the type assertion explicitly with the comma-ok form and return a proper validation error, and reserve the panic recovery for genuinely unexpected failures.

Third, a correctness issue independent of error handling: `createInvoice` does a `SELECT` to check the customer exists, then does the `INSERT` for the invoice as a separate statement, with no transaction wrapping the two. If the customer is deleted between the check and the insert (unlikely but possible with concurrent admin actions), or if the insert itself partially succeeds across multiple tables (invoice header plus line items, both shown here as separate `Exec` calls), you can end up with orphaned or partial data. Wrap the check-and-insert-and-line-items sequence in a `sql.Tx`, and make sure you're checking the error from `tx.Commit()` too, not just the individual `Exec` calls — a commit can fail even when every statement inside it succeeded.

Smaller things: the mutation resolver takes `ctx context.Context` but never uses it to derive a request-scoped logger or propagate cancellation into the DB calls — worth threading it through to the `sqlx` calls as `ExecContext`/`QueryContext` so a client disconnect or deadline actually cancels the in-flight query instead of letting it run to completion uselessly. And `gqlerror.Errorf` messages currently include the raw underlying DB error text in a couple of places, which risks leaking schema details (table/column names) to API consumers — those should go to server-side logs with the request ID, and the client-facing message should be generic.

This needs another pass before merging — the swallowed errors are actively hiding failures from clients right now, which is the most important thing to fix, but the missing transaction is the one most likely to cause real data problems later.
