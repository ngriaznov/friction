Went through the new Structured Streaming job for inventory updates. The overall shape — reading from the `inventory_changes` Kafka topic, applying a `mapGroupsWithState` to maintain running stock levels per SKU per warehouse, and sinking to the `current_inventory` Delta table — is a sensible architecture for this problem, and using `mapGroupsWithState` rather than a stateless transform is the right call given you need running totals rather than independent per-event processing.

A few things I'd want resolved before this runs against production inventory data, since incorrect stock counts have pretty direct business impact. First, I don't see a watermark configured anywhere (`withWatermark` doesn't appear in the read stream setup), which matters a lot here given inventory events can plausibly arrive out of order across warehouses with different network conditions. Without a watermark, state for every SKU/warehouse combination is retained indefinitely, which is both a memory-growth risk over time and means the job has no defined policy for how late an event can arrive before being dropped — right now it seems to be "infinitely late is fine," which usually isn't actually the intended behavior once someone thinks it through, it's just the default you get by not deciding.

Second, the checkpoint location is set to a local-ish path pattern (`/tmp/checkpoints/inventory_stream`) rather than durable storage like S3 or ADLS. If the job restarts on a different node, or `/tmp` gets cleared, you lose the checkpoint and the job will either fail to resume or, worse, silently reprocess from an arbitrary offset depending on your `startingOffsets` configuration, which for a stateful stock-level job means double-counting or missing updates. This needs to point at durable, shared storage before this is production-ready.

Third, smaller: the `foreachBatch` sink writing to Delta doesn't appear to be using `MERGE` semantics — it looks like a plain append. If the point is to maintain "current" inventory per SKU/warehouse rather than an append-only event log, I'd expect an upsert (`MERGE INTO ... WHEN MATCHED THEN UPDATE ... WHEN NOT MATCHED THEN INSERT`) keyed on SKU and warehouse, otherwise `current_inventory` accumulates a growing history rather than reflecting current state, and every downstream reader has to know to take the latest row per key themselves.

Good foundational structure, but the watermark and checkpoint-durability issues in particular need to be fixed before this goes anywhere near production — those aren't style nits, they're the kind of thing that causes quiet data corruption weeks after launch when nobody's looking.
