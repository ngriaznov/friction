The new indexes in this migration look well targeted — `idx_orders_customer_date` on `(customer_id, order_date)` directly supports the dashboard query pattern you referenced in the PR description, and adding `idx_line_items_order_id` closes an obvious gap given how often that table gets joined against `orders`. No concerns on the indexing changes themselves.

The materialized view, `mv_daily_revenue_by_region`, is where I'd push back before approving. There's no `REFRESH MATERIALIZED VIEW` scheduled anywhere in this diff or referenced in the PR — as it stands, this view will be correct at the moment it's created and then silently stale forever after, since Postgres materialized views don't auto-refresh. If the dashboard is going to query this view expecting current data, someone needs to own a scheduled refresh (a cron job, an Airflow task, a pg_cron entry), and that ownership and cadence should be part of this PR, not a follow-up that might not happen. I'd also flag that a plain `REFRESH MATERIALIZED VIEW` takes an exclusive lock and blocks reads against the view for the duration — for a dashboard that's presumably queried during business hours, you likely want `REFRESH MATERIALIZED VIEW CONCURRENTLY`, which requires a unique index on the view (not present here) to work.

Smaller point: the migration doesn't include a corresponding down-migration for the materialized view drop, while the index migrations do have their `DROP INDEX` counterparts. Worth being consistent so a rollback doesn't require someone to remember the manual cleanup step.

Indexes are good to go as-is. Requesting changes on the materialized view specifically — needs a refresh strategy and a unique index before this is production-ready, not just schema-valid.
