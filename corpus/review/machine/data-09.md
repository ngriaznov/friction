The overall star schema shape here is right for what you're building — a `fct_subscription_events` fact table surrounded by `dim_customer`, `dim_plan`, and `dim_date` — and using a Type 2 SCD for `dim_customer` to track plan tier and billing address changes over time is the correct call given you said you need historical accuracy for reporting, not just current-state lookups.

A few things I'd tighten up before calling the design final. You've got `customer_id` (the natural/business key) doing double duty as the join key from the fact table directly into `dim_customer`, but since `dim_customer` is SCD2 with multiple rows per `customer_id` over time, that join is ambiguous unless you're also filtering on an effective-date range at query time — which is easy to get wrong and easy to forget three joins deep in someone's ad hoc query six months from now. Generate a proper surrogate key (`customer_key`) on `dim_customer`, assign it at the fact-table grain when the event is loaded (i.e., resolve which version of the customer was active as of the event timestamp during your ETL, not at query time), and have the fact table reference `customer_key` instead of `customer_id`. That moves the "which version was active" logic into the pipeline once, instead of every analyst having to reconstruct it in every query.

Second, `dim_date` is described as generated but I don't see fiscal-period columns (fiscal_quarter, fiscal_year) even though the PR mentions finance is a consumer of this — worth confirming with them now whether calendar quarters are sufficient or whether you need a separate fiscal calendar, since retrofitting that later means backfilling every fact table that joins to this dimension.

Third, minor: `effective_start_date` / `effective_end_date` on the SCD2 dimension — confirm the convention for the currently-active row's `effective_end_date`. Some conventions use a far-future sentinel date (9999-12-31), others use null. Either is fine, but it should be documented and consistent, since a null there breaks any `BETWEEN` range join and a sentinel breaks any naive `IS NULL` "is this current" check. Pick one, document it in the table comment, and make sure downstream consumers know which.

Good foundation, just needs the surrogate key resolution nailed down before other teams start building on top of it.
