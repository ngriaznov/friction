The stubs work, the tests are green, but I'd tighten up the WireMock matching before this gets much bigger, because the current approach is going to produce false-positive test passes.

Most of your stubs use `urlPathMatching(".*\\/quotes\\/.*")` with `.willReturn(...)` regardless of query parameters, method, or body. That means a test asserting behavior for `GET /quotes/EURUSD?venue=primary` would get the same stubbed response as a completely different request to `GET /quotes/EURUSD?venue=backup`, because the matcher doesn't distinguish them. If `QuoteClient` ever starts sending the wrong query parameter due to a bug, none of these tests would catch it — the overly broad matcher would happily serve the stub anyway. I'd tighten these to `urlEqualTo` or `urlPathEqualTo` plus explicit `withQueryParam` matchers for the parameters that actually matter to the test's assertion.

Related: `WireMockServer` is started once in a `@BeforeAll` and stubs are registered per test in `@BeforeEach`, but I don't see `wireMockServer.resetAll()` anywhere between tests. If a stub registered in one test isn't specific enough, it can leak into a later test and mask a missing stub that should have produced a 404 there. Adding `resetAll()` (or scoping via `resetToDefaultMappings()`) in an `@AfterEach` would make each test's stub set explicit and independent, and it'll surface exactly the over-broad-matcher issue above the moment you add it, so I'd do both together.

One more: a couple of tests assert only that `response.getStatusCode()` is 200, without asserting on the deserialized body. Given the whole point of `QuoteClient` is parsing the provider's JSON into your `Quote` model, I'd expect at least one test per shape variant (missing optional fields, provider's occasional string-typed price field) that actually asserts on the parsed object, not just the transport status.

Nothing here is fundamentally wrong, and the direction — testing the HTTP client against a fake server instead of mocking the client interface — is the right call for catching real serialization issues. It just needs sharper boundaries between test cases.
