This PR adds token-bucket rate limiting to the Go API gateway, implemented as middleware in `middleware/ratelimit.go` using `golang.org/x/time/rate`, keyed per API key with buckets stored in an in-process `sync.Map`.

The token-bucket choice and using the standard library's rate limiter rather than hand-rolling one is a good call, and keying per API key rather than per IP is the right granularity for a gateway sitting in front of authenticated traffic. The middleware placement (after auth, before routing) is also correct — you need the API key resolved before you can look up its bucket.

Main concern: this is an API gateway, which I'd assume runs as more than one replica in production, and `sync.Map` is process-local. Unless this gateway is deployed as a single instance (worth confirming explicitly, since "gateway" often implies horizontal scaling), each replica enforces its own independent limit, so the effective rate a client experiences is the configured limit multiplied by replica count. If horizontal scaling is or will be in play, the bucket state needs to move to Redis — either the classic `INCR`+`EXPIRE` fixed-window approach or a Lua-scripted token-bucket for accuracy — rather than living in each process's memory.

Second, smaller: buckets are created lazily on first request via `sync.Map.LoadOrStore` and never evicted, so every API key that's ever made a request keeps a live entry for the life of the process. For a gateway with a large or churning set of API keys this is an unbounded memory growth pattern, even if slow. An LRU with a reasonable cap, or a periodic sweep of buckets untouched for some window, would bound this.

Everything else — the 429 response including `Retry-After` computed from the limiter's reservation, and the config being per-key rather than global — looks right. I'd approve this if it's confirmed single-instance with a follow-up ticket for the Redis-backed version before scaling out, but if this gateway already runs multiple replicas today, I'd want that fixed before merge rather than after, since silently under-enforcing rate limits is the kind of thing that's easy to not notice until it's a problem.
