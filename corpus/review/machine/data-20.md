Nice addition. Using `pydantic` models to validate the shape of incoming webhook payloads before they hit the ingestion queue, combined with `pandera` schema checks once the batch lands as a DataFrame, gives you validation at both the right boundaries — the API edge and the tabular-processing edge — which is a good split of responsibilities rather than trying to force one tool to cover both.

The `pandera.DataFrameSchema` definitions for `raw_events` are clear and the use of `Check.in_range` on `event_timestamp` to reject obviously bad epoch values (things like the classic 1970 default or far-future dates from client clock skew) is a nice practical touch that a plain type check wouldn't catch.

One thing worth adding: right now a validation failure raises and the whole batch is rejected. For a nightly batch job that might be fine, but given this is sitting in front of a webhook ingestion path, I'd want to know what happens to an individual malformed event within an otherwise-valid batch — does one bad row currently take down the whole batch, or is there partial-success handling? If it's all-or-nothing, that's worth calling out explicitly (maybe it's the right tradeoff for now), but I'd at least want a follow-up ticket to consider quarantining bad rows to a dead-letter path rather than blocking the whole batch on one malformed record.

Small nit: the pydantic models and pandera schemas duplicate several field definitions (types, nullability) since they're validating overlapping stages of the same data. Not asking you to unify them in this PR, but worth a comment noting the duplication is intentional so someone doesn't "simplify" one without realizing it'll drift from the other. Approving as is.
