This PR adds a WebSocket implementation to the existing C networking library, introducing `ws_handshake.c` for the HTTP upgrade dance and `ws_frame.c` for RFC 6455 frame encoding/decoding, plumbed into the existing event-loop abstraction in `src/loop.c`. Substantial piece of work, and getting a WebSocket implementation right in C is genuinely hard to do safely, so I went through the frame parsing carefully — that's where the risk concentrates in this kind of code, and I found issues there I'd want fixed before this goes near untrusted clients.

`ws_frame_parse` reads the payload length field and, for the extended 64-bit length case (`len == 127`), reads eight bytes off the wire and casts them directly into a `uint64_t` used as an allocation size for `malloc(payload_len)` with no upper bound check. A malicious or buggy peer can send a frame claiming a payload length near `UINT64_MAX`; on a 32-bit build this truncates when passed to `malloc` and you get a much smaller allocation than the code believes it has, and even on 64-bit this is an easy way to make the process attempt a multi-exabyte allocation and abort, or with a more moderate but still large value, exhaust memory. RFC 6455 doesn't mandate a specific max frame size, but essentially every real implementation enforces an application-configurable cap for exactly this reason — I'd add a `max_frame_size` field to the connection config and reject (with a close frame, not just silently dropping the connection) anything over it before allocating.

Second, the masking-key XOR loop in `ws_frame_unmask` operates byte-by-byte over the payload using `payload[i] ^= mask[i % 4]`, which is correct but will be a measurable cost on large payloads — every client-to-server frame is masked per the spec, so this runs on all inbound data. Not a blocker, but worth knowing that a batched/word-at-a-time XOR (or reusing a SIMD trick if this library already leans on intrinsics elsewhere) would meaningfully help throughput once correctness is settled; I'd file this as a follow-up rather than hold up this PR for it.

Third, the close-frame handling in `ws_conn_close` writes the close code as host-endian into the frame buffer rather than network byte order (big-endian per the spec) — I traced through `ws_frame_encode` and confirmed the length fields are correctly byte-swapped with `htons`/`htobe64`, but the close status code field specifically is written with a raw `memcpy` from a `uint16_t` without the corresponding `htons`. On a little-endian host (which is most deployment targets) this will send the wrong close code to compliant clients, and depending on the browser or client library, may cause it to log or surface the wrong disconnect reason. Small in isolation but worth catching since it's the kind of bug that only shows up when someone's debugging a disconnect and the wrong code makes them chase the wrong cause.

On the positive side, the handshake code correctly validates the `Sec-WebSocket-Key` and computes the accept hash with the fixed GUID per spec, and rejects upgrade requests missing required headers rather than assuming they're present — that part I don't have concerns about.

I'd treat the unbounded allocation as a must-fix before this touches real traffic — it's a straightforward remote resource-exhaustion vector — and the close-code endianness as a should-fix given it's a compliance bug with real debugging cost down the line. The masking performance note can wait for a follow-up PR.
