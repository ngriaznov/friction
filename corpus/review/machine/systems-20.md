This PR fixes the four crashes that came out of the recent AFL run against the binary protocol parser in `src/proto/decode.c`, referencing the four saved crash inputs now checked into `tests/corpus/regressions/`. Good practice keeping the actual crashing inputs as regression tests rather than just describing the bugs in the commit message — that's exactly what should happen after a fuzzing find.

I went through each fix against its corresponding crash input:

The first fix addresses an out-of-bounds read in `decode_varint` where the continuation-bit loop had no bound on how many bytes it would consume, so a malformed input of all-continuation-bit bytes would walk past the end of the buffer looking for a terminating byte that never comes. The fix caps the loop at the maximum bytes a valid varint of the protocol's widest integer type could need (5 bytes for a 32-bit value, matches the protocol's varint format as far as I can tell from the spec doc referenced in the comment) and returns a decode error past that. This looks correct and the included regression input reproduces the original crash and now decodes to an error instead.

The second fix, in `decode_length_prefixed_bytes`, changes a signed comparison to an unsigned one — the length field is read as an `int32_t` and was being compared with `<` against the remaining buffer size directly. A negative length value (a large `uint32_t` reinterpreted as negative when the field is technically meant to be unsigned per the protocol but declared signed in this struct) would pass the `< remaining` check because a negative number compares less than practically anything, and then get used as a `memcpy` size after an implicit conversion back to a large unsigned value, reading far past the buffer. The fix looks right, but I'd go one step further and change the field's declared type from `int32_t` to `uint32_t` at the source (wherever this struct is defined) so the same class of bug can't resurface at a different comparison site elsewhere in the codebase that reads this field — right now the fix is local to one call site, but the underlying type is still signed, and I'd bet there's at least one more place that trusts it.

Third and fourth fixes are both null-pointer-dereference guards added after allocation failures that weren't being checked (`malloc` returning null under simulated memory pressure, which AFL's `-m` flag apparently triggered). Straightforward, correctly placed, both return decode errors rather than crashing. No concerns.

All four fixes look correct against their respective regression inputs, and I don't see anything half-fixed. My one ask, not a blocker for this PR specifically: given AFL found four issues in this one file in a single run, it's probably worth setting up continuous fuzzing (an AFL or libFuzzer job in CI, even nightly rather than per-PR) for this parser going forward rather than relying on periodic manual runs, since untrusted-input parsers like this tend to keep surfacing this exact class of bug as the format or the code evolves. Happy to approve this as-is and file that as a separate follow-up if you'd rather not scope-creep this PR.
