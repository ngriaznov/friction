This PR switches the `TransactionListView` in the Django REST Framework API from `PageNumberPagination` to a custom cursor pagination class subclassing DRF's `CursorPagination`, ordered by `-created_at`. Touches `transactions/views.py`, a new `transactions/pagination.py`, and the API docs snippet in the same PR.

Straightforward and correct use of DRF's built-in `CursorPagination`, which already handles the tie-breaking and cursor encoding concerns that come up when you roll this by hand, so there's not much to add — using the framework's implementation here rather than a custom one from scratch is the right call for something this well-trodden. The `ordering = '-created_at'` setting matches how the view was already sorted under the old pagination, so behavior for clients that don't care about the pagination mechanism itself should be unaffected.

One thing to double check: DRF's `CursorPagination` requires the ordering field to be effectively unique, or at least have a stable tiebreaker, to avoid skipped or duplicated rows when multiple records share the same `created_at` value — which for a transactions table seems plausible if transactions are ever bulk-inserted or backdated. DRF's docs note it falls back to using the `id` implicitly in some versions but I'd confirm this explicitly against your DRF version rather than assuming, since this has changed across releases; a quick test with several records sharing an identical `created_at` timestamp (force it in a factory) would settle it either way.

Small nit on the docs snippet update: it documents the new `cursor` query param but doesn't mention that `page` and `page_size` (from the old pagination class) will now return a 404 or be silently ignored — worth a line for API consumers who might have bookmarked or cached the old param names, even internally.

This looks good to me. Approving — the ordering-uniqueness question is worth a quick test but I wouldn't hold up the merge on it given how likely DRF's default behavior is already correct here.
