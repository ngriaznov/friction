I want to flag up front that this HTTP/1.1 header parser, as written, has at least one memory-safety bug that's exploitable from untrusted input, so "substantial changes" undersells it a little — this shouldn't go anywhere near a socket in its current form.

`parse_header_line` finds the colon with `strchr(line, ':')` and then does `memcpy(name_buf, line, colon - line)` into a fixed-size `char name_buf[64]` with no length check. Any header name of 64 bytes or more overflows a stack buffer. This is precisely the class of bug that made header parsers a perennial CVE source in the 2000s and 2010s (think the various embedded HTTP stacks), and a fuzzer will find it in seconds. You need to either bound the copy with a length check against `sizeof(name_buf) - 1` and reject or truncate, or better, avoid the fixed buffer entirely and work with pointer/length pairs into the original request buffer instead of copying into per-header scratch space at all — that also removes a whole class of these bugs at once and is faster since it avoids the copy.

Second: the function that scans for the end of headers looks for `"\r\n\r\n"` using a hand-rolled loop that reads `buf[i]` through `buf[i+3]` without checking `i + 3 < buf_len` first, so on a request that ends exactly mid-way through a partial header block (very common with a slow client or one deliberately sending a request in small chunks) this reads past the end of the receive buffer. Given this is presumably fed directly from `recv()`, that's a read of adjacent heap or stack memory driven by network input — worth taking seriously even though it's "only" a read, because in a parser that echoes headers back (redirects, error pages) an out-of-bounds read like this can turn into an information leak.

Third, there's no limit on the number of headers accepted, so a request with thousands of headers will happily be processed until whatever fixed-size header array you're filling overflows — I didn't see a bound in `parse_request`, only in `parse_header_line` for the individual header. Real servers cap both total header count and total header block size for exactly this reason; you'll want both, and you'll want them checked before any parsing work happens on a given line, not after.

On the positive side, the request-line parsing (method/URI/version) is done correctly with proper bounds checks, and the tokenizer for header values correctly skips leading whitespace per RFC 7230's `OWS` rule, which a lot of hand-written parsers get wrong. That part I'd keep as-is.

I'd want the buffer overflow and the out-of-bounds read fixed as blocking issues, plus a header-count/size limit added, before this goes anywhere near real traffic. I'd also strongly suggest running this under AFL or libFuzzer for a while once those are fixed — a raw-pointer C parser over untrusted bytes is exactly the kind of code that benefits most from fuzzing, and it's cheap to set up given you already have a single-entry `parse_request(const char*, size_t)` function to target.
