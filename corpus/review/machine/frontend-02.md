The slice itself is written well — normalized state shape with `entities` and `ids`, clean reducers, correct use of Immer's draft mutation style inside `createSlice`. My concern is entirely on the selector side, specifically `selectVisibleOrders`, which you've defined as a plain function that filters and sorts `Object.values(state.orders.entities)` on every call.

Because this selector isn't memoized, every component that calls `useSelector(selectVisibleOrders)` recomputes the filter and sort on every single dispatched action, not just actions that touch the orders slice. Redux's `useSelector` does a reference-equality check on the return value to decide whether to re-render, and since `.filter().sort()` always returns a brand-new array, every dispatch anywhere in the app — including unrelated ones like a UI toggle in a totally different slice — will cause this component to re-render, because the selector's return reference always changes. That's the classic case for `reselect`. Wrap this in `createSelector`, with the raw entities and the current filter/sort criteria as input selectors, and the derived array as the output. Reselect will cache the computed array and only produce a new reference when one of the actual inputs changes.

One nuance worth flagging: your filter criteria comes from `state.ui.orderFilter`, which is an object (`{ status, dateRange }`) rather than a primitive. If `orderFilter` itself is reconstructed as a new object anywhere in a reducer even when its contents are unchanged, memoization breaks silently — reselect's default equality check is reference equality on inputs, so a new-but-equal object still busts the cache. Worth double-checking that the reducer setting `orderFilter` doesn't do something like `state.ui.orderFilter = { ...action.payload }` unconditionally on unrelated actions.

Separately, I'd question whether the sort belongs in the selector at all versus being computed once at insertion time or handled by the component via a memoized `useMemo` that takes the selector's raw output. Sorting a potentially large order list on every relevant state change is more work than it needs to be if the sort key rarely changes; but that's a smaller optimization than fixing the reference-identity problem, which is actively causing unnecessary renders right now, not hypothetically.

Minor naming nit: `selectVisibleOrders` reads like it selects orders that are visible on screen (e.g., viewport-visible for virtualization purposes), when it actually means "orders matching the current filter." Something like `selectFilteredOrders` would remove that ambiguity for the next person reading it.

Good use of `createEntityAdapter` for the base CRUD reducers, and I like that you kept the async thunk's pending/fulfilled/rejected handling terse rather than sprinkling loading flags everywhere. Once the selector memoization is sorted out, this is good to merge.
