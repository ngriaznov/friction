I like the direction of this — moving `ProductAvailabilityController` onto WebFlux with R2DBC for the underlying `product_stock` reads is a reasonable choice if this endpoint genuinely needs to handle high concurrent request volume with limited threads, and the reactive repository setup (`R2dbcRepository<ProductStock, Long>`) is wired up correctly at the plumbing level. But there are a few places in the actual handler chain that quietly reintroduce blocking, and since the entire value proposition of this migration is non-blocking I/O, those need to be fixed before this ships, not treated as follow-ups.

The main one: `ProductAvailabilityService.checkAvailability()` calls `warehouseClient.getStockLevel(sku)` partway through the reactive chain, and `WarehouseClient` is still the old `RestTemplate`-based HTTP client — a blocking call. It's wrapped in `Mono.fromCallable { warehouseClient.getStockLevel(sku) }`, which does make it composable with the rest of the `Mono` chain syntactically, but `fromCallable` alone doesn't move the blocking call off the event loop thread — it needs `.subscribeOn(Schedulers.boundedElastic())` as well, and that's missing here. As written, this blocking HTTP call executes directly on one of Netty's event loop threads, and since WebFlux typically runs with a small fixed number of those (default is CPU core count), a handful of concurrent requests hitting a slow warehouse API can stall the entire event loop for every other in-flight request on that thread, which is a worse failure mode than the blocking `RestTemplate` version you're replacing ever had, because now it's not isolated to one request's own worker thread.

Same pattern shows up again in `AuditLogger.recordAccess()`, called via `.doOnNext()` in the chain — that method writes to the old JDBC-backed audit table synchronously. `doOnNext` runs on whatever thread the chain is currently executing on, so this has the identical event-loop-blocking problem. Either migrate the audit write to R2DBC too, or if that's out of scope for this PR, wrap it with `Mono.fromRunnable { ... }.subscribeOn(Schedulers.boundedElastic())` and make sure it's actually subscribed to (a bare `doOnNext` with a synchronous side effect won't get scheduled off-thread just by living inside a reactive operator).

The R2DBC query itself in `ProductStockRepository.findBySku` looks fine, and I appreciate the test using `StepVerifier` rather than blocking on the `Mono` to get a value out in `ProductAvailabilityServiceTest` — that's the correct way to test reactive chains and a lot of migrations get this wrong by calling `.block()` in test code, which this doesn't do.

Also worth a look: `checkAvailability` doesn't set any timeout on the `warehouseClient` call within the reactive chain. In the old blocking version, `RestTemplate` presumably had a connect/read timeout configured at the client level; once this is wrapped in a `Mono`, you'd also want a `.timeout(Duration.ofSeconds(...))` in the chain itself so a hung warehouse API doesn't hold a `boundedElastic` thread indefinitely once the scheduling fix above is in place — `boundedElastic` is bounded, and it's easy to exhaust it too under sustained slow-downstream conditions if nothing ever times out.

I'd want the `subscribeOn` fix on both blocking calls, plus the timeout, before this merges — the current version could make event-loop starvation worse under load than what it's replacing, which would be a bad outcome for a change whose whole purpose is improving throughput under load.
