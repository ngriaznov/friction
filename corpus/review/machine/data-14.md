This is a good cleanup. Replacing the ad hoc `ROW_NUMBER()`-based surrogate keys in `stg_orders.sql` and `stg_customers.sql` with `dbt_utils.generate_surrogate_key(['source_system', 'natural_id'])` removes a real footgun — the old approach assigned keys based on row order in a given run, which meant the same natural key could get a different surrogate key across runs if upstream ordering wasn't perfectly stable. The hash-based approach is deterministic regardless of row order, which is exactly the property you want for something other models will join against.

A couple of things worth checking before merge. `generate_surrogate_key` hashes its inputs after casting to string and concatenating, and null handling matters here — confirm none of the columns going into the key (particularly `source_system`) can be null in practice, since two rows that are both null in one of the key fields will hash identically regardless of what else differs, silently merging records that should stay distinct. A quick `dbt test` with a `not_null` constraint on those columns would catch this at the source rather than downstream in the key itself.

Also, since this changes the actual surrogate key values (new hash instead of old sequential integers), anything downstream that persisted the old keys — dashboards with hardcoded IDs, external systems that received exports keyed on the old values — is going to break silently on the next full-refresh. Worth confirming in the PR description whether this is a full-refresh-required change and calling that out explicitly for whoever runs the deploy, since it's easy to forget and end up with half-migrated key spaces if the incremental models aren't rebuilt from scratch.

Model logic and tests otherwise look solid — approving contingent on confirming the null-handling question and documenting the full-refresh requirement.
