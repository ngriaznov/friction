This is a big, necessary migration and the bulk of it is done carefully — the `javax.*` to `jakarta.*` package rename across the entity classes, the DTOs, and the validation annotations looks complete and consistent, and I appreciate that it's a single mechanical commit separate from the actual behavior changes further down. Went through it section by section.

Entity and persistence layer: the `jakarta.persistence.*` imports are correctly swapped throughout, and `hibernate-core` is bumped to the 6.x line that Spring Boot 3.2's parent POM expects. One thing to double check — Hibernate 6 changed the default behavior around `@Enumerated(EnumType.STRING)` handling for a couple of edge cases involving enums with custom `@Column` length constraints, and I see `OrderStatus` on the `Order` entity has a `@Column(length = 20)` alongside `@Enumerated(STRING)`. Worth confirming with an integration test that persisting the longest enum value still round-trips correctly under Hibernate 6, since this is exactly the kind of thing that passes unit tests against mocks and only breaks against a real database.

Security config: `WebSecurityConfigurerAdapter` is gone in Spring Security 6, and the rewrite to a `SecurityFilterChain` bean in `SecurityConfig` looks like a faithful translation of the old rule set — the permit-all paths, the JWT filter insertion point, and the CORS configuration all made the trip. I did notice the old config had `.and()` chaining that implied a specific filter ordering, and the new lambda-DSL version reorders a couple of `.authorizeHttpRequests()` matchers relative to the original `.antMatchers()` sequence. Spring Security matches rules in declaration order, so if that reordering was accidental rather than deliberate, it's worth re-verifying the actual authorization behavior with a request-level test per role rather than trusting that the translation preserved intent — I'd want to see that in the test additions before merging, and right now I only see unit tests on the filter class itself, not an end-to-end authorization test through the real filter chain.

`javax.validation` to `jakarta.validation`: straightforward, all the `@NotNull`/`@Size`/`@Valid` usages caught. Good.

Actuator and metrics: config property names for a few Micrometer settings changed between Boot 2.7 and 3.2 (`management.metrics.export.*` shape changed in a couple of places), and I see `application.yml` still has one old-style key (`management.metrics.distribution.percentiles-histogram.http.server.requests`) sitting alongside what look like the newer equivalents. Worth checking whether that's now silently ignored rather than doing anything, since a stale unused config key won't fail the build but will fail silently at runtime.

Build file: the Gradle `springBootVersion` bump and the corresponding `ext['hibernate.version']` override are correctly aligned with what Boot 3.2's BOM expects. No complaints there.

Given the size and blast radius of this change, I'd want the authorization-ordering question and the enum-persistence question answered with actual tests before this merges — everything else here looks like a clean, faithful migration and I'm comfortable with the mechanical parts as-is.
