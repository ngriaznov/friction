Nothing here is broken — the build works, the modules resolve, CI presumably passes — but this is exactly the kind of build file that turns into a slow-motion problem six months from now, so let me go through what I'd change before it gets worse.

The core issue is that every one of your seven subprojects (`api`, `worker`, `scheduler`, `notification-service`, and three internal libs) declares its own version string for Jackson, for the Spring Boot dependencies, and for Testcontainers, each in its own `build.gradle`. Right now they mostly agree — Jackson 2.15.2 everywhere, for instance — but "mostly agree" is not a property Gradle enforces for you, and I can already see one drift: `notification-service` is pinned to `testcontainers:1.19.0` while everything else is on `1.19.3`. That's the kind of mismatch that produces a test that fails only in one module's CI job and eats an afternoon before someone notices the version diff. Move these into a Gradle version catalog (`gradle/libs.versions.toml`) and reference `libs.jackson.databind` etc. from each subproject's `build.gradle`. It's a bounded, mechanical migration and it gives you a single file to bump for security patches instead of grepping seven build files.

Second, `allprojects { dependencies { ... } }` in the root `build.gradle` applies `spring-boot-starter-web` to every subproject, including the two that are plain libraries with no HTTP surface (`common-model`, `event-schemas`). That's dragging Tomcat and the whole web stack into artifacts that should have effectively zero runtime dependencies. It also means any consumer of `common-model` as a library transitively pulls in a web server. Push shared dependencies down into a `subprojects` block scoped to just the services that need them, or better, use `java-library` and mark web dependencies `implementation` only where they're actually used.

Third, I'd double check `resolutionStrategy.force` in the root build — you've forced `commons-lang3` to `3.9` with a comment saying "needed for legacy-integration compat," but `legacy-integration` isn't in this repo's module list anymore per the settings.gradle, so this may be a stale pin actively holding back a security-patched transitive version elsewhere. Worth confirming it's still needed before carrying it forward.

Smaller things: the `test` task in several modules sets `maxParallelForks = Runtime.runtime.availableProcessors()`, which on a shared CI runner with several concurrent jobs can oversubscribe and actually slow things down rather than speed them up — I'd cap it explicitly (e.g., `availableProcessors() / 2` with a floor of 1) rather than assuming exclusive access to the machine. And a few subprojects still use the deprecated `compile` configuration instead of `implementation`/`api` — that still works on this Gradle version but it's worth cleaning up while you're already touching these files for the version catalog migration.

None of this blocks a merge if this build is already in production use — it's stable — but I'd treat the version catalog move as the highest-value follow-up, since it directly prevents the kind of silent drift I called out with Testcontainers above.
