The author posted a Django middleware meant to rate-limit API requests per client IP, implemented with a module-level `defaultdict(list)` storing timestamps and a sliding-window check in `__call__`, and asked whether it was ready to deploy behind Gunicorn.

Short answer: not as-is, and the reason is specific to how you're running it. A module-level dict lives in the memory of a single Python process. The moment you run this behind Gunicorn with more than one worker (which you should be, for anything handling real traffic), each worker has its own independent copy of that dict, so a client can get up to `limit × worker_count` requests through before any single worker's view of their rate would reject them. If you deploy with `--workers 4`, your "10 requests per minute" limit is actually closer to 40 per minute in practice, and it gets worse if you also scale out to multiple hosts, where each host adds its own multiplier on top. The fix is to move the counters to something shared across processes and hosts — Redis is the standard choice here, using `INCR` with `EXPIRE` for a fixed window or a sorted set (`ZADD`/`ZREMRANGEBYSCORE`) for a proper sliding window. `django-ratelimit` or `django-redis` plus a small custom check would save you from hand-rolling this.

Separate from the multi-process issue, the in-memory list also never gets cleaned up for IPs that stop sending requests — you're appending timestamps per IP forever and only trimming the list for the specific IP on its next request, so an attacker (or just a long tail of one-time visitors) leaves entries that sit in memory indefinitely. Even after moving to Redis this matters less because you'd set a TTL, but flagging it in case you keep any in-process component.

Also worth checking: are you keying purely on `request.META['REMOTE_ADDR']`? If this app is behind a load balancer or reverse proxy, that will be the proxy's IP for every request unless you're reading `X-Forwarded-For` (and validating it against a trusted proxy list, since that header is client-controllable if read naively).

I'd hold off on deploying this until the shared-state problem is fixed; the current version will pass a quick single-process smoke test and then silently under-enforce in production, which is a worse failure mode than not having rate limiting at all because it gives false confidence.
