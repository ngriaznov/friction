Using `react-window`'s `VariableSizeList` for this comment thread was the right call given rows genuinely vary in height (collapsed vs. expanded comments, with-image vs. text-only), but the dynamic height measurement approach you've got is going to cause visible jank, so let's dig into that.

You're computing `getItemSize(index)` by returning a hardcoded estimate (`80` for text comments, `200` for comments with images) rather than measuring actual rendered height. That's a reasonable starting point, but the moment real content varies from those estimates — a long comment that wraps to six lines instead of two, or an image that isn't the assumed aspect ratio before it loads — you'll get overlapping rows or extra blank space, since `VariableSizeList` trusts whatever `getItemSize` reports rather than the DOM's actual layout.

The standard pattern here is to measure rows after they render and feed corrected heights back into the list. Wrap each row in a component that uses a `ref` and `ResizeObserver` (or even just measures `offsetHeight` in a `useLayoutEffect` on mount), report the measured height up via a callback, cache it in a `Map` or ref keyed by index, and call `listRef.current.resetAfterIndex(index)` when a measured height differs from the estimate. This is exactly the pattern shown in `react-window`'s own dynamic-size examples, and while it's more code, it's what actually keeps the list correct once real content is involved. Right now you have the scaffolding for variable sizing without the feedback loop that makes it accurate.

Separately: images inside rows are not being handled with any placeholder or reserved space before they load, so when an image finishes loading after the row has already been measured/rendered at the estimated height, the row will visibly jump. Reserve space with an explicit `aspect-ratio` or a fixed placeholder height that matches the final rendered size, sourced from image metadata if you have it (width/height from the API response), rather than letting the browser's natural image reflow drive a late resize.

One more: `itemKey` isn't passed to `VariableSizeList`, so react-window is using index as the implicit key. If comments can be inserted, removed, or reordered (e.g., a new comment added at the top, or sorting by "most liked"), index-based keys will cause react-window to misattribute cached measurements to the wrong comment, and you'll see stale heights applied to unrelated rows. Pass `itemKey={(index) => comments[index].id}` and make sure `getItemSize` is also looked up by a stable id-keyed cache rather than by index alone, otherwise reordering will silently reintroduce the same bug at a different id.

The rest — using `AutoSizer` to size the list container, `overscanCount` set to a small positive number to pre-render a couple of off-screen rows — all looks reasonable and I wouldn't touch it. Get the measurement feedback loop and stable keys in place and this should hold up well even with a few thousand comments.
