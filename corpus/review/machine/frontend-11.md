The native HTML5 drag-and-drop API is a reasonable choice here given you want to avoid a dependency for what's ostensibly a simple kanban-style reorder, but a couple of things in this implementation are going to cause real problems, particularly around mobile and accessibility, which native DnD doesn't handle at all on its own.

Functionally: `onDragStart` sets `event.dataTransfer.setData('text/plain', cardId)`, and `onDrop` reads it back with `getData('text/plain')` to know which card moved where. That's correct and works. But `onDragOver` is missing `event.preventDefault()` in one of the two drop-zone components (the "done" column handler has it, the "in progress" column handler doesn't), which means drops are silently rejected in that column — by default, browsers don't allow dropping anywhere, and calling `preventDefault()` in `dragover` is what opts an element into being a valid drop target. That's a straightforward bug, not a design question, and should be an easy fix.

Bigger issue: native HTML5 drag-and-drop has no mobile/touch support at all — `draggable="true"` and the drag events it fires are a desktop-mouse-only API by spec, so this entire feature is currently unusable on any touchscreen device. If mobile support matters for this product (worth confirming with whoever owns the requirements), native DnD is the wrong foundation and you'd want something like `dnd-kit` or `@hello-pangea/dnd`, both of which implement pointer-event-based dragging that works across mouse and touch. If mobile genuinely doesn't matter here, that's a legitimate call, but it should be a documented, deliberate decision rather than something discovered later by a user on an iPad.

Accessibility is the other major gap: there's no keyboard-operable equivalent for reordering cards. A screen-reader or keyboard-only user has no way to move a card between columns at all in the current implementation. This is a common blind spot with drag-and-drop UIs generally, not specific to your choice of native API, but it's worth raising now rather than as an afterthought — at minimum, each card should have a context menu or button-based "move to column" action that achieves the same result without requiring a pointer drag.

On the state update side: `onDrop` computes the new column and calls `updateCardPosition(cardId, newColumnId, index)` directly against the backend on every drop, with the UI only updating after the API call resolves — meaning that during the round-trip, the card visually snaps back to its old position and then jumps to the new one once the response comes back. That's a noticeable flicker. An optimistic update (move the card immediately in local state, roll back on API failure) would feel considerably smoother and is a fairly standard pattern for this kind of interaction.

The `dragover`/`preventDefault()` bug needs fixing regardless, but the mobile and accessibility gaps are the ones I'd want a real answer on before this ships broadly — not necessarily blocking this specific PR if it's explicitly scoped to desktop-only for now, but I'd want that scope written down somewhere, because "we'll add mobile later" has a way of never happening once the desktop version is out.
