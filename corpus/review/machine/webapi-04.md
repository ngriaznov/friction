The question showed a Python GraphQL API built with Strawberry, specifically a `Query.orders` field returning a list of `Order` types, where each `Order.customer` field resolver does its own `Customer.objects.get(id=self.customer_id)` lookup, and the author was asking why a query for 100 orders with nested customer names was slow and generating what their APM tool called "excessive" database round trips.

This is the textbook GraphQL N+1: each field resolver is independent by design, so when a client asks for `orders { id customer { name } }`, Strawberry calls your `customer` resolver once per `Order` object in the result set, and each call does its own synchronous DB hit. There's no way around this by rearranging the resolver code alone — the fix is a batching layer, and in the Python GraphQL ecosystem that's `strawberry.dataloader.DataLoader` (or `aiodataloader` if you're on Graphene). You'd write a `load_customers(keys: list[int])` batch function that does a single `Customer.objects.filter(id__in=keys)` call, wrap it in a `DataLoader`, instantiate one per-request (typically in your context getter, not as a module-level singleton — a shared loader across requests will leak identity-map state and stale results between users), and have the `customer` resolver call `await loader.load(self.customer_id)` instead of hitting the ORM directly. DataLoader coalesces all the `load` calls that happen within the same event loop tick into one batch call, which turns your 100 separate customer lookups into 1.

A couple of things to watch once you add this. If you're on Django's synchronous ORM under an async GraphQL resolver, you'll need `sync_to_async` around the batch query or you'll block the event loop the same way as before, just fewer times. Also make sure the DataLoader's batch function preserves the input key order and returns `None` (not an exception, and not just a shorter list) for keys with no match, or you'll get subtly misaligned results — the contract for the batch function is that the output list must be the same length and order as the input keys.

Longer term, since you mentioned this is a public-ish API, you'll also want a query complexity or depth limiter (Strawberry has hooks for this via extensions) since nested list-of-list queries can still be expensive even after batching fixes the round-trip count — that's a separate concern from what's currently breaking, but worth a backlog item.

Nothing else in the schema jumps out as wrong; this is really a one-issue review, it's just an issue that needs a real architectural fix rather than a query tweak.
