This PR implements a general-purpose webhook delivery system for the Django app — a `WebhookSubscription` model, a `deliver_webhook` Celery task, a signal handler that enqueues deliveries when various domain events fire, and a `WebhookDelivery` model that logs each attempt. It's a fairly large PR (roughly a dozen files) so this is a substantial change to review.

The overall design is sound: decoupling event production (the signal handlers) from delivery (the Celery task) via an enqueue step, and logging each delivery attempt in `WebhookDelivery` for observability, is the right shape for this kind of system. I also like that `WebhookSubscription` has a `secret` field used to HMAC-sign the outgoing payload in the `X-Webhook-Signature` header — that's often missed in a first pass at this feature and it's good to see it included from the start.

That said, there are several things I think need to change before this merges, roughly in priority order.

`deliver_webhook` has no idempotency mechanism. Celery's `acks_late` combined with a worker crash or a task exceeding the visibility timeout can cause the same task to run twice, and separately, the retry-on-failure logic in this task (via `self.retry`) doesn't check whether a previous attempt actually succeeded before retrying — I don't see an `event_id` uniqueness check anywhere. If a subscriber's endpoint is slow enough to exceed your task's own timeout but still eventually processes the request, a retry will deliver the same event twice with no way for either your system or the subscriber to know that happened unless the subscriber does their own dedup (which you can help with by including a stable `event_id` in the payload — I see `event.id` is passed in, so that part exists; the gap is that your own system doesn't track "we've already attempted event X for subscription Y" as a hard constraint).

The signal handlers enqueue the Celery task directly inside the same request/transaction as the domain event (e.g., `order_shipped` signal calls `deliver_webhook.delay(...)` synchronously within the view's transaction). If the transaction is rolled back after the signal fires but before commit — which Django signals don't protect against, since `post_save` fires before the transaction commits unless you're using `transaction.on_commit` — you can enqueue a webhook for an event that never actually persisted. I'd wrap the `.delay()` calls in `transaction.on_commit(lambda: deliver_webhook.delay(...))` so the task only gets queued once the underlying data is actually committed.

Retry backoff: similar to a few other webhook implementations I've reviewed, this one retries on any exception from the `requests.post` call, including 4xx responses, with a flat retry count and no distinction between "subscriber endpoint is broken" (4xx, don't keep retrying the same payload) and "subscriber endpoint is temporarily down" (5xx/timeout, retry with backoff makes sense). I'd split those and add exponential backoff via `retry_backoff=True` on the task.

Smaller items: `WebhookDelivery.response_body` stores the full response body from the subscriber's endpoint with no length cap — a misbehaving or malicious endpoint could return a huge body and bloat your delivery-log table; truncate before storing. Also, subscription URLs aren't validated against internal/private IP ranges before use, which means a subscriber could register a webhook URL pointing at your own internal network (SSRF) — worth validating the resolved IP isn't in a private range at delivery time, not just at registration time, since DNS can change between registration and delivery.

This is a good foundation and most of the pieces are there, but between the transaction-commit ordering issue and the missing idempotency/SSRF protections, I'd request changes rather than approve as-is.
