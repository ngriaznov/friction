This PR replaces the single `RwLock<HashMap<K, V>>` in `src/store/map.rs` with a striped map — a fixed array of sixteen independently locked shards, each key routed to a shard by hashing — to reduce writer contention under the store's concurrent workload. The approach is sound and the implementation matches the well-known pattern closely: `shard_index` hashes the key with the same hasher used inside each shard's `HashMap` so you're not paying for two different hash computations per operation, and each shard is its own `RwLock<HashMap<K, V>>` behind a `Box<[_]>` rather than a `Vec`, which is a nice touch since the shard count is fixed at construction and doesn't need to grow.

One correctness question rather than a definite bug: `iter_all` acquires each shard's read lock one at a time, iterating and releasing before moving to the next shard, rather than holding all sixteen locks simultaneously. That means a full iteration is not a consistent snapshot across the whole map — a concurrent writer could remove a key from shard 3 after you've already passed it, and by the time you reach shard 3 you won't see the removal, while insertions happening in shards you've already passed won't be seen either. If callers of `iter_all` expect point-in-time consistency (common for something like a debug dump or a metrics export) this could surprise someone. If the intended semantics are "best-effort snapshot, no cross-shard consistency guaranteed," that's a completely reasonable design for a striped map, but it should be stated explicitly in the doc comment on `iter_all`, since the previous single-lock implementation did give full consistency and this is an observable behavior change for existing callers.

Small thing: shard count is a compile-time constant (16) rather than configurable at construction. That's fine for now, but worth a comment on why 16 was chosen (presumably matched to expected core count or contention testing) so a future reader doesn't have to guess whether it's arbitrary.

This is a clean, well-scoped concurrency improvement. I'd just get the `iter_all` consistency semantics documented explicitly before merge — everything else looks good to me.
