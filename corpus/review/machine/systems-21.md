This PR converts the sensor-polling and telemetry-upload paths in the embedded firmware from blocking calls to `async`/`.await` using `embassy`, touching `src/sensors.rs` and `src/telemetry.rs` and adding the embassy executor setup in `src/main.rs`. Given the stated goal — letting the MCU sleep between sensor reads instead of busy-waiting on blocking I2C transactions — this is a reasonable direction for the power budget this device apparently needs to hit.

The conversion of the I2C read path itself looks right: `Sensor::read_temperature` now `.await`s on the async I2C trait instead of the blocking one, and the executor is configured to enter a low-power sleep state between polls via embassy's built-in idle hook, which is the actual point of the change. I don't have concerns about the core async plumbing.

Two things I'd want resolved before this ships to hardware, since embedded failure modes here are harder to debug after the fact than a desktop async bug:

The telemetry upload task and the sensor-polling task both run as separate embassy tasks sharing a `Mutex<TelemetryBuffer>` (the `embassy_sync` mutex, not `std::sync::Mutex`, which is correct for a no_std target), but I don't see a bound on how long the upload task can hold that lock while it's blocked on the radio write, which per the diff can itself be a multi-second operation on a lossy link with retries. If the sensor task's `.await` on acquiring the same mutex means it can't record new readings for the duration of a slow upload, you're silently dropping sensor samples during exactly the conditions (poor connectivity, retries in flight) where you'd most want continuous data. I'd either give the sensor task its own buffer that gets swapped/drained by the upload task rather than sharing one buffer and one lock, or explicitly document that sample loss during upload stalls is accepted behavior — right now it's neither documented nor obviously intentional.

Second, stack sizing: embassy tasks each get a statically-sized stack (or, if this executor variant doesn't preallocate per-task, a shared arena), and converting from a straight-line blocking function to an `async fn` state machine changes the actual stack/state size needed, sometimes substantially, since the compiler has to hold live variables across `.await` points inside the generated state machine. I don't see the stack size constants in `main.rs` having been revisited after this conversion. Given this is memory-constrained embedded hardware, I'd want to see this actually measured (embassy has tooling for this, or a manual worst-case trace through the largest `.await`-spanning locals) rather than assumed unchanged, since a stack overflow on this class of MCU tends to manifest as silent memory corruption rather than a clean fault.

I like the direction and the core conversion is done competently — I'd want the buffer/lock contention question settled explicitly (either fixed or documented as accepted) and the stack sizing re-verified before this goes on hardware that's hard to get physical access to for debugging afterward.
