This PR adds a new multi-step wizard component (`OnboardingWizard`) used for the new user setup flow — four steps (account details, team info, integration selection, plan selection), with a shared progress indicator and per-step validation before allowing "Next." I spent a good amount of time on this one since wizard components have a lot of state-management surface area and this is going to be reused for at least two other flows per the PR description, so it's worth getting right now rather than living with rough edges everywhere it gets copied.

Overall architecture: state for all four steps lives in a single `useReducer` in the top-level `OnboardingWizard` component, with each step reading its relevant slice via props and dispatching a shared `UPDATE_FIELD` action type with a `step` and `field` key. That's a reasonable choice for this kind of form — keeping all the data in one place makes cross-step validation and final submission straightforward, and I'd rather see this than four separate `useState` calls per step scattered around with prop-drilling headaches. The reducer itself is well-organized, actions are clearly typed with a discriminated union, and I don't see any mutation of the previous state — good adherence to reducer purity throughout.

Now for the substantive issues.

First, step validation. Each step component (`AccountDetailsStep`, `TeamInfoStep`, etc.) has its own internal `isValid` check that gates the "Next" button, which is fine, but the validation logic is duplicated rather than shared — `AccountDetailsStep` validates the email field with one regex inline, and if I search the codebase, there's a very similar (but not identical — this one's missing the `+` character in local-parts) email regex already defined in `src/utils/validators.ts` used elsewhere in the app. Two slightly different email validation regexes in the same app is the kind of inconsistency that causes confusing, hard-to-reproduce bugs down the line ("why did my email work on the login form but not signup?"). Please consolidate onto the shared validator, and more generally, I'd want per-step validation extracted into named functions or a schema (this seems like a natural fit for `zod`, which I see is already a dependency) rather than inline JSX-adjacent conditionals, both for reuse and because it'll make step validation testable in isolation from the rendering.

Second, and this is the one I'd most want fixed before merge: browser back/forward and refresh handling. Right now, all wizard state lives in the in-memory reducer with nothing persisted, so a user who's filled out three of four steps and accidentally refreshes the page, or navigates back and forward via browser history, loses everything and starts over from step one. For an onboarding flow specifically — often the very first interaction a new user has with the product — losing their progress on an accidental refresh is a bad first impression and a plausible source of drop-off. I'd want at least session-storage persistence of the in-progress wizard state, restored on mount if present, cleared on successful final submission. This doesn't need to be complicated — a `useEffect` that writes the reducer state to `sessionStorage` on every change, and an initializer that reads it back, covers the common case.

Third, the step transition itself directly mutates a `currentStep` number in the reducer and the component conditionally renders `{currentStep === 1 && <AccountDetailsStep />}` and so on, rather than something like a switch or a lookup array. Functionally this works fine, but it means every step component's state is fully unmounted and remounted when navigating away and back to it (going from step 2 to step 3 and back to step 2 unmounts and remounts `AccountDetailsStep` entirely) — this doesn't lose data since the data lives in the parent reducer, so no correctness bug, but any local UI-only state within a step (e.g., a step-local "show password" toggle, if one exists) would reset every time. Worth being aware of if any step later grows local UI state; not something to fix now given no step currently has any.

Fourth, accessibility: the progress indicator at the top (four numbered circles connected by a line) has no ARIA semantics indicating current step, completed steps, or total step count to a screen reader — it's purely decorative markup with no `aria-current` on the active step and no accessible name summarizing progress (e.g., "Step 2 of 4: Team Info"). This is a common gap in wizard components generally, and worth fixing now while this is early and about to be reused, rather than after three more flows have copied the same pattern.

Fifth, smaller: the final submit button on step four calls the submission API directly from within the step component rather than from the parent wizard, which slightly breaks the pattern established by the rest of the component (where the wizard owns orchestration and steps are presentation-plus-local-validation only). I'd move the actual submission call up to `OnboardingWizard` and have the step just report "ready to submit" via a callback, both for consistency and because the wizard-level component is a more natural place to handle the loading/error UI for a cross-cutting concern like final submission.

To summarize: I want the duplicated email validation consolidated, session persistence added for refresh/back-button resilience, and the progress indicator given proper ARIA semantics before this merges — those three matter most given this is about to become a template other flows copy. The submission-call placement and step remounting are smaller and I'd be fine with either fixing now or tracking as quick follow-ups. Good foundational work otherwise; the reducer design in particular is solid and I wouldn't want that rearchitected.
