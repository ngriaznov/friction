This PR adds Terraform for the AKS cluster plus a paired Azure Key Vault instance under `modules/azure/aks-platform`, with the cluster's kubelet identity granted `get`/`list` access to Key Vault secrets via the Secrets Store CSI driver integration. The overall shape is right for how most teams do secret delivery into AKS, but there are a few things I'd want changed before this goes in.

The `azurerm_kubernetes_cluster` resource uses `identity { type = "SystemAssigned" }` for the cluster identity, which is fine, but the separate kubelet identity block needed for the CSI driver's Key Vault access isn't configured as `UserAssigned` — with a system-assigned cluster identity, the kubelet identity is auto-created and harder to reference cleanly from outside the cluster resource for the Key Vault access policy you're setting up in this same PR. I'd switch to `identity { type = "UserAssigned" }` with an explicit `azurerm_user_assigned_identity` resource so the kubelet identity's principal ID is a first-class Terraform-managed value you can reference directly in the Key Vault access policy, rather than reaching into the cluster resource's computed `kubelet_identity` attribute the way this PR currently does — it works, but it's more fragile across provider version bumps.

The Key Vault resource has `purge_protection_enabled = false`. For anything backing production secrets, I'd want this `true` — without purge protection, a Key Vault (and everything in it) can be permanently and immediately deleted rather than soft-deleted with a recovery window, which is a meaningful blast-radius difference if someone runs the wrong `terraform destroy` against the wrong workspace.

The `network_acls` block on the Key Vault defaults to `bypass = "AzureServices"` and `default_action = "Allow"`, meaning the vault is reachable from any network by default rather than restricted to the AKS subnet or a private endpoint. Given this module also provisions a VNet with a dedicated subnet for the cluster (elsewhere in this PR), I'd expect the Key Vault to be locked down to that subnet via `network_acls.default_action = "Deny"` plus a `virtual_network_subnet_ids` allow-list, or better, a private endpoint. As written, this vault is more open than the surrounding network topology suggests was intended.

On the positive side, the `azurerm_role_assignment` granting the kubelet identity `Key Vault Secrets User` scoped to just this vault (rather than a broader subscription-level role) is correctly minimal, and using the RBAC-based access model (`rbac_authorization_enabled = true`) rather than the legacy access-policy model is the right choice for a new Key Vault going forward.

Requesting changes on `purge_protection_enabled` and the network ACL default — both are the kind of setting that's cheap to get right now and expensive to fix retroactively once secrets are already flowing through this vault in production.
