A few things stand out about this Deployment manifest that are worth fixing before you run this in a real cluster, and a couple that are just preference.

The biggest issue: you've set `resources.limits.cpu` but not `resources.requests.cpu`, which means the scheduler has no idea how much CPU this pod actually needs and will happily co-locate a dozen of these on one node, and then they'll all throttle simultaneously under load. Requests and limits aren't optional-one-or-the-other — set both, and for CPU specifically consider whether you want a limit at all; a lot of people now recommend leaving CPU unlimited (request only) since CPU throttling under a hard limit tends to cause worse tail latency than letting it burst, whereas memory should always have both request and limit set to the same value to avoid OOM-kill surprises from noisy neighbors.

Second: your `livenessProbe` and `readinessProbe` are pointed at the same endpoint (`/health`) with the same thresholds. That's a common mistake — liveness should only fail when the process is unrecoverable and needs a restart (deadlocked, corrupted state), while readiness should fail whenever the app temporarily can't serve traffic (still warming up, dependency briefly down). If your `/health` handler checks downstream dependencies like the database, a transient DB blip will cause Kubernetes to kill and restart your app pods instead of just pulling them out of the Service endpoints list — which is exactly the wrong response to a transient dependency failure and can turn a 30-second blip into a full restart storm. Split these into a lightweight liveness check (process responds at all) and a readiness check that's allowed to fail independently.

Third, `imagePullPolicy: Always` combined with a mutable `:latest` tag is going to make rollbacks unreliable — if you ever need to roll back a bad deploy, `kubectl rollout undo` will just repull whatever `:latest` currently points to, which may not be the previous version at all. Tag images with the git SHA or a semantic version and reference that explicitly; keep `Always` only if you must, but ideally switch to `IfNotPresent` once you're using immutable tags.

Smaller point: no `terminationGracePeriodSeconds` override and no `preStop` hook, so if this service holds long-lived connections (looks like it might, given the `PORT` env suggests a gRPC service), pods getting cycled during a rolling update will drop in-flight requests abruptly rather than draining. A `preStop` sleep of a few seconds combined with your Service's `readinessProbe` failing first usually smooths that out.

Everything else — labels, the `strategy: RollingUpdate` with sane `maxUnavailable`/`maxSurge`, the `securityContext` with `runAsNonRoot: true` — looks solid and shows you've thought about this before. I'd request changes on the probe split and the requests/limits gap specifically; the rest can go in as a follow-up.
