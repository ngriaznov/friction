Overall this is a solid `react-hook-form` + `zod` setup for the signup form, and I like that validation logic lives entirely in the `zodResolver`-backed schema rather than scattered across `onChange` handlers. A few things I'd change before merging, though.

The async username-availability check is the main concern. You've wired it as a `.refine()` inside the zod schema that calls `fetch('/api/username-available')` directly, which means it runs on every validation pass — including on every keystroke if your mode is `onChange`, which it is here (`mode: 'onChange'` in the `useForm` config). That's an API call per character typed into the username field, with no debouncing. At minimum, debounce the check (300ms is typical), and I'd actually pull it out of the schema entirely and handle it as a separate `useEffect` keyed off the watched username value with its own loading/error state, rather than trying to shoehorn an async network call into synchronous-feeling schema validation. Mixing the two makes error messages harder to reason about — is "username taken" a zod issue or a separate concern? Right now it's ambiguous in the code even though the UI treats it uniformly.

Second, the refine call has no abort/cancellation handling, so it has the same race-condition shape as any un-cancelled async check: if a user types "alice", then quickly changes to "alicia", and the "alice" request resolves after the "alicia" one, you can end up showing a stale availability result. Pass an `AbortController` signal through and cancel on each new keystroke's debounce reset.

On the schema itself: password confirmation is done with `.refine()` comparing `data.password === data.confirmPassword` at the top level, which is correct, but the error is attached via `path: ['confirmPassword']` — good, that's exactly right and a common mistake to skip, so nice catch there.

One correctness issue: the phone number field uses a regex (`/^\d{10}$/`) that assumes a US-only, unformatted 10-digit number, but the input itself doesn't restrict formatting, so a user typing `(555) 123-4567` — which is how most people naturally type a phone number — will fail validation with no indication of what format is expected beyond a generic "invalid phone number" message. Either strip non-digit characters before validating, or give the field an input mask so what's typed matches what's validated. Right now there's a mismatch between what the UI invites the user to type and what the schema accepts.

Small thing: `formState.isSubmitting` isn't used anywhere to disable the submit button, so a slow network allows double-submission via repeated clicks. That's a quick fix — `disabled={formState.isSubmitting}` on the button.

Nice touches: using `formState.errors` destructured per-field rather than a single generic error banner is good for accessibility and usability, and I see `aria-invalid` and `aria-describedby` wired to each field's error message, which a lot of RHF forms skip entirely. Keep that.

Net: functionally close, but the async validation approach needs rework before this is production-ready, and the phone regex will generate real support tickets. Requesting changes on those two; everything else is good.
