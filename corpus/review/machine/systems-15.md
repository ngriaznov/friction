This PR swaps the default global allocator over to `jemalloc` via the `tikv-jemallocator` crate, adding the `#[global_allocator]` attribute in `src/main.rs` and wiring up a `jemalloc-stats` feature that exposes allocator metrics through the existing `/metrics` endpoint in `src/metrics.rs`. The motivation in the description — reducing fragmentation and improving multi-threaded allocation throughput under the service's actual workload — makes sense for a long-running server with lots of small concurrent allocations, and jemalloc is a reasonable, well-trodden choice here rather than something exotic.

The metrics integration itself is done well: you're reading the stats through jemalloc's `mallctl` interface at a fixed interval rather than on every request, which avoids adding allocator-introspection overhead to the hot path, and the exposed metrics (resident, allocated, active, fragmentation ratio derived from active/allocated) are the right set to actually diagnose fragmentation issues if they come up later.

A few things I'd want addressed before merging a change this fundamental to every allocation in the process:

There's no benchmark included. A PR whose entire justification is "faster/less fragmented under our workload" needs numbers, ideally from something closer to production traffic than a microbenchmark, given that jemalloc's advantages over the system allocator are workload-dependent — it can also be a regression for allocation patterns dominated by a few very large allocations, which glibc's malloc already handles reasonably via mmap. Given this repo runs on both Linux and macOS in CI, I'd want to see before/after numbers for both, since jemalloc's win margin over the platform default varies a lot between glibc malloc and macOS's allocator.

Second, this changes memory behavior for every consumer of this crate, including anyone using it as a library rather than the binary — setting `#[global_allocator]` in `main.rs` only affects the binary target, which I think is what's intended here, but worth confirming explicitly in the PR description since it wasn't stated, and worth a comment in the code noting that this is binary-only and deliberately not applied if this crate is ever used as a dependency.

Third, no mention of interaction with existing `Drop` impls or FFI boundaries that might assume the system allocator — specifically, if anything in this codebase passes allocations across an FFI boundary to a C library that frees with its own `free()` (I didn't see one in the diff, but the codebase has an FFI module elsewhere), mixing allocators across that boundary is a use-after-free waiting to happen. Worth a quick audit and a note in the PR if you've already checked and it's clean.

I like the direction and the metrics work is genuinely nice, but I'd want the benchmark numbers before merging — swapping the allocator underneath a production service on vibes rather than measurement is the kind of change that's very hard to attribute a later regression to, six months from now when nobody remembers this PR happened.
