This PR adds idempotency key support to the FastAPI `POST /v1/payments` endpoint, following the Stripe-style pattern: clients send an `Idempotency-Key` header, the handler checks a new `idempotency_keys` table for a prior response before processing, and stores the response after a successful charge. Touches `app/api/payments.py`, a new `app/services/idempotency.py`, and the migration for the new table.

This is a genuinely important endpoint to get idempotency right on, so I read through carefully. The overall shape is correct: look up the key first, if found return the stored response verbatim, if not found proceed with the charge and store the result keyed by `(idempotency_key, request_body_hash)`. Including the body hash in the lookup key, not just the raw key string, is a nice touch I don't always see — it correctly handles the case where a client reuses a key with a different payload, which per the Stripe convention should be treated as a conflict rather than silently returning the old response for a different request.

One real gap: the check-then-act sequence in `idempotency.py` — `existing = get_by_key(key)`, then if `None`, proceed to charge and afterward `save(key, response)` — has a race window between two concurrent requests carrying the same idempotency key arriving close together (which is exactly the scenario idempotency keys are meant to protect against, e.g., a client retrying a request whose response was lost in transit while the original is still in flight). As written, both requests can pass the `get_by_key` check before either has saved a result, and both proceed to charge the card. You need the lookup-and-claim to be atomic — either an `INSERT ... ON CONFLICT DO NOTHING` on the idempotency key up front (before doing the charge) that reserves the slot with a "processing" status, with the second concurrent request seeing the conflict and either waiting or returning a 409/425 to retry shortly, or a `SELECT ... FOR UPDATE` inside a transaction that serializes the two. Given this guards actual money movement, I'd treat this as a blocking issue rather than a nice-to-have.

Second: what happens if the process crashes or the request times out after the charge succeeds but before `save(key, response)` writes the row? The next retry with the same key would see no existing entry and charge again. Reserving the row before charging (as above, with a status column: `processing` → `completed`/`failed`) also fixes this, since a retry that finds a `processing` row past some reasonable staleness threshold can decide to wait, fail closed, or re-check the charge's actual status with the payment provider rather than blindly retrying — worth deciding which of those behaviors you want for the in-flight case explicitly, since right now a retry during a stuck "processing" state isn't handled at all.

Smaller: no TTL or cleanup on the `idempotency_keys` table — Stripe expires idempotency keys after 24 hours; you probably want something similar rather than the table growing unbounded forever, and you'll want a decision on what happens if a client reuses a key after it's expired (treat as new vs. reject).

Good instinct to build this and the body-hash-in-key detail shows real care, but the race condition around concurrent claims needs to be closed before this merges — as-is it doesn't actually prevent the double-charge scenario it's meant to prevent under the exact conditions (near-simultaneous retries) where it matters most.
