This PR adds a `TicketSpinlock` to the `no_std` crate's `src/sync/spinlock.rs`, replacing the plain test-and-test-and-set spinlock that was there before with a ticket-based one for fairness under contention on the target's multi-core configuration. I like ticket locks for this use case — they fix the starvation problem the old CAS-retry lock could have under sustained contention, where a thread that just released the lock can win the next race against a thread that's been waiting — and the implementation is close, but there's an ordering gap I'd want fixed.

`lock()` does `let my_ticket = self.next_ticket.fetch_add(1, Ordering::Relaxed);` and then spins on `self.now_serving.load(Ordering::Relaxed) == my_ticket`. Both should not be `Relaxed`. The load that exits the spin loop needs to be `Acquire`, and the store in `unlock()` that increments `now_serving` needs to be `Release` — otherwise you get a valid ticket ordering (the numbers themselves are correct since `fetch_add` is atomic regardless of ordering) but no happens-before relationship between the critical section the previous ticket-holder ran and the critical section this thread is about to run. On a strongly-ordered target this might never surface in testing, but on anything with weaker memory ordering (and plenty of embedded cores, including many Arm Cortex-M/A configurations depending on what this targets) this is a real bug: the thread acquiring the lock can see stale values for data the previous holder wrote and believed was protected by the lock. Given a spinlock's entire reason to exist is protecting shared data across cores, getting this ordering wrong defeats the purpose while looking like it works.

Separately, `fetch_add` on `next_ticket` also being `Relaxed` is fine as-is — that operation only needs atomicity, not ordering, since the ticket number itself carries no data, only the load in the spin loop and the unlock store need the acquire/release pair.

Smaller note: the spin loop calls `core::hint::spin_loop()` on each iteration, which is correct and good — please don't remove that in a later revision for "simplicity," it matters for power and for not thrashing the interconnect on multi-core spins.

Please fix the load/store orderings to Acquire/Release before merging — this is a correctness bug in the exact property a lock exists to provide, not a style nit, even though the ticket-fairness logic itself is otherwise implemented correctly.
