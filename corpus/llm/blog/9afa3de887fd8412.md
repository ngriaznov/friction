# We left Gerrit for GitHub PRs, and I miss about three things

We ran Gerrit for four years. Five engineers, one monolith, one very well-behaved review culture. Last quarter we moved code review to GitHub pull requests. I want to write down what we actually gained and what I still grumble about, because most posts on this topic are written by people who clearly never liked one of the two tools.

## Why we moved

The honest answer is not "Gerrit is bad." It's that Gerrit was the only piece of infrastructure we still self-hosted, and it was owned by exactly one person — me — who had been on call for it since 2021. Twice a year the JVM would decide it needed more heap, or a plugin would break on upgrade, and I'd spend a Saturday on it. Our code was already on GitHub for CI and releases. Reviews were the last thing pinning the old box in place.

The second reason was hiring. We onboarded two people in six months, and both spent their first week fighting `git push origin HEAD:refs/for/main` and the Change-Id hook. They'd both reviewed code professionally for years. Neither had used Gerrit. That's a real cost, and at five people it's a big fraction of the team's ramp time.

## What got easier

Everything social. Comments on PRs get read, because GitHub emails look like the emails people already triage. Our designer, who is not an engineer, now leaves comments on frontend changes. That never happened on Gerrit — she had an account and never logged in.

Linking also got easier in a way I underestimated. Issues, PRs, commits, and CI runs all live in one place and cross-reference automatically. On Gerrit we had a wiki page explaining how to correlate a change number with a Jira ticket. That page is now deleted, and nobody has missed it.

CI setup collapsed from a Jenkins job plus a Gerrit trigger plugin plus a verification label into a YAML file in the repo. I don't love GitHub Actions, but I love that it's one thing instead of three.

## What I miss

**Per-commit review.** This is the big one and I don't think GitHub has an answer. In Gerrit, a change is a commit. You review a commit, it gets amended, you see the diff between patchsets, and the thing that lands is the thing you approved. GitHub reviews a branch. Force-pushes wipe review context, "changes since your last review" is approximate, and the squashed merge commit is not an artifact anyone ever looked at directly. We've compensated with a strict "small PRs" norm, which is fine, but it's a norm rather than a property of the tool.

**Relation chains.** Stacking dependent changes in Gerrit is native. In GitHub it's PRs targeting other PRs, and reviewing the third one in a stack means mentally subtracting the first two. There are third-party tools for this. We tried one for a month and dropped it.

**The scoring model.** Gerrit's +1/+2 distinction let a teammate say "this looks fine to me but I'm not the right approver" without ambiguity. GitHub gives you approve, request changes, or comment. We approximate the middle ground with a comment saying "non-blocking LGTM," which works because we're five people who trust each other and would obviously not scale.

## Would I do it again

Yes, though with less confidence than I had going in. The migration itself was two days of scripting to import open changes and a week of everyone typoing `git review`. The tool is worse at reviewing code and better at everything surrounding reviewing code, and it turns out that at our size the surrounding stuff dominates.

If we were twenty people on a shared monolith with long-lived stacks, I'd have argued to stay.
