# The bug that only existed on Tuesdays at 2 p.m.

For about six weeks our warehouse inventory service would crash roughly once a day, always during the afternoon picking surge, never in staging, and never under any load test I could construct. The stack traces were garbage — a mutex lock deep inside libstdc++, or sometimes a jump into an address that was obviously not code. Classic memory corruption. The kind of bug where you start doubting the compiler.

Here is how it actually went, including the two days I spent chasing the wrong thing.

## What the service does

It tracks on-hand and reserved quantities per SKU across a few hundred thousand SKUs. Handler threads take a request ("reserve 3 of ABC-119 for order 88214"), find the SKU's record, and adjust counters under a per-SKU lock. Per-SKU locking rather than one big lock, because contention on hot SKUs was the whole reason the service existed.

The lock table looked like this:

```cpp
std::unordered_map<SkuId, std::unique_ptr<SkuEntry>> table_;
std::shared_mutex table_mutex_;
```

Each `SkuEntry` held a `std::mutex` plus the counters. A handler took a shared lock on `table_mutex_`, looked up the entry, released the shared lock, then locked the entry's own mutex. Textbook.

## The wrong lead

My first suspect was the reservation counter. There was a fast path that read `available_` atomically with `memory_order_relaxed` to reject obviously-impossible requests before bothering with the lock. Check-then-act, and the check was unsynchronised. I found it, I stared at it, I convinced myself it was the bug, and I fixed it.

It was a real bug. It could oversell inventory by a few units under contention. It was not causing the crashes. I know that because the crashes continued, and because after I fixed it the crash rate did not change at all — which, in hindsight, was the most useful data point of the week. If your fix doesn't move the number, you fixed something else.

## Getting the machine to tell me

Two tools mattered.

**ThreadSanitizer**, once I stopped trying to reproduce the load and instead just ran the production binary under TSan on a canary box during the afternoon peak. This costs about 5x in throughput, which we could absorb on one instance out of twelve. Within forty minutes TSan gave me a report: a write to a `std::mutex`'s internal state racing with a read of the same bytes, from two threads, one of which was inside `~SkuEntry`.

**rr**, to actually understand it. TSan told me *what* raced; it did not tell me why an entry was being destroyed while somebody was using it. I recorded the canary under rr, replayed the failure, and set a hardware watchpoint on the entry's memory. Reverse-continue from the destructor landed me exactly where I needed to be.

## The actual bug

There was an eviction path I had entirely forgotten about. To keep memory bounded, a background thread periodically dropped `SkuEntry` objects for SKUs that had not been touched in an hour. It took an exclusive lock on `table_mutex_` and erased the map entry, destroying the `SkuEntry` and its mutex with it.

Now look at the handler sequence again:

1. Take shared lock on `table_mutex_`.
2. Look up entry, keep the raw pointer.
3. **Release shared lock.**
4. Lock `entry->mutex`.

Between steps 3 and 4 the entry can be evicted. The handler then locks a `std::mutex` that has already been destroyed. That is undefined behaviour with a very wide blast radius: sometimes it works, sometimes it corrupts the allocator, sometimes it hangs.

Why only during the afternoon surge? Because eviction only had anything to evict once the table had grown large enough, and the window between steps 3 and 4 only got hit when the machine was loaded enough for the handler thread to be descheduled right there. Both conditions came together during the picking rush. My load tests hammered a small SKU set, so the evictor never ran.

## The fix

Two changes.

First, entries became `std::shared_ptr<SkuEntry>`, and the lookup returns a `shared_ptr` copy made *while still holding* the shared lock on the table. The evictor can erase the map entry whenever it likes; the object stays alive until the last handler using it is done. This is refcount overhead on every lookup, and it cost us about 3% throughput. Worth it.

Second, the evictor now checks `use_count() == 1` before erasing, so it skips entries in active use rather than merely deferring their destruction. That is advisory, not a correctness guarantee — the `shared_ptr` is what makes it correct — but it keeps eviction from constantly thrashing hot SKUs.

## What I'd do differently

Run TSan in production earlier. I spent two days trying to build a reproduction and forty minutes getting the answer once I stopped. Load tests that don't include your background maintenance threads aren't load tests of your system.

Also: the relaxed-atomic fast path is still gone. Different bug, still a bug.
