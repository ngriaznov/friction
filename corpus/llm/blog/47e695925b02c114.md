# Our commit message house style

There are five of us on this team and we've all worked somewhere with a commit message policy nobody followed. So this isn't a policy. It's a description of what we actually do, written down so new people don't have to guess.

## The rule

A commit message answers one question: **why did this change happen?** The diff already says what changed. If your message is a prose translation of the diff, delete it and write something else.

Concretely, that means:

- Subject line under about 70 characters, imperative mood, no trailing period.
- A blank line, then a body if the change needs one. Wrap at 72.
- The body explains the reason, the alternative you rejected, or the thing that will bite the next person. Not the mechanics.
- Link the ticket if there is one, at the bottom, on its own line.

We don't enforce a prefix taxonomy. We tried `feat:` / `fix:` / `chore:` for a quarter and mostly ended up arguing about whether a refactor that fixed a bug was a `fix`. Nobody missed it after we dropped it.

## Two real examples

From our own history, before and after we started paying attention.

**Before:**

```
fix bug in date handler
```

**After:**

```
Parse invoice dates as UTC, not local time

Billing runs at 23:30 in the scheduler's local timezone. For
customers in UTC+2 that pushed the parsed date to the next day,
so invoices dated the 31st landed in the following month's
report and the totals never reconciled.

We parse as UTC everywhere now. Display formatting still uses
the customer's timezone.

REV-1184
```

The first version told you nothing you couldn't get from the diff. The second one is the reason someone found this bug in twenty minutes instead of two days, six months later.

**Before:**

```
update deps
```

**After:**

```
Pin http-client to 4.2.1

4.3.0 changed the default connect timeout from 30s to 5s. Our
partner API routinely takes 8-12s to hand back a first byte, so
the upgrade turned a slow endpoint into a failing one.

Unpin once we've moved that call behind the queue worker.
```

That last line is the part that matters. It's a note to whoever eventually wonders why we're three minor versions behind, and it saves them the archaeology.

## Why we bother

Mostly for `git log -S` and `git blame`. When you're staring at a strange line of code at 4pm on a Friday, the commit message is the only place the author's reasoning survives. Pull request descriptions rot when the repo moves hosts. Slack threads are gone in ninety days. The commit message is the one artifact that travels with the code forever.

Write it for the person doing the archaeology. Some of the time, that person is you.
