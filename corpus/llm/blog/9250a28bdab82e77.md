# Postmortem: 40 minutes of write failures from an ALTER TABLE

On March 4th we took the `subscriptions` table offline for writes for roughly 40 minutes during what was supposed to be a routine schema migration. Every checkout attempt in that window failed. This is the writeup we circulated internally, lightly edited for publication.

## Impact

Between 14:12 and 14:52 UTC, all writes to `subscriptions` blocked. Downstream that meant:

- 1,840 checkout attempts returned a 500. We do not know how many of those users came back.
- Plan upgrades and cancellations failed the same way.
- Reads were unaffected, so the app looked healthy to anyone browsing. That made the blast radius less obvious than it should have been.

Billing itself was never at risk; the payment processor holds authorization state, and nothing was double-charged.

## Timeline

**14:10** — Deploy pipeline starts release `2024.3.4-1`, which includes migration `0287_add_trial_source`.

**14:12** — The migration issues `ALTER TABLE subscriptions ADD COLUMN trial_source varchar(64) NOT NULL DEFAULT 'unknown'`. Writes begin queuing behind the resulting `ACCESS EXCLUSIVE` lock.

**14:14** — Error rate alert fires on the checkout service. First responder acknowledges.

**14:17** — Responder finds the 500s but attributes them to the payment processor, since the errors surface as timeouts in the payment client. Roughly nine minutes go into that dead end.

**14:26** — A second engineer notices the deploy timestamp lines up and pulls up `pg_stat_activity`. The `ALTER TABLE` is visible, along with a long queue of waiting statements.

**14:31** — Discussion about whether to kill the migration. Nobody is confident about what a half-applied `ALTER` leaves behind, so we wait.

**14:52** — The migration commits. The queue drains in under two seconds. Error rate returns to baseline.

**15:20** — Incident closed.

## Root cause

The immediate cause is unglamorous: our Postgres version rewrites the entire table when you add a `NOT NULL` column with a default. `subscriptions` has 61 million rows. The rewrite took 40 minutes and held an exclusive lock the whole time.

We had actually known this. There is a line in our migration checklist about avoiding defaults on large tables. The checklist lives in a wiki page that nobody reads during a normal Tuesday deploy.

The more interesting cause is that nothing in our tooling knew the difference between a migration that touches 200 rows and one that touches 61 million. Migrations ran automatically as a pipeline step, with the same treatment regardless of table size. The author of `0287` had tested it against a development database seeded with about 4,000 subscriptions, where it completed instantly.

And the nine minutes we lost chasing the payment processor were a monitoring failure. We had no alert on lock wait time, so the signal that would have pointed straight at the cause was not being watched.

## What we changed

**Migrations no longer run inside the deploy pipeline.** They are a separate, explicitly triggered step. This is more annoying and we accept that.

**A lint step blocks risky patterns.** We added `squawk` to CI, configured to fail on adding a `NOT NULL` column with a default, adding a non-concurrent index, and changing a column type, when the target table exceeds one million rows. Row counts come from a nightly snapshot of `pg_class.reltuples`. The check can be overridden with an annotation in the migration file, which requires a second approver.

**Lock waits are alerted.** Any lock held longer than 30 seconds on a table in our top-20 list by size pages the on-call engineer, with the blocking query in the alert body. We tested this by reproducing the incident on a staging clone.

**We wrote down the kill decision.** The 20 minutes spent debating whether to cancel the migration should not have to happen again. There is now a short runbook: for a DDL statement inside a transaction, `pg_cancel_backend` is safe and rolls back cleanly. It says so in three sentences, with the caveat that `CREATE INDEX CONCURRENTLY` is the exception because it runs outside a transaction and leaves an invalid index behind.

The correct version of the original migration, which we shipped two days later, adds the column as nullable, backfills in batches of 10,000, and adds the constraint afterward with `NOT VALID` followed by a separate `VALIDATE CONSTRAINT`. Three migrations instead of one. It took eleven minutes and locked nothing.
