# Why We Left Gerrit for GitHub Pull Requests

For three years, our five-person backend team ran code review through Gerrit. It was the tool two of our early engineers had used at a previous job with a much larger org, and it came with genuinely powerful review semantics: every commit was its own reviewable unit, patch sets tracked the full history of a change as it evolved, and the scoring system (+2/-2/-1/+1) gave reviewers a precise, unambiguous way to signal "this is mergeable" versus "I have concerns." We liked all of that. We just didn't like much else.

## What Gerrit actually cost us

The friction showed up in onboarding first. Every new hire needed a walkthrough of `git push origin HEAD:refs/for/main`, Change-Ids in commit messages, and a review UI that looked and behaved like nothing else in their toolchain. We wrote an internal wiki page just to explain the mental model, and people still got tripped up rebasing a change and accidentally creating a duplicate patch set instead of amending the existing one.

The bigger cost was integration. Our CI system, our issue tracker, and our deploy tooling all had first-class GitHub support and only bolted-on or community-maintained Gerrit support. We were maintaining a webhook relay just to get Gerrit review events into Slack. Every new tool we wanted to try — a bot for flagging stale PRs, a code-owners enforcement action, a simple review-assignment round robin — either didn't support Gerrit at all or required us to write and maintain the integration ourselves. For a five-person team, that maintenance burden was disproportionate to the benefit.

## What we missed after switching

We won't pretend the migration was purely upside. Gerrit's per-commit review model is genuinely better for reviewing a stack of small, logically separate changes — GitHub's pull request model flattens everything into one diff per PR, and reviewing a large PR commit-by-commit is clunkier than Gerrit ever was. We also lost the strict "every comment must be resolved" enforcement; GitHub lets you merge with open conversation threads unless you bolt on a separate check for it, which we ended up doing with a required status check that fails if any review thread is unresolved.

## What got easier

Everything downstream of review got noticeably smoother. Branch protection rules, required status checks, and CODEOWNERS files gave us most of the enforcement guarantees we'd built custom tooling for in Gerrit, for free. New engineers were productive on day one because they already knew the PR workflow from personal projects. And because nearly every third-party tool we evaluated afterward — dependency bots, security scanners, deploy previews — assumed GitHub PRs as the integration point, we stopped writing glue code entirely.

Six months in, the team's verdict is unanimous: GitHub PRs are a worse code review tool in isolation, but a much better fit for a small team that doesn't have the headcount to maintain custom tooling around a more powerful but more demanding system. We'd make the same call again.
