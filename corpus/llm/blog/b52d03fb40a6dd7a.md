# We Killed Our Internal RPC Framework

For about six years, every service we ran talked to every other service through something called Conduit. It was ours. Two engineers wrote it in 2018 because the options at the time didn't fit how we deployed, and for a while it was genuinely good: a schema file, a code generator, typed clients in three languages, connection pooling that did the right thing under load.

Last quarter we deprecated it. Everything new is plain REST over HTTP, JSON bodies, OpenAPI specs. Roughly forty services will be migrated by the end of the year.

People keep asking whether this was a "we hate our own code" decision. It wasn't. Conduit worked. The problem was that it cost more to keep working than it was worth.

## What it actually cost

The maintenance bill was never one big number. It was a hundred small ones.

The Python client lagged the Go client by about eight months on every feature, because the person who cared about Python left and nobody replaced them. When we adopted a new tracing vendor, someone had to write a Conduit interceptor by hand — the vendor shipped middleware for standard HTTP and for gRPC, and neither helped us. Same story for the service mesh evaluation we abandoned in 2022, largely because getting mTLS to work with Conduit's custom framing would have meant maintaining a fork of the sidecar.

Then there was onboarding. A new backend hire could not debug a request with curl. They could not paste a call into Postman. They had to install our code generator, which required a specific protoc version, which required a specific Python, and the setup doc was four screens long and wrong in two places. Every new engineer lost a day to this, and the ones who came from companies with normal HTTP stacks kept asking why, and we kept not having a satisfying answer.

The final push came from outside. We started selling an API to customers, which had to be REST. So we built an HTTP edge layer that translated inbound REST into Conduit calls. Now we were maintaining a bespoke RPC framework *and* a translation layer, and every new endpoint had to be defined twice.

## What we gave up

I want to be honest that this wasn't free.

Conduit's generated clients caught type mismatches at compile time. JSON over HTTP does not, and we've shipped at least three bugs that Conduit would have blocked — a field renamed on the producer side, a number that became a string, an enum that grew a variant nobody handled. We've clawed most of that back with strict OpenAPI specs and generated clients from those specs, but it's a weaker guarantee and the generation step is opt-in per service, which means it isn't universal.

We also lost some throughput. Conduit's binary framing on a persistent connection beat JSON over HTTP/1.1 by a comfortable margin on our highest-volume internal path. We measured about 18% more CPU on the serialization side after migration. For one service, that mattered enough that we kept it on Conduit and will move it last, once we've got HTTP/2 keep-alives tuned properly.

## The migration plan

We didn't do a big-bang rewrite, and I'd argue nobody should.

Every Conduit service got an HTTP handler mounted alongside the existing RPC handler, sharing the same underlying service methods. That's a small, safe change — the business logic doesn't move, only the transport in front of it. Services published both interfaces for as long as they needed to.

Callers then migrated one at a time, on their own schedule, behind a per-caller config flag. We built a dashboard from access logs showing, for each service, how many requests still arrived over Conduit and from whom. That dashboard did more to drive the migration than any amount of nagging in Slack, because team leads could see their own name on a list.

Once a service's Conduit request count hit zero and stayed there for two weeks, the owning team deleted the RPC handler and the schema file. Fourteen services have done this so far.

New services simply cannot use Conduit — the service template doesn't include it, and the code generator now prints a deprecation warning that says so.

## Would I do it again

Yes, but I'd do it two years earlier. The signal was clear back when we couldn't adopt the service mesh: we had built something that made every off-the-shelf tool harder to use. That's the real cost of a custom protocol, and it compounds quietly until one day you notice you're paying it everywhere.
