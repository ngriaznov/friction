# We Killed Our Feature Branches. Here's What Broke First.

For about three years our team ran what I'd call textbook GitFlow, except nobody had read the textbook recently. Feature branches lived for two to six weeks. Release branches got cut on Thursdays. Merging anything into `develop` after a long absence meant an afternoon of resolving conflicts in files you hadn't opened since the branch was created.

The breaking point was a payments refactor that took eleven weeks. When it finally merged, it conflicted with two other in-flight branches, and the person who wrote it had rotated to another team. We spent nine days making it green again. Nine days of work that produced zero customer-visible change.

So we went trunk-based. Everyone commits to `main`, several times a day, behind feature flags. That's the whole model. Getting there took about four months.

## The flag system came first, and that was correct

We didn't touch branching policy until we had a flag service we trusted. This turned out to matter enormously. The first thing anyone asks when you say "commit unfinished code to main" is "what stops it from running?" If the answer is hand-waving, nobody moves.

We used an off-the-shelf provider rather than building our own. The important properties were: flags evaluate locally from a cached ruleset (no network call in the request path), flags default to off if the cache is cold, and every evaluation is logged so we can prove a flag was actually off in production. That last one won more arguments than the other two combined.

## Half-finished features in production are fine, until the schema moves

Application code behind a flag is easy. You write the new code path, it's dark, nothing calls it. The hard part is everything that isn't application code.

Database migrations were the first real fight. You cannot flag a dropped column. We landed on a rule that every schema change is decomposed into expand-then-contract: add the new column, dual-write to both, backfill, switch reads behind the flag, and only then — in a separate change, weeks later — drop the old one. This is slower. It is meaningfully more work per migration. It's also the only thing we found that actually works, and it had the side effect of making rollbacks safe, which we hadn't been able to say before.

The second fight was partially-built UI. A half-implemented settings page is not just invisible when flagged off; it's a route that might still be reachable if someone types the URL, an entry in a nav config, a string in the translation files that a translator will ask about. We eventually wrote a lint rule that flags any new route not registered in the flag manifest.

## What we didn't anticipate

Flag debt is real and it accumulates fast. Six months in, we had 140 flags, of which maybe 30 were doing anything. Dead flags are worse than no flags — they make code unreadable and they make people nervous about deleting branches of logic they don't understand.

We now require an expiry date on every flag at creation. When it passes, a bot opens a PR removing the flag and inlining whichever branch is live. If nobody merges it in two weeks, it goes on the team's board as a real ticket. Roughly 80% of those PRs merge without discussion.

## Was it worth it

Time from first commit to production went from a median of nine days to about four hours. Merge conflicts are essentially gone as a category of work.

But be honest with yourself about the cost. Expand-contract migrations are more work. Flag hygiene is more work. What you're buying is the elimination of a specific, expensive failure — the eleven-week branch — and if you don't actually have that failure, you might be paying for nothing.
