We needed rate limiting on our public API a while back — enough abuse from a handful of misbehaving integration partners that "just ask them nicely to slow down" stopped being a viable strategy — and I want to walk through why we landed on token bucket over the sliding-window approach we tried first, because the reasons only became obvious once we'd actually built the alternative and watched it misbehave.

Sliding window looked appealing on paper. The idea is straightforward: for each API key, keep a log of request timestamps, and on each new request, count how many timestamps fall within the trailing window — say, the last sixty seconds — and reject if that count exceeds the limit. It's precise, it doesn't have the fixed-window problem of allowing a burst right at a window boundary, and it's easy to explain to a partner asking why they got a 429. We implemented it with a Redis sorted set per API key, timestamps as both score and member, trimming anything older than the window on each request with `ZREMRANGEBYSCORE` before counting.

The problem showed up under real load, not in testing. Every single request requires a read, a write to remove expired entries, and a count, all against the same sorted set key, and for our higher-volume partners making dozens of requests per second, that sorted set was getting hammered with concurrent modifications. We were seeing lock contention and, worse, an unbounded-feeling memory footprint per key during traffic spikes, since a burst of legitimate traffic right at the start of a window means the sorted set temporarily holds every timestamp in that burst before any of them age out. It worked, but it felt like we were paying a lot of operational complexity for a guarantee — exact request counts in an exact trailing window — that our partners didn't actually need. Nobody was going to notice or care about the difference between a rate limit enforced over exactly the trailing sixty seconds versus one that allows some bounded burst above the stated limit.

Token bucket gave up that precision and got a much simpler, much cheaper implementation in return. Each API key gets a bucket with a maximum capacity — say, 100 tokens — that refills at a fixed rate, say 10 tokens per second, up to that cap. Every request consumes one token; if the bucket's empty, the request gets rejected. The entire state per key is two numbers: current token count and a last-refill timestamp. We store both in a single Redis hash per key and do the refill calculation lazily on read — compute elapsed time since the last timestamp, add the appropriate number of tokens capped at the bucket size, then check and decrement in one atomic Lua script to avoid a race between two concurrent requests both reading the same stale token count.

```lua
local tokens = tonumber(redis.call('HGET', KEYS[1], 'tokens')) or capacity
local last = tonumber(redis.call('HGET', KEYS[1], 'last')) or now
local elapsed = now - last
tokens = math.min(capacity, tokens + elapsed * refill_rate)
if tokens < 1 then
  return 0
else
  redis.call('HSET', KEYS[1], 'tokens', tokens - 1, 'last', now)
  return 1
end
```

That's the whole algorithm, and it runs as a single round trip to Redis per request instead of the read-trim-count-write pattern the sorted set needed. It also naturally allows short bursts up to the bucket capacity, which turned out to be a feature rather than a bug once we thought about it honestly — legitimate integrations often send a small burst on startup or after a reconnect, and token bucket absorbs that gracefully instead of rejecting the first several requests the way a stricter window-based limiter would.

We did lose something: token bucket doesn't give partners a clean, easily-explained guarantee like "at most 100 requests per minute, measured exactly." What we tell partners now is "100 requests per minute average, with bursts up to 100 allowed," which is a slightly fuzzier promise but has been enough for every partner conversation we've actually had. Given the operational headache the sorted set version caused us, that was an easy trade to make in hindsight, even though at the time it felt like we were giving up rigor for convenience.
