This one took me the better part of three weeks to run down, and I'm writing it up mostly so future-me has something to search for the next time memory usage on a Node process quietly climbs for no reason anyone can explain.

The worker in question processes incoming webhook events from a handful of third-party integrations — think payment providers, shipping carriers, that sort of thing — normalizes them, and writes them into our main database. It's a long-running process, no serverless involved, restarted maybe once a week by our deploy pipeline and otherwise expected to just sit there and chew through events forever. Our monitoring first flagged it because the memory graph for that service had stopped looking like the sawtooth pattern every other Node service in our fleet has — the one where garbage collection pulls memory back down every few minutes — and instead looked like a staircase, climbing steadily with no drops, over about four days until the process got OOM-killed by Kubernetes and restarted.

My first instinct was that it was a straightforward buffering problem — maybe we were accumulating some array of events that never got flushed. I added some crude logging around the sizes of our main in-memory structures and let it run for a day. Nothing. The structures I was watching stayed flat while total process memory kept climbing, which told me the leak was somewhere I wasn't looking, probably something the V8 heap snapshot wouldn't even show me directly if it was off-heap.

That sent me to `--inspect` and Chrome DevTools' memory profiler, taking heap snapshots a few hours apart and diffing them. This is where things got interesting: the diff kept surfacing a growing number of retained `EventEmitter` listener objects, specifically on an internal event bus we use to fan out normalized webhook events to a few different downstream handlers — one for the database write, one for a metrics counter, one for an audit log. The count of listeners on one particular event name was growing linearly with uptime, roughly matching the number of distinct webhook sources we'd seen since the last restart.

That was the thread to pull. Digging into the handler registration code, I found that every time we saw a webhook from a source we hadn't seen in the current process lifetime, we spun up a per-source handler object to manage some source-specific normalization logic, and that handler's constructor subscribed itself to the shared event bus to listen for a "flush" event used for periodic batching. The bug was that we created a new per-source handler object on every single event from that source, not just the first one — a caching check that was supposed to reuse an existing handler had an off-by-one in a Map key that included a timestamp, so it always missed. Each new handler object subscribed a new listener to the bus and the old handler objects, and their listeners, were never cleaned up, because nothing ever called `removeListener`. Since our event bus was a Node `EventEmitter` with no max-listener ceiling override, it happily accumulated thousands of orphaned listeners, each one closing over its own handler object, which closed over buffers of recent event data, which closed over God knows what else in the chain.

The fix ended up being two changes. First, the actual cache-key bug, so we stopped creating a new handler per event. Second, and this felt like the more important one long-term, I added an explicit `removeListener` call in a cleanup path that fires whenever a source handler is genuinely being replaced or expired, so the leak couldn't quietly come back in a different form if someone touched this code later without understanding the pattern. I also added a metric for `emitter.listenerCount()` on the shared bus, sampled every minute, specifically so this class of bug shows up as a slow, visible climb the next time instead of taking three weeks of heap snapshot archaeology to notice.

The process has been running steady for six weeks since. Memory graph is back to its normal sawtooth. The thing that still bugs me is how long it took to even suspect event listeners — I went looking for buffers and queues first because that's the leak I'd seen before, and it took actually looking at the heap snapshot diff, not just guessing based on past experience, to find the real culprit.
