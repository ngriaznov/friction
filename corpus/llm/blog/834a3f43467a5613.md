# The worker that ate 40MB a day

Our ingest worker is a boring piece of software. It pulls messages off a queue, normalizes them, writes them to Postgres, and acknowledges. It had been running more or less untouched for a year and a half. Then in March it started getting restarted by the orchestrator every few days, and I lost about two weeks to finding out why.

## The symptoms

The first sign was not a crash. It was a graph. Our resident memory chart for the worker pool had, over the previous month, developed a very tidy sawtooth: a slow linear climb over roughly four days, a vertical drop, and then the climb again. The drops lined up exactly with OOM kills. Four days at about 40MB a day, and the container hit its 512MB limit.

Nobody had noticed earlier because nothing visibly broke. The restart was clean, the queue redelivered whatever was in flight, and throughput dipped for about eleven seconds. If our platform team hadn't started paging on restart counts, this could have gone on indefinitely.

Two things about that sawtooth were useful immediately. It was *linear*, not stepped, which suggested something accumulating per unit of work rather than a handful of large allocations. And it was suspiciously stable — the same slope every cycle regardless of time of day, which meant it tracked message volume, not wall-clock time.

## What didn't work

I spent the first several days doing the obvious wrong thing, which was reading code and guessing. I found three plausible culprits: a `Map` used as a dedupe set that I thought was unbounded (it wasn't — it had a TTL sweep I'd forgotten about), a logging transport that buffered on backpressure, and a cache of compiled schema validators keyed by tenant. I "fixed" the validator cache by adding an LRU bound. The slope did not change.

This is the part of the story where I wish I'd said "stop guessing" a week earlier.

## Heap snapshots

The thing that actually worked was embarrassingly standard. I started the worker with `--inspect`, let it run against a replayed sample of production traffic until it had processed a few hundred thousand messages, and took three heap snapshots: one at startup, one after 100k messages, one after 300k. Then I loaded them into Chrome DevTools and used the comparison view between snapshot 1 and snapshot 3.

The comparison view sorts by delta, and the delta was not subtle. `#Delta` for one constructor was in the hundreds of thousands where everything else was in the dozens. The constructor was, of all things, our own `MessageContext` class — a small per-message object holding a trace ID, the raw payload, and a few timing fields.

Hundreds of thousands of live `MessageContext` objects, when there should have been at most a few dozen in flight at any moment.

## Retainers

DevTools will show you the retainer path for any object, which is the chain of references keeping it alive. For one of those contexts the path was:

```
MessageContext
  <- context (in closure)
  <- listener
  <- _events.drain
  <- PoolWrapper
```

`PoolWrapper` is our thin wrapper around the database connection pool. It's a singleton. It lives forever. And somewhere in the message handler, something was attaching a `drain` listener to it.

The code was three lines, and I had written them:

```js
async function handle(msg) {
  const ctx = new MessageContext(msg);
  pool.on('drain', () => metrics.poolDrained(ctx.traceId));
  // ...
}
```

Every message added a listener. Every listener closed over that message's context. Nothing ever removed them. The pool object held the whole chain, and each context held the raw payload, which for our traffic averages a bit under 400 bytes. Multiply by roughly 100,000 messages a day and you get — near enough — 40MB a day.

The other thing this explains is why we never saw a `MaxListenersExceededWarning`. Someone had set `pool.setMaxListeners(0)` during an unrelated incident two years ago to silence a noisy warning. That warning was Node telling us about this exact bug class, and we had turned it off.

## The fix

The fix was to not do that. The metric didn't need per-message context at all — a drain event is a property of the pool, not of whichever message happened to be in flight when it fired. One listener registered at startup, incrementing a counter. Four lines deleted, two added.

Memory has been flat at 180MB for four months.

## What I'd tell past me

Take the heap snapshot first. The comparison view answered in twenty minutes a question I'd been guessing at for a week, and it would have answered it on day one just as well.

Also: if a runtime is warning you about something, and your response is to turn off the warning, write down why. We didn't, and it cost us.
