# The One-Page Design Doc That Fixed Our Planning Problem

We are six engineers. For most of our first two years we planned work in Slack threads and a shared whiteboard, and it mostly worked, in the way that mostly-working things do — right up until it didn't.

About eighteen months ago we started requiring a design doc for anything expected to take more than a day. Not an RFC process, not a review board. A single page, written before the first commit, in a shared folder anyone can read.

## The template

Five headings. That's the whole thing.

**Problem.** What is broken or missing, described in terms a support person would recognize. If you can't write this without naming a technology, you probably started from a solution.

**Why now.** What changed to make this worth doing this quarter instead of next year. This section kills more proposals than any other, and that is a feature.

**Approach.** How you plan to build it, in enough detail that a teammate could argue with you. Two or three paragraphs. Diagrams welcome, not required.

**What we're not doing.** Explicit non-goals. This is the section people skip and the section that saves the most time later, because it's where scope creep gets pre-emptively named.

**Open questions.** Things you genuinely don't know yet. A doc with an empty open-questions section is usually a doc written after the fact.

There's no approval step. You write it, drop the link in the team channel, and wait a day. If nobody comments, you build it. If someone comments, you talk. Maybe a third of docs get substantive pushback, and roughly half of those change the plan.

We deliberately did not add a template section for timelines, staffing, or success metrics. Every time someone has proposed adding one, the doc got longer and fewer people read it. The point is that it fits on a screen.

## The project that convinced us

The template exists because of a rate limiter.

We were getting hammered by a handful of API clients doing bulk exports, and one engineer picked up "add rate limiting" as a two-day task. It seemed obvious enough not to need a doc. Everyone agreed rate limiting was good. Nobody wrote down what "rate limiting" meant.

He built a per-IP token bucket in the edge proxy. Reasonable design, cleanly implemented, shipped on a Thursday.

On Friday our largest customer's integration started failing. They ran everything through a single NAT gateway, so all forty of their services shared one IP and collectively blew through the limit in seconds. We turned it off. Then we discovered that the actual abusive traffic wasn't concentrated by IP at all — it was one API key spread across a rented proxy pool, which per-IP limiting was structurally incapable of catching.

Two days of work, four days of firefighting, and a rebuild against API keys with per-plan quotas. The rebuild took a week.

Every question that would have caught this is one the template asks. *What is broken* — abusive bulk exports from one account, not from one address. *What we're not doing* — we weren't trying to stop distributed attacks, so why were we reaching for a network-layer tool? *Open questions* — how do our biggest customers' networks actually look from our side?

None of that requires seniority or process. It requires ten minutes and a blank page before the branch gets cut. That turns out to be the hard part.
