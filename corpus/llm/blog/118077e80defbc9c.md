A couple of months ago a contractor on our team pushed a commit that included a live AWS secret key, hardcoded in a config file that was supposed to read from an environment variable. It sat in our repo for about four hours before anyone caught it during code review, and by the time we rotated the key we'd already seen a handful of suspicious API calls from an IP range we didn't recognize. Nothing catastrophic happened — the key only had access to a couple of S3 buckets with nothing sensitive in them — but it was the kind of scare that makes you actually go build the thing you'd been meaning to build for a year.

So I wrote a pre-commit hook. Nothing fancy, no external service, just a shell script that runs before every commit and greps the staged diff for patterns that look like secrets.

The core of it is a set of regexes for the usual suspects: AWS access keys (`AKIA[0-9A-Z]{16}`), AWS secret keys (a 40-character base64-ish string near the word "secret"), generic API key assignments (`api_key\s*=\s*['"][A-Za-z0-9]{20,}`), and private key headers like `-----BEGIN PRIVATE KEY-----`. It runs `git diff --cached` and checks only what's actually staged, not the whole working tree, so it doesn't choke on unrelated files sitting around dirty.

```bash
#!/bin/sh
PATTERNS='AKIA[0-9A-Z]{16}|-----BEGIN (RSA |EC )?PRIVATE KEY-----|(?i)(api|secret)[_-]?key["\047]?\s*[:=]\s*["\047][A-Za-z0-9/+]{20,}'

MATCHES=$(git diff --cached -U0 | grep -E "^\+" | grep -Ev '^\+\+\+' | grep -EP "$PATTERNS")

if [ -n "$MATCHES" ]; then
  echo "Possible secret detected in staged changes:"
  echo "$MATCHES"
  echo "Commit blocked. Use 'git commit --no-verify' to override."
  exit 1
fi
```

It's deliberately dumb. I looked at tools like git-secrets and truffleHog first, and they're more thorough, but I wanted something the whole team could read in thirty seconds and understand exactly what it does and doesn't catch, rather than a black box that occasionally cries wolf for reasons nobody can debug. The `--no-verify` escape hatch is intentional too — there are legitimate false positives, like test fixtures with fake-looking keys, and I'd rather let people override with a conscious decision than have them disable the hook entirely out of frustration.

We distribute it through a `scripts/install-hooks.sh` that symlinks it into `.git/hooks/pre-commit` on setup, since Git doesn't version hooks by default. I added a line to our onboarding doc, and more usefully, a CI job that runs the same grep against the full diff on every pull request, so even someone who skipped local setup or committed with `--no-verify` gets caught before merge.

It's caught four real secrets since I added it, three of them mine. Turns out the person who wrote the hook is not immune to pasting a Stripe test key into a local `.env.example` and staging it by accident. That's honestly the best endorsement I can give it — it's saved me from myself more than anyone else.
