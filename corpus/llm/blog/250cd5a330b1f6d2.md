# Three CRMs, one customer table, and the night we stopped guessing

We inherited three CRMs the way most companies do: by acquisition. Sales ran on Salesforce, the support org that came with the 2023 acquisition ran on a HubSpot instance nobody wanted to migrate, and the professional services team ran a Dynamics install that predated everyone currently employed. Finance wanted one number for "how many customers do we have." Nobody could produce it.

The ask was a single `dim_customer` table in the warehouse, refreshed nightly, that every downstream dashboard could trust. Here's how we built it and where it got ugly.

## Extraction: boring on purpose

We resisted the urge to be clever. Each CRM gets its own extractor, each extractor writes raw JSON to S3 partitioned by `source/date/`, and nothing else touches those files. Salesforce and Dynamics both support change-tracking queries, so those pull incrementally on `SystemModstamp` / `modifiedon` with a two-hour lookback window to absorb clock skew. HubSpot's incremental API was flaky enough at our object volume that we just do a full pull; it's 400k contacts and takes eleven minutes, which is cheaper than debugging it.

Raw stays raw. If a field arrives as the string `"NULL"` because someone typed it into a text box, it lands in S3 as `"NULL"`. We fix it downstream where the fix is visible in code review.

## Staging: one shape, three sources

Each source gets a staging model that renames fields into a common vocabulary and does nothing else opinionated. `email_primary`, `company_name`, `country_code`, `created_at`, `source_system`, `source_record_id`. The only transformation with judgment in it is normalization: lowercase and trim emails, strip `+tag` suffixes for matching purposes only (we keep the original), normalize company names by dropping punctuation and the usual legal suffixes — Inc, LLC, Ltd, GmbH, BV.

That last one matters more than it sounds. "Northwind Traders, Inc." and "northwind traders llc" are the same account in three systems and none of them agree on the string.

## Matching: the part that actually took the time

Our resolution runs in three passes, most confident first.

**Pass 1 — exact normalized email.** Deterministic, high precision, catches about 71% of cross-system links.

**Pass 2 — domain plus normalized company name.** For records where the email is a shared inbox (`billing@`, `info@`) and the person-level match fails. Adds another 14%.

**Pass 3 — fuzzy company name within the same country.** Trigram similarity above 0.85. This one we gated behind a review queue for the first six weeks. It surfaced real matches like "Rheinmetall Systeme" vs "Rheinmetall Systemtechnik" that turned out to be *different* legal entities, so the queue earned its keep.

Anything unmatched becomes its own customer. We'd rather over-count than silently merge two real companies into one.

## Conflicts: precedence, not consensus

Once records are grouped into a customer, something has to decide which `company_name` wins when all three sources disagree. We tried a "most recently modified wins" rule first. It was a disaster — HubSpot's automation touched `lastmodified` on every contact nightly, so HubSpot always won, including on fields HubSpot was worst at.

What we shipped instead is a per-field precedence table, declared in a YAML file that lives next to the models:

```yaml
billing_country:
  order: [dynamics, salesforce, hubspot]
company_name:
  order: [salesforce, dynamics, hubspot]
support_tier:
  order: [hubspot]           # only HubSpot knows this
annual_contract_value:
  order: [dynamics, salesforce]
```

For each field we take the first non-null value walking the order. Salesforce owns account naming because sales ops actually curates it. Dynamics owns billing geography because it's wired to the invoicing system. HubSpot owns support tier because it's the only system that has the concept.

The important part isn't the ordering — it's that the ordering is a reviewable artifact with a name on the commit. When someone disputes a value in a dashboard, the answer to "why does it say that" is a file, not a conversation.

We also emit a `conflicts` table alongside the dim: one row per customer, per field, per disagreeing source, with the losing values. It's ugly and nobody looks at it most weeks. But when the head of RevOps swore a customer's country was wrong, we pulled up seven months of exactly which system said what, and the argument ended in four minutes.

## What we'd do differently

Build the conflicts table first, not last. We spent two weeks tuning match thresholds against intuition when we could have been measuring. And add the review queue on day one — we shipped fuzzy matching before we had a way to see what it was doing, and got lucky that nothing merged badly before we noticed.

Nightly run is now nineteen minutes end to end. Finance has their number.
