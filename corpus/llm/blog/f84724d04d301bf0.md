I built a three-node Kubernetes cluster out of Raspberry Pi 4s over a series of weekends this spring, and since I get asked about it every time someone spots the little acrylic tower on my shelf, here's the full writeup: the networking, the storage pain, and what it's actually running now that the novelty has worn off.

The hardware is three Pi 4 Model Bs, 8GB RAM each, each with a 128GB SD card for the OS and a USB 3.0 SSD for anything that actually needs decent I/O. I picked up a cheap acrylic stacking case with a mounting plate for a small unmanaged 5-port gigabit switch, so the whole thing sits as one unit rather than three boards with cables running everywhere. Power is the one place I didn't cheap out — I used a single powered USB-C hub rated well above what three Pis pull under load, after an earlier attempt with individual phone chargers gave me random reboots on the node running the heaviest workload, which turned out to be undervoltage, not anything software-related. Cost me a day of confused `dmesg` reading before I noticed the tiny lightning-bolt undervoltage icon that the Pi actually shows you if you're looking.

For networking I went simple: all three nodes on the same flat subnet behind the switch, static IPs assigned via DHCP reservations on my main router rather than configured on the Pis themselves, because I've been burned before by static config on the device getting out of sync with what the network thinks. I run k3s instead of full Kubernetes — Rancher's lightweight distribution strips out a lot of the control-plane weight that doesn't make sense on hardware this small, and it ships with a decent default (Flannel for CNI, Traefik for ingress) that I didn't feel a need to fight on day one. One node runs as server, the other two as agents. The whole cluster came up in under twenty minutes the first time, which felt suspiciously easy given everything else about this project.

Storage was the actual headache, and I mean actual headache, not the fun kind. My first attempt used the local-path provisioner that ships with k3s, backed by the SD cards, and I learned within about a week that SD cards do not want to be a database's disk. Write amplification from anything doing frequent small writes — I was running a Postgres instance for a couple of side projects — degraded card performance noticeably within days and I was staring down the barrel of replacing SD cards every few months. I moved persistent volumes onto the USB SSDs instead, which meant setting up local-path on a non-default mount point on each node and being careful that pods requesting storage actually landed on nodes where I'd provisioned it, since I didn't want to deal with a distributed storage layer like Longhorn on hardware this underpowered. It works, but it means my persistent workloads aren't really portable across nodes anymore, which defeats a bit of the point of a cluster. I've made peace with that tradeoff for now; the alternative was fighting Longhorn's resource requirements on 8GB nodes, which felt like more suffering than the payoff justified.

As for what's actually running on it day to day: Pi-hole for DNS-level ad blocking across the house, which was honestly the first thing I deployed and remains the thing everyone in the household would notice if it went down. A small Postgres instance backing two personal projects that get maybe a few hundred requests a day combined. Uptime Kuma for monitoring the rest of my home lab, including, a little recursively, the cluster itself. And Home Assistant, which I moved over from a standalone Pi specifically to get automatic restarts and slightly less manual babysitting.

It is, by any reasonable measure, wildly over-engineered for what it does. I could run all of this on a single Pi with none of the orchestration. But I wanted to actually understand Kubernetes primitives — nodes, pods, services, ingress, persistent volumes — by living with them at a scale where a mistake costs me an evening, not a production incident, and on that front it's been worth every weekend.
