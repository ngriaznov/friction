I got tired of news sites auto-playing video with sound the instant a tab loads, so I built a small Chrome extension to stop it. Nothing groundbreaking, but the permissions story and one particular bug were annoying enough to be worth writing down.

The core approach is a content script that runs at `document_start` and does two things: mutes and pauses any `<video>` element it finds, and sets up a `MutationObserver` to catch videos that get inserted into the DOM after initial page load, which is most of them on a modern news site built on some framework that hydrates content client-side. For the manifest, I went with Manifest V3, which meant a content script declared for `<all_urls>` with `run_at: document_start`, plus the `scripting` permission so I could optionally inject the mute logic into iframes too, which turned out to matter more than I expected. I deliberately left off `webRequest` and any blocking network permissions — I didn't want to intercept or block requests, just neutralize playback after the fact, so the permission footprint stays about as small as it can for something that needs to touch every page.

```js
function silence(video) {
  video.muted = true;
  video.autoplay = false;
  if (!video.paused) video.pause();
}

document.querySelectorAll('video').forEach(silence);

new MutationObserver((mutations) => {
  for (const m of mutations) {
    for (const node of m.addedNodes) {
      if (node.tagName === 'VIDEO') silence(node);
      if (node.querySelectorAll) node.querySelectorAll('video').forEach(silence);
    }
  }
}).observe(document.documentElement, { childList: true, subtree: true });
```

That worked fine on the first dozen sites I tested, including ones with fairly aggressive autoplay setups. Then I hit a site — I won't name it, but it's a large general-interest news outlet — where video kept playing with sound despite the extension supposedly being active, and no errors in the console to explain it.

Took me a while to realize the video wasn't in the top-level document at all. It was inside a lazy-loaded iframe, one that didn't even exist in the DOM on initial page load; it got created by the site's own JavaScript only once an ad slot or article widget scrolled into view, and the iframe's `src` pointed at a separate origin entirely. Content scripts declared in the manifest for the top frame don't automatically run inside iframes, especially cross-origin ones, unless you explicitly opt into `all_frames: true` in the manifest — which I hadn't, because I'd only tested on sites where the video lived in the main document. Setting `all_frames: true` fixed same-origin iframes immediately, but cross-origin iframes needed the content script to be permitted to run there too, which is where the broader host permissions actually earned their keep — without `<all_urls>` covering the iframe's origin as well, my script would never even get injected into it, mutation observer or not.

Once I set `all_frames: true` and confirmed my host permissions actually covered the iframe origins these ad and video widgets load from — which took some trial and error watching the extension's own console output per-frame — the lazy-loaded case started getting caught the moment the iframe's document was created, since `document_start` fires per-frame, not just once for the top document.

It's a small extension, maybe 80 lines total including the manifest, but that iframe bug was a good reminder that "runs on every page" and "runs everywhere content actually lives" are not the same claim, especially once a site is composed out of a dozen embedded origins you never see in the address bar.
