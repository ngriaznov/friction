# Rate limiting our public API with a token bucket

We opened up our API to third-party developers this quarter, and within about a week one integration partner had a retry loop gone wrong that was sending us upward of 200 requests per second from a single API key. Nothing fell over, but it was close enough that rate limiting jumped from "nice to have eventually" to "this sprint."

## Why token bucket

We looked at three approaches: a fixed window counter, a sliding window, and a token bucket. Fixed window is trivial to implement — increment a counter keyed by API key and the current minute, reject once it crosses the threshold — but it has the well-known boundary problem: a client can burst up to the limit in the last second of one window and again in the first second of the next, giving it effectively double the allowed rate for a brief moment. For an API where a single burst can mean a partner's retry storm, that gap was enough to disqualify it.

Sliding window log — keeping a timestamp per request and counting how many fall within the trailing window — fixes the boundary problem but doesn't fix the operational cost. Each request means storing and pruning a growing list of timestamps per key. At our request volume, keeping a per-key list in Redis and trimming it on every request would have meant a `ZADD` plus a `ZREMRANGEBYSCORE` plus a `ZCARD` per request, three round-trips where a token bucket needs one.

The token bucket gave us the smoothing we wanted without the per-request list. Each API key gets a bucket with a fixed capacity and a refill rate. Every request costs one token; if the bucket is empty, the request is rejected with a 429. Tokens refill continuously at the configured rate, so a client that has been idle can burst up to the bucket's capacity, but a client sending a steady stream is capped at the refill rate indefinitely. That matched our actual requirement: allow reasonable bursts (a client paginating through a large result set shouldn't get throttled mid-page) while capping sustained load.

## The data structure

We didn't store a token count and a timestamp separately and run a scheduled job to refill buckets — with thousands of API keys, most of them idle at any given moment, a background refill job would have been pure waste. Instead each bucket is represented by two fields in Redis: the token count as of the last update, and the timestamp of that update. On each request, we compute elapsed time since the stored timestamp, multiply by the refill rate, add that to the stored count (capped at bucket capacity), and only then check whether a token is available. This is the standard "lazy refill" trick — the bucket only gets recomputed when someone asks it a question, so idle keys cost us nothing.

The whole read-modify-write happens in a single Lua script executed via `EVAL`, which keeps the check-and-decrement atomic without needing a distributed lock. That mattered more than we expected once we had multiple API gateway instances behind a load balancer, all potentially handling requests from the same key concurrently.

## What we shipped

Default limit is 50 requests per second sustained, burst capacity of 200. Enterprise-tier keys get a higher configured rate, set per-key rather than per-tier in the database, since two of our largest partners needed custom limits from day one. The 429 response includes a `Retry-After` header computed from the current deficit and refill rate, so well-behaved clients can back off correctly instead of guessing.

Three weeks in, the rate limiter has tripped for exactly the kind of runaway retry loop that prompted building it, and the offending client got a clean 429 instead of us getting paged.
