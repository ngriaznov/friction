## Incident summary

On the afternoon of a routine deploy, a database migration intended to add a new indexed column to our `orders` table instead took an exclusive lock on that table for approximately 40 minutes, during which every read and write to `orders` — meaning checkout, order history, and our fulfillment worker — either queued or timed out. This is the postmortem we wrote up internally, lightly edited for a general audience.

**Impact:** Checkout was effectively unavailable for 40 minutes. Order history pages returned errors or hung. Fulfillment processing backed up but did not lose data, since those jobs retried. We estimate low four figures in lost checkout attempts based on comparable traffic from the prior week, though we can't know how many of those customers came back later.

## Timeline (all times approximate, local)

**2:14 PM** — Deploy pipeline runs a migration to add a new `fulfillment_priority` column to `orders`, along with a `NOT NULL` default and a new index on it, as three separate migration steps executed in a single transaction by our migration tool.

**2:15 PM** — The `ADD COLUMN ... NOT NULL DEFAULT` step begins. On our version of Postgres, adding a column with a non-null default requires rewriting every existing row to populate that default, which on a table with roughly 40 million rows took far longer than anyone anticipated. This step held an `ACCESS EXCLUSIVE` lock on `orders` for its entire duration, blocking all reads and writes, not just other DDL.

**2:16 PM** — First alerts fire: checkout error rate crosses threshold. On-call engineer acknowledges within two minutes.

**2:19 PM** — On-call confirms via dashboards that the spike correlates with the deploy that went out five minutes earlier and begins investigating the migration specifically.

**2:24 PM** — On-call identifies the migration as the likely cause by checking `pg_stat_activity` and seeing the `ALTER TABLE` still running, holding a lock with a long queue of blocked queries behind it.

**2:26 PM** — Decision point: killing the migration mid-rewrite risks leaving the table in a partially-rewritten, potentially inconsistent state depending on exactly where Postgres was in the operation, and we weren't confident enough in that recovery path under pressure. On-call escalates to a second engineer and the team lead, and the group decides to let the migration finish rather than kill it, given the ambiguity.

**2:26 PM – 2:54 PM** — Migration continues running. Checkout remains down. Status page updated at 2:31 PM. Customer support notified at 2:33 PM to prepare a canned response.

**2:54 PM** — Migration completes. Lock releases. Backed-up connections drain over the next two to three minutes as queued requests process.

**2:57 PM** — Checkout error rate returns to baseline. Fulfillment queue backlog (which had grown but not been lost) clears over the following twenty minutes as workers catch up.

**3:15 PM** — Incident declared resolved. Backlog fully drained, all systems nominal.

## Root cause

The direct cause was adding a `NOT NULL DEFAULT` column to a 40-million-row table in a single blocking operation, which on our Postgres version rewrites the entire table under an exclusive lock rather than the lock-free path that newer Postgres versions support for constant defaults. The underlying cause was process, not a one-off mistake: we didn't have a rule requiring large-table migrations to be reviewed for lock behavior before merge, and our migration tool didn't warn about long-running DDL or split it into safer steps automatically. The engineer who wrote the migration had tested it against a staging database with a few thousand rows, where the same operation completes in under a second, so nothing in local or staging testing surfaced the problem.

## What we're changing

We added a required review step for any migration touching a table over some threshold of estimated rows, checked automatically by a script that queries table size in the target environment before a migration is allowed to run in production. For this specific class of problem, we're standardizing on the safe pattern of adding nullable columns first, backfilling the default in batches with a background job, and only adding the `NOT NULL` constraint afterward using `NOT VALID` plus a separate validation step, which avoids the full-table rewrite entirely. We also added a hard timeout to our migration runner so that any DDL statement running longer than five minutes against production gets automatically killed rather than left to a human judgment call mid-incident, which was the most uncomfortable part of the response — nobody wants to be the one deciding whether to kill an in-flight schema change with no clear rollback story. That decision shouldn't rest on a single on-call engineer's nerve at 2:26 in the afternoon.
