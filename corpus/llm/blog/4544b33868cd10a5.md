# I Built a Chrome Extension to Kill Autoplay Video, and Then Fought It for a Week

The trigger was a hotel lobby. I opened a news article on my laptop at 6 a.m. and a video ad started playing at full volume three feet from a stranger reading a paperback. I muted the tab, apologized, and decided that was the last time.

Existing blockers mostly work by nuking the elements outright, which breaks the article layout and sometimes takes the text with it. I wanted something dumber: let the player exist, just never let it start.

## The manifest

The whole thing is MV3 with a content script and nothing else. No background service worker, no storage, no options page in the first version.

```json
{
  "manifest_version": 3,
  "name": "Hushplay",
  "version": "0.1.0",
  "content_scripts": [
    {
      "matches": ["<all_urls>"],
      "js": ["hush.js"],
      "run_at": "document_start",
      "all_frames": true
    }
  ]
}
```

Two details matter here. `run_at: document_start` is non-negotiable — if you wait for `document_idle`, the player has already called `play()` and you are chasing it. And `all_frames: true`, because on news sites the video almost never lives in the top document. It lives in an iframe from a video partner.

I deliberately did not request `host_permissions` or `tabs`. A content script matching `<all_urls>` gets me DOM access, which is all I need, and it keeps the permission warning at "read and change data on sites you visit" instead of adding scary extras.

## The actual trick

Rather than hunting for `<video>` elements on a timer, I patch the prototype before any page script runs:

```js
const origPlay = HTMLMediaElement.prototype.play;
HTMLMediaElement.prototype.play = function () {
  if (!this.dataset.hushAllowed) {
    return Promise.reject(new DOMException("blocked", "NotAllowedError"));
  }
  return origPlay.apply(this, arguments);
};
```

Rejecting with `NotAllowedError` is the important part. That is exactly what Chrome throws when its own autoplay policy blocks a video, so every player library already handles it — they show the poster frame and a play button and move on. Throwing a generic error instead left some players spinning forever.

A click handler sets `dataset.hushAllowed` on whatever the user actually clicks, so pressing play works normally.

## The bug that ate a week

It worked everywhere except two sites, where video below the fold played anyway. Same code, same manifest, `all_frames` set. Console in the iframe showed my script had run.

The iframes were lazy-loaded. The page inserted `<iframe src="about:blank">` and swapped in the real `src` when you scrolled near it. Chrome injects content scripts into `about:blank` frames by inheriting from the parent, but the *navigation* to the real URL creates a fresh document — and my patch was applied to the old one. The player then loaded into a clean, unpatched realm.

The fix was to stop treating injection as one-shot. I re-apply the patch inside a `MutationObserver` on iframe `src` changes, and I also register the patch as a small inline script the frame re-executes, so a re-navigated frame gets it again. Not elegant. Works.

Source is up on my Codeberg if anyone wants to make it less ugly.
