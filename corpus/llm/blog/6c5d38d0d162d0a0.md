# Chasing a Slow Leak Through a Node.js Worker

For about three weeks, one of our background worker processes had a habit of getting restarted by the process manager every twelve to eighteen hours. Not crashing exactly — just quietly climbing in memory until it tripped the container's limit and got killed and rescheduled. Nobody was losing sleep over it, because the restarts were clean and the queue it served just picked back up where it left off. But "clean and automatic" is exactly the kind of problem that eventually stops being either.

## The first signs

The worker in question consumes jobs off a queue, does some transformation work, and writes results to S3. Our monitoring dashboard showed RSS climbing in a slow, almost perfectly linear line from the moment the process started, with no sawtooth pattern you'd expect from normal garbage collection pressure. That shape is usually the first tell: real GC behavior looks like a jagged sawtooth as young generation objects get collected. A smooth, unbroken climb means something is being retained that should have been freed.

Heap snapshots were the obvious next step, but here's the annoying part: this worker doesn't process any single job that "should" leak. Jobs are small, transformations are fast, and nothing about the workload looked unusual. Whatever was leaking was leaking a tiny amount per job, invisible in any single snapshot comparison unless you let a lot of jobs run first.

## Narrowing it down

I let the worker run under `--inspect` in a staging environment, fed it a synthetic load of a few thousand identical jobs, and took heap snapshots at the start, middle, and end. Comparing the middle and end snapshots in Chrome DevTools' heap profiler showed a steadily growing count of one specific object: instances of our internal `JobContext` class, thousands of them, none garbage collected, even though every job had long since finished and returned.

The retainer graph pointed at an `EventEmitter` — specifically, the shared `queueClient` object that every job's `JobContext` was subscribing to for a `"progress"` event, so it could relay progress updates upstream. The subscription happened in the `JobContext` constructor. The problem was that nothing ever called `removeListener` when a job finished. Every single job, successful or failed, added one more permanent listener to that shared emitter and left it there forever, along with a closure holding a reference to that job's entire context — input payload, intermediate buffers, all of it.

Node doesn't even warn you about this by default until you cross the default max-listener threshold of ten, at which point it logs a `MaxListenersExceededWarning` to stderr. We had that warning turned off months earlier because an unrelated, genuinely harmless case was spamming our logs, and turning it off meant we lost the one built-in signal that would have caught this in days instead of weeks.

## The fix, and the actual root cause

The fix itself was small: capture the listener reference in `JobContext`, and call `queueClient.removeListener("progress", this._onProgress)` in a `finally` block once the job settles, whether it resolved or rejected. Fifteen lines, one focused pull request.

The more useful fix was re-enabling the max-listeners warning, but scoped correctly this time — pointed only at the emitters we control internally, rather than the noisy third-party one that caused us to disable it in the first place. We also added an assertion to our test harness that runs a batch of fake jobs through a `JobContext` and fails if listener counts on the shared emitter haven't returned to baseline afterward.

The instructive part of this one wasn't the bug itself, which is a fairly ordinary "forgot to unsubscribe" mistake. It was how long a linear-but-slow leak can hide behind an auto-restarting process manager that quietly absorbs the symptom before anyone has to think about the cause.
