# The query that made me give up on the ORM

I like ORMs. I've defended them in arguments. For a CRUD service where most requests touch one row by primary key, an ORM saves you from a thousand lines of tedium and buys you migrations, connection pooling, and type-checked models for free.

Our analytics service is not that kind of service. It has eleven tables, four of them enormous, and essentially every endpoint is a grouped aggregate over a date range. Last spring I ripped the ORM out of the query layer and replaced it with hand-written SQL. Here's the query that pushed me over.

## The query

Product wanted a cohort retention view: for each signup week, how many of those accounts were still active in each subsequent week, split by plan tier. In SQL this is a couple of CTEs and a self-join on a generated week series. Maybe forty lines, and every line says what it does.

In the ORM it was not forty lines. It was a builder chain about ninety lines long with three subquery objects assigned to intermediate variables, two raw fragments injected because there's no expression API for `generate_series`, an alias collision I had to work around by naming things `c1` and `c2`, and a `.distinct()` that silently changed the meaning of the aggregate. When I finally got it returning correct numbers, I couldn't read it. Neither could the reviewer. We approved it on the strength of the test fixtures rather than on understanding what it did.

Then it turned out to be slow — about 9 seconds on production-sized data. So I dumped the generated SQL to look at the plan. It was 300 lines of nested subselects with generated alias names, and the planner had chosen a hash aggregate over a sort that a `DISTINCT ON` would have avoided entirely.

At that point I was debugging SQL anyway. I was just doing it through a translation layer that I now had to fight to change. I rewrote it by hand and it ran in 340 ms.

## What actually changed

The rewrite wasn't dramatic. We kept the ORM for models, migrations, and the handful of genuinely row-oriented writes — user settings, saved views, API keys. Every read path that aggregates now lives in a `queries/` directory as a `.sql` file, loaded at startup and executed with bound parameters, mapping results into small dataclasses.

Three things got better and one got worse.

Better: query plans are now something I look at directly, against the exact text that runs in production. When something is slow, `EXPLAIN ANALYZE` on the file tells me why, and I edit the same file.

Better: code review got real again. A reviewer who knows SQL can read a forty-line query and say "this join will fan out." Nobody can say that about a builder chain.

Better: the files are portable. Our data analyst opens the same `.sql` in her editor when she wants to check a number against the dashboard. That was impossible before.

Worse: we lost compile-time safety on the shape of results. A renamed column in a migration now fails at runtime rather than at build. We patched over this with a test that runs every query file against a schema-only test database in CI and asserts the returned column names. It catches the realistic cases, and it takes four seconds.

## The rule I'd use next time

Ask what fraction of your queries are shaped like "get me this row" versus "summarise these rows." If it's mostly the first, keep the ORM and don't think about it. If it's mostly the second, you will end up reading generated SQL sooner or later — and once you're doing that, the abstraction has stopped abstracting and started charging rent.
