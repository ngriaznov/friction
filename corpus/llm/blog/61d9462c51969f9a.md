# Three Raspberry Pis, One Kubernetes Cluster, and a Lot of Swearing

Every home lab project starts the same way: a completely reasonable goal quietly balloons into a weekend-eating obsession. Mine was "learn Kubernetes properly by running something real on it." Three Raspberry Pi 4 boards later, I had a cluster. Getting there took longer than I want to admit.

## The hardware

I went with three Pi 4s, 8GB RAM each, on a PoE HAT so I could power everything through a single switch instead of running a rat's nest of USB-C cables to a power strip. One Pi became the control plane, the other two workers. Storage was a 128GB USB 3.0 SSD per board rather than microSD cards — I'd read enough horror stories about SD cards dying under sustained write load from etcd to skip that mistake entirely.

## Networking: the part nobody warns you about

I assumed networking would be the easy part. It was not. I run k3s rather than full upstream Kubernetes — lighter weight, and it ships with a sane set of defaults for exactly this kind of low-power cluster. The catch is Flannel, k3s's default CNI, needed a specific backend for my setup. My managed switch does IGMP snooping in a way that periodically dropped VXLAN traffic between nodes, which manifested as pods on different nodes intermittently losing the ability to reach each other's services. It took an embarrassing number of hours staring at `tcpdump` output before I traced it to the switch config rather than anything in Kubernetes itself. Disabling IGMP snooping on that VLAN fixed it immediately.

The other networking wrinkle was giving the cluster a stable entry point. I run MetalLB in layer-2 mode with a small pool of addresses carved out of my home LAN's DHCP range, which lets `LoadBalancer` services get a real, pingable IP instead of living only as `NodePort` entries I'd have to remember.

## Storage headaches

Local persistent storage on a three-node bare-metal cluster is its own swamp. I initially tried `local-path-provisioner`, which k3s bundles by default, but it ties a volume to whatever node it was created on — fine until that node needs a reboot for a firmware update, at which point anything depending on that volume just sits pending. I ended up moving to Longhorn for anything that needed to survive a node going down, which replicates block storage across the cluster. It's noticeably heavier on these boards than I'd like — three replicas of anything on ARM SBCs with 8GB of RAM adds up fast — but for the handful of stateful services I run, it's been worth the overhead.

## What's actually running on it

After all that, the workload is almost anticlimactic: Pi-hole for DNS-level ad blocking, a Postgres instance backing a personal budgeting app, Uptime Kuma for monitoring the rest of my home network, and a small Node-RED instance tied to a couple of Zigbee sensors. None of it strictly needed Kubernetes — a single Pi running Docker Compose would have handled all of it with room to spare. That was never really the point.

## Was it worth it

Genuinely, yes. Reading about pod scheduling, CNI plugins, and persistent volume claims is one thing; watching a node get unplugged mid-demo and seeing Kubernetes reschedule the affected pods elsewhere without me touching anything is another. It made concepts that felt abstract in a course finally click. If you're considering something similar: budget more time for networking than you think you need, skip microSD storage entirely, and don't expect it to save you money over just running a single more powerful box — the value here is entirely in what you learn getting it working, not in the hardware.
