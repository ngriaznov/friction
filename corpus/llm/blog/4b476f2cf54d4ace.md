# Three Raspberry Pis and a lot of opinions about storage

I built a Kubernetes cluster in my basement last spring. Three Raspberry Pi 4s, 8GB each, stacked in one of those acrylic cases with the tiny fans that sound like a mosquito with a grudge. Total hardware cost, including the switch and the PoE hats I later regretted, was around $420.

I want to be upfront: I did not need this. Everything running on it now would fit comfortably on a single Pi with Docker Compose, and would probably have better uptime. I built it because I wanted to understand Kubernetes from the bottom rather than from the `kubectl apply` end, and there is no substitute for having to fix the thing yourself at 11pm.

Here is what actually took the time.

## Networking, which was easier than expected

I used k3s. Full upstream Kubernetes on ARM is possible and people do it, but k3s bundles containerd, Flannel, and a local storage provisioner into one binary, and the install is genuinely one command. Server on the first node, agents on the other two, join token copied over. Fifteen minutes.

Two things I had to sort out before that worked.

Static addresses. I originally let DHCP hand out leases and told myself the reservations in my router would hold. They did, until a firmware update cleared them and two nodes swapped addresses. The etcd datastore was unhappy in ways I did not enjoy diagnosing. Now every node has a static IP configured in `/etc/dhcpcd.conf`, and I keep a text file mapping MAC addresses to names.

Cgroups. Raspberry Pi OS ships with memory cgroups disabled, and k3s will not start without them. You add `cgroup_memory=1 cgroup_enable=memory` to the end of `/boot/cmdline.txt` — on one line, no newline, the file is picky — and reboot. This is documented, but it is documented in a place you find after the third failed install.

For getting traffic in, I run MetalLB in layer 2 mode with a small pool of addresses carved out of my home subnet, plus Traefik as the ingress. Services get real LAN addresses. It works, it has never once needed my attention, and it is the single most satisfying part of the setup.

## Storage, which was the whole project really

The thing nobody tells you: SD cards die under Kubernetes. Not "might eventually degrade" — die, in weeks. etcd writes constantly, container logs write constantly, and consumer SD cards have write endurance measured in the hundreds of cycles. I killed two cards in the first month. The second failure took the cluster's entire state with it, which is how I learned that k3s stores its datastore in `/var/lib/rancher` and that I had never backed it up.

I moved all three nodes to USB 3.0 SSDs. This is the standard advice and it is correct. Boot from USB requires a bootloader update on older Pi 4s (`rpi-eeprom-update -a`), and then you flash the SSD instead of the card. The performance difference is not subtle — `apt upgrade` went from a coffee break to under a minute.

That solved node reliability. It did not solve shared storage, which is a different and much more annoying problem. k3s ships local-path-provisioner, which binds a PVC to a directory on whatever node the pod landed on. This is fine right up until the pod reschedules, at which point it comes back with an empty volume and no explanation.

I tried Longhorn first. It is the recommended answer and it is a genuinely good project, but on three Pi 4s it wanted more memory and more CPU than I had to spare, and I watched the replica rebuild traffic saturate my gigabit switch for twenty minutes after a node reboot. I ran it for three weeks and gave up.

What I landed on is unglamorous: an NFS export from a Synology NAS I already owned, plus `nfs-subdir-external-provisioner` for dynamic PVCs. It is a single point of failure. It is also stable, fast enough, backed up nightly by the NAS itself, and I have not thought about it since I set it up. For a home cluster that is the right trade.

## What I actually run on it

The honest list, eight months in:

**Pi-hole**, with two replicas and a shared MetalLB address. DNS going down takes the house offline in a way that generates immediate complaints, so this was the first workload I made properly redundant.

**Home Assistant**, which is the only thing on the cluster my household notices. It talks to a Zigbee coordinator over USB, which means it is pinned to one specific node with a node selector, which means it is not really benefiting from Kubernetes at all. I know.

**Uptime Kuma**, monitoring the other services and a handful of external ones.

**A Minecraft server** for my nephew, which gets scaled to zero most of the year.

**Gitea**, mirroring a few personal repos.

That is it. Five things. The cluster idles at maybe 12% CPU across all three nodes.

## Was it worth it

Yes, but not for the reasons I expected. I have not saved money and I have not gained reliability over a single well-maintained box. What I got was a place where breaking things costs nothing. I have drained nodes, corrupted etcd, misconfigured RBAC, and blown away the whole cluster twice. Doing that on hardware I own, with no change ticket and nobody paged, taught me more than two years of reading.

If you are considering it: buy SSDs on day one, and decide your storage story before you deploy anything you would miss.
