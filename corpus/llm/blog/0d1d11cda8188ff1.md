# One Failure in Twenty

For most of last spring, our integration suite failed about one run in twenty. Not the same test each time. Not with the same error. Just a red build, roughly once a day, in a pipeline that ran forty or fifty times.

The team's response was the obvious one: hit retry. The retry passed. Everyone moved on. We had all learned to read a failed CI badge as "probably nothing," which is a terrible thing for a team to learn.

## Why we couldn't reproduce it

The first two attempts at fixing this went nowhere because we tried to reproduce the failure locally. Running the suite on a laptop, it passed. Running it a hundred times in a loop overnight, it passed a hundred times. Running it in CI, it failed at the usual rate.

That gap should have been the clue. We read it as "CI is slow and flaky" and started adding timeouts.

Adding timeouts is the classic wrong turn with flaky tests, and we took it all the way. Waits went from 2 seconds to 10. A couple of tests got explicit retry decorators. The failure rate dropped to maybe one in forty, which felt like progress and was actually just us hiding the signal. The suite went from nine minutes to fourteen.

## The thing that actually helped

What broke it open was boring: we started saving the test execution order as a build artifact.

Our runner shards tests across four CI workers and assigns them by wall-clock balancing, so the order isn't stable between runs. Once we had a few weeks of orderings paired with pass/fail outcomes, someone pulled them into a notebook and looked for patterns. There was one. Every failing run had `test_billing_export` executing on the same worker as, and earlier than, one of about six tests in the accounts module.

With that, reproduction was trivial. Run those two tests in that order, and the second one fails every single time.

## Shared database state, of course

The cause was as mundane as the investigation was long.

Our integration tests share a Postgres instance per worker. Each test is supposed to run inside a transaction that gets rolled back at teardown, so nothing leaks. `test_billing_export` had, at some point, been changed to exercise a code path that issues a `COMMIT` — the export job writes a checkpoint row so it can resume after a crash, and the test was verifying exactly that behavior.

Committing inside the test broke the enclosing transaction's isolation. The checkpoint row survived teardown. Anything running afterward on that worker saw an extra row in a table that the accounts tests scanned when computing balances. Six of them asserted on totals. Four in twenty runs put the billing test before one of those six on the same worker. One in twenty runs of the full suite, give or take.

Everything about the failure rate followed from shard assignment. Nothing about it followed from timing, which is why every timeout we added did nothing except make the suite slower.

## What we changed

We fixed the immediate bug by giving the export test a dedicated schema that gets dropped after it runs. That took twenty minutes.

The changes that mattered more:

**Order randomization, seeded and logged.** Every run now shuffles test order with a seed printed at the top of the output. A failure is reproducible with one flag. This surfaced two more order-dependent tests within a week — both of which had presumably been failing occasionally for months.

**Post-test state assertions.** In CI, each test's teardown now checks that the row counts in a handful of shared tables match what they were beforehand. A test that leaks state fails immediately, with its own name attached, instead of poisoning a neighbor.

**We deleted every retry decorator.** All of them. If a test is unreliable, we want to know on the run where it broke, not three runs later.

The suite is at fourteen minutes and we haven't gotten it back down yet. But it's been about four months without an unexplained red build, and people have stopped reflexively clicking retry. That second part took longer to fix than the test did.
