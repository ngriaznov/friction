I've spent the last two years writing plain JavaScript on a mid-sized web app — a few hundred thousand lines, a decent number of contributors rotating through it — and I finally moved the whole thing to TypeScript over the last six weeks. I went in expecting to like it in theory and resent it in practice. That's roughly what happened, but not evenly across the codebase.

The type errors that caught real bugs almost all clustered around two shapes of problem. The first was API response handling. We fetch data from a handful of internal services, and it turns out we had at least six places where we assumed a field would always be present on a response object when the backend actually made it optional, and in each case there was a real, if rare, path where that assumption broke and produced either a silent `undefined` bug or, in one case, a crash that had been happening in production intermittently for months without anyone connecting it back to this. TypeScript flagged every one of those the moment I added proper interface definitions for our API responses, because `undefined` isn't assignable to a required string field, full stop. That alone justified a good chunk of the migration effort to me.

The second was function signatures drifting out of sync with their call sites over time. We had a formatting utility that had picked up a third parameter eighteen months ago, and about a dozen call sites around the codebase were still calling it with two arguments, silently getting a default that was wrong for their context. Nobody had noticed because the wrong default produced output that was plausible-looking, just subtly off. TypeScript's arity checking caught every single one of those in about four seconds, which is the kind of bug that plain JavaScript essentially cannot catch without a test written specifically to catch it, and nobody writes that test until after they've been bitten.

The busywork side is real too, and it's mostly around anything touching external, loosely-typed data — form state, third-party library callbacks without great type definitions, and honestly a fair amount of our own Redux-adjacent state management, which needed generic type parameters threaded through in a way that added real friction for approximately zero bug-catching benefit. I spent an embarrassing number of hours getting a reducer's action types to satisfy the compiler for logic that was correct the entire time and just needed a type annotation broad enough to shut the compiler up. There's also a category of error I'd call performative strictness — cases where the compiler is technically right that a value could theoretically be null, based on a type definition three layers removed from any code path that could actually produce null, and I ended up sprinkling non-null assertions in a handful of spots I'm not thrilled about, because getting it "properly" correct would have meant restructuring code that wasn't broken.

Net assessment after two years of the alternative and six weeks of this: worth it, but not because it made writing new code faster — if anything it's slower day to day. It's worth it because of what it caught in code that had already shipped and that everyone, myself included, had stopped double-checking by hand.
