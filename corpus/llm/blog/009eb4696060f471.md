# Two years of JavaScript, then TypeScript

We finally converted our app to TypeScript this spring. It's a mid-sized thing — about 40k lines, a React frontend and an Express API, maybe six people touching it regularly. I'd written plain JavaScript on it for two years and had opinions about TypeScript formed entirely from other people's blog posts. Now I have opinions formed from actually using it, and they're mixed in ways I didn't expect.

The conversion took three weeks in the background, mostly `allowJs: true` and then chipping away file by file. Nobody stopped shipping features.

## What actually caught bugs

The nullability checks. Not close. `strictNullChecks` found things I'd have sworn weren't in there.

The worst one was in our invoice total calculation — a function that took an optional `discount` object and did `discount.percentOff * subtotal`. It had a guard, but the guard checked `if (discount)` while a different code path passed `{ percentOff: undefined }` for "no discount applied." So the guard passed, the multiply produced `NaN`, and `NaN` propagated all the way to a rendered total that displayed as "$NaN" to about eleven customers before someone reported it. That was six weeks before the conversion. TypeScript flagged that exact line in the first pass.

The second real category: renamed API fields. Our backend changed `created_at` to `createdAt` in one endpoint and we missed two call sites. In JS those became `undefined` and rendered as blank dates. With types on the response objects it was a compile error.

Third: discriminated unions on our WebSocket message handler. We have about fifteen message types, and the switch statement had drifted out of sync with what the server actually sent. Adding a union type and an exhaustiveness check surfaced two message types we were silently dropping.

## What felt like busywork

Typing third-party stuff that has no types, or bad types. We use a charting library whose `@types` package describes an older major version. I spent the better part of a day writing declaration overrides for it and the result was worse documentation than the library's own website.

Generic React components. Anything with render props or a polymorphic `as` prop turns into a signature I can't read and can't confidently modify. I've caught myself reaching for `any` on these and then feeling guilty, which is the worst of both worlds.

And the ceremony around narrow one-off shapes. If I'm mapping an array into a temporary structure that gets consumed four lines later, writing an interface for it adds nothing. Inference handles most of these, but not all, and the ones it misses feel arbitrary.

## Where I've landed

Worth it, clearly, but not because of the type system's expressiveness — because of null safety and refactor confidence. I renamed a core domain concept last month across 60 files and the compiler walked me through it. In the JS version I'd have grepped, missed something, and found out in production.

The busywork is real, but it concentrates in a few painful corners rather than spreading across everything. I'd do it again, and I'd do it earlier.
