A bump allocator with a free list is a reasonable middle ground when you can't use a real heap but also can't tolerate never freeing anything, which is the pure-bump-allocator limitation. Here's the basic design and the tradeoffs.

**Pure bump allocation first, since the free list builds on it.** You start with one big static buffer:

```c
static uint8_t heap[HEAP_SIZE];
static size_t bump_offset = 0;

void *bump_alloc(size_t size) {
    size = (size + 7) & ~7;              // round up to 8-byte alignment
    if (bump_offset + size > HEAP_SIZE) return NULL;
    void *ptr = &heap[bump_offset];
    bump_offset += size;
    return ptr;
}
```

This is essentially free — a pointer add and a bounds check, no metadata scanning, no locking concerns if you're single-threaded. The catch is there's no `free()` that does anything: the offset only moves forward. Fine for allocations that live for the whole program (init-time buffers, lookup tables) but useless if you're allocating and releasing things in a loop.

**Adding a free list gets you reuse, at a real cost in complexity and per-allocation overhead.** Each allocation gets a small header before the returned pointer:

```c
typedef struct block_header {
    size_t size;
    struct block_header *next_free;
} block_header_t;

static block_header_t *free_list = NULL;

void *my_alloc(size_t size) {
    size = (size + 7) & ~7;

    block_header_t *prev = NULL, *cur = free_list;
    while (cur) {
        if (cur->size >= size) {
            if (prev) prev->next_free = cur->next_free;
            else free_list = cur->next_free;
            return (void *)(cur + 1);       // memory just past the header
        }
        prev = cur;
        cur = cur->next_free;
    }

    // no suitable free block, fall back to bumping
    block_header_t *hdr = bump_alloc(sizeof(block_header_t) + size);
    if (!hdr) return NULL;
    hdr->size = size;
    return (void *)(hdr + 1);
}

void my_free(void *ptr) {
    block_header_t *hdr = (block_header_t *)ptr - 1;
    hdr->next_free = free_list;
    free_list = hdr;
}
```

`my_free` just prepends the block back onto a singly-linked free list — no coalescing, no bookkeeping about neighbors. `my_alloc` checks the free list first (first-fit, in this version — walks until it finds a block big enough) and only falls through to bumping fresh memory if nothing on the free list fits.

**Fragmentation is the honest tradeoff here, and it's handled badly, on purpose, because handling it well is what a general-purpose allocator does at much higher cost.** Since there's no coalescing of adjacent free blocks and no splitting of oversized ones (this version returns a block that's bigger than requested rather than splitting off the remainder), you accumulate free blocks of specific sizes that only satisfy requests of roughly that size. If your allocation sizes are heterogeneous — some 16 bytes, some 400 bytes, mixed freely — you'll end up with free blocks that never get reused because nothing you ever request is close to their size, and the bump pointer keeps climbing for new sizes even while "wasted" freed memory sits unused in the list. This is worse fragmentation behavior than a real allocator like dlmalloc, which coalesces neighbors on free and splits blocks on alloc specifically to fight this.

The tradeoffs versus a general-purpose allocator, concretely:

- **No coalescing** means adjacent freed blocks don't merge back into one larger block, so you can end up "free" but unable to satisfy a large request even though the total free memory would technically cover it.
- **No splitting** means a request for 8 bytes that reuses a 200-byte free block wastes 192 bytes for as long as that block is in use again.
- **First-fit free-list search is O(n)** in the number of free blocks, versus the segregated free lists / binning that real allocators use to get closer to O(1).
- **What you get in exchange:** no external dependency, a tiny and fully auditable code path (important for MISRA/safety-critical contexts), deterministic worst-case behavior for the bump path, and zero risk of the heap corruption bugs that come from complex allocator metadata.

If your embedded workload has a small, fixed set of allocation sizes (common in firmware — fixed-size message buffers, fixed-size task control blocks), consider running several separate free lists, one per size class, instead of one general list — that turns the O(n) search into O(1) and sidesteps the fragmentation problem almost entirely, since same-size blocks are always interchangeable. That's basically a slab allocator and is usually the better fit than a general first-fit free list once you know your allocation sizes ahead of time, which in embedded work you usually do.
