A covering index avoids a table lookup (a "bookmark lookup" back into the clustered index, in MySQL/InnoDB terms) whenever every column the query needs — both the columns in the `WHERE` clause and every column in the `SELECT` list — is present in the index itself. When that's true, MySQL can satisfy the entire query from the index's own leaf pages without ever visiting the underlying table row. That's what `Using index` in the `Extra` column means: the index alone was "covering" enough to answer the query.

Let's walk through a concrete example. Suppose you have:

```sql
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT,
  status VARCHAR(20),
  created_at DATETIME,
  total DECIMAL(10,2)
);

CREATE INDEX idx_customer ON orders (customer_id);
```

And you run:

```sql
SELECT customer_id, status
FROM orders
WHERE customer_id = 42;
```

With only `idx_customer` on `customer_id`, `EXPLAIN` gives you something like:

```
id  select_type  table   type  key           key_len  rows  Extra
1   SIMPLE       orders  ref   idx_customer  4        12    Using where
```

`type: ref` and `key: idx_customer` tell you the index is used to locate matching rows efficiently — that part is fine. But `Extra` says `Using where`, not `Using index`, because `status` isn't in the index. For every one of those 12 matching rows, MySQL has to take the `customer_id` value found in the index, follow it into the clustered index (the primary key B-tree, where InnoDB stores full rows), and pull `status` from there. That's the table lookup — one extra random I/O per matching row, which adds up fast on a large table with a selective-but-not-tiny result set.

Now add `status` to the index so it's a genuine covering index for this query:

```sql
CREATE INDEX idx_customer_covering ON orders (customer_id, status);
```

Re-run the same query and `EXPLAIN` now shows:

```
id  select_type  table   type  key                    key_len  rows  Extra
1   SIMPLE       orders  ref   idx_customer_covering  4        12    Using index
```

Same access type, same estimated rows, but `Extra` now reads `Using index` — MySQL found `customer_id` to satisfy the `WHERE` clause and `status` to satisfy the `SELECT`, both in the same index leaf entries, so it never touches the table. This matters most when you're scanning or seeking many rows: turning N random-access lookups into zero is the entire performance win, and it's why covering indexes are a go-to trick for read-heavy hot paths — you're trading a slightly wider (and slightly more expensive to maintain) index for eliminating a whole class of I/O at read time.

A quick note on the third flag you mentioned, `Using filesort`, because it's a different axis of the same output column and people conflate the two. `Using filesort` shows up when MySQL has to do an additional sorting pass that it can't satisfy from index order — typically because you're sorting by a column, or column combination, that doesn't match the index's leading columns in the right order. It's independent of `Using index`/`Using where`: a query can be fully covered by an index and still need `Using filesort` if the `ORDER BY` doesn't align with that index's column order, and conversely a query with no covering index at all can avoid `Using filesort` entirely if the index it does use already produces rows in the order requested.

So, in short: `Using index` means "answered from the index alone, no table lookup." `Using where` (without `Using index`) on an index-using plan means "the index found the rows, but at least one needed column forced a trip back to the table." `Using filesort` means "an extra sort step was required," and it can appear alongside either of the other two depending on whether the `ORDER BY` happens to match the index you're using for lookups.
