The compiler isn't inferring lifetimes in the clever sense — it's applying three fixed, purely syntactic rules to fill in the annotations you left out. If the rules produce a complete signature, your code compiles. If they don't, you get the "missing lifetime specifier" error. That's the whole mechanism, and once you know the rules you can predict the outcome by looking at a signature.

Some terminology first: an *input position* is a lifetime in a parameter type, an *output position* is a lifetime in the return type. The rules are:

1. Every elided lifetime in input position gets its own fresh lifetime parameter.
2. If there is exactly one input lifetime (elided or not), it is assigned to every elided output lifetime.
3. If one of the parameters is `&self` or `&mut self`, the lifetime of `self` is assigned to every elided output lifetime.

Rule 1 always runs first. Then rule 2 is tried, then rule 3. If elided output lifetimes remain unfilled after all three, elision fails and you must annotate.

**Example that compiles:**

```rust
fn first_word(s: &str) -> &str
```

Rule 1 gives the parameter a lifetime: `fn first_word<'a>(s: &'a str) -> &str`. There is now exactly one input lifetime, so rule 2 fires and assigns it to the return type:

```rust
fn first_word<'a>(s: &'a str) -> &'a str
```

Nothing is left elided, so it compiles. This is why the vast majority of single-reference functions never need annotations.

**Example that doesn't:**

```rust
fn longest(x: &str, y: &str) -> &str
```

Rule 1 gives `fn longest<'a, 'b>(x: &'a str, y: &'b str) -> &str`. Rule 2 doesn't apply — there are two input lifetimes, not one. Rule 3 doesn't apply — there's no `self`. The return lifetime is still unknown, so the compiler stops and asks you. It genuinely cannot tell whether the result borrows from `x` or `y`; that's a semantic question the rules don't attempt to answer. You write it yourself:

```rust
fn longest<'a>(x: &'a str, y: &'a str) -> &'a str
```

**Where rule 3 saves you:**

```rust
impl Parser {
    fn field(&self, name: &str) -> &str { /* ... */ }
}
```

Rule 1 assigns two fresh lifetimes. Rule 2 fails, same as before — two inputs. But rule 3 applies, and the return type is tied to `&self`:

```rust
fn field<'a, 'b>(&'a self, name: &'b str) -> &'a str
```

This is the rule people trip over, because it's silently opinionated. The returned `&str` borrows from `self`, never from `name`. If you actually wanted to return a slice of `name`, elision gives you the wrong signature and you'll get a confusing borrow error at the call site rather than at the definition. In that case annotate explicitly and tie the output to `'b`.

One more thing worth knowing: these rules apply to `fn` signatures and `impl` blocks. They do not apply to struct definitions — a struct holding a reference always needs an explicit lifetime parameter, no exceptions.
