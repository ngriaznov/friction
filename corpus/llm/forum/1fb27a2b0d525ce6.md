The pattern isn't slow because the input is long. It's slow because there are exponentially many ways for the regex engine to *try* to match it, and it insists on trying all of them before it gives up.

Here's a pattern shaped like yours:

```
^(\s*\w+)*$
```

Innocent enough — "a line made of words separated by optional whitespace." Now feed it a string that almost matches but fails at the very end:

```
"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaa!"
```

Thirty `a`s and a `!`. On my machine this takes about 40 seconds. Add one more `a` and it takes 80.

## Why it blows up

The problem is that the outer `*` and the inner `\w+` can both consume the same characters, and the engine has no way to know which split is "right" until it tries.

Consider just `aaaa`. The group `(\s*\w+)` can match:

- `aaaa` in one iteration
- `aaa` + `a` in two
- `aa` + `aa`
- `aa` + `a` + `a`
- `a` + `aaa`
- ... and so on

Every way of cutting a string of *n* identical characters into ordered non-empty pieces is a valid path, and there are 2^(n-1) of those. For a backtracking engine (PCRE, Python's `re`, Java, JavaScript, .NET) each one is a separate branch to explore.

If the string matches, the engine finds a path early and stops — you never notice. If the string *fails*, there's no early exit. The trailing `!` can't match `$`, so the engine backs up, reshuffles the split, and tries again. And again. It has to exhaust all 2^(n-1) arrangements before it can conclude "no match." That's the catastrophe: the cost is paid only on failure, which is exactly the input an attacker controls.

The general red flag is a quantifier inside a group that is itself quantified, where the two can match overlapping text: `(a+)+`, `(a|a)*`, `(\s*\w+)*`, `(.*,)*`.

## Fixing it

Make the alternatives disjoint so there's only one way to split the input. Since a separator must be whitespace and a word must not be, anchor the structure:

```
^\w+(\s+\w+)*$
```

Now `\s+` and `\w+` can't compete for the same characters — there is exactly one possible parse of any input, and failure is detected in linear time. Same 31-character string: microseconds.

Two other options:

**Atomic groups / possessive quantifiers**, where your engine supports them, tell the engine not to backtrack into a group once it's matched:

```
^(?>\s*\w+)*$
```

**A non-backtracking engine.** Go's `regexp`, Rust's `regex`, and RE2 are all built on automata and have no backtracking to catastrophe with. If you're matching untrusted input and can switch, that's the durable fix — rewriting patterns by hand only protects the ones you remember to audit.
