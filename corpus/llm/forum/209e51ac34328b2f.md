**Q: How would I design a CLI tool in Python to deduplicate a large photo library using perceptual hashing?**

**A:**

The short version: hash every image with a perceptual hash, bucket images whose hashes are close together by Hamming distance, then treat each bucket as a candidate duplicate group for review. The details worth getting right are which hash to use and how you handle bursts.

**Why a perceptual hash instead of a checksum**

A cryptographic checksum like SHA-256 tells you whether two files are byte-identical, nothing more. Re-save a JPEG at a different quality setting, resize it, or strip its EXIF data, and the checksum changes completely even though the image looks the same to a human. A perceptual hash instead derives a fingerprint from the image's visual content — usually by shrinking it to a small fixed size, converting to grayscale, and encoding relative pixel intensities (or frequency-domain coefficients, for pHash specifically) into a bit string. Two images that look alike produce hashes that differ in only a handful of bits, regardless of file format, compression level, or minor resizing.

`dHash` (difference hash) is a good default: it's fast to compute and reasonably robust to compression artifacts and small resizes. `pHash` (based on the discrete cosine transform) is more robust still, particularly to changes in aspect ratio or heavier compression, at the cost of being slower to compute over a large library. For a first pass over tens of thousands of photos, dHash is usually the pragmatic choice; you can always re-run pHash on the candidate groups dHash surfaces if you want a second opinion.

**Bucketing by Hamming distance**

Once every image has a hash (a 64-bit integer is typical for both dHash and pHash), you compare pairs by Hamming distance — the number of differing bits. Comparing every image to every other image is O(n²), which gets slow past a few thousand photos, so in practice you want a BK-tree or a locality-sensitive hashing index built over the hash space, which lets you query "all hashes within distance k of this one" in roughly logarithmic time instead of scanning the whole set.

A distance threshold of 5–10 (out of 64 bits) is a reasonable starting point for catching resized or recompressed duplicates without also catching genuinely different photos. Anything below that and you'll miss real duplicates that went through heavier processing; anything much above it and you'll start grouping visually similar but distinct photos together, which brings us to the harder problem.

**Burst-mode shots**

This is the case that trips up naive implementations. A three-shot burst of someone blinking will produce near-identical hashes — often within the same Hamming distance you're using to catch actual duplicates — because the frames are visually almost the same. Treating them as duplicates and auto-deleting all but one is exactly the kind of mistake that erodes trust in a dedup tool.

The practical fix is to never auto-delete based on hash proximity alone. Surface every group as a candidate for manual review, and include capture timestamp (from EXIF) alongside the hash distance in that review. Photos taken within a second or two of each other with a very small hash distance are almost certainly a burst, not a duplicate, and are worth flagging differently in your UI than two files with the same hash distance but timestamps months apart, which are far more likely to be a genuine re-save of the same original. Some tools also factor in file size and resolution deltas as a secondary signal: an identical hash but very different resolution is a strong indicator of a genuine duplicate rather than a burst frame.
