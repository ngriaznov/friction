So I've been putting this off for about two years and finally had to deal with it. Branch had 41 commits on it. Actual meaningful changes: maybe six. The rest were things like "wip", "wip 2", "fix", "fix the fix", "why", and one that just said "asdf" which I'm not proud of.

Reviewer very politely asked if I could "tidy the history a bit" before she looked at it. Fair.

`git rebase -i main` drops you into an editor with all 41 commits listed oldest first, each with `pick` in front. You change `pick` to something else to tell git what to do. The ones I actually used:

- `pick` — keep it as is
- `squash` (or `s`) — fold into the commit above, and you get to edit the combined message
- `fixup` (or `f`) — same but throws the message away
- `reword` (or `r`) — keep the changes, edit the message
- `drop` (or `d`) — delete it entirely

Big thing that took me a minute to internalise: `squash`/`fixup` merge **upward**, into whatever is above them in the list. So you put `pick` on the commit you want to survive and mark everything after it as `fixup`. I had it backwards on my first attempt and produced garbage, but that's what `git rebase --abort` is for and I used it three times.

First real pass I just went through and marked every "wip"/"fix" as `f` under whichever real commit it belonged to. That got 41 down to 7. Then a second `rebase -i` with `reword` on all seven to write messages that a human could read.

**The conflict.** Halfway through, on commit 5 of 7, rebase stops and tells me `src/handlers/upload.py` conflicts. Which makes sense in hindsight — I'd rewritten that file twice on the branch, and by squashing the intermediate steps I'd asked git to replay a change that assumed a state that no longer existed.

Resolution is the same as any merge conflict, edit the file, but the part I didn't know: you do **not** commit. You `git add` the resolved file and then `git rebase --continue`. If you run `git commit` you get a mess. (I ran `git commit`. I got a mess. `git rebase --abort` again.)

Second gotcha: while you're mid-rebase you're in detached HEAD and `git status` is genuinely useful — it prints exactly what step you're on and what to do next. I'd been ignoring that output for years.

Then `git push --force-with-lease`. Use `--force-with-lease`, not `--force`. If someone else pushed to your branch in the meantime, lease refuses; plain force silently deletes their work.

Diff is identical to before, history is seven readable commits, reviewer approved it the next morning. Should have learned this ages ago.
