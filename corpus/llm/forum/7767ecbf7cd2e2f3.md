A covering index avoids the table lookup when **every column the query touches — SELECT list, WHERE, ORDER BY, GROUP BY — is present in the index itself.** At that point InnoDB can answer entirely from the secondary index B-tree and never has to follow the primary key back into the clustered index.

That second step is the thing you're trying to eliminate. Every InnoDB secondary index entry stores the indexed columns plus the primary key value. If you select a column that isn't in the index, the engine has to take that PK and do a separate lookup in the clustered index, once per matching row. On a query returning 50,000 rows, that's 50,000 random-ish reads.

Here's a concrete example. Table:

```sql
CREATE TABLE orders (
  id          INT UNSIGNED NOT NULL AUTO_INCREMENT,
  customer_id INT UNSIGNED NOT NULL,
  status      TINYINT NOT NULL,
  total_cents INT NOT NULL,
  created_at  DATETIME NOT NULL,
  notes       TEXT,
  PRIMARY KEY (id),
  KEY idx_customer (customer_id)
) ENGINE=InnoDB;
```

And the query:

```sql
SELECT customer_id, total_cents
FROM orders
WHERE customer_id = 4711
ORDER BY total_cents DESC;
```

## Before

```
+----+-------------+--------+------+---------------+--------------+---------+-------+------+---------------------------------------+
| id | select_type | table  | type | possible_keys | key          | key_len | ref   | rows | Extra                                 |
+----+-------------+--------+------+---------------+--------------+---------+-------+------+---------------------------------------+
|  1 | SIMPLE      | orders | ref  | idx_customer  | idx_customer | 4       | const | 8214 | Using where; Using filesort           |
+----+-------------+--------+------+---------------+--------------+---------+-------+------+---------------------------------------+
```

Two problems visible in `Extra`:

- **`Using where`** here means rows are being filtered after being read — but more importantly, note the *absence* of `Using index`. Without it, the engine is reading the index to find PKs and then hitting the clustered index for `total_cents`. That's 8,214 lookups.
- **`Using filesort`** means the index order doesn't match the requested sort order, so MySQL materializes the result set and sorts it separately. On a big result set this spills to a temp file on disk.

## After

Add a composite index that includes the sort column:

```sql
ALTER TABLE orders ADD KEY idx_cust_total (customer_id, total_cents);
```

```
+----+-------------+--------+------+----------------+----------------+---------+-------+------+--------------------------+
| id | select_type | table  | type | possible_keys  | key            | key_len | ref   | rows | Extra                    |
+----+-------------+--------+------+----------------+----------------+---------+-------+------+--------------------------+
|  1 | SIMPLE      | orders | ref  | idx_cust_total | idx_cust_total | 4       | const | 8214 | Using index              |
+----+-------------+--------+------+----------------+----------------+---------+-------+------+--------------------------+
```

**`Using index`** is the payoff. The index now contains `customer_id` and `total_cents`, and the PK (`id`) is there implicitly — that covers every column in the query. Zero clustered-index reads.

The `Using filesort` also vanished, for a separate reason: the index is ordered `(customer_id, total_cents)`, so within the `customer_id = 4711` range the rows are already in `total_cents` order. MySQL walks the index backwards for `DESC` and hands them back as-is.

## Things that break the covering property

- **Adding a column to the SELECT list.** `SELECT customer_id, total_cents, status` reintroduces the lookup, because `status` isn't in the index. This is the most common way a covering index silently stops covering: someone adds a field to the query six months later and nobody re-checks the plan.
- **`SELECT *`.** Never covers on any table with more columns than the index.
- **Column order in the index.** `KEY (total_cents, customer_id)` would still technically cover, but you'd lose the `ref` access type on `customer_id` and end up with an index scan. Leading columns need to match your equality predicates.
- **BLOB/TEXT columns.** `notes` can't be usefully covered.

## Reading `Extra` in general

- `Using index` — covered, no table lookup. What you want.
- `Using where` alone — rows read from the table, then filtered. Normal, not necessarily bad.
- `Using index condition` — index condition pushdown. Some filtering happens at the index level, but a table lookup still happens for surviving rows. Better than nothing, worse than covering.
- `Using filesort` — an explicit sort pass. Fixable by making the index order match your `ORDER BY`, as above.
- `Using temporary; Using filesort` together usually means a `GROUP BY` that no index satisfies.

One caveat: covering indexes are not free. `idx_cust_total` is wider than `idx_customer`, so it costs more disk, more buffer pool, and more work on every write. Adding one per query gets expensive fast. Add them where the query is hot and the row count is large, and check `EXPLAIN` again after any change to the SELECT list.
