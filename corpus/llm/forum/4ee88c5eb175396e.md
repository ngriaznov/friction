P-hacking is what happens when the analysis has enough researcher-degrees-of-freedom — which subgroup to test, which covariates to include, when to stop collecting data, which of several outcome measures to report — that a "significant" result can be found in noise just by trying enough variations and reporting the one that worked. The multiple comparisons problem is the more specific, more mechanical version of this: even with no flexibility in the analysis at all, testing many independent hypotheses at a fixed alpha guarantees you'll find some "significant" results by chance alone, purely from running enough tests.

Here's the worked example. Say you test 20 independent null hypotheses, each at alpha = 0.05, and suppose every single one of them is actually true (no real effects anywhere — this is the null case we're worried about). Under a true null, each individual test has exactly a 5% chance of falsely rejecting (a Type I error) just from sampling noise. The probability that a single test does *not* produce a false positive is 0.95. If the tests are independent, the probability that *none* of the 20 produce a false positive is:

0.95^20 ≈ 0.358

So the probability of getting *at least one* false positive somewhere among the 20 tests is:

1 − 0.358 ≈ 0.642

That's a 64% chance of at least one "statistically significant" result, from data with no real effect in it whatsoever, just by virtue of running 20 tests. This is the whole problem in one number: alpha = 0.05 controls the error rate *per test*, not across a family of tests, and people intuitively (and wrongly) read "p < 0.05" as "5% chance this is a fluke" regardless of how many tests were run to get there.

The Bonferroni correction is the simplest fix: divide your desired family-wise alpha by the number of tests, and use that as the per-test threshold. For 20 tests targeting a family-wise error rate of 0.05:

0.05 / 20 = 0.0025

So instead of calling anything with p < 0.05 significant, you'd require p < 0.0025 for any individual test to count, across all 20. Plugging that back into the same math: the per-test false positive probability is now 0.0025, so the family-wise probability of at least one false positive is 1 − (1 − 0.0025)^20 ≈ 0.0488, back down near the intended 5% for the whole family rather than for each test in isolation.

Two honest caveats people often skip. First, Bonferroni assumes worst-case dependence and is conservative when tests are correlated (not truly independent, as in the example) — it controls the family-wise error rate correctly but at a real cost in statistical power, meaning real effects are more likely to be missed as the number of tests grows, since the bar per test gets proportionally harder to clear. For large numbers of comparisons, methods that control the false discovery rate instead (Benjamini-Hochberg being the standard one) are usually preferred in fields like genomics that routinely run thousands of tests, because FDR control accepts a controlled proportion of false positives among the *significant* results rather than trying to eliminate any single false positive across the whole family, which gives back a lot of the power Bonferroni gives away.

Second — and this is the part that actually matters for spotting p-hacking in the wild rather than just computing corrections — the correction only helps if all the tests that were actually run get counted. If someone runs 20 comparisons, finds one at p = 0.03, and reports only that one without mentioning the other 19, no correction applied after the fact fixes anything, because the correction needs the denominator (the true number of tests attempted) to be honestly reported in the first place. That's the mechanism behind most real-world p-hacking: not lying about the numbers in any single test, just selectively reporting which of many tests get written up.
