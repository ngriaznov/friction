A covering index avoids a table lookup when every column the query needs — both the ones in the `WHERE` clause and the ones in the `SELECT` list — is present in the index itself, so MySQL never has to follow the index entry back to the clustered/primary table (a "bookmark lookup") to fetch the rest of the row.

Say you have:

```sql
CREATE TABLE orders (
  id INT PRIMARY KEY,
  customer_id INT,
  status VARCHAR(20),
  created_at DATETIME,
  total DECIMAL(10,2)
);
```

and a query like:

```sql
SELECT customer_id, total FROM orders WHERE status = 'shipped' ORDER BY created_at;
```

With only, say, an index on `status`, `EXPLAIN` would show something like:

```
type: ref
key: idx_status
rows: 41203
Extra: Using where; Using filesort
```

`Using where` here means MySQL used the index to find matching rows on `status`, but still had to go back to the base table to fetch `customer_id` and `total` for each matching row, since those columns aren't in `idx_status`. `Using filesort` means the results then had to be sorted separately in memory/on disk because the index order (by `status`) doesn't match the requested order (`created_at`) — this is a separate, additional cost, not part of the "covering" question, but it commonly shows up alongside these queries and is worth fixing at the same time.

Now add a composite index that includes everything the query touches, in an order that also satisfies the sort:

```sql
CREATE INDEX idx_status_created_covering
  ON orders (status, created_at, customer_id, total);
```

`EXPLAIN` now shows:

```
type: ref
key: idx_status_covering
rows: 41203
Extra: Using index; Using where
```

`Using index` (sometimes called a "covering index scan") means every column needed by the query is satisfied directly from the index's own leaf pages — MySQL never touches the primary table at all for this query. That's the win: for a large table this can be an order of magnitude fewer page reads, because a secondary index is typically much narrower than the full row and more of it fits in the buffer pool, and you skip the random I/O of the extra lookup per matching row entirely. `Using where` can still appear alongside `Using index` — it just means a filter condition was applied, it doesn't imply the extra table access; the presence or absence of the table access is what `Using index` alone (without a separate "Using where" implying re-fetch) tells you.

Also notice `Using filesort` disappeared. Because `created_at` is the second column in the composite index, rows matching a given `status` are already stored in `created_at` order within the index, so MySQL can walk the index directly for the `ORDER BY` instead of collecting matches and sorting them afterward. This is a nice side effect of composite index design but only works because `status` (the equality predicate) comes before `created_at` (the sort column) in the index — swap that order and you'd lose the sort benefit even though you'd keep the covering benefit.

Two practical notes: column order in the composite index matters — equality-filtered columns first, then columns used for range/sort, then the remaining "just needs to be included" columns last — and covering indexes trade write cost for read cost, since every insert/update now has to maintain a wider index. For a table that's read far more than written, that trade is usually worth it; for a heavy-write table, measure before adding several wide covering indexes speculatively.
