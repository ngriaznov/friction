The important distinction to get right first is `Type=simple` vs `Type=notify`, because it changes what systemd considers "started."

With `Type=simple` (the default), systemd considers the service started the moment it forks the process — it does not wait for your daemon to actually finish initializing. That's fine for something trivial, but if your daemon has a slow startup (opening a database connection, warming a cache, binding a socket after some setup), anything that depends on it via `After=`/`Requires=` may race ahead before it's actually ready.

`Type=notify` fixes this by having your program call `sd_notify(0, "READY=1")` (from libsystemd, or reimplemented by hand — it's just a datagram to a Unix socket named in `$NOTIFY_SOCKET`, so you don't strictly need to link libsystemd) once it's genuinely ready to serve. systemd blocks "service started" until that notification arrives. This also unlocks watchdog support: your daemon periodically calls `sd_notify(0, "WATCHDOG=1")` as a keepalive, and if `WatchdogSec=` elapses without one arriving, systemd considers the process hung and kills/restarts it. This is a real liveness check, not just "is the process running" — a deadlocked-but-still-running process gets caught by this in a way `Type=simple` + `Restart=on-failure` alone never would, because from the OS's perspective a hung process hasn't failed, it's just stopped doing anything.

`Restart=on-failure` covers the crash case: it restarts the unit if it exits with a non-zero code, is killed by a signal, or times out — but not on a clean `0` exit, which is what you want for something meant to keep running (you don't want a graceful shutdown treated the same as a crash and immediately restarted). Pair it with `RestartSec=` to avoid a hot crash-loop hammering the CPU with zero-delay restarts, and consider `StartLimitIntervalSec=`/`StartLimitBurst=` so systemd gives up and reports failure after too many restarts in too short a window rather than looping forever.

A minimal example putting this together:

```ini
[Unit]
Description=My Daemon
After=network-online.target
Wants=network-online.target

[Service]
Type=notify
ExecStart=/usr/local/bin/mydaemond --config /etc/mydaemon/config.yaml
Restart=on-failure
RestartSec=5s
WatchdogSec=30s
StartLimitIntervalSec=60
StartLimitBurst=5
User=mydaemon
Group=mydaemon

[Install]
WantedBy=multi-user.target
```

With `WatchdogSec=30s`, your program needs to call `sd_notify(0, "WATCHDOG=1")` at less than half that interval — systemd's own docs recommend pinging at roughly `WATCHDOG_USEC/2` (available to your process as an env var once `Type=notify` is active), so every 10-15 seconds here, to leave margin for scheduling jitter before you'd falsely trip the watchdog.

One gotcha: if you set `Type=notify` but your program never actually calls `sd_notify`, systemd will wait for `TimeoutStartSec` (default 90s) and then consider the start a failure and kill it — a common source of "my service that used to work now fails to start" after switching from `simple` to `notify` without adding the notify call in code. Test it manually with `systemd-notify --ready` from a shell first if you want to isolate whether the unit file or the application code is the problem.
