The short version: hash perceptually, bucket by Hamming distance, and treat burst sequences as a separate problem from duplicates — because they are.

**Why not a checksum**

A byte-level digest answers "are these the same file," which is almost never the question. Re-encoding a JPEG at a different quality, stripping EXIF, or resizing changes every byte while leaving the picture identical. In a real photo library the bulk of your duplicates arrive exactly that way: a messaging app downscales to 1600px, a backup tool re-compresses, an editor writes out a copy with a different color profile. SHA-256 sees four unrelated files.

A perceptual hash summarizes image content. dHash is the one I'd start with — downscale to 9×8 grayscale, compare each pixel to its right neighbor, emit one bit per comparison, and you have 64 bits. It's cheap, it's about ten lines with Pillow, and it's robust to scaling and moderate compression. pHash (DCT-based) tolerates heavier artifacts and small gamma shifts but costs several times more per image; use it as a second pass on ambiguous pairs rather than as your primary hash. aHash is not worth it — too many false positives on flat backgrounds.

```python
from PIL import Image

def dhash(path, size=8):
    img = Image.open(path).convert("L").resize((size + 1, size), Image.LANCZOS)
    px = list(img.getdata())
    bits = 0
    for row in range(size):
        base = row * (size + 1)
        for col in range(size):
            bits = (bits << 1) | (px[base + col] < px[base + col + 1])
    return bits
```

**Bucketing near-duplicates**

Similarity is popcount of the XOR. Distance 0–2 is essentially certain, 3–6 is "almost always the same photo," above 10 is noise. Pick a threshold, don't pick a similarity percentage — the percentage hides the fact that you're working in a 64-dimensional Hamming space.

The naive approach is all-pairs, which is O(n²) and dies somewhere around 50k images. Two practical fixes:

1. **BK-tree.** Build a metric tree over your hashes and query each one for neighbors within distance *k*. Sublinear in practice for small *k*, and it's maybe 40 lines of code.
2. **Multi-index hashing.** Split the 64-bit hash into four 16-bit chunks. By pigeonhole, any two hashes within distance 3 must agree exactly on at least one chunk. Index each chunk in a dict, look up candidates, then verify with a real distance computation. This is the one I'd use — it's just four dictionaries and it scales to millions.

Then union-find over the surviving pairs to form groups, rather than treating each pair independently. Otherwise you get overlapping groups and your delete logic gets confusing fast.

**The burst-mode problem**

This is where naive tools do damage. Ten frames shot at 8fps of the same static scene will land within distance 2–4 of each other. They are genuinely different photographs and the user wants to keep them, or at least choose among them.

Perceptual hashing alone cannot distinguish this case, so use metadata:

- If EXIF `DateTimeOriginal` values are within a couple of seconds and the camera model matches, flag the group as a burst rather than a duplicate set.
- If dimensions and file size are near-identical too, that reinforces it — real duplicates usually differ in resolution or bytes, because that's how they got created.
- Conversely, if two files have the same hash but were taken on the same second *and* have identical dimensions and byte length, you're probably looking at a literal copy.

Present bursts in your report under a different heading, don't auto-select a keeper, and require an explicit flag before the tool will touch them. Your users will forgive a missed duplicate. They will not forgive a deleted photo.
