A bump allocator with a free list is a reasonable choice here, but it's worth being precise about what you're building, because "bump allocator with a free list" is really two allocators glued together and the seam is where the bugs live.

## The basic bump allocator

The pure form is trivial. You own a region of memory, you keep a cursor, and allocation moves the cursor forward:

```c
static uint8_t heap[HEAP_SIZE];
static size_t  cursor = 0;

void *bump_alloc(size_t n) {
    n = (n + (ALIGN - 1)) & ~(size_t)(ALIGN - 1);   /* round up */
    if (n > HEAP_SIZE - cursor) return NULL;         /* no overflow */
    void *p = &heap[cursor];
    cursor += n;
    return p;
}
```

Note the bounds check is written as `n > HEAP_SIZE - cursor` rather than `cursor + n > HEAP_SIZE`. The latter can overflow and wrap on a hostile size. `ALIGN` should be the alignment of your widest scalar — `_Alignof(max_align_t)` if you have it, otherwise 8 on most 32-bit targets with doubles.

That's the whole allocator. It's a handful of instructions and it never fragments, because it never frees. If your program's allocation pattern is phase-structured — build a bunch of objects, use them, throw them all away — you can add `bump_reset()` that sets `cursor = 0` and you're done. Arena-per-phase beats a free list for both speed and predictability, so check whether you actually need individual frees before you build one.

## Adding the free list

If you do need individual frees, the usual scheme is a segregated free list keyed by size class. Give every block a small header:

```c
typedef struct block {
    size_t size;            /* payload bytes, already aligned */
    struct block *next;     /* only valid while on a free list */
} block_t;
```

`free()` pushes the block onto the list for its size class. `alloc()` checks the appropriate list first and only bumps the cursor if the list is empty:

```c
void *pool_alloc(size_t n) {
    int cls = size_class(n);
    if (cls >= 0 && free_lists[cls]) {
        block_t *b = free_lists[cls];
        free_lists[cls] = b->next;
        return (uint8_t *)b + sizeof(block_t);
    }
    return bump_alloc(n + sizeof(block_t)); /* returns header-adjusted ptr */
}
```

With fixed size classes (say 16/32/64/128/256 bytes) you get O(1) alloc and free, no coalescing, no searching. That's the version I'd ship on an MCU.

## Fragmentation: what actually happens

The honest answer is that this scheme does not handle fragmentation, it *contains* it. Because blocks only ever return to the list for their own size class, memory freed from the 32-byte class can never satisfy a 64-byte request. Over a long run, your heap partitions itself into per-class pools sized by the historical high-water mark of each class. You get internal fragmentation from rounding requests up to a class, and permanent partitioning between classes.

For an embedded workload this is usually a feature, not a defect. The steady state is bounded and reachable: run your worst-case workload, look at the high-water mark of each class, and you have a number you can put in a design document. A general-purpose allocator with coalescing and splitting uses memory more efficiently but its worst case is much harder to characterize, and "harder to characterize" is exactly what you don't want in a system that has to run for months without a reboot.

If you can't tolerate the class partitioning, the next step up is a boundary-tag allocator with coalescing of adjacent free blocks — add a footer with the size, check the neighbors on free, merge when both are free. That's maybe 150 more lines and it gives up the O(1) free.

## Practical notes

- **Don't `free()` bump-allocated memory into a list it didn't come from.** If you mix a reset-style arena and a free-list pool in one program, keep them in separate regions.
- **Poison freed memory in debug builds.** `memset(payload, 0xDD, size)` on free catches use-after-free fast, and costs nothing in release.
- **Alignment applies to the payload, not the header.** Size the header to a multiple of `ALIGN` so the returned pointer stays aligned.
- **Interrupt safety.** If you allocate from an ISR, the list push/pop needs a critical section. If you can avoid allocating from an ISR at all, do that instead.

Measure before you elaborate. On most embedded projects the arena-reset version turns out to be sufficient, and every line you don't write is a line that can't be wrong at 3am in the field.
