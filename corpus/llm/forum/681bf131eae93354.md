**Q: Why does running many hypothesis tests inflate my false positive rate, and how does a Bonferroni correction actually fix it?**

Short answer: your alpha of 0.05 controls the false positive rate *per test*, not across a whole batch of tests. Run enough tests and you're almost guaranteed to see a "significant" result somewhere, even if nothing real is going on.

**Why it happens**

Say you're testing 20 completely independent hypotheses, all of which are genuinely null — there's no real effect anywhere. At alpha = 0.05, each individual test has a 5% chance of a false positive, and a 95% chance of correctly failing to reject the null. That sounds safe until you ask about the whole batch at once.

The probability that *all 20* tests correctly come back non-significant is:

```
0.95^20 ≈ 0.358
```

Which means the probability that *at least one* test falsely comes back significant is:

```
1 - 0.358 ≈ 0.642
```

So with 20 independent null hypotheses, you have roughly a 64% chance of getting at least one "statistically significant" result purely by chance — not because there's a real effect, but because you gave randomness 20 separate chances to produce a fluke. This is the multiple comparisons problem, and "p-hacking" is what happens when someone (often unintentionally) runs many tests, or many variations of one test, and reports only the one that came back below 0.05 as if it were the whole story.

This is exactly why "we tested 30 variables and found one significant correlation" is a red flag in a paper unless the analysis explicitly accounts for the number of tests run. It's also why pre-registration exists — it forces you to commit to which comparisons you're testing before you see the data, so you can't quietly test twenty things and report the one that worked.

**How Bonferroni fixes it**

The Bonferroni correction is blunt but easy to reason about: instead of comparing each p-value to your original alpha, you divide alpha by the number of tests, `m`, and use that as your new per-test threshold.

```
alpha_corrected = alpha / m
```

For our 20-test example with alpha = 0.05:

```
alpha_corrected = 0.05 / 20 = 0.0025
```

So instead of calling anything below p = 0.05 significant, you now require p < 0.0025 for any individual test to count. This pushes the *family-wise error rate* — the probability of at least one false positive across the whole batch — back down toward roughly 0.05, because you've made each individual test much harder to pass by chance.

You can check this arithmetic the same way as before. If every one of the 20 tests is null and each now has only a 0.0025 chance of a false positive, the probability of at least one false positive across all 20 is:

```
1 - (1 - 0.0025)^20 ≈ 0.0488
```

which lands right back near your original target of 5%, as intended.

**The tradeoff**

Bonferroni is conservative — it controls false positives well but at a real cost to statistical power, especially as `m` grows large. With 100 comparisons your per-test threshold drops to 0.0005, and a real, modest effect can easily fail to clear that bar. If you're running large numbers of tests (genomics, A/B testing many metrics at once) and want more power while still controlling error meaningfully, look at the Benjamini-Hochberg procedure instead, which controls the *false discovery rate* rather than the family-wise error rate and is much less punishing as `m` grows. Bonferroni is the right default when `m` is small and you need a strict, easy-to-defend guarantee; it's the wrong tool when you're screening hundreds of candidates and expect several real effects among them.
