**Q: How do I use Docker multi-stage builds to shrink my Node.js image? Mine is 900MB and I keep hearing this should be well under 200MB.**

**A:**

A 900MB Node image almost always means you're shipping the same layer twice: once for building (dev dependencies, a compiler toolchain for native modules, source files, maybe TypeScript output) and again because that build layer never gets removed. Multi-stage builds fix this by splitting the Dockerfile into stages and only copying the *artifacts* you need out of the build stage into a clean runtime image — everything else, including the entire `node_modules` used to build it, gets discarded when the final image is produced.

Here's the shape of it:

```dockerfile
# ---- build stage ----
FROM node:20 AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

# ---- runtime stage ----
FROM node:20-alpine
WORKDIR /app
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
CMD ["node", "dist/main.js"]
```

A few things doing the actual work here:

**Separate `npm ci` calls, not a copied `node_modules`.** The build stage installs everything, including devDependencies, because it needs the compiler, bundler, and type checker to produce `dist/`. The runtime stage runs its *own* `npm ci --omit=dev`, so it only installs production dependencies, fresh, without the giant devDependency tree ever touching the final image. Don't copy `node_modules` across stages with `COPY --from=build` — copy the built output and reinstall production deps clean.

**`node:20-alpine` for runtime.** The full `node:20` image bundles a lot you don't need at runtime — build tools, extra glibc packages, apt caches. Alpine is built on musl instead of glibc and is a fraction of the size, typically 40-60MB versus several hundred for the full Debian-based image. If you have native addons that specifically need glibc, `node:20-slim` (Debian, but stripped down) is a decent middle ground. Distroless images (`gcr.io/distroless/nodejs`) go further still, dropping the shell and package manager entirely, which is great for attack surface but makes debugging inside the container harder — worth it once you're confident the image is stable, less so while you're still iterating.

**`.dockerignore` matters more than people expect.** Without one, `COPY . .` in the build stage happily drags your local `node_modules`, `.git` directory, and test fixtures into the build context, which bloats build time and cache invalidation even if it doesn't directly bloat the final image. At minimum:

```
node_modules
.git
dist
*.log
```

**Layer ordering for cache reuse.** Copying `package*.json` and running `npm ci` *before* copying the rest of your source means Docker only re-runs the (slow) install step when your dependencies actually change, not on every source edit. This doesn't shrink the image, but it's the difference between a 5-second and a 90-second rebuild loop during development.

Put together, going from ~900MB to ~120MB is usually just: multi-stage split, alpine base, production-only install in the final stage, and a `.dockerignore` that isn't empty. None of these are exotic techniques individually — the size problem is almost always that one of these four is simply missing.
