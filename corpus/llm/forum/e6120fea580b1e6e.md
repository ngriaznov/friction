900MB for a Node image almost always means you're shipping the entire build toolchain — devDependencies, a compiler/bundler, source maps, the npm cache, and often a full Debian base — into production. Multi-stage builds fix this by letting you use a fat image to *build* the app and then throw that image away, copying only the finished artifacts into a slim one.

Here's roughly the shape of it for a typical TypeScript/webpack app:

```dockerfile
# ---- build stage ----
FROM node:20 AS build
WORKDIR /app

COPY package*.json ./
RUN npm ci

COPY . .
RUN npm run build          # tsc / webpack / vite / whatever
RUN npm prune --production # drop devDependencies from node_modules

# ---- runtime stage ----
FROM node:20-alpine
WORKDIR /app

COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY package*.json ./

USER node
EXPOSE 3000
CMD ["node", "dist/index.js"]
```

A few things doing the heavy lifting here:

**The build stage is allowed to be huge.** It has the full `node:20` image (Debian-based, includes build tools, python, etc. if you need node-gyp), all your devDependencies, and your raw source. None of that matters because it's discarded — only what you explicitly `COPY --from=build` survives into the final image.

**`npm prune --production` before copying node_modules.** This is easy to miss: if you `npm ci` once with all deps and never prune, you'll copy devDependencies (webpack, typescript, eslint, test frameworks — often the majority of node_modules by size) straight into your slim runtime image, defeating half the point. Alternatively, do two separate installs — one with `npm ci` for the build, and a second `npm ci --omit=dev` in the runtime stage — which some people prefer because it guarantees a clean install rather than relying on prune to catch everything.

**The runtime base.** `node:20-alpine` swaps Debian for Alpine Linux, which alone typically cuts 150-200MB off the base image because Alpine's package set and libc (musl instead of glibc) are much smaller. This is usually the single biggest lever after removing devDependencies. Watch out for native modules built against glibc — if anything in your dependency tree ships prebuilt binaries or uses node-gyp with glibc assumptions, you may need `node:20-slim` (Debian-based but stripped down) instead, or rebuild inside the alpine build stage so the binaries match musl.

If you want to go further, `gcr.io/distroless/nodejs20-debian12` gets you even smaller and more secure — no shell, no package manager, nothing but the Node runtime and your files — at the cost of debugging being harder since you can't `docker exec` into a shell that doesn't exist. Good for prod, more annoying in day-to-day troubleshooting.

**Don't forget `.dockerignore`.** Without one, `COPY . .` in the build stage will pull in `node_modules` from your host (wrong platform/arch binaries, plus enormous size), `.git`, build output from previous local runs, and anything else lying around. Something like:

```
node_modules
.git
dist
*.log
.env
```

This mostly matters for build cache efficiency and correctness rather than final image size (since the runtime stage only copies specific paths), but it prevents subtle bugs like stale local `dist/` output getting into your source copy and shadowing what `npm run build` produces.

Stack those together — pruned deps, alpine or distroless base, discarded build stage, sane dockerignore — and going from ~900MB to ~120MB is a completely normal outcome, not an aggressive target.
