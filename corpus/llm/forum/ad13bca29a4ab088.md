**Q: How do I write a simple bump allocator with a free list in C for an embedded target with no malloc?**

I'm targeting a microcontroller with no libc heap and need something better than static allocation for a handful of small, similarly-sized objects that get created and destroyed at runtime. What's a reasonable minimal allocator design here?

---

**A:**

For embedded work without a general-purpose `malloc`, a bump allocator paired with a free list is usually the right level of complexity — simple enough to audit by hand, fast enough to run in an interrupt handler if you need to, and predictable in a way that a full allocator with coalescing and multiple size classes is not.

### The basic bump allocator

A bump allocator carves memory out of a fixed-size static buffer (your "arena") by simply advancing a pointer:

```c
#define ARENA_SIZE 4096
static uint8_t arena[ARENA_SIZE];
static size_t bump_offset = 0;

void *bump_alloc(size_t size) {
    size = (size + 7) & ~((size_t)7); // 8-byte align
    if (bump_offset + size > ARENA_SIZE) {
        return NULL; // arena exhausted
    }
    void *ptr = &arena[bump_offset];
    bump_offset += size;
    return ptr;
}
```

That's it — no headers, no bookkeeping per allocation, just an offset that only ever moves forward. The catch is obvious: there's no way to give memory back. Once `bump_offset` reaches the end of the arena, you're done until you reset the whole thing, which is fine for a one-shot parsing pass but not for anything long-running.

### Adding a free list

If your objects are all the same size (or you're willing to round up to a small number of fixed size classes), you can recover individual allocations with a free list layered on top of the bump allocator. The trick is that a freed block, while unused, can store a pointer to the next freed block right inside itself — you don't need separate bookkeeping memory:

```c
typedef struct free_node {
    struct free_node *next;
} free_node_t;

static free_node_t *free_list = NULL;
#define BLOCK_SIZE 32 // fixed size class

void *pool_alloc(void) {
    if (free_list != NULL) {
        void *ptr = free_list;
        free_list = free_list->next;
        return ptr;
    }
    return bump_alloc(BLOCK_SIZE);
}

void pool_free(void *ptr) {
    free_node_t *node = (free_node_t *)ptr;
    node->next = free_list;
    free_list = node;
}
```

`pool_alloc` checks the free list first, and only falls through to the bump allocator when there's nothing to reuse. `pool_free` just prepends the freed block onto the list. Both operations are O(1) and use no additional storage beyond the arena itself, which is exactly what you want on a device with a few kilobytes of RAM total.

### The tradeoffs

Compared to a general-purpose allocator like dlmalloc or a first-fit heap, you're giving up a lot:

- **No variable-size allocations without size classes.** If your objects genuinely vary in size, you either round everyone up to the largest size class (wasting memory) or maintain multiple free lists, one per class, which adds complexity back in.
- **No coalescing.** A general allocator merges adjacent free blocks to satisfy larger requests later. Here, freed blocks only ever get reused at their original size, because the free list has no concept of adjacency.
- **Fragmentation is structural, not incidental.** In this scheme, "fragmentation" doesn't really apply in the traditional sense, since every block in a size class is interchangeable — but if you have multiple size classes and one class's free list is empty while another has plenty of spare capacity, that memory is effectively stranded. You cannot borrow across classes without a redesign.
- **No shrinking the arena.** The bump offset never decreases except via the free list recycling blocks it already handed out. If usage patterns are bursty, you're sized for peak demand at all times.

In exchange, you get O(1) allocation and deallocation with no fragmentation search, no locking concerns beyond whatever you already need for concurrent access, and a tiny, auditable code path — which matters a lot when you're debugging on a device with no debugger attached and a UART as your only window into what's happening.

For most embedded use cases with a small, known number of object types, this pattern (one bump arena, one free list per size class) covers the vast majority of needs. Reach for something more sophisticated only if you actually observe pathological memory pressure from stranded capacity across classes — don't build that complexity preemptively.
