The key design decision here is picking a hash that's tolerant of small pixel-level changes, and that rules out a byte-level checksum (MD5/SHA1/etc.) immediately. A cryptographic checksum changes completely if a single bit changes, which means two photos that are visually identical but were re-saved, re-compressed, or resized by even one pixel will produce completely unrelated hashes. That's fine for detecting exact-file duplicates (two copies of the same file), but it's useless for the much more common case of "same photo, different JPEG quality" or "same photo, thumbnail vs full-res."

Perceptual hashes solve this by hashing a low-frequency representation of the image content rather than its bytes. dHash (difference hash) is the simplest to implement and fast enough for a CLI tool: shrink the image to something like 9x8 grayscale pixels, then for each row set a bit if pixel[x] < pixel[x+1]. You end up with a 64-bit hash that's stable across resizing, mild recompression, and small brightness/contrast shifts. pHash is more robust to bigger transformations (rotation, more aggressive compression) because it uses a DCT and keeps the low-frequency coefficients, but it's slower and honestly overkill for a "clean up my photo library" tool. I'd default to dHash and only reach for pHash if you're seeing false negatives on real data.

For the deduplication logic itself:

1. Walk the library, compute a dHash for every image, and store (path, hash, mtime, file size) in a small SQLite database or even just a dict pickled to disk — you don't want to recompute hashes on every run.
2. Since exact hash equality is rare and near-duplicates are the norm, you need Hamming distance comparison, not a dict lookup. Bucket first: group images by the top N bits of the hash (or by a locality-sensitive hash bucket) so you're not doing O(n²) comparisons across the whole library. Within each bucket, do pairwise Hamming distance and treat anything under a threshold — 5 or fewer differing bits out of 64 is a common starting point — as a near-duplicate cluster.
3. Union-find (disjoint set) is the right data structure for grouping transitively related near-duplicates into clusters, rather than just pairs.

Now the part people usually get wrong: burst-mode shots. If someone holds the shutter for two seconds, you'll get 10-30 frames that are visually near-identical under dHash — same framing, same subject, tiny differences in exact pose or focus. These are *not* duplicates in the sense the user cares about; they're candidates for "pick the best one," not "delete all but one automatically." Two things help:

- Use EXIF timestamps (down to the sub-second field if the camera writes it) to detect burst sequences — a cluster of shots within ~1 second of each other from the same camera is almost certainly a burst, not separately-taken duplicate photos.
- Don't auto-delete burst clusters. Surface them as a review group instead ("these 14 photos look the same, pick your favorite") rather than silently keeping the first and discarding the rest. Sharpness/blur detection (variance of Laplacian) is a decent heuristic for suggesting which frame in the burst to keep, but let the human confirm before anything gets deleted.

For the CLI itself, `click` or `argparse` with subcommands like `scan`, `review`, and `purge` keeps the destructive step separate from the analysis step, which you want anyway given how much these thresholds need tuning per library. Log every match with its Hamming distance so users can retroactively adjust the threshold without rescanning.
