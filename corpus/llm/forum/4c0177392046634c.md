Your 900MB is almost entirely things you needed to *build* the app and don't need to *run* it. A multi-stage build lets you do the building in one image and then copy only the output into a second, much smaller one. Nothing from the first stage survives into the final image except what you explicitly copy.

Here's the shape of it. Assume a TypeScript app that compiles to `dist/`.

```dockerfile
# ---- build stage ----
FROM node:20 AS build
WORKDIR /app

COPY package.json package-lock.json ./
RUN npm ci                 # dev deps included — we need tsc

COPY . .
RUN npm run build          # emits dist/

RUN npm prune --omit=dev   # now node_modules is runtime-only

# ---- runtime stage ----
FROM node:20-alpine
WORKDIR /app
ENV NODE_ENV=production

COPY --from=build /app/node_modules ./node_modules
COPY --from=build /app/dist ./dist
COPY --from=build /app/package.json ./

USER node
CMD ["node", "dist/server.js"]
```

The `FROM ... AS build` names the first stage; `COPY --from=build` pulls files out of it. The build stage is discarded — it never gets pushed and never gets pulled by whatever runs your container.

Where the savings come from, roughly:

- **The base image.** `node:20` is about 1.1GB because it carries a full Debian userland plus build-essential, python, and git for native module compilation. `node:20-alpine` is around 130MB. That single line is usually more than half your reduction.
- **Dev dependencies.** TypeScript, your test runner, eslint, and their transitive deps commonly run 200–400MB. `npm prune --omit=dev` in the build stage strips them before the copy. (You could instead run a fresh `npm ci --omit=dev` in the runtime stage, but then you need a package manager and possibly a compiler there, which partly defeats the point.)
- **Source and build cruft.** `.git`, tests, fixtures, coverage output, and any `node_modules` you had lying around locally.

That last one is what `.dockerignore` is for, and it matters more than people expect. Without it, `COPY . .` sends your entire working directory to the daemon as build context — including `.git`, which on a mature repo can be hundreds of megabytes, and your local `node_modules`, which will also *shadow* the one `npm ci` just installed and can be built for a different platform. Minimum:

```
node_modules
.git
dist
coverage
*.log
.env*
```

This speeds up builds noticeably too, since the context upload happens on every build.

**On base images.** Alpine uses musl instead of glibc. For pure-JS dependencies this is a non-issue. If you have native modules, they'll be compiled against musl in the build stage — which means your build stage also needs to be Alpine, or you'll copy glibc-linked `.node` binaries into a musl runtime and get cryptic loader errors at startup. If you hit that, either make both stages `node:20-alpine`, or use `node:20-slim` (Debian, glibc, ~200MB) for the runtime instead. Slim is the safer default when native modules are involved; the difference between slim and alpine is much smaller than the difference between either and the full image.

Distroless (`gcr.io/distroless/nodejs20-debian12`) goes further — no shell, no package manager, no busybox. It's glibc-based, so native modules built on `node:20` or `node:20-slim` work fine. The tradeoff is that `docker exec` into a running container gets you nothing, since there's no `sh`. If your debugging story is "read the logs," distroless is great. If it's "shell in and poke around," you'll hate it. There's a `:debug` tag with a busybox shell for when you need it.

With alpine and pruned deps you should land somewhere around 120–150MB, most of which is Node itself. Check where the rest is going with `docker history <image>` — it breaks size down per layer and usually makes the remaining fat obvious.
