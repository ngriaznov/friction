The elision rules exist so you don't have to write out lifetimes for the overwhelming majority of functions, but they only apply in specific, mechanical situations. When your signature doesn't match one of the patterns below, the compiler gives up and makes you spell it out. There are three rules, applied in order, and elision stops as soon as one of them fully resolves the output lifetime.

**Rule 1: each elided input lifetime gets its own fresh lifetime parameter.**

This doesn't resolve anything by itself, it's just bookkeeping — `fn foo(x: &i32, y: &i32)` is treated internally as `fn foo<'a, 'b>(x: &'a i32, y: &'b i32)`. No output here, so this rule alone never lets a function compile if it also returns a reference.

**Rule 2: if there is exactly one input lifetime (elided or not), that lifetime is assigned to all elided output lifetimes.**

```rust
fn first_word(s: &str) -> &str {
    s.split_whitespace().next().unwrap_or("")
}
```

There's exactly one reference parameter, so the compiler applies rule 2: the return type's lifetime is tied to `s`'s lifetime. This desugars to `fn first_word<'a>(s: &'a str) -> &'a str`, and it compiles without you writing anything.

**Rule 3: if one of the parameters is `&self` or `&mut self`, the lifetime of `self` is assigned to all elided output lifetimes**, regardless of how many other parameters there are.

```rust
impl Document {
    fn title(&self, fallback: &str) -> &str {
        if self.title.is_empty() { fallback } else { &self.title }
    }
}
```

There are two input lifetimes here (`&self` and `fallback`), so rule 2 doesn't apply — with two inputs it wouldn't know which one to pick. But rule 3 kicks in because the receiver is `&self`, so the output gets tied to `self`'s lifetime, giving `fn title<'a, 'b>(&'a self, fallback: &'b str) -> &'a str`. Note that this compiles even though the function body sometimes returns `fallback` — the *signature* only cares about what's declared, and here it's declaring (correctly, since `self.title` is the actual return in one branch) that the output lives as long as `self`. If you tried to actually return `fallback` unconditionally the elided signature would still typecheck fine as long as the caller's `fallback` reference outlives... actually here it would fail to compile if you *only* ever returned `fallback`, because callers are entitled to assume the tie to `self`. That's a separate issue from elision itself.

Now here's a case where none of the rules apply and you must annotate:

```rust
fn longest(x: &str, y: &str) -> &str { // error: missing lifetime specifier
    if x.len() > y.len() { x } else { y }
}
```

Two input lifetimes, no `&self`, so rule 2 doesn't apply (ambiguous which input) and rule 3 doesn't apply (no receiver). You have to write `fn longest<'a>(x: &'a str, y: &'a str) -> &'a str` yourself, telling the compiler the output is tied to whichever of the two is shorter-lived — that's information elision can't guess for you, since either parameter could be the one that matters.

So as a rule of thumb: one reference in, one reference out — free. Method with `&self` returning a reference — free. Two or more independent reference parameters with a reference return — you're writing it by hand.
