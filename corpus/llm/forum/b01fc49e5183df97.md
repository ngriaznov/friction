This is a classic case of **catastrophic backtracking**, and it almost always comes from nested quantifiers — a quantified group that itself contains a quantified sub-pattern, where multiple ways of splitting the same input string satisfy the same match.

## A problematic pattern

Here's a pattern that looks innocent but will hang on the right (or wrong) input:

```
^(a+)+$
```

Tested against a string like `"aaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaaX"` (thirty-some `a`s followed by a character that breaks the match), this can take seconds, minutes, or effectively forever depending on the engine and string length, even though the string is short and the pattern looks simple.

## Why it blows up

The outer `(a+)+` says "one or more repetitions of (one or more `a`s)." The problem is that a run of, say, 20 `a` characters can be split into groups in exponentially many ways: one group of 20, or two groups of 10 and 10, or a group of 1 followed by a group of 19, and so on — every composition of 20 as a sum of positive integers is a valid way for the outer `+` to consume the inner `a+` groups.

When the overall match eventually fails (because of that trailing `X` with no `a` to match it), a backtracking engine doesn't just give up — it systematically retries every other way of splitting the run of `a`s, hoping one of them lets the rest of the pattern succeed. Since there are roughly 2^(n-1) such splits for a run of n characters, the engine's work grows exponentially with input length. Add ten characters to the input and the runtime roughly multiplies by a thousand. This is why the input can look tiny and still lock up a process — it's not the string length that matters, it's the number of ways the engine can carve it up, and that number explodes combinatorially.

This is sometimes called "evil regex" territory, and it's a well-known category of denial-of-service vulnerability (ReDoS) when the pattern is applied to untrusted user input, like a form field or URL path.

## The fix

The core issue is redundancy: the inner quantifier and the outer quantifier can both consume the same characters in different ways. The fix is to collapse them so there's only one way to match a given run:

```
^a+$
```

If you genuinely need a more complex nested structure — say, matching repeated groups of "one or more letters followed by an optional digit" — the trick is to make the quantifiers **possessive** or use an **atomic group**, if your engine supports them, so the engine commits to the first successful split of each group instead of backtracking through all of them:

```
^(?>a+)+$        # atomic group, most PCRE-flavored engines
^(?:a+)+$        # non-capturing, same performance risk unless the alternatives don't overlap
```

Atomic groups tell the engine "once this subpattern matches, don't backtrack into it" — which is exactly what removes the exponential search. If your regex flavor doesn't support atomic groups (JavaScript historically didn't, though possessive-like behavior can sometimes be approximated with lookahead tricks), the safest fix is almost always to rewrite the pattern so no character can be matched by two different quantified parts of the same expression. When in doubt, test candidate patterns against a deliberately long, non-matching input before shipping them anywhere near user-supplied data.
