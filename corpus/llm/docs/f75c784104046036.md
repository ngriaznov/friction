# How caching works in Ledgerline

Ledgerline sits between your application code and the database, and like most ORMs it spends a lot of its time answering the same questions repeatedly. The caching layer exists to notice that repetition and short-circuit it. This page explains what gets cached, when the cache is thrown away, and why Ledgerline gives you two different scopes to choose from.

## What actually gets cached

Ledgerline caches *query results*, not objects and not rows. When you execute a query through the session API, Ledgerline builds a cache key from three things: the compiled SQL text, the bound parameter values, and the identity of the mapped class the query returns. If a later query produces the same key, the cached result is returned without a round trip to the database.

The value stored under that key is a list of primary keys plus a snapshot of the column values for each row. It is not a list of live model instances. When you read from the cache, Ledgerline reconstructs instances (or returns the ones already tracked by your session, if it has them). This matters more than it sounds like it should: it means a cached result never hands two different parts of your code the same mutable object by accident, and it means a stale cache entry cannot silently resurrect an object you already deleted in this session.

Two categories of query are never cached:

- Queries with `FOR UPDATE` or any other explicit locking clause. Caching a row you asked the database to lock would defeat the point.
- Queries that call a database function Ledgerline cannot prove is deterministic — `now()`, `random()`, and anything registered as volatile in the dialect.

You can also opt a single query out with `.no_cache()`, which is the usual escape hatch for reporting queries that would otherwise flood the cache with entries nobody reads twice.

## Invalidation on writes

Ledgerline invalidates by table, not by row. Every cache entry records the set of tables its query touched. When a flush writes to a table — insert, update, or delete — every cache entry whose table set contains that table is dropped.

This is deliberately coarse. Row-level invalidation sounds more efficient, and for simple `WHERE id = ?` lookups it would be. But an ORM query can filter on anything, and working out whether a newly inserted row *would have* matched some arbitrary `WHERE` clause is, in the general case, the same problem as running the query again. Table-level invalidation is cheap, has no false negatives, and is easy to reason about when you are staring at a bug at four in the afternoon.

The practical consequence is that a table with a high write rate gets very little benefit from caching. If you have one table absorbing constant appends and another that changes twice a day, the second one is where the wins are. `ledgerline.cache_stats()` reports hit rate per table, which is the fastest way to find out whether your assumptions match reality.

Invalidation happens at flush time, not at commit time. Inside an open transaction your own writes are visible to your own subsequent reads, which is what you want. If the transaction rolls back, the dropped entries are simply gone — Ledgerline does not attempt to restore them.

## Per-request versus process-level scope

The two scopes differ in lifetime and in who can see the entries.

A **per-request cache** is created when you open a session and discarded when you close it. Nothing is shared between concurrent requests. It exists to eliminate the duplicate queries that come from ordinary code structure: a template that calls `user.organization` in three places, a serializer that re-fetches a lookup table per item. Hit rates here are often high and the entries are short-lived enough that staleness is not a concern. This is the default.

A **process-level cache** lives for the lifetime of the worker process and is shared by every session in it. It is the right choice for genuinely static data — currency codes, feature definitions, a permissions matrix. It is the wrong choice for anything a user can edit, because a write in worker A does not invalidate the entry in worker B. Ledgerline cannot see across process boundaries, so cross-process staleness is your problem to bound, usually with a TTL:

```python
ledgerline.configure_cache(
    scope="process",
    tables=["currency", "feature_flag"],
    ttl_seconds=300,
)
```

Anything not listed in `tables` falls back to per-request scope. Starting with per-request everywhere and promoting individual tables once you have measured them is a good deal safer than the reverse.
