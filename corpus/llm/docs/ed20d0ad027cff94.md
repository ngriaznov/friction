# Setting Up Automatic Backups

Corkboard stores all of your notes, attachments, and metadata in a single SQLite database file. Because everything lives in one file, backing it up is straightforward, but it's easy to forget to do manually — this guide walks through automating the process with cron so you don't have to think about it.

## Where Corkboard keeps its data

By default, Corkboard's database lives at `~/.corkboard/data.db`, and attachments (images, PDFs, and other files dropped into notes) are stored alongside it in `~/.corkboard/attachments/`. If you've overridden the data directory with the `CORKBOARD_HOME` environment variable, adjust the paths below accordingly.

## A simple backup script

Rather than calling `sqlite3` or `cp` directly from cron, it's worth wrapping the backup in a small script so you get consistent naming and can add error handling later. Create `~/.corkboard/backup.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

BACKUP_DIR="$HOME/.corkboard/backups"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
DB_PATH="$HOME/.corkboard/data.db"

mkdir -p "$BACKUP_DIR"

sqlite3 "$DB_PATH" ".backup '$BACKUP_DIR/corkboard-$TIMESTAMP.db'"

tar -czf "$BACKUP_DIR/attachments-$TIMESTAMP.tar.gz" -C "$HOME/.corkboard" attachments

find "$BACKUP_DIR" -name "corkboard-*.db" -mtime +30 -delete
find "$BACKUP_DIR" -name "attachments-*.tar.gz" -mtime +30 -delete
```

The `.backup` command is SQLite's built-in online backup facility — it produces a consistent snapshot even while Corkboard is running and writing to the database, which a plain file copy can't safely guarantee. The script also prunes backups older than 30 days so `~/.corkboard/backups` doesn't grow without bound; adjust the `-mtime` value to taste.

Make the script executable:

```
chmod +x ~/.corkboard/backup.sh
```

Run it once by hand to confirm it works and that `~/.corkboard/backups/` fills in as expected.

## Scheduling with cron

Open your crontab:

```
crontab -e
```

To back up nightly at 2:30 AM:

```
30 2 * * * /home/youruser/.corkboard/backup.sh >> /home/youruser/.corkboard/backup.log 2>&1
```

Use an absolute path to the script and to your home directory, since cron runs with a minimal environment and won't reliably expand `~`. Redirecting output to a log file makes it much easier to diagnose a silent failure later — if backups stop appearing, check `backup.log` first.

## Where backups end up

After the cron job has run a few times, `~/.corkboard/backups/` will contain pairs of files like:

```
corkboard-20240311-023000.db
attachments-20240311-023000.tar.gz
```

The `.db` file is a complete, independent copy of your note database at that point in time — not a diff — so any single backup file is enough to restore from on its own.

## Restoring from a backup

Corkboard must be closed before restoring, since it will otherwise overwrite the file you're replacing.

1. Quit Corkboard (and stop the systemd service if you're running it that way: `systemctl --user stop corkboard`).
2. Move the current database aside, just in case: `mv ~/.corkboard/data.db ~/.corkboard/data.db.old`.
3. Copy the backup into place: `cp ~/.corkboard/backups/corkboard-20240311-023000.db ~/.corkboard/data.db`.
4. If you also need attachments from that point, extract them: `tar -xzf ~/.corkboard/backups/attachments-20240311-023000.tar.gz -C ~/.corkboard/`. This will overwrite newer attachments with older ones, so only do this if you're restoring the whole system to that date.
5. Start Corkboard again and confirm your notes look correct before deleting `data.db.old`.

It's worth testing this restore procedure once on a spare machine or VM before you actually need it — a backup you've never restored from is only a guess at a backup.
