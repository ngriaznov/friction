# Ratchet API Reference

Ratchet is a lightweight task-queue service that accepts jobs over HTTP, holds them in a durable queue, and hands them off to workers. This page documents the three endpoints you'll use most often: enqueuing a job, checking its status, and cancelling a job that hasn't started yet.

All endpoints are served under a versioned base path, `https://your-ratchet-host/v1`, and require an `Authorization: Bearer <token>` header. Responses are JSON. Timestamps are ISO 8601 in UTC.

## Enqueue a job

`POST /v1/jobs`

Submits a new job to the queue. The body must include a `queue` name and a `payload` object, which is opaque to Ratchet and passed through unchanged to whatever worker picks the job up. Optional fields let you control priority and delay.

Request body fields:

- `queue` (string, required) — name of the queue to enqueue into. Queues are created implicitly on first use.
- `payload` (object, required) — arbitrary JSON passed to the worker.
- `priority` (integer, optional, default `0`) — higher values are dequeued first within the same queue.
- `run_after` (string, optional) — ISO 8601 timestamp; the job will not be dequeued before this time.
- `max_attempts` (integer, optional, default `3`) — number of delivery attempts before the job is marked `failed`.

Example:

```
curl -X POST https://your-ratchet-host/v1/jobs \
  -H "Authorization: Bearer $RATCHET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{
    "queue": "email-digests",
    "payload": { "user_id": 4821, "digest_type": "weekly" },
    "priority": 5
  }'
```

Response (`201 Created`):

```
{
  "id": "job_9f3a2c",
  "queue": "email-digests",
  "state": "queued",
  "priority": 5,
  "attempts": 0,
  "max_attempts": 3,
  "created_at": "2026-07-26T14:02:11Z",
  "run_after": null
}
```

Note the `id` — every subsequent operation on this job references it.

### Idempotent enqueueing

If your client might retry a request after a network timeout, pass an `Idempotency-Key` header alongside the `POST`. Ratchet stores the response body against that key for 24 hours; a repeated request with the same key returns the original `201 Created` response (including the original `id`) instead of creating a second job. This is the recommended way to guard against duplicate jobs from retried HTTP calls — do not rely on the payload contents alone to detect duplicates, since two genuinely different jobs may have identical payloads.

```
curl -X POST https://your-ratchet-host/v1/jobs \
  -H "Authorization: Bearer $RATCHET_TOKEN" \
  -H "Idempotency-Key: 6e1f-retry-attempt-1" \
  -H "Content-Type: application/json" \
  -d '{"queue": "email-digests", "payload": {"user_id": 4821}}'
```

## Check job status

`GET /v1/jobs/{id}`

Returns the current state of a job. The `state` field is one of `queued`, `running`, `succeeded`, `failed`, or `cancelled`. If the job has been attempted, `attempts` reflects how many times, and `last_error` is populated for the most recent failure.

Example:

```
curl https://your-ratchet-host/v1/jobs/job_9f3a2c \
  -H "Authorization: Bearer $RATCHET_TOKEN"
```

Response (`200 OK`):

```
{
  "id": "job_9f3a2c",
  "queue": "email-digests",
  "state": "succeeded",
  "priority": 5,
  "attempts": 1,
  "max_attempts": 3,
  "created_at": "2026-07-26T14:02:11Z",
  "started_at": "2026-07-26T14:02:13Z",
  "finished_at": "2026-07-26T14:02:15Z",
  "last_error": null
}
```

If the job ID doesn't exist, this returns `404 Not Found` with an `error` field describing the problem. There's no bulk status endpoint yet — for polling many jobs, query them individually or subscribe to the (separately documented) webhook events, which fire on every state transition and avoid polling entirely.

## Cancel a pending job

`DELETE /v1/jobs/{id}`

Cancels a job that is still `queued`. This is the one place Ratchet enforces a state check on your behalf: you cannot cancel a job that's already `running`, `succeeded`, or `failed` — Ratchet returns `409 Conflict` in that case, since a worker may already be holding the payload.

Example:

```
curl -X DELETE https://your-ratchet-host/v1/jobs/job_9f3a2c \
  -H "Authorization: Bearer $RATCHET_TOKEN"
```

Successful response (`200 OK`):

```
{
  "id": "job_9f3a2c",
  "state": "cancelled",
  "cancelled_at": "2026-07-26T14:05:40Z"
}
```

Conflict response (`409 Conflict`), for example if the job already started running:

```
{
  "error": "job_9f3a2c is in state 'running' and cannot be cancelled"
}
```

If you need to stop work that's already running, that's a worker-side concern — Ratchet has no way to interrupt code that's already executing, so design long-running jobs to check a cancellation flag themselves if you need that behavior.

## Error responses

Every error response shares a common shape regardless of endpoint:

```
{
  "error": "human-readable message",
  "code": "machine_readable_code"
}
```

The `code` field is the one to branch on programmatically; the message text is not guaranteed to stay stable across Ratchet releases. Common codes you'll encounter across these three endpoints:

- `unauthorized` (`401`) — missing or invalid bearer token.
- `queue_name_invalid` (`400`) — queue names must be lowercase alphanumerics and hyphens, under 64 characters.
- `job_not_found` (`404`) — returned by both `GET` and `DELETE` when the `id` doesn't exist or belongs to a different account.
- `job_not_cancellable` (`409`) — returned by `DELETE` when the job is past the `queued` state.
- `rate_limited` (`429`) — you've exceeded your token's request quota; check the `Retry-After` header for how long to back off.

Client libraries should treat `429` and `5xx` responses as retryable and everything else as terminal, with the idempotency key described above making retries on `POST /v1/jobs` safe by default.

## Rate limits and pagination

Job creation is rate-limited per API token; the current limit is returned in the `X-RateLimit-Remaining` response header on every request, and the window resets at the time given in `X-RateLimit-Reset`. There is no list-all-jobs endpoint on this version of the API — Ratchet is intentionally designed around clients holding on to the job IDs they create, rather than querying the queue as a source of truth. If your use case needs to enumerate jobs by queue or state, the metrics export (documented separately) is the recommended path, since it's built for aggregate queries rather than individual job lookups.

## Webhooks

As a supplement to polling `GET /v1/jobs/{id}`, you can configure a webhook URL per queue in the dashboard. Ratchet will `POST` a small event body to that URL on every state transition — `queued` to `running`, `running` to `succeeded` or `failed`, and `queued` to `cancelled`. Each webhook delivery includes a `Ratchet-Signature` header computed as an HMAC-SHA256 of the raw request body, using the signing secret shown in the dashboard when you configure the webhook; verify this signature before trusting the payload, since webhook endpoints are public URLs by nature. Webhook delivery is at-least-once, so consumers should treat repeated deliveries of the same event as normal and dedupe on the `job_id` plus `state` pair rather than assuming single delivery.
