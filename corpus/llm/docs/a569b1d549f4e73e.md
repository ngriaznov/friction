# How Caching Works in Ledgerline

Ledgerline includes a built-in caching layer that sits between your Python code and the database, intended to reduce redundant round trips for read-heavy workloads. This page explains what gets cached, how invalidation works, and the distinction between the two cache scopes Ledgerline supports.

## What gets cached

Ledgerline caches the results of query objects, not raw SQL strings and not model instances directly. When you execute a query such as:

```python
users = User.query.filter(User.active == True).all()
```

Ledgerline computes a cache key from the compiled query — its table, filter conditions, ordering, and limit/offset — and stores the resulting rows against that key. A structurally identical query issued again, even from a different part of your codebase, will hit the same cache entry.

Two important consequences follow from this. First, queries that differ only by parameter value still get distinct cache keys — `filter(User.id == 1)` and `filter(User.id == 2)` are cached separately, as you'd expect. Second, queries built with unbound or dynamic conditions (e.g. raw SQL fragments passed through `.raw()`) bypass the cache entirely, because Ledgerline can't safely reason about what tables or rows they touch.

Caching is opt-in per query via `.cached()`:

```python
users = User.query.filter(User.active == True).cached().all()
```

It is not applied globally by default, since caching every query in an application with heavy write traffic can do more harm than good.

## Invalidation on writes

Ledgerline tracks, for every cached query result, which tables contributed rows to it. When a write occurs — an `insert`, `update`, or `delete` against a tracked model — Ledgerline invalidates every cached entry that touched that table, rather than trying to determine precisely which rows changed.

This is deliberately coarse. A more surgical approach (tracking which specific rows a cached query result depends on) would require significantly more bookkeeping and would still be wrong in the presence of joins and aggregate queries, where a change to one row can affect the correctness of a result set that never directly selected that row. Table-level invalidation trades some cache efficiency for a correctness guarantee that's much easier to reason about: if you write to a table, every cached query touching that table is gone on the next read.

In practice this means a write-heavy table with many cached queries against it will see a lower cache hit rate than a mostly-static reference table (say, a list of countries), which is usually the right trade-off — the tables you write to often are exactly the tables where stale cached data is most likely to cause a visible bug.

You can bypass this and force a fresh read of a specific query with `.cached(refresh=True)`, which re-executes the query and overwrites the existing cache entry rather than reading from it.

## Per-request vs. process-level scope

Ledgerline supports two cache scopes, chosen with the `scope` argument to `.cached()`:

```python
User.query.cached(scope="request").all()
User.query.cached(scope="process").all()
```

**Request scope** ties the cache to the current unit of work — typically a single web request when Ledgerline is used inside a request-response framework, or a single `with Session()` block otherwise. The cache is discarded automatically when that unit of work ends. This is the safer default: request-scoped entries can never leak stale data across requests, since nothing persists past the request boundary. It's also the scope Ledgerline uses when you call `.cached()` without an explicit `scope` argument.

**Process scope** shares a single cache across every request handled by that worker process, backed by an in-memory LRU store by default (or Redis, if configured via `LEDGERLINE_CACHE_BACKEND`). This scope is where the real performance win lives, since a cache entry populated by one request can serve many subsequent ones, but it also means invalidation correctness matters much more — a bug in table-tracking at process scope can serve stale data to every user hitting that worker, not just within one request.

A reasonable rule of thumb: use request scope by default for anything computed from a query that's expensive to build (heavy joins, N+1-prone relationship loading) but only read once or twice per request. Reach for process scope deliberately, for queries you know are read far more often than the underlying tables are written to — reference data, configuration tables, anything close to read-only in normal operation.

Process-scope entries also respect a `ttl` argument as a safety net independent of write-based invalidation:

```python
Country.query.cached(scope="process", ttl=3600).all()
```

This isn't a substitute for correct invalidation, but it bounds how long a cache entry can survive if invalidation ever fails to fire — for instance, if a table is modified through a raw SQL statement that Ledgerline's write-tracking doesn't see.
