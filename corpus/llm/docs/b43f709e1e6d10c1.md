# Route traffic to multiple backends by path prefix

This guide shows how to put Wharfgate in front of three backend services and split incoming requests between them based on the beginning of the request path. By the end you will have a single public listener on port 443 that sends `/api/*` to an application server, `/auth/*` to an identity service, and everything else to a static site container.

You should already have Wharfgate installed (`wharfgate --version` should print something) and the three backends reachable from the machine running the proxy. Path routing does not require TLS, but the example config below terminates it, since that is the usual reason for putting a proxy in front of anything.

## How prefix matching works

Wharfgate evaluates `route` blocks in the order they appear in the config file and stops at the first prefix that matches. That means ordering matters: a route for `/` placed above a route for `/api` will swallow every request. Put your most specific prefixes first and your catch-all last.

Prefixes are matched on path segments, not raw characters. A route for `/api` matches `/api` and `/api/v2/orders`, but not `/apiary`. If you want the character-level behavior instead, use `prefix_raw` in place of `prefix`.

By default the matched prefix is left on the request when it is forwarded, so the backend sees `/api/v2/orders`. Many backends are mounted at the root and expect `/v2/orders` instead. Set `strip_prefix = true` on the route to trim it.

## The config file

Wharfgate reads `/etc/wharfgate/gateway.toml` unless you pass `--config`. Here is a complete file for the three-service setup:

```toml
[listener]
bind = "0.0.0.0:443"
tls_cert = "/etc/wharfgate/certs/site.pem"
tls_key  = "/etc/wharfgate/certs/site.key"

[[upstream]]
name    = "app"
targets = ["10.0.3.11:8080", "10.0.3.12:8080"]
policy  = "least_conn"

[[upstream]]
name    = "identity"
targets = ["10.0.3.20:9000"]

[[upstream]]
name    = "static"
targets = ["10.0.3.30:80"]

[[route]]
prefix       = "/api"
upstream     = "app"
strip_prefix = true
timeout      = "30s"

[[route]]
prefix   = "/auth"
upstream = "identity"
timeout  = "10s"

[[route]]
prefix   = "/"
upstream = "static"
```

A few notes on the fields. `policy` controls how requests are spread across the targets in an upstream and accepts `round_robin` (the default), `least_conn`, or `ip_hash`. The `timeout` is the total time allowed for the backend to send a complete response; when it expires Wharfgate returns 504 and logs the route name. Single-target upstreams like `identity` and `static` do not need a policy, but declaring them as upstreams rather than inline addresses means you can add a second target later without touching the route blocks.

Validate before you reload:

```
wharfgate check --config /etc/wharfgate/gateway.toml
wharfgate reload
```

`reload` swaps the configuration in place and does not drop in-flight connections. If `check` reports an unreachable target it is a warning, not an error — Wharfgate will start anyway and mark that target unhealthy.

## A note on health checks

Wharfgate does passive health checking out of the box. A target that returns a connection error or a 5xx response three times in a row is pulled out of rotation for 15 seconds, then given a single trial request. That is enough for most deployments, and it costs nothing when everything is healthy.

Passive checking has one real weakness: a backend that has been down since before the proxy started never receives the traffic that would reveal it, so the first few user requests pay for the discovery. If that matters, add an active probe per upstream:

```toml
[[upstream]]
name    = "app"
targets = ["10.0.3.11:8080", "10.0.3.12:8080"]
policy  = "least_conn"

  [upstream.health]
  path     = "/healthz"
  interval = "5s"
  timeout  = "2s"
  healthy_after   = 2
  unhealthy_after = 3
```

Point `path` at an endpoint that checks the things the service actually needs — a database handle, say — rather than one that returns 200 unconditionally. A health endpoint that cannot fail tells you nothing.

Current status for every target is available at `wharfgate status`, which prints the upstream name, target address, state, and time since the last state change.
