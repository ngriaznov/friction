# Routing Three Backend Services with Wharfgate

This guide walks through configuring Wharfgate, a lightweight load balancer, to route incoming traffic to three backend services based on URL path prefix. By the end you'll have a single Wharfgate instance sitting in front of an `accounts` service, a `billing` service, and a `search` service, each reachable through a distinct path on the same public hostname.

## Why path-based routing

Running one reverse proxy in front of several small services means clients only need to know about one hostname and port. Wharfgate inspects the incoming request path, matches it against a list of prefixes you configure, and forwards the connection to whichever upstream pool owns that prefix. Everything else — TLS termination, connection keep-alive, load distribution across replicas — is handled the same way regardless of which service ends up receiving the request.

## Installing Wharfgate

Wharfgate ships as a single static binary. Download the release for your platform, place it somewhere on your `PATH`, and confirm it runs:

```
wharfgate --version
```

You'll also need a configuration file, which by default Wharfgate looks for at `/etc/wharfgate/wharfgate.toml`, though you can point it elsewhere with `--config`.

## Writing the config file

Wharfgate's config is TOML. At the top level you declare a `listen` address, then one `[[route]]` block per backend. Here's a complete example routing three services:

```toml
listen = "0.0.0.0:443"
tls_cert = "/etc/wharfgate/certs/fullchain.pem"
tls_key = "/etc/wharfgate/certs/privkey.pem"

[[route]]
prefix = "/accounts"
strip_prefix = true
upstreams = ["10.0.1.11:8080", "10.0.1.12:8080"]

[[route]]
prefix = "/billing"
strip_prefix = true
upstreams = ["10.0.1.21:8080", "10.0.1.22:8080"]

[[route]]
prefix = "/search"
strip_prefix = false
upstreams = ["10.0.1.31:9000"]
```

A few details worth calling out:

- **Route order matters.** Wharfgate matches prefixes top to bottom and stops at the first match, so put more specific prefixes before general ones if any overlap.
- **`strip_prefix`** controls whether the matched prefix is removed before the request reaches the upstream. The accounts and billing services expect requests at their own root path, so the prefix is stripped. The search service was written to expect the `/search` prefix itself, so it's left in place.
- **`upstreams`** accepts a list. When a route has more than one address, Wharfgate load-balances across them using round-robin by default; you can switch to `least_connections` with a `balance` key inside the route block if one backend runs noticeably slower under load.

Once the file is saved, start Wharfgate with:

```
wharfgate --config /etc/wharfgate/wharfgate.toml
```

## Adding health checks

Wharfgate polls each upstream on an interval and stops sending it traffic if it fails enough consecutive checks. Add a `[health_check]` block per route to enable this:

```toml
[[route]]
prefix = "/accounts"
strip_prefix = true
upstreams = ["10.0.1.11:8080", "10.0.1.12:8080"]

[route.health_check]
path = "/healthz"
interval_seconds = 5
unhealthy_threshold = 3
```

With this in place, if `10.0.1.11:8080` fails three consecutive checks against `/healthz`, Wharfgate removes it from rotation and continues sending traffic only to `10.0.1.12:8080`. It keeps polling the unhealthy address in the background and adds it back automatically once checks start passing again. Without a health check block, Wharfgate will still retry a failed connection against the next upstream in the list, but it won't proactively stop routing to a backend that's degraded rather than fully down — so for anything running more than one replica, it's worth the few extra lines.

That's the whole setup: one listener, three prefix-matched routes, and a health check per route so a single unhealthy instance doesn't take the whole path down with it.
