# The Anvildb consistency model

Anvildb stores every key on several machines at once and lets you decide, per request, how many of those machines have to agree before the request is considered done. This page explains what that means in practice: how replicas are chosen, how quorum reads and writes work, what you give up when you ask for lower latency, and how the cluster behaves when the network splits.

## Replicas and the replication factor

Each keyspace is created with a replication factor (RF), typically 3 or 5. When you write key `orders/8812`, Anvildb hashes the key to a position on the ring and stores the value on the RF nodes that follow that position. Those nodes are the key's *replica set*. There is no primary among them. Any replica can serve a read, and any replica can accept a write and forward it to its peers.

This is deliberate. A leaderless design means no failover pause when a node dies, and no single node whose loss stalls writes for a shard. The cost is that replicas can disagree, and reconciling that disagreement is what the rest of this page is about.

## Quorum reads and writes

Every request carries a consistency level. The two numbers that matter are **W**, the number of replicas that must acknowledge a write before the coordinator returns success, and **R**, the number of replicas that must respond to a read before the coordinator returns a value.

The guarantee follows from simple arithmetic. If

```
R + W > RF
```

then the set of replicas that acknowledged the most recent write and the set that answered your read must overlap by at least one node. That overlapping node holds the newest value. Anvildb resolves the returned versions by their commit timestamps and hands back the newest one, so a read that satisfies the inequality will never miss a write that has already been acknowledged.

With RF=3, the common choices are:

| Level | R | W | Notes |
|---|---|---|---|
| `ONE` | 1 | 1 | Fastest. R+W = 2, no overlap guarantee. |
| `QUORUM` | 2 | 2 | R+W = 4 > 3. Overlap guaranteed. |
| `ALL` | 3 | 3 | Overlap guaranteed, but any single node failure blocks the request. |

You can also mix them. `W=ALL` with `R=ONE` satisfies the inequality and gives very fast reads, at the price of writes that fail whenever one replica is down. That combination suits configuration data that is read constantly and written rarely. The mirror image — `W=ONE, R=ALL` — suits high-volume ingest where reads are infrequent and can afford to be slow.

## The latency trade-off

Raising R or W does not make a request do more work in the sense of more CPU or more disk. It makes the coordinator wait for more responses, which means the request's latency is governed by a slower order statistic of the replica response times. With RF=3 and W=1, you wait for the fastest of three replicas. With W=2, you wait for the second-fastest. With W=3, you wait for the slowest — and in a cluster of any size, the slowest replica on any given request is regularly much slower than the median, because of garbage collection pauses, compaction, a noisy neighbour, or a network hiccup.

The practical consequence is that p50 latency barely moves as you raise the consistency level, while p99 latency moves a great deal. Teams who benchmark with averages are frequently surprised when they raise a level in production and their tail latency doubles. Benchmark with percentiles.

Anvildb sends the request to all RF replicas regardless of level; the level only controls how many responses the coordinator waits for before replying. Late responses are still used to trigger read repair, so a low consistency level does not mean stale replicas stay stale.

## Behaviour during a network partition

Suppose a five-node cluster splits into a group of three and a group of two, and RF=3 with a key whose replicas straddle the split — two replicas on the majority side, one on the minority side.

At `QUORUM` (R=W=2), the majority side can still assemble two replicas, so reads and writes there continue to succeed. The minority side cannot reach two replicas for that key, so its requests fail with `InsufficientReplicas` after the coordinator timeout. Anvildb chooses to fail rather than serve a value it cannot vouch for. This is the CP posture in the usual shorthand: during a partition, consistency is preserved and availability is sacrificed on the minority side.

At `ONE`, both sides remain available for that key, and both sides can accept conflicting writes. When the partition heals, Anvildb reconciles by last-write-wins on the commit timestamp. Whichever write carries the later timestamp survives; the other is discarded silently. If clock skew between the two sides exceeds the interval between the conflicting writes, the *earlier* write can win. Anvildb monitors skew and logs a warning above 250 ms, but it cannot prevent this outcome.

The healing process itself has two mechanisms. **Hinted handoff** lets a coordinator store a write destined for an unreachable replica and replay it once that replica returns, for up to three hours by default. **Anti-entropy repair**, run as a background job, compares Merkle trees between replicas and streams the differing ranges. Partitions longer than the hint window rely entirely on repair, which is why the recommended operational practice is to run a full repair after any outage that exceeds it.

## Choosing a level

Use `QUORUM` unless you have a specific reason not to. Drop to `ONE` for data where a stale read is harmless — cached derivations, metrics, session heartbeats. Raise to `ALL` only for the narrow case of data that must be readable at `ONE` immediately afterward, and accept that those writes will fail during routine maintenance.
