# Sending email alerts from Pulsecheck

By default Pulsecheck records outages but doesn't tell anyone about them. This guide walks through wiring up SMTP, deciding when an alert should fire, and muting a check that has started flapping.

You'll need shell access to the host running Pulsecheck and credentials for an SMTP relay you can send through.

## 1. Configure SMTP

Mail settings live under the `notify.smtp` block in `pulsecheck.yml`, usually at `/etc/pulsecheck/pulsecheck.yml`.

```yaml
notify:
  smtp:
    host: smtp.example-relay.net
    port: 587
    username: pulsecheck@example.com
    password_file: /etc/pulsecheck/smtp.pass
    starttls: true
    from: "Pulsecheck <pulsecheck@example.com>"
```

Two things trip people up here. First, `password_file` points at a file containing the password and nothing else — no trailing newline is required, but Pulsecheck strips one if present. There is also a `password` key that takes the secret inline; it works, but the config file is world-readable in most packaged installs, so prefer the file form and `chmod 600` it.

Second, port 587 with `starttls: true` is the common case. If your relay only offers implicit TLS on port 465, set `port: 465` and `tls: true` instead, and leave `starttls` off. Setting both is a config error and Pulsecheck will refuse to start.

Reload and send a test message:

```
pulsecheckctl reload
pulsecheckctl notify test --to you@example.com
```

The test bypasses all thresholds and goes straight out through the relay, so a failure here is always an SMTP problem, not a rules problem. Check `journalctl -u pulsecheck -n 50` for the relay's rejection text.

## 2. Set alert thresholds

Thresholds are per-check, defined under the check's `alert` block. A check with no `alert` block never notifies.

```yaml
checks:
  - name: api-gateway
    url: https://api.example.com/healthz
    interval: 30s
    alert:
      to: [oncall@example.com]
      after: 3
      recover: true
      repeat_every: 30m
```

`after: 3` means three consecutive failed probes before the first email. At a 30-second interval that's roughly 90 seconds of downtime — long enough to ride out a single dropped request, short enough to still be useful. Raising `after` is the main lever for noise; raising `interval` costs you detection time as well.

`recover: true` sends a second email when the check passes again. `repeat_every` re-sends the alert while the check is still down; omit it to get exactly one email per outage.

## 3. Silence a flapping check

A check that oscillates between up and down will generate an email on every transition. To stop the bleeding without editing config:

```
pulsecheckctl silence add api-gateway --for 2h --reason "flapping, investigating upstream LB"
```

The check keeps running and keeps recording history — only the notification is suppressed. List and clear silences with:

```
pulsecheckctl silence list
pulsecheckctl silence rm api-gateway
```

Silences expire on their own and survive a restart. If a check flaps regularly rather than exceptionally, the durable fix is `flap_window` in the check's `alert` block, which requires the check to hold a single state for that long before any transition counts:

```yaml
    alert:
      flap_window: 5m
```

Start with a silence, then decide whether the flapping is the monitored service's problem or the monitor's.
