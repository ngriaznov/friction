# Setting up CI for a Rust project with Millwheel

This guide walks through a working Millwheel pipeline for a Cargo project: building and testing on every push, caching the `~/.cargo` registry and the `target/` directory so runs don't recompile the whole dependency tree, and publishing test results so failures show up in the run summary instead of buried in log output.

It assumes you already have a Millwheel account connected to your repository host, and a project that builds with `cargo build` locally.

## The pipeline file

Millwheel reads `.millwheel/pipeline.yml` from the repository root. A minimal Rust pipeline looks like this:

```yaml
version: 2

defaults:
  image: rust:1.83-bookworm

stages:
  - check
  - test

jobs:
  fmt-and-clippy:
    stage: check
    steps:
      - run: rustup component add rustfmt clippy
      - run: cargo fmt --all -- --check
      - run: cargo clippy --all-targets -- -D warnings

  unit-tests:
    stage: test
    steps:
      - run: cargo test --all-features --no-fail-fast
```

Jobs in the same stage run in parallel; stages run in order. If `fmt-and-clippy` fails, `unit-tests` never starts, which is usually what you want — there's no point burning eight minutes of compile time to discover a trailing comma.

The `image` key accepts any Docker image reachable from the runner. Pinning a specific Rust minor version rather than `rust:latest` is worth doing: a toolchain bump that lands mid-week and breaks a lint is a confusing thing to debug in CI.

## Caching Cargo dependencies

Without caching, every run downloads and compiles all your dependencies from scratch. For a project with a few dozen crates in the tree, that's the difference between a two-minute run and a twelve-minute one.

Millwheel caches are declared per job with a `cache` block:

```yaml
  unit-tests:
    stage: test
    cache:
      - key: cargo-registry-{{ checksum "Cargo.lock" }}
        restore-keys:
          - cargo-registry-
        paths:
          - ~/.cargo/registry
          - ~/.cargo/git
      - key: cargo-target-{{ arch }}-{{ checksum "Cargo.lock" }}
        restore-keys:
          - cargo-target-{{ arch }}-
        paths:
          - target
    steps:
      - run: cargo test --all-features --no-fail-fast
```

Two things to note. First, keying on the checksum of `Cargo.lock` means the cache is invalidated exactly when your dependency set changes, and not otherwise. The `restore-keys` list gives Millwheel a prefix to fall back on when there's no exact hit — you get last week's cache and recompile only what moved, rather than starting from nothing.

Second, the `target/` cache should include the architecture in its key. Artifacts built on an x86_64 runner are useless to an arm64 one, and restoring the wrong ones produces link errors that look like compiler bugs.

Millwheel writes caches only from jobs that succeed. A job that fails partway through won't poison the cache with a half-populated `target/` directory.

One caveat: `target/` grows without bound if you never clear it. Old artifacts from deleted dependencies stay around. If you see cache upload times creeping past a minute or two, add a step that prunes it — `cargo install cargo-sweep` and `cargo sweep --time 14` before the cache is saved works well enough.

## Publishing test results

`cargo test` prints human-readable output, which Millwheel will happily archive as a log, but it won't parse it into per-test results. To get a structured summary, emit JUnit XML.

The simplest route is `cargo-nextest`, which supports JUnit output natively:

```yaml
    steps:
      - run: cargo install cargo-nextest --locked
      - run: cargo nextest run --profile ci
      - publish_results:
          format: junit
          path: target/nextest/ci/junit.xml
```

with a `.config/nextest.toml` alongside it:

```toml
[profile.ci.junit]
path = "junit.xml"
```

Add `cargo-nextest` to the cached `~/.cargo` paths, or the install step will rebuild it on every run.

The `publish_results` step attaches the parsed results to the run. Failed tests appear in the run summary with their assertion output, and Millwheel flags tests that have failed intermittently across recent runs — useful for spotting flakiness before someone gets in the habit of hitting "retry."

## Verifying it works

Push the pipeline file and check the run in the Millwheel UI. On the second push you should see cache restore lines near the top of the job log and a substantially shorter build time. If the second run is as slow as the first, the usual cause is a cache key that changes every run — check that you're not accidentally interpolating something like the commit SHA into it.
