# Driftline's Branching Model

Driftline wraps git with a small set of opinions about how branches should be organized and merged. This page explains the recommended branching model — feature branches and release branches — and how `driftline sync` differs from a plain `git rebase`, which is the command it's most often confused with.

## Feature branches

Every unit of work in Driftline starts as a feature branch, cut from `main`:

```
driftline start add-search-filter
```

This is roughly equivalent to `git checkout -b add-search-filter main`, but it also records the branch's parent in Driftline's own metadata (stored in `.driftline/branches.toml`, not in git refs), which is what later lets `driftline sync` and `driftline status` reason about a branch's relationship to `main` even after `main` has moved on considerably.

Feature branches are meant to be short-lived and are expected to be kept up to date with `main` as it moves, rather than diverging for weeks and facing a large merge at the end. Driftline's own tooling nudges toward this: `driftline status` flags a feature branch as "stale" once it's more than a set number of commits behind `main` (configurable, default 20), as a reminder to sync before the eventual merge gets harder than it needs to be.

## Release branches

Where feature branches are for individual pieces of work, release branches represent a version that's being stabilized for shipping. A release branch is cut from `main` at the point you're ready to start hardening for a release:

```
driftline release start 2.4
```

This creates a `release/2.4` branch and, critically, registers it in Driftline's metadata as a release branch rather than a feature branch — this distinction matters because Driftline treats the two differently. Feature branches are expected to sync from `main`; release branches are expected to receive only targeted fixes, cherry-picked or synced in deliberately, and to eventually feed back into `main` via `driftline release finish`, which merges the release branch back and tags the release commit.

Bug fixes discovered during stabilization are typically committed directly to the release branch and then propagated forward to `main` with `driftline release backport 2.4`, rather than being written against `main` and pulled backward — this ordering matters because it guarantees the release branch always reflects exactly what's being shipped, without depending on cherry-picks landing cleanly against a `main` that's already moved past the release point.

## `driftline sync` versus `git rebase`

On the surface, `driftline sync` looks like a rebase: it takes your feature branch's commits and replays them on top of the current tip of `main`. The differences are in what happens around that replay.

**Conflict handling.** A plain `git rebase` stops at the first conflicting commit and leaves you to resolve it, continue, and repeat for each subsequent conflicting commit in turn. `driftline sync` instead computes conflicts against the *final* state of `main` up front, using a three-way merge against the branch's recorded parent point rather than main's current tip commit-by-commit, and presents all conflicting hunks across the whole branch in a single pass. In practice this means you resolve overlapping changes once, rather than potentially resolving the same logical conflict repeatedly as it reappears commit after commit during a traditional rebase.

**Metadata tracking.** After a successful sync, Driftline updates the branch's recorded parent point in `.driftline/branches.toml` to the new base commit. This is what lets `driftline status` correctly report "up to date with main" afterward, and it's also why running a plain `git rebase main` on a Driftline-managed branch (instead of `driftline sync`) leaves Driftline's own bookkeeping stale — the rewritten commits will exist correctly in git, but Driftline will still think the branch's base is the old, pre-rebase commit until you either run `driftline sync` (which is a no-op on the actual commits at that point, since there's nothing left to replay) or `driftline status --repair` to resync just the metadata.

**Safety net.** Before rewriting anything, `driftline sync` creates a recovery ref (`refs/driftline/backup/<branch>-<timestamp>`) pointing at the branch's pre-sync state. This isn't something `git rebase` does on its own — you'd normally rely on the reflog for that, which works but expires and isn't branch-specific. `driftline undo-sync` uses this ref to restore the branch to exactly where it was before the most recent sync, which is a much narrower and more predictable operation than trying to reconstruct the right state from a general-purpose reflog.

The practical upshot: for a straightforward feature branch a few commits behind `main`, `driftline sync` and `git rebase main` will usually produce the same end result. The difference shows up on branches that have drifted further, or where conflicts touch several commits — that's where the batched conflict resolution and the recovery ref earn their keep.
