# The Gridleaf File Format (`.glf`), version 3

This document describes the on-disk layout of a Gridleaf workbook so that you can write a parser for it. It covers the container header, the sheet metadata section, and the cell encoding scheme. It does not cover formula bytecode, chart definitions, or the revision journal; those live in separate sections and are documented elsewhere.

All multi-byte integers are little-endian. All offsets are absolute byte offsets from the start of the file unless stated otherwise. Strings are UTF-8 and are never NUL-terminated — every string carries an explicit length.

## Container header

The first 64 bytes of every `.glf` file are the container header. Its layout is fixed:

| Offset | Size | Field | Notes |
| --- | --- | --- | --- |
| 0 | 6 | magic | ASCII `GRDLF\x00` |
| 6 | 2 | format version | 3 for files written since 2019 |
| 8 | 2 | writer version | informational; do not branch on it |
| 10 | 2 | flags | see below |
| 12 | 4 | sheet count | number of entries in the metadata section |
| 16 | 8 | metadata offset | start of the sheet metadata section |
| 24 | 8 | string pool offset | start of the shared string pool |
| 32 | 8 | string pool length | in bytes |
| 40 | 4 | header CRC32 | over bytes 0..39 |
| 44 | 20 | reserved | zero-filled; ignore, do not reject |

Two flag bits matter. Bit 0 (`COMPRESSED`) means every section after the header is individually zstd-compressed; each section then begins with a 4-byte uncompressed length followed by the compressed frame. Bit 3 (`BIG_ROWS`) means row indices are 32-bit rather than 24-bit throughout the file. Bits 1, 2, and 4–15 are unused; a conformant parser ignores them rather than failing.

Reject the file if the magic does not match, if the format version is greater than 3, or if the header CRC does not verify. Do not reject on unknown writer versions — several third-party tools write arbitrary values there.

## String pool

Cell text is not stored inline. Instead, every distinct string in the workbook lives once in the string pool, and cells refer to it by index. The pool is a sequence of records:

```
varint  byte_length
bytes   utf8_data
```

The varint is the usual LEB128 encoding, seven bits per byte, high bit set to continue. Indices are assigned in order of appearance starting at 0. Sheet names, cell text, and comment bodies all draw from this same pool, so a parser should read the pool eagerly and keep it as a flat array.

Duplicate strings are permitted, though the reference writer deduplicates them. Do not assume index 0 is the empty string; older writers omit it entirely.

## Sheet metadata section

The metadata section is an array of `sheet count` fixed-size records, 48 bytes each:

| Offset | Size | Field |
| --- | --- | --- |
| 0 | 4 | sheet id (stable across saves) |
| 4 | 4 | name index into the string pool |
| 8 | 8 | cell block offset |
| 16 | 8 | cell block length |
| 24 | 4 | used row count |
| 28 | 4 | used column count |
| 32 | 4 | frozen rows |
| 36 | 4 | frozen columns |
| 40 | 4 | tab colour, 0xAARRGGBB, zero meaning unset |
| 44 | 4 | sheet flags |

Sheet flag bit 0 marks the sheet hidden; bit 1 marks it protected. Sheet ids are not necessarily contiguous and not necessarily ordered — a workbook where sheets have been deleted and reordered will show gaps. Presentation order is the order of records in this section, not the sheet id.

The used row and column counts are hints for preallocation. They can be larger than the real extent if rows were deleted, so treat them as an upper bound rather than a guarantee, and never size an array from them without a sanity cap.

## Cell encoding

Each sheet's cell block is a sequence of row groups. A row group begins with:

```
uint24 (or uint32 if BIG_ROWS)  row_index
uint16                          cell_count
```

followed by `cell_count` cell records. Rows appear in ascending order, and rows containing no cells are simply absent — there is no run-length or skip encoding at the row level.

A cell record is:

```
uint16  column_index
uint8   type_tag
uint32  style_id
        payload (variable, determined by type_tag)
```

The type tags are:

- `0x00` — empty. No payload. Used when a cell has styling but no value.
- `0x01` — number. 8-byte IEEE 754 double.
- `0x02` — shared string. 4-byte index into the string pool.
- `0x03` — inline string. Varint length followed by UTF-8 bytes. Rare, but writers emit it for strings over 4 KiB.
- `0x04` — boolean. One byte, 0 or 1.
- `0x05` — error. One byte from the error enum (1 = `#DIV/0!`, 2 = `#VALUE!`, 3 = `#REF!`, 4 = `#NAME?`, 5 = `#N/A`).
- `0x06` — formula. Varint length, then formula bytecode, then a cached result encoded exactly as tags `0x01`–`0x05`, including its own type tag byte.
- `0x07` — date. 8-byte double, days since 1899-12-30, matching the widespread spreadsheet convention including its leap-year quirk.

Type tags 0x08 and above are reserved. A parser that meets one cannot skip the record, because payload length is not self-describing — it must abandon the sheet and report the file as partially readable.

Style ids index a style table that is stored after the last cell block; a value of 0xFFFFFFFF means "no explicit style".

## Practical notes

Column indices within a row group are ascending but may contain gaps. Nothing in the format forbids two records for the same cell; if you encounter that, the later record wins, which is what the reference implementation does.

When writing files, prefer shared strings over inline strings, keep row groups sorted, and always recompute the header CRC last. Files that violate ordering still load in Gridleaf itself but are rejected by several third-party readers.
