# Setting up automatic backups

Corkboard keeps everything — notes, tags, attachment metadata, and your search index — in a single SQLite database. If you lose that file, you lose the app. This guide walks through scheduling a nightly backup with cron and restoring from one when you need to.

## Before you start

You need shell access on the machine running Corkboard and the ability to edit a crontab. Find your data directory first:

```
corkboard config get data_dir
```

On a default Linux install this prints `/var/lib/corkboard`. The database lives at `<data_dir>/corkboard.db`. Everything below assumes that path; substitute your own if it differs.

## Why not just copy the file

Copying `corkboard.db` with `cp` while the server is running will usually work and occasionally produce a corrupt backup — SQLite may be mid-write when the copy starts. Instead of stopping the service every night, use the built-in command, which takes a consistent snapshot using SQLite's online backup API:

```
corkboard backup create
```

This writes a timestamped file such as `corkboard-2026-03-14T02-00-11.db.gz` into the backup directory and prints the full path. No downtime, no partial writes.

## Where backups go

By default that's `<data_dir>/backups`. Change it if you want backups on a different disk than the database, which you probably do:

```
corkboard config set backup_dir /mnt/backups/corkboard
```

Corkboard will create the directory if it doesn't exist, but it won't fix permissions — make sure the user running the cron job can write there.

Retention is handled by the same command. Set how many snapshots to keep and older ones are pruned after each successful backup:

```
corkboard config set backup_retention 14
```

Set it to `0` to disable pruning entirely and manage the files yourself.

## Scheduling with cron

Edit the crontab for the user that owns the data directory (usually `corkboard`, not root):

```
sudo -u corkboard crontab -e
```

Add a line to run the backup at 2:15 a.m. every night:

```
15 2 * * * /usr/bin/corkboard backup create >> /var/log/corkboard/backup.log 2>&1
```

Use the absolute path to the binary. Cron runs with a minimal `PATH` and a bare `corkboard` will silently fail to resolve. Redirecting both streams to a log file matters too — without it, failures go to a mail spool nobody reads.

Confirm the schedule works by checking the log the next morning, or force a run immediately with the same command from your shell.

## Restoring

Stop the service first. Restoring into a live database is the one operation that will genuinely corrupt things:

```
sudo systemctl stop corkboard
corkboard backup restore /mnt/backups/corkboard/corkboard-2026-03-14T02-00-11.db.gz
sudo systemctl start corkboard
```

The restore command decompresses the archive, verifies its integrity, and moves the current database aside as `corkboard.db.pre-restore` before swapping the snapshot into place. If the restore fails partway, that file is your way back.

Once the service is up, open the web UI and check that a note you remember editing recently is present. A backup you've never restored is a backup you don't know you have — test one now rather than during an outage.
