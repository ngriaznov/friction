# The Driftline branching model

Driftline does not invent a new version control system. It wraps git, and everything it does ends up as ordinary commits and refs that any git client can read. What Driftline adds is a set of conventions about *which* branches exist and *when* they move, plus one command — `driftline sync` — that keeps a branch current without the failure modes people usually hit with `git rebase`.

This page explains the branching model the tool assumes. You can use Driftline against a repository organized some other way, but several commands will warn, and `driftline release` will refuse to run.

## Two long-lived branches

The model has exactly two branches that live forever:

- `main` — always deployable. Every commit on `main` has passed CI and is a candidate for production.
- `next` — the integration branch. Feature work lands here first.

Everything else is temporary and gets deleted after it merges. This is deliberate: Driftline's branch listing (`driftline status`) sorts by age and starts complaining about anything older than fourteen days, on the theory that a branch nobody has touched in two weeks is either abandoned or too big.

## Feature branches

A feature branch starts from `next` and is named with the pattern `feat/<short-slug>`. Driftline creates it for you:

```
driftline start payment-retries
```

That checks out `next`, fetches, and branches from the current tip. The important part is the fetch — Driftline always branches from the *remote* tip, not your possibly-stale local copy. This eliminates the most common source of pointless merge conflicts, which is two people branching from different ancestors a day apart.

Feature branches are expected to be short. The tool nudges you toward small ones: `driftline finish` refuses to open a merge request for a branch with more than forty changed files unless you pass `--large`, which also requires a one-line justification that gets recorded in the merge commit trailer. Whether that friction is useful depends on your team, and it can be turned off in `.driftline.toml`.

## Release branches

When you want to cut a release, `driftline release 2.4` creates `release/2.4` from the current `next`, and immediately merges it into `main` once CI is green. From that point, `release/2.4` accepts only fixes.

The rule Driftline enforces is that fixes go to the release branch *first*, then get forward-ported to `next`. This is the opposite of what many teams do by habit — fix on the mainline, then cherry-pick backward — and the reason is traceability. A cherry-pick creates a new commit with a new hash and no automatic record of its origin, so six months later nobody can tell whether a given fix made it into 2.4. Driftline's forward-port (`driftline forward-port`) writes an `X-Driftline-Origin` trailer with the original commit hash, and `driftline audit 2.4` uses those trailers to list every fix that exists on the release branch but not on `next`.

Release branches are kept until the release is out of support, then deleted. Their history is already in `main`, so nothing is lost.

## How `driftline sync` differs from `git rebase`

This is the part people ask about most, so it is worth being precise.

`driftline sync` on a feature branch does, roughly, `git fetch` followed by `git rebase origin/next`. If your branch is a clean stack of commits with no conflicts, the two are equivalent and you should not notice a difference.

The differences show up in the awkward cases:

**It refuses to rebase published, shared branches.** Before rewriting anything, `sync` checks whether the remote branch has more than one contributor in its reflog-visible history and whether anyone else's local ref is tracking it (via a lightweight lease file the tool writes on push). If so, it merges instead of rebasing and tells you why. Rebasing a branch two people are working on is the classic way to lose a colleague's afternoon.

**It preserves your work-in-progress.** `sync` stashes uncommitted changes, rebases, and restores the stash, aborting cleanly if the restore would conflict. Plain `git rebase` simply refuses to start with a dirty tree.

**Conflict resolutions are cached.** Driftline enables and manages `rerere` per repository, so if you sync daily against a fast-moving `next`, you resolve each recurring conflict once rather than every morning.

**It never rebases onto a branch you didn't ask for.** `sync` reads the branch's recorded base — set at `driftline start` time and stored in the branch config — instead of guessing from the upstream tracking ref. A branch started from `release/2.4` syncs against `release/2.4`, even if your `next` is checked out.

If you want the plain behavior, `driftline sync --raw` passes through to `git rebase` with no additional checks.
