# Ratchet Jobs API

The Jobs API is how you put work into Ratchet and find out what happened to it. Three operations cover almost every use case: enqueue a job, read its status, and cancel it while it is still waiting.

All endpoints live under `https://api.ratchet.example/v1`. Requests must carry an API key in the `Authorization` header as `Bearer rt_live_...`. Request and response bodies are JSON; send `Content-Type: application/json` on anything with a body.

Job IDs are opaque strings prefixed with `job_`. Do not parse them, and do not assume a fixed length — the prefix is stable, the rest is not.

## Enqueue a job

```
POST /v1/jobs
```

Creates a job and places it on a queue. The response returns immediately; the job runs later on a worker.

### Request fields

| Field | Type | Required | Notes |
| --- | --- | --- | --- |
| `queue` | string | yes | Name of the queue. Created on first use. |
| `payload` | object | yes | Arbitrary JSON handed to your worker. Max 256 KB. |
| `priority` | integer | no | 0–9, higher runs sooner. Defaults to 5. |
| `run_at` | RFC 3339 timestamp | no | Earliest time the job may start. Defaults to now. |
| `max_attempts` | integer | no | Retries on failure. Defaults to 3. |
| `idempotency_key` | string | no | See below. |

If you pass an `idempotency_key`, Ratchet stores it for 24 hours. A second enqueue with the same key and the same queue returns the original job with HTTP 200 instead of creating a duplicate. This is the safest way to enqueue from code that might be retried — a webhook handler, for instance, or anything behind a load balancer that can replay a request.

```bash
curl -X POST https://api.ratchet.example/v1/jobs \
  -H "Authorization: Bearer $RATCHET_KEY" \
  -H "Content-Type: application/json" \
  -d '{
        "queue": "thumbnails",
        "payload": {"asset_id": 88213, "width": 640},
        "priority": 7,
        "idempotency_key": "asset-88213-thumb-640"
      }'
```

```json
{
  "id": "job_9fQ2xLbT4m",
  "queue": "thumbnails",
  "status": "pending",
  "priority": 7,
  "attempts": 0,
  "max_attempts": 3,
  "run_at": "2025-03-11T14:02:07Z",
  "created_at": "2025-03-11T14:02:07Z"
}
```

A fresh job returns 201. A deduplicated one returns 200 with the existing record. Both bodies have the same shape, so you can ignore the distinction unless you are counting enqueues.

Errors: 400 for a malformed body or an oversized payload, 401 for a bad key, 429 if you exceed the enqueue rate limit for your account. The 429 response carries a `Retry-After` header in seconds.

## Check job status

```
GET /v1/jobs/{job_id}
```

```bash
curl https://api.ratchet.example/v1/jobs/job_9fQ2xLbT4m \
  -H "Authorization: Bearer $RATCHET_KEY"
```

```json
{
  "id": "job_9fQ2xLbT4m",
  "queue": "thumbnails",
  "status": "succeeded",
  "priority": 7,
  "attempts": 2,
  "max_attempts": 3,
  "run_at": "2025-03-11T14:02:07Z",
  "started_at": "2025-03-11T14:02:11Z",
  "finished_at": "2025-03-11T14:02:19Z",
  "result": {"url": "https://cdn.example/t/88213-640.jpg"},
  "last_error": null
}
```

`status` is one of:

- `pending` — accepted, not yet claimed by a worker.
- `running` — a worker holds a lease on it.
- `succeeded` — finished; `result` holds whatever the worker returned.
- `failed` — all attempts exhausted; `last_error` holds the final error message.
- `cancelled` — cancelled before it started.

Note that `attempts` can be greater than one on a successful job. A job that failed twice and succeeded on the third try reports `succeeded` with `attempts: 3`, and `last_error` still contains the message from the last failed attempt. Treat `status` as authoritative and `last_error` as diagnostic only.

Unknown IDs return 404 with `{"error": {"code": "not_found"}}`. Finished jobs and their payloads are retained for 30 days, after which a lookup also returns 404.

Polling this endpoint in a tight loop is the wrong shape for anything time-sensitive. Register a completion webhook instead and use `GET /v1/jobs/{id}` for spot checks and debugging.

## Cancel a pending job

```
POST /v1/jobs/{job_id}/cancel
```

Cancellation is only possible while the job is `pending`. Once a worker has claimed the job, Ratchet will not interrupt it — there is no safe general way to kill work already in flight.

```bash
curl -X POST https://api.ratchet.example/v1/jobs/job_9fQ2xLbT4m/cancel \
  -H "Authorization: Bearer $RATCHET_KEY"
```

```json
{
  "id": "job_9fQ2xLbT4m",
  "queue": "thumbnails",
  "status": "cancelled",
  "attempts": 0,
  "cancelled_at": "2025-03-11T14:02:09Z"
}
```

Cancelling a job that is already `running`, `succeeded`, or `failed` returns 409:

```json
{
  "error": {
    "code": "not_cancellable",
    "message": "job is running and cannot be cancelled",
    "status": "running"
  }
}
```

Cancelling a job that is already `cancelled` returns 200 with the existing record, so the call is safe to retry.

If you need cooperative cancellation for long-running work, set a flag your worker checks between units of work — Ratchet's cancel endpoint deliberately does not try to solve that problem for you.
