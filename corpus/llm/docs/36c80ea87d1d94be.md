# Deploying a static blog to a CDN with Ferrycart

Ferrycart takes a directory of built HTML, CSS, and images and pushes it to a CDN edge network, keeping every upload as a numbered release so you can roll back without rebuilding. This guide walks through a first deploy of a static blog, then covers the two things people always need next: getting the CDN token out of the config file, and undoing a bad deploy.

The guide assumes you already have a site generator producing output into a local directory. Ferrycart does not build anything itself.

## Before you start

Install the CLI and confirm it runs:

```
npm install -g ferrycart
ferrycart --version
```

You will also need an API token from your CDN provider with permission to create and activate deployments. Ferrycart supports Fastly, Bunny, and Cloudflare backends; the token scope differs slightly between them, so check your provider's docs for which permission grants deployment activation.

## Initializing the project

Run `ferrycart init` from the root of your blog repository:

```
cd ~/projects/my-blog
ferrycart init
```

The command asks four questions: which CDN backend you use, the name of the site as it appears in your provider account, the local directory holding built output (commonly `public/`, `_site/`, or `dist/`), and whether to add a `.ferrycartignore` file. Answering them writes `ferrycart.toml`:

```toml
[site]
name = "my-blog"
backend = "bunny"
source = "public"

[deploy]
keep_releases = 10
index = "index.html"
not_found = "404.html"
```

`keep_releases` controls how many previous uploads stay available for rollback. Older releases are pruned on the next successful deploy. Setting it below 3 is a bad idea — you want at least a couple of known-good targets.

Commit `ferrycart.toml`. It contains no secrets.

## Supplying the CDN token

Ferrycart never reads credentials from `ferrycart.toml`, deliberately, so that the file is safe to check into a public repository. The token comes from the environment:

```
export FERRYCART_TOKEN="your-token-here"
```

Two optional variables cover less common setups. `FERRYCART_ACCOUNT` is required for Cloudflare and Bunny, where a single token can address multiple accounts. `FERRYCART_ENDPOINT` overrides the API base URL and is mainly useful for testing against a mock server.

For local work, keep the token in a `.env` file that is listed in `.gitignore`, and load it with `direnv` or your shell of choice. For CI, use whatever secret storage your runner provides. If `FERRYCART_TOKEN` is unset, Ferrycart exits before uploading anything and prints the variable name it expected — it will not fall back to an interactive prompt, which keeps unattended runs from hanging.

## Your first deploy

Build the site, then deploy:

```
npm run build
ferrycart deploy
```

Ferrycart hashes every file in the source directory, compares the hashes against the previous release, and uploads only what changed. On a first deploy that means everything; on a typical blog post it means one or two HTML files and maybe an image. Output looks roughly like this:

```
release 14 · 3 changed, 218 unchanged
  uploading posts/soil-blocking.html      4.1 KB
  uploading index.html                    9.7 KB
  uploading feed.xml                     31.2 KB
activating release 14 ... done (2.3s)
```

Activation is atomic. Visitors see release 13 until the switch, then release 14. There is no window where half the files are new.

Add `--dry-run` to see the change list without uploading. It is worth doing the first time, if only to confirm that `source` points where you think it does.

## Rolling back

Every activated upload keeps its release number. List them:

```
ferrycart releases
```

```
  15  2 minutes ago   active    3 files changed
  14  3 days ago                12 files changed
  13  6 days ago                1 file changed
```

To go back, activate an earlier release by number:

```
ferrycart rollback 14
```

This re-points the CDN at the files already stored for release 14. Nothing is uploaded, so a rollback typically completes in a couple of seconds — much faster than rebuilding and redeploying. Purging the edge cache happens automatically as part of activation, but propagation is still subject to your provider's usual timing.

A rollback does not delete release 15. If you fix the underlying problem in your source and redeploy, Ferrycart creates release 16 and moves forward normally. Should you need to return to 15 as-is, `ferrycart rollback 15` works until pruning removes it.

One caveat worth knowing: rollback restores files, not redirect rules or custom headers, which are configured on the provider side and live outside Ferrycart's release history. If a deploy broke because of a header change, revert that separately.
