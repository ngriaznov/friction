# Tutorial: Build a webhook receiver with Hookline

By the end of this tutorial you will have an Express server that accepts webhook deliveries on `POST /hooks/billing`, verifies that each request really came from the sender, and replies with `200 OK` fast enough that the sender does not retry.

Hookline is Express middleware. It does three things: it captures the raw request body before anything parses it, it checks the signature header against a shared secret, and it rejects deliveries whose timestamps are too old to be legitimate. Everything after that is your own handler code.

## Before you start

You need Node.js 18 or newer and a project with Express already installed. If you are starting from nothing:

```bash
mkdir billing-hooks && cd billing-hooks
npm init -y
npm install express
```

## Step 1: Install Hookline

```bash
npm install hookline
```

Hookline has no runtime dependencies beyond Node's built-in `crypto` module, so this should finish quickly.

## Step 2: Understand the raw-body problem first

This is the part people get wrong, so it is worth reading before you write any code.

Signature verification works by recomputing an HMAC over the exact bytes the sender signed. If `express.json()` runs first, it consumes the request stream, parses the JSON, and throws the original bytes away. Re-serializing `req.body` back to a string will not reliably reproduce those bytes — key order, whitespace, and Unicode escaping can all differ. The HMAC will not match, and you will spend an afternoon convinced your secret is wrong.

Hookline solves this by mounting before your JSON parser and stashing the raw buffer on the request. Mount order matters. Get it wrong and nothing works.

## Step 3: Wire up the receiver

Create `server.js`:

```js
const express = require('express');
const { verify } = require('hookline');

const app = express();

app.post(
  '/hooks/billing',
  verify({
    secret: process.env.BILLING_WEBHOOK_SECRET,
    header: 'x-billing-signature',
    tolerance: 300,
  }),
  (req, res) => {
    const event = req.body;
    console.log('verified event', event.type, event.id);
    res.sendStatus(200);
  }
);

app.listen(3000, () => console.log('listening on :3000'));
```

Three options are doing the work here:

- **`secret`** is the shared signing key from the sender's dashboard. Read it from the environment. Do not commit it.
- **`header`** names the header carrying the signature. Every provider picks a different name, so there is no useful default.
- **`tolerance`** is the maximum age, in seconds, of a signed timestamp Hookline will accept. Five minutes is a reasonable starting point. It exists so that someone who captures a valid delivery cannot replay it against you a week later.

Notice that `verify()` parses the body for you once the signature checks out, so `req.body` is already an object inside the handler. You do not need `express.json()` on this route. If you use it elsewhere in the app, mount it on the other routes rather than globally.

## Step 4: Try it locally

Start the server with a secret:

```bash
BILLING_WEBHOOK_SECRET=whsec_test123 node server.js
```

Hookline ships a small signing helper so you can generate a valid request without waiting for a real delivery:

```bash
npx hookline sign \
  --secret whsec_test123 \
  --body '{"type":"invoice.paid","id":"inv_9012"}' \
  --url http://localhost:3000/hooks/billing
```

You should see `verified event invoice.paid inv_9012` in the server log and a `200` from the CLI.

Now break it on purpose. Run the same command with `--secret whsec_wrong`. Hookline responds `401` and your handler never runs. That is the behavior you want: an unverified request should not reach any code that touches your database.

## Step 5: Respond quickly, work later

Most webhook senders enforce a timeout — often ten seconds — and retry anything slower. If your handler charges a card, sends an email, or calls three other services before replying, you will eventually process the same event twice.

Acknowledge first, then do the work:

```js
app.post('/hooks/billing', verify({ /* ... */ }), (req, res) => {
  res.sendStatus(200);
  queue.enqueue('billing-event', req.body).catch((err) => {
    console.error('enqueue failed', req.body.id, err);
  });
});
```

Even with this, assume duplicates will arrive. Retries happen for reasons outside your control, including network failures after you have already responded. Store each event's `id` and skip ones you have seen.

## What to do next

Two things worth adding before this goes to production. First, log every rejected delivery with its reason — a sudden run of `401`s usually means a secret was rotated and nobody told you. Second, put the receiver behind a route that does not require session authentication, and confirm your reverse proxy is not stripping the signature header. Proxies that normalize headers are a common cause of verification failures that look like Hookline bugs.
