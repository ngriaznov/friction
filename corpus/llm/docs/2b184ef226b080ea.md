# Cinderquery Query Language Reference

Cinderquery searches structured log events. A query is a pipeline: a filter expression selects events, and optional stages after the pipe character transform or summarize what survived the filter.

```
<filter> [| <stage>] [| <stage>] ...
```

If you write nothing but a bare string, Cinderquery treats it as a full-text match against the raw message body. Everything else described here is more specific than that, and more specific is almost always faster.

## Field filters

Fields are referenced by name. Nested fields use dot notation, and names containing spaces or punctuation must be backquoted.

```
status = 500
request.method = "POST"
`k8s.pod name` = "checkout-7f9d"
```

Supported comparison operators:

| Operator | Meaning | Notes |
|---|---|---|
| `=`, `!=` | equality | Strings compare case-sensitively |
| `<`, `<=`, `>`, `>=` | ordered comparison | Numeric and timestamp fields only |
| `~` | regex match | RE2 syntax; no backreferences |
| `!~` | regex non-match | |
| `in` | membership | Right side is a bracketed list |
| `has` | substring | Faster than `~ ".*x.*"` |

Combine filters with `and`, `or`, and `not`. Parentheses group; `and` binds tighter than `or`, so write parentheses when you mean otherwise.

```
service = "checkout" and (status >= 500 or latency_ms > 2000)
region in ["us-east-1", "eu-west-1"] and not path has "/health"
```

Two unary operators handle sparse data. `exists field` matches events where the field is present at all, and `empty field` matches events where it is present but null or the empty string. An event missing a field never matches a comparison against it, so `status != 200` will silently exclude events that have no `status` at all. Write `status != 200 or not exists status` if you want those back.

## Time ranges

Every query is bounded by a time range. If you do not specify one, Cinderquery applies the last 15 minutes.

Relative ranges use the `last` keyword with a duration:

```
last 4h
last 30m
last 7d
```

Durations accept `s`, `m`, `h`, `d`, and `w`. Absolute ranges use `from` and `to` with RFC 3339 timestamps or bare dates, interpreted in the account's configured timezone:

```
from 2031-04-02T09:00:00Z to 2031-04-02T11:30:00Z
from 2031-04-02 to 2031-04-03
```

The `to` clause is optional; omitting it means "up to now." Time clauses go at the front of the query, before the filter:

```
last 6h | service = "checkout" and status = 503
```

Note the pipe after the time clause. This is a common stumbling block — the time range is a stage, not a prefix modifier.

## Aggregation

Aggregations appear in a `stats` stage. The general shape is:

```
stats <function>(<field>) [, <function>(<field>) ...] [by <field> [, <field>]]
```

| Function | Description |
|---|---|
| `count()` | Number of matching events; takes no argument |
| `sum(f)` | Sum of a numeric field |
| `avg(f)` | Arithmetic mean, ignoring events missing `f` |
| `min(f)`, `max(f)` | Extremes |
| `p50(f)`, `p95(f)`, `p99(f)` | Approximate percentiles (t-digest, ~1% error) |
| `distinct(f)` | Exact count of unique values, up to 100k, then estimated |
| `rate()` | Events per second across the query window |

The `by` clause groups results. Cardinality is capped at 10,000 groups by default; beyond that, Cinderquery returns the largest groups and sets a `truncated` flag on the response.

Two stages commonly follow `stats`:

- `sort <field> [asc|desc]` — order the result rows. Defaults to `desc`.
- `limit <n>` — keep the first `n` rows.

There is also `timeslice <duration>`, which buckets results for charting. It goes inside the `by` clause:

```
stats count() by timeslice(5m), status
```

## Worked examples

**1. Find slow database calls from one service, grouped by query fingerprint.**

```
last 2h
| service = "orders" and component = "db" and duration_ms > 500
| stats count(), p95(duration_ms) by query_fingerprint
| sort p95(duration_ms) desc
| limit 20
```

**2. Compare error rates across deployment versions during a rollout.**

```
from 2031-04-02T14:00:00Z to 2031-04-02T16:00:00Z
| service = "checkout"
| stats count() by timeslice(1m), build_version, status >= 500
```

Boolean expressions are valid grouping keys; the column will contain `true` and `false`.

**3. Identify which clients are hitting a deprecated endpoint.**

```
last 7d
| path has "/v1/legacy" and not user_agent ~ "^(kube-probe|Prometheus)"
| stats count(), distinct(account_id) by user_agent
| sort count() desc
| limit 50
```

## Limits

Queries are capped at 60 seconds of execution and 10 pipeline stages. Regex filters cannot be the first predicate evaluated against an unindexed field on ranges longer than 24 hours; add an indexed equality filter (`service`, `host`, `env`) to narrow the scan first.
