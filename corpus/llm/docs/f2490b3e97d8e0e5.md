# Setting Up Automatic Backups for Corkboard

Corkboard stores all of your notes in a single SQLite database, which makes backups simple: back up that one file on a schedule, keep a handful of recent copies, and you're covered against disk failure, accidental deletion, and bad upgrades alike. This guide walks through scheduling backups with cron, where they land on disk, and how to restore one if things go wrong.

## Where Corkboard keeps its data

By default, a self-hosted Corkboard instance stores its database at:

```
/var/lib/corkboard/corkboard.db
```

If you overrode `CORKBOARD_DATA_DIR` in your environment configuration, your database lives at `$CORKBOARD_DATA_DIR/corkboard.db` instead. Confirm the path before continuing — the backup script below assumes the default.

## Writing the backup script

Corkboard ships a `corkboard-backup` helper alongside the main binary, which safely copies the database using SQLite's online backup API (so it works even while the server is running and writes are in flight). Create a small wrapper script at `/usr/local/bin/corkboard-backup.sh`:

```bash
#!/usr/bin/env bash
set -euo pipefail

BACKUP_DIR="/var/backups/corkboard"
TIMESTAMP=$(date +%Y%m%d-%H%M%S)
mkdir -p "$BACKUP_DIR"

corkboard-backup --output "$BACKUP_DIR/corkboard-$TIMESTAMP.db"

# Keep the last 14 backups, delete anything older
find "$BACKUP_DIR" -name 'corkboard-*.db' -mtime +14 -delete
```

Make it executable:

```
chmod +x /usr/local/bin/corkboard-backup.sh
```

## Scheduling with cron

Open your crontab with `crontab -e` and add a line to run the backup every night at 2:30 AM:

```
30 2 * * * /usr/local/bin/corkboard-backup.sh >> /var/log/corkboard-backup.log 2>&1
```

Redirecting output to a log file is worth doing from the start — if a backup silently starts failing (disk full, permissions changed), you want a paper trail rather than discovering it during a restore.

## Where backups end up

With the script above, each backup lands in `/var/backups/corkboard/` as a timestamped file, e.g. `corkboard-20260115-023000.db`. Because these are full SQLite database files, you can copy them anywhere else you'd like extra redundancy — an S3 bucket, a NAS, another server — using whatever sync tool you already trust. Many self-hosters add a second cron line that runs `rclone copy` or `rsync` against the backup directory a few minutes after the backup job finishes.

## Restoring from a backup

To restore, stop the Corkboard service first so nothing is writing to the database mid-copy:

```
systemctl stop corkboard
```

Then copy your chosen backup file over the live database, keeping a copy of the current (possibly corrupted) file just in case:

```
mv /var/lib/corkboard/corkboard.db /var/lib/corkboard/corkboard.db.bad
cp /var/backups/corkboard/corkboard-20260115-023000.db /var/lib/corkboard/corkboard.db
chown corkboard:corkboard /var/lib/corkboard/corkboard.db
```

Restart the service and confirm your notes are back:

```
systemctl start corkboard
```

Log in and spot-check a few recently edited notes. If everything looks right, you can safely delete the `.bad` file. If you're restoring after an upgrade gone wrong, downgrade the Corkboard binary to match the version that created the backup before starting the service, since newer schema migrations may not be reversible.
