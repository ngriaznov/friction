# Routing to Multiple Backends by Path Prefix

This guide covers configuring Wharfgate to route incoming requests to three backend services based on the URL path prefix, a common setup when you're splitting a monolith into services fronted by a single public hostname.

## The scenario

Suppose you're running three backend services:

- an `api` service on `127.0.0.1:9001`, which should receive everything under `/api/`
- a `docs` service on `127.0.0.1:9002`, serving `/docs/`
- a `web` service on `127.0.0.1:9003`, serving everything else

Wharfgate matches routes in the order they're declared, using the first prefix match, so the catch-all route needs to be listed last.

## The config file

Wharfgate reads its configuration from `wharfgate.yaml` by default. Here's a complete config for the scenario above:

```yaml
listen: 0.0.0.0:443
tls:
  cert: /etc/wharfgate/tls/fullchain.pem
  key: /etc/wharfgate/tls/privkey.pem

routes:
  - prefix: /api/
    upstream: 127.0.0.1:9001
    strip_prefix: false
    health_check:
      path: /healthz
      interval: 5s
      timeout: 2s
      unhealthy_threshold: 3

  - prefix: /docs/
    upstream: 127.0.0.1:9002
    strip_prefix: false
    health_check:
      path: /healthz
      interval: 10s
      timeout: 2s
      unhealthy_threshold: 3

  - prefix: /
    upstream: 127.0.0.1:9003
    strip_prefix: false
    health_check:
      path: /
      interval: 15s
      timeout: 3s
      unhealthy_threshold: 2
```

A few things worth calling out:

`strip_prefix` controls whether Wharfgate removes the matched prefix before forwarding the request. With `strip_prefix: false`, a request to `/api/users` is forwarded to the `api` upstream as `/api/users` — the backend needs to know about and handle the `/api` prefix itself. Setting it to `true` instead forwards it as `/users`, which is convenient when a backend service was written without any awareness that it's mounted under a prefix at all. Pick whichever matches how your backend is actually built; mixing the two approaches inconsistently across routes is a common source of confusing 404s.

Route order matters because Wharfgate uses first-match, not longest-match, prefix routing. If the catch-all `/` route were listed first, it would swallow every request before the more specific `/api/` and `/docs/` rules ever got a chance to match. Always order routes from most specific to least specific.

## Reloading the config

After editing `wharfgate.yaml`, reload without dropping active connections:

```
wharfgate reload
```

This sends `SIGHUP` to the running process, which re-reads the config file and swaps in the new routing table atomically — in-flight requests finish against the old table, and new requests use the new one. A malformed config file is rejected without affecting the currently running configuration, and the error is written to Wharfgate's log with the line number of the problem.

## A note on health checks

Each route's `health_check` block controls whether Wharfgate considers that backend eligible to receive traffic at all. Wharfgate polls the given `path` on the upstream at the configured `interval`; if a response isn't received within `timeout`, or a non-2xx status is returned, that counts as one failed check. Once `unhealthy_threshold` consecutive checks have failed, Wharfgate stops routing traffic to that upstream and returns `503 Service Unavailable` for requests matching its prefix, rather than forwarding to a backend it believes is down.

There's no requirement that all three routes use the same health-check path or cadence — in the example above, the `web` route checks `/` instead of a dedicated `/healthz` endpoint, and polls less frequently, since it's assumed to be a lower-traffic, less critical path than the API. Match the interval and threshold to how quickly you need Wharfgate to notice and react to a backend going down versus how much load you're willing to put on that backend just for health checking.

Once a backend recovers and starts passing health checks again, Wharfgate resumes routing to it automatically — no manual intervention or reload is needed.
