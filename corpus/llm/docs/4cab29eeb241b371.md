# Building a Webhook Receiver with Hookline

This tutorial walks through building a small Node.js server that receives webhooks, verifies their signatures, and responds correctly, using the Hookline middleware library. By the end you'll have a working receiver you can point a real webhook provider at.

## Installing Hookline

Hookline is published on npm and works as Express middleware:

```
npm install hookline express
```

It has no other runtime dependencies beyond Node's built-in `crypto` module, which it uses for signature verification.

## Setting up a basic server

Start with a minimal Express app:

```js
const express = require('express');
const app = express();

app.listen(3000, () => {
  console.log('Listening on port 3000');
});
```

Webhook payloads need to be verified against their raw, unparsed body — most signature schemes sign the exact bytes that were sent, and if Express's JSON parser has already re-serialized the body, the signature check will fail even for a legitimate request. Hookline handles this by capturing the raw body itself, so don't add `express.json()` in front of it on your webhook route.

## Adding the Hookline middleware

Import `hookline` and mount it on the route that will receive webhooks:

```js
const hookline = require('hookline');

app.post(
  '/webhooks/incoming',
  hookline({
    secret: process.env.WEBHOOK_SECRET,
    header: 'x-signature',
    algorithm: 'sha256',
  }),
  (req, res) => {
    console.log('Verified payload:', req.hookline.body);
    res.sendStatus(200);
  }
);
```

The `secret` option is the shared signing secret you and the webhook provider both know — never commit this to source control; load it from an environment variable as shown. `header` names the HTTP header carrying the signature (providers vary here: some use `X-Signature`, others `X-Hub-Signature-256`, and so on — check your provider's docs). `algorithm` selects the HMAC digest algorithm used to compute it; `sha256` is by far the most common.

## How verification works

When a request hits this route, Hookline:

1. Reads the raw request body as a Buffer, before any other middleware can touch it.
2. Computes an HMAC of that raw body using `secret` and `algorithm`.
3. Compares the computed digest against the value in the header named by `header`, using a constant-time comparison to avoid leaking timing information about how close an attacker's guess is.
4. If they match, attaches the parsed JSON body to `req.hookline.body` and calls `next()`. If they don't match, or the header is missing, it responds with `401 Unauthorized` and never calls your route handler.

This means your handler only ever runs for requests that passed verification — you don't need to duplicate the check yourself.

## Handling different signature formats

Some providers prefix the signature with the algorithm name, like `sha256=abcdef...`. Hookline handles this automatically for the common formats, but if your provider does something unusual, you can supply a custom extractor:

```js
hookline({
  secret: process.env.WEBHOOK_SECRET,
  header: 'x-signature',
  algorithm: 'sha256',
  extractSignature: (headerValue) => headerValue.replace('sha256=', ''),
})
```

## Responding correctly

Most webhook providers treat any non-2xx response as a delivery failure and will retry, often with exponential backoff, for a limited window (commonly 24–72 hours) before giving up. A few things worth getting right:

- Respond with `200` (or `202` if you're queuing the work rather than processing it inline) as soon as verification succeeds and you've durably queued or begun processing the payload. Don't make the provider wait on slow downstream work — if handling the webhook involves calling other services, hand it off to a job queue and return immediately.
- Avoid responding `200` before verification has actually run — it's tempting to return early during development, but this trains the provider (and you) to think delivery is working when signatures may be silently failing.
- If your handler throws after Hookline's middleware has already verified the request, make sure your error-handling middleware still returns a definite status code. An unhandled exception that hangs the connection will look like a timeout to the provider and trigger unnecessary retries.

## Testing locally

Since most webhook providers need a publicly reachable URL, use a tunneling tool like ngrok during development:

```
ngrok http 3000
```

Point your provider's webhook configuration at the resulting `https://` URL plus your route path, and trigger a test event from the provider's dashboard. Hookline logs a warning to stderr (not a rejection) when it sees a request with no signature header at all, which is a useful signal that you're hitting the route from something other than the real provider — for instance, a stray browser request or an incorrectly configured health check.

With verification, queuing, and a fast response in place, this receiver is a reasonable starting point for anything from payment notifications to CI status callbacks.
