# Building a Webhook Receiver with Hookline

This tutorial walks through building a small webhook receiver in Node.js using Hookline, a middleware library for verifying and routing incoming webhook requests. By the end, you'll have a working endpoint that accepts a webhook, verifies its signature, and responds correctly to the sender.

## What Hookline does

Webhook providers (payment processors, source control hosts, chat platforms) typically sign each request body with a shared secret so the receiver can confirm the payload wasn't forged or altered in transit. Hookline handles that verification step as Express-compatible middleware, so you don't have to hand-roll HMAC comparisons for every provider you integrate with.

## Installing the package

Hookline is distributed on npm. In an existing Node.js project (or a fresh one created with `npm init -y`), install it alongside Express:

```
npm install hookline express
```

Hookline supports Node 16 and later. It has no native dependencies, so installation should be quick even on constrained CI runners.

## Setting up a basic server

Create a file called `server.js`:

```js
const express = require("express");
const { verifySignature } = require("hookline");

const app = express();

// Hookline needs the raw request body to compute the signature,
// so capture it before any JSON parsing happens.
app.use(express.json({
  verify: (req, res, buf) => {
    req.rawBody = buf;
  },
}));

app.post("/webhooks/incoming", verifySignature({
  secret: process.env.WEBHOOK_SECRET,
  header: "x-hookline-signature",
}), (req, res) => {
  console.log("Verified payload:", req.body);
  res.sendStatus(200);
});

app.listen(3000, () => {
  console.log("Webhook receiver listening on port 3000");
});
```

A few things worth noting here. First, `verifySignature` reads `req.rawBody`, not `req.body` — signatures are computed over the exact bytes sent, and re-serializing parsed JSON would produce a different string and fail verification. That's why the `verify` callback in `express.json()` is required; skipping it is the most common reason a Hookline integration fails in testing.

Second, the `secret` option should come from an environment variable or secrets manager, never a hardcoded string. Most providers give you this secret when you register the webhook endpoint in their dashboard.

## Verifying an incoming signature

Under the hood, `verifySignature` computes an HMAC-SHA256 digest of the raw body using your secret, then compares it — using a constant-time comparison to avoid timing attacks — against the value in the header you specify. If the signature is missing or doesn't match, Hookline short-circuits the request with a `401 Unauthorized` before your route handler ever runs, so you can trust that anything reaching your handler is authentic.

If you need to support a provider with a different signing scheme (some prefix the signature with an algorithm name, like `sha256=...`), pass a `parseSignature` function:

```js
verifySignature({
  secret: process.env.WEBHOOK_SECRET,
  header: "x-hub-signature-256",
  parseSignature: (value) => value.replace(/^sha256=/, ""),
})
```

## Responding correctly

Most webhook providers treat any non-2xx response as a delivery failure and will retry — often on an exponential backoff schedule, sometimes for up to 24 hours. Two rules keep this well-behaved:

- Respond with `200` (or `202` if you're queuing the work) as soon as verification succeeds, before doing any slow downstream processing.
- If your handler does need to do real work — writing to a database, calling another API — do it asynchronously after sending the response, so the provider doesn't time out and retry a request you actually received successfully.

## Testing locally

Since providers need a publicly reachable URL, use a tunneling tool like `ngrok` during development:

```
ngrok http 3000
```

Point your webhook provider's dashboard at the resulting `https://` URL plus `/webhooks/incoming`, trigger a test event from the provider's side, and watch your server logs for the verified payload. If verification fails, double-check that you're reading the raw body correctly and that the secret matches what's configured on the provider's end — those two issues account for the overwhelming majority of Hookline setup problems.

From here, you can add additional routes for other event types, log verification failures for monitoring, or plug the verified payload into a job queue for further processing.
