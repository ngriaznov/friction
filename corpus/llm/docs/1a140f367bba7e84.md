# How Emberscript Collects Garbage

Emberscript manages memory for you. Objects are allocated when you create them and reclaimed when nothing can reach them anymore. This page explains the strategy the runtime uses, what it costs at runtime, and which knobs are worth turning.

## Why generational

Most objects in an Emberscript program die almost immediately. A string built inside a loop body, a temporary table returned from a helper, the intermediate results of a chain of map calls — these are unreachable a few microseconds after they are created. A much smaller set of objects survives: module tables, configuration loaded at startup, long-lived caches, the closure graph of a running server.

The generational hypothesis says that if you scan only the young objects, you spend a tiny amount of work per unit of memory reclaimed, because nearly all of what you scan is already dead. Emberscript takes that bet. Its heap is split into two spaces:

- **The nursery** (young generation), a contiguous region where every new allocation lands.
- **The mature space** (old generation), where objects go once they have survived enough nursery collections.

Allocation in the nursery is a pointer bump. The runtime keeps a cursor into the free region, increments it by the object size, and returns. There is no free-list search and no header scan, which is why allocating in a hot loop is cheap even though the loop produces garbage.

## Minor collections

When the nursery cursor reaches the end of the region, the runtime runs a **minor collection**. It walks the roots — the value stack, active call frames, the global table, and any handles held by native extensions — and copies every reachable nursery object into a survivor area. Objects that nothing points to are simply not copied; the whole nursery is then declared empty and the cursor resets to the start.

The cost of a minor collection is proportional to the *surviving* data, not to the nursery size. A 32 MB nursery in which 200 KB survives costs about as much to collect as a 4 MB nursery in which 200 KB survives. This is the single most important fact for tuning, and we come back to it below.

An object that survives two minor collections is **promoted**: it is copied into the mature space and stops being scanned by minor collections entirely.

### The write barrier

Promotion creates a problem. If a mature object holds a reference to a nursery object, and minor collections never scan mature objects, that nursery object looks unreachable and gets freed while still in use.

Emberscript solves this with a write barrier. Every store of a reference into an object field passes through a check: if the target object lives in the mature space and the value being stored lives in the nursery, the target is added to a remembered set. Minor collections treat the remembered set as an extra root set.

The barrier costs a compare and a rarely taken branch on each reference store. It is one of the reasons a program that repeatedly mutates a long-lived array with fresh objects can be slower than one that rebuilds the array wholesale.

## Major collections and stop-the-world pauses

The mature space is collected by a mark-and-sweep pass, called a **major collection**. Most of the marking runs incrementally, interleaved with your program in small slices, so a major cycle usually does not show up as a single long stall.

A full stop-the-world pause can still happen. In practice there are three causes:

1. **Every minor collection is stop-the-world.** These are short — typically well under a millisecond for small survivor sets — but they are unconditional.
2. **The final mark phase of a major cycle** must run without mutation to close out the incremental marking safely.
3. **Allocation failure.** If the mature space cannot satisfy a promotion and the incremental collector has not finished, the runtime falls back to a complete blocking collection. This is the pause that shows up in latency graphs, and it is a symptom of the collector not being given enough headroom.

Native extensions that hold the runtime lock for a long time also delay collection, because a pause cannot begin until all threads reach a safepoint.

## Tuning the young generation

The nursery size is set with `--nursery-size` (accepting a value like `16M`) or at embed time through `ember_config_set_nursery`. The default is 4 MB.

Raising it trades memory for throughput. Because minor collection cost tracks survivors rather than capacity, a larger nursery means fewer collections for roughly the same work each, and — more subtly — it gives short-lived objects more time to die before a collection ever looks at them, so the survivor set shrinks too.

Reasonable starting points:

- **Batch and CLI workloads:** 32–64 MB. Throughput matters, occasional pauses do not.
- **Request-serving processes:** 8–16 MB, sized so that a typical request's allocations fit comfortably inside one nursery.
- **Embedded or memory-constrained hosts:** keep the default, or drop to 1 MB and accept more frequent, very cheap collections.

Measure before and after with `EMBER_GC_LOG=1`, which prints one line per collection with the surviving byte count and the elapsed time. If survivor bytes per minor collection are climbing as you grow the nursery, you have long-lived data being allocated in a loop, and no nursery size will fix that — the allocation pattern is what needs to change.
