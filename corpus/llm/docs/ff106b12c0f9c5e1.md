# Configure rate limiting in Tollbooth

Rate limiting in Tollbooth is defined per route and evaluated before any upstream request is made. This guide covers setting a per-client limit, allowing short bursts above that limit, and replacing the default 429 response body with your own.

You will need a running gateway (0.9 or later), write access to `tollbooth.yaml`, and the ability to reload the gateway process.

## Set a per-client limit

Limits live under the `rate_limit` key of a route. A minimal configuration looks like this:

```yaml
routes:
  - id: search-api
    path: /v1/search
    upstream: http://search.internal:8080
    rate_limit:
      key: client_id
      rate: 100/m
```

`rate` accepts a count and a window separated by a slash. The window suffixes are `s`, `m`, `h`, and `d`. `100/m` and `6000/h` are not equivalent: the first refills continuously over a one-minute window, the second over an hour, so the second permits a much longer stretch of traffic before it starts rejecting.

The `key` field decides what counts as "a client." Tollbooth ships with three built-in keys:

| Key | Derived from |
| --- | --- |
| `client_id` | The authenticated principal resolved by the auth filter |
| `ip` | The peer address, or `X-Forwarded-For` if `trust_proxy: true` is set globally |
| `header:<name>` | The literal value of the named request header |

If the key cannot be resolved for a given request — an unauthenticated call on a route keyed by `client_id`, for example — Tollbooth falls back to the value of `on_missing_key`, which defaults to `deny`. Set it to `allow` if you want anonymous traffic to pass through unmetered, or to `ip` to fall back to address-based counting.

Counters are held in the configured store. The default in-memory store is per-instance, so a limit of `100/m` across four gateway replicas effectively permits 400 requests per minute. For a shared counter, point `store` at Redis:

```yaml
rate_limit_store:
  type: redis
  address: redis.internal:6379
  prefix: tb
```

## Allow bursts

A plain `rate` uses a token bucket whose capacity equals the rate, which means a client that saves up its budget can spend the whole minute's allowance in one second. When you want to permit that deliberately — a client that batches its calls at the top of each hour, say — raise the bucket capacity with `burst`:

```yaml
    rate_limit:
      key: client_id
      rate: 100/m
      burst: 150
```

The bucket now holds 150 tokens and refills at 100 per minute. A client that has been idle can fire 150 requests immediately, after which it is held to the sustained rate. Setting `burst` lower than `rate` is rejected at load time.

## Customize the 429 response

By default a throttled request gets an empty body, a `429` status, and a `Retry-After` header in seconds. Override the body per route:

```yaml
    rate_limit:
      key: client_id
      rate: 100/m
      response:
        status: 429
        headers:
          Content-Type: application/problem+json
        body: |
          {
            "type": "https://errors.example.com/rate-limit",
            "title": "Too many requests",
            "detail": "Limit is {{ .Limit }} per {{ .Window }}.",
            "retry_after": {{ .RetryAfter }}
          }
```

The body is a Go text template rendered per request. Available fields are `.Limit`, `.Window`, `.RetryAfter` (integer seconds), `.Remaining`, and `.Key`. Avoid putting `.Key` in a response body on IP-keyed routes, since it echoes the caller's address back to them.

Setting `status` to something other than 429 is allowed but rarely a good idea; clients and SDKs treat 429 specially.

## Reload and verify

Run `tollbooth check -c tollbooth.yaml` to validate, then `tollbooth reload` to apply without dropping connections. Confirm the limit is live by watching the `tollbooth_ratelimit_rejected_total` counter, labelled by route id, while replaying traffic against the route.
