# How Caching Works in Ledgerline

Ledgerline includes a built-in caching layer designed to reduce redundant database round-trips without requiring you to manage a separate cache server for common cases. This page explains the model behind it: how query results get cached, how the cache learns about writes, and the difference between the two cache scopes Ledgerline supports.

## Why a caching layer at all

Most ORMs re-issue a SQL query every time you call `.all()` or `.first()`, even if nothing in the underlying table has changed since the last call. In request-heavy code paths — a template that loops over the same lookup table three times, or a service that re-reads a small reference table on every function call — this adds up to a lot of identical round-trips. Ledgerline's caching layer intercepts these calls and, when it can prove the result is still valid, returns the cached rows instead of touching the database again.

## Query result caching

When you execute a query through a `Model.query()` call, Ledgerline computes a cache key from the compiled SQL statement and its bound parameters. If a result for that exact key already exists in the cache, Ledgerline returns the cached rows directly, skipping the database entirely. If not, it runs the query normally and stores the result under that key before returning it.

This is deliberately conservative: two queries only share a cache entry if they are identical after parameter binding. `User.query(status="active")` and `User.query(status="pending")` never collide, and neither do queries against different tables. The cache does not try to reason about semantic equivalence between differently-written queries that happen to return the same rows — it keys strictly on the compiled statement.

## Invalidation on writes

The harder problem is knowing when a cached result has gone stale. Ledgerline handles this by tracking, for every cache entry, which tables contributed rows to that query. When you call `.save()`, `.delete()`, or run a bulk `update()`/`delete()` against a model, Ledgerline looks up every cache entry tagged with that model's table and evicts it immediately, before the write's transaction commits.

This is a table-level invalidation strategy, not a row-level one. Updating a single `Invoice` row invalidates every cached query that touched the `invoices` table, even queries that filtered to completely different rows. This trades some cache efficiency for correctness and simplicity: row-level invalidation would require tracking primary keys per cached query and reasoning about joins, which becomes unreliable quickly. In practice, most performance wins come from read-heavy, write-light tables — reference data, configuration, lookup tables — where table-level invalidation costs little because writes are rare.

Invalidation is transactional: if a transaction that writes to `invoices` rolls back, the eviction is undone along with it, so a failed write never leaves you with an incorrectly-emptied cache.

## Per-request versus process-level scope

Ledgerline caches operate at one of two scopes, chosen when you configure the caching layer.

**Per-request scope** creates a fresh, empty cache at the start of each request (or each unit of work, if you're not in a web context) and discards it when that unit of work finishes. This scope is safe by default: it can never serve a request stale data left over from a previous request, because nothing persists between them. It's most useful for eliminating duplicate queries within a single request — the classic case of the same lookup being issued five times while rendering one page.

**Process-level scope** keeps the cache alive for the lifetime of the worker process, shared across every request that process handles. This catches far more redundant queries, since popular lookups get reused across users and requests, but it requires the invalidation logic described above to actually be correct for your access patterns — including writes made by *other* processes, which process-level caching does not see unless you also configure a shared invalidation channel (Ledgerline supports Redis pub/sub for this; see the Distributed Cache Invalidation reference page).

If you're unsure which to use, start with per-request scope. It has no correctness surface area beyond a single request and still eliminates most accidental query duplication. Move to process-level caching only for tables you've profiled as genuinely hot and rarely written.
