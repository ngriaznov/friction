# Branching with Driftline

Driftline is a wrapper around Git that adds opinionated commands for teams who want a consistent branching model without writing it down in a wiki page nobody reads. This page explains the model Driftline expects and how its signature command, `driftline sync`, differs from a plain `git rebase`.

## The three branch types

Driftline recognizes three kinds of branches, distinguished by naming convention rather than by any special Git object:

- **Trunk** — a single long-lived branch, almost always `main`. Trunk is always deployable. Nothing is committed to it directly; it only receives merges from release branches.
- **Feature branches** — short-lived branches named `feature/<ticket>-<slug>`, cut from trunk. A feature branch exists for the lifetime of a single unit of work and is deleted once it lands.
- **Release branches** — named `release/<version>`, cut from trunk at the point a release is cut, and used to stabilize that version: cherry-picking fixes, bumping version numbers, and tagging. Release branches are long-lived only in the sense that old ones stick around for reference; no new work is planned on them.

This is a fairly conventional trunk-based layout. What Driftline adds is tooling that keeps feature branches from drifting too far from trunk, and a stronger set of guardrails around what can land on a release branch.

## Why feature branches need `driftline sync`

A plain `git rebase main` replays your branch's commits on top of the current tip of `main`. That works, but it has two properties that cause friction on a team where several people are rebasing feature branches against a fast-moving trunk multiple times a day:

1. It rewrites every commit on the branch, even ones that were already rebased cleanly against an earlier version of `main`, which produces new commit hashes and can make force-pushes to a shared feature branch look more disruptive than they are.
2. It gives you no help distinguishing a merge conflict caused by your own change from one caused by an unrelated concurrent change landing on `main` at the same time.

`driftline sync` addresses both. Internally it still uses Git's rebase machinery, but it first checks whether your branch's fork point has moved — that is, whether new commits have landed on `main` since you last synced — and only replays commits from that fork point forward, rather than blindly replaying the whole branch. If nothing has changed upstream, `driftline sync` is a no-op and reports "already in sync" instead of silently rewriting history for no reason.

When a conflict does occur, `driftline sync` annotates it with the commit and author on `main` that introduced the conflicting change, and offers to open a three-way diff scoped to just the conflicting hunk, rather than dropping you into the same merge-conflict markers Git would show for a manual rebase. This is the single biggest quality-of-life difference teams report after adopting Driftline: conflict resolution stops requiring a second person to explain "what actually changed."

## Landing on trunk and cutting a release

Feature branches land on trunk through `driftline land`, which requires a clean `driftline sync` first and squashes the branch into a single commit by default (configurable per-repository). Once trunk has accumulated the commits intended for a release, `driftline release cut <version>` branches `release/<version>` from the current tip of trunk. From that point, fixes destined for the release go through `driftline backport <version>`, which cherry-picks a commit from trunk onto the release branch and records the mapping so that `driftline release cut` for the *next* version can warn you if a backported fix was never re-applied to trunk — a common source of regressions in projects using plain Git, where a hotfix lands on a release branch and quietly never makes it back upstream.

## Summary

The branching model itself — trunk, feature branches, release branches — is not unusual. What Driftline changes is the mechanics of keeping feature branches current and the bookkeeping around what has and hasn't made it back to trunk after a release-branch fix. Teams evaluating Driftline should expect the branch *names* to look familiar; the difference shows up in daily conflict resolution and in release hygiene over time.
