# Ratchet REST API Reference

Ratchet exposes a REST API for enqueuing, inspecting, and cancelling jobs on a task queue. All endpoints are served under `/v1` and expect/return JSON. Authentication uses a bearer token passed in the `Authorization` header on every request; examples below omit it for brevity but it is required in any real deployment.

## Enqueue a job

```
POST /v1/jobs
```

Request body:

```json
{
  "queue": "email-sends",
  "payload": {
    "to": "user@example.com",
    "template": "welcome"
  },
  "priority": 5,
  "max_attempts": 3,
  "run_after": "2024-03-01T00:00:00Z"
}
```

- `queue` (required) — the name of the queue this job belongs to. Queues are created implicitly on first use.
- `payload` (required) — an arbitrary JSON object passed unmodified to whatever worker picks up the job.
- `priority` (optional, default `0`) — higher values are dequeued first within the same queue.
- `max_attempts` (optional, default `5`) — how many times Ratchet will retry the job on failure before marking it `failed` permanently.
- `run_after` (optional) — an ISO 8601 timestamp; the job won't be dequeued before this time, even if a worker is idle and waiting.

Example request:

```
curl -X POST https://ratchet.example.com/v1/jobs \
  -H "Authorization: Bearer $RATCHET_TOKEN" \
  -H "Content-Type: application/json" \
  -d '{"queue":"email-sends","payload":{"to":"user@example.com","template":"welcome"}}'
```

Example response (`201 Created`):

```json
{
  "id": "job_8f2a1c9e",
  "queue": "email-sends",
  "status": "pending",
  "priority": 0,
  "attempts": 0,
  "max_attempts": 5,
  "created_at": "2024-02-28T14:03:11Z",
  "run_after": null
}
```

The `id` returned here is what you'll use to check status or cancel the job later. Ratchet job IDs are opaque strings and should not be parsed for meaning — their format is not part of the API contract and may change between versions.

## Check job status

```
GET /v1/jobs/{id}
```

Example request:

```
curl https://ratchet.example.com/v1/jobs/job_8f2a1c9e \
  -H "Authorization: Bearer $RATCHET_TOKEN"
```

Example response (`200 OK`):

```json
{
  "id": "job_8f2a1c9e",
  "queue": "email-sends",
  "status": "completed",
  "priority": 0,
  "attempts": 1,
  "max_attempts": 5,
  "created_at": "2024-02-28T14:03:11Z",
  "started_at": "2024-02-28T14:03:12Z",
  "completed_at": "2024-02-28T14:03:14Z",
  "result": {
    "message_id": "msg_991a"
  }
}
```

`status` is one of `pending`, `running`, `completed`, `failed`, or `cancelled`. A `failed` job includes an additional `error` field with the last failure's message; a job that failed and has retries remaining shows `pending` again with `attempts` incremented, rather than `failed`, since it will be retried automatically.

Requesting a job ID that doesn't exist returns `404 Not Found` with a standard error body:

```json
{
  "error": "job_not_found",
  "message": "No job with id job_doesnotexist"
}
```

## Cancel a pending job

```
DELETE /v1/jobs/{id}
```

Only jobs in `pending` status can be cancelled. A job that's already `running` will finish its current attempt; Ratchet does not support interrupting a job mid-execution, since it has no way to know whether doing so would leave the worker's side effects in an inconsistent state. A `completed`, `failed`, or already-`cancelled` job returns an error rather than silently succeeding.

Example request:

```
curl -X DELETE https://ratchet.example.com/v1/jobs/job_8f2a1c9e \
  -H "Authorization: Bearer $RATCHET_TOKEN"
```

Example response (`200 OK`):

```json
{
  "id": "job_8f2a1c9e",
  "queue": "email-sends",
  "status": "cancelled",
  "cancelled_at": "2024-02-28T14:05:00Z"
}
```

If the job is not cancellable, Ratchet responds `409 Conflict`:

```json
{
  "error": "job_not_cancellable",
  "message": "Job job_8f2a1c9e is running and cannot be cancelled"
}
```

## Listing jobs in a queue

Not covered above but worth mentioning: `GET /v1/queues/{queue}/jobs` returns a paginated list of jobs for a given queue, filterable by `status` via a query parameter (e.g. `?status=failed`), which is often the fastest way to find a specific job when you don't already have its ID — for instance, when triaging a batch of failures after a downstream outage.

## Rate limits

The API enforces a per-token rate limit, returned in the `X-RateLimit-Remaining` and `X-RateLimit-Reset` response headers on every request. Exceeding the limit returns `429 Too Many Requests`. Enqueueing jobs in bulk should use the batch endpoint (`POST /v1/jobs/batch`, not detailed here) rather than looping individual `POST /v1/jobs` calls, both to avoid hitting this limit and because it's substantially faster server-side.
