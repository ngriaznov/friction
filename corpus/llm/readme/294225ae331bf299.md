# notesync-swift

Offline-first note syncing for iOS, built on top of Core Data.

Your app keeps writing to Core Data exactly as it already does. notesync-swift watches the managed object context, records every insert, update and delete into a durable local queue, and drains that queue against your server whenever the device has connectivity. Nothing blocks on the network. A note saved in airplane mode at 30,000 feet is a note that syncs on landing.

Requires iOS 15+ and Swift 5.9.

## Installation

Swift Package Manager. In Xcode, **File → Add Package Dependencies**, or add it to `Package.swift`:

```swift
dependencies: [
    .package(url: "https://github.com/notesync/notesync-swift.git", from: "2.1.0")
]
```

Then add `NoteSync` to your target's dependencies.

## Getting started

Point the engine at your persistent container and your server, and start it. That's the whole setup.

```swift
import NoteSync

let engine = SyncEngine(
    container: persistentContainer,
    endpoint: URL(string: "https://api.example.com/v1/notes")!,
    auth: .bearer { await tokenStore.currentToken() },
    entityName: "Note"
)

try engine.start()
```

The `auth` closure is called before each request, so token refresh is your app's business and the engine never caches a stale credential.

Sync status is published, so you can drive UI from it directly:

```swift
struct SyncBadge: View {
    @ObservedObject var engine: SyncEngine

    var body: some View {
        switch engine.status {
        case .idle(let lastSynced):
            Text("Synced \(lastSynced, style: .relative) ago")
        case .syncing(let pending):
            Label("Syncing \(pending) change(s)", systemImage: "arrow.triangle.2.circlepath")
        case .offline(let pending):
            Label("\(pending) waiting", systemImage: "wifi.slash")
        case .failed(let error):
            Label(error.localizedDescription, systemImage: "exclamationmark.triangle")
        }
    }
}
```

`status` is `@Published` on the main actor. The engine itself does its work off the main thread on a private queue context.

## Conflict resolution

Conflicts are inevitable when the same note is edited on a phone and an iPad while both are offline. notesync-swift resolves them with **field-level last-writer-wins**, not whole-record last-writer-wins.

Every tracked attribute carries its own modification timestamp in a shadow table. When the server reports a version mismatch, the engine merges attribute by attribute: for each field, the version with the later timestamp survives. If your iPad changed the title and your phone changed the body, you keep both edits. Only a genuine collision on the same field discards anything.

Timestamps come from the server's clock, stamped when a change is accepted, with the device's local clock used only as a tiebreaker for changes queued while offline. This keeps device clock drift from silently eating edits.

If field-level merging isn't right for your data model, supply your own resolver:

```swift
engine.conflictResolver = { local, remote in
    // Return the winning snapshot, or a merged one you construct.
    local.updatedAt > remote.updatedAt ? local : remote
}
```

Deletes always win over concurrent edits. A note deleted on one device stays deleted, on the theory that resurrecting something the user threw away is more surprising than losing a late edit.

## Background sync

Foreground sync is automatic: the engine drains the queue on save, on app foreground, and whenever `NWPathMonitor` reports the network coming back.

For background sync, register the engine's task identifier in your `Info.plist` under `BGTaskSchedulerPermittedIdentifiers`:

```
com.notesync.refresh
```

and hand off registration during launch:

```swift
func application(_ app: UIApplication,
                 didFinishLaunchingWithOptions opts: LaunchOptions?) -> Bool {
    SyncEngine.registerBackgroundTask(identifier: "com.notesync.refresh")
    return true
}
```

The engine schedules a `BGAppRefreshTask` after each foreground sync, with a minimum interval of 15 minutes. iOS decides when — or whether — to actually run it, based on usage patterns and battery state, so treat background sync as opportunistic rather than guaranteed. The queue is durable, so a task that never runs costs you nothing but freshness.

Background runs are capped at 25 seconds and will checkpoint and reschedule if the queue is still draining when the budget expires.

## Server contract

The server needs to support three operations: a paginated pull since a cursor, a batch push with per-record version numbers, and a `409` response carrying the current server state on version mismatch. See `docs/protocol.md` for the wire format.
