# backupctl

backupctl is a small collection of bash scripts that automate nightly
backups of a LAMP stack server: a MySQL dump of each database, an rsync
copy of the web root, and rotation of old archives so backups don't slowly
fill the disk.

## Required environment variables

backupctl reads database credentials from the environment rather than
taking them as arguments, so they don't end up in `ps` output or shell
history. Set these before running, typically in `/etc/backupctl.env`:

```bash
BACKUPCTL_DB_HOST=localhost
BACKUPCTL_DB_USER=backup
BACKUPCTL_DB_PASS=changeme
BACKUPCTL_WEBROOT=/var/www
BACKUPCTL_DEST=/var/backups/backupctl
BACKUPCTL_RETAIN_DAYS=14
```

The MySQL user referenced by `BACKUPCTL_DB_USER` needs at least `SELECT`,
`LOCK TABLES`, and `SHOW VIEW` privileges across the databases you want
backed up.

## Installing the cron entry

`backupctl` ships a single entry point, `backup.sh`, meant to run once a
night:

```
0 2 * * * . /etc/backupctl.env && /opt/backupctl/backup.sh
```

Sourcing the env file in the crontab line (rather than having `backup.sh`
read it directly) keeps the credentials out of the script's own working
directory and makes it easy to swap in different credentials per server
without touching the script.

## Where backups go and how retention works

Each nightly run creates a timestamped subdirectory under
`BACKUPCTL_DEST`:

```
/var/backups/backupctl/2024-02-18-020000/
  db/
    app_production.sql.gz
    app_production_sessions.sql.gz
  webroot.tar.gz
```

Every database backupctl can see (excluding `information_schema`,
`performance_schema`, `mysql`, and `sys`) gets its own gzipped dump. The
web root is archived as a single tarball rather than dumped per-directory.

After a successful run, `backup.sh` deletes any dated subdirectory older
than `BACKUPCTL_RETAIN_DAYS`. Retention only counts complete, successfully
finished backups — if a run fails partway through, its partial directory
is left in place rather than counted toward rotation, so a failed backup
never silently ages out a good one.

## Restoring

`restore.sh` reverses the process. Given a backup directory, it restores
each database dump via `mysql` and extracts the web root tarball back into
place:

```
/opt/backupctl/restore.sh /var/backups/backupctl/2024-02-18-020000
```

It restores every database found under `db/` in that backup unless you
pass `--db=name` to restore just one, and it always prompts for
confirmation before overwriting the web root, since that step is
destructive to whatever's currently there.

## Requirements

`mysqldump`, `mysql`, `rsync`, `tar`, and `gzip` need to be on `PATH`.
Nothing else — no package to install, just copy the scripts wherever you
like and point cron at them.
