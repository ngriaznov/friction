# feedwell

feedwell is a self-hosted RSS and Atom feed reader with a lightweight web UI. It's built for people who want to own their reading list instead of renting it from a hosted service — run it on a spare box, a home server, or a small VPS, and point any WSGI-compatible server at it.

## Features

- **Folder organization** — group feeds into folders and sub-folders, reorder them by drag-and-drop, and collapse folders you're not actively reading.
- **Read/unread tracking** — every article is tracked per-user, with keyboard shortcuts for marking read, marking all-read-in-folder, and starring for later.
- **Full-text search across cached articles** — feedwell indexes the full body of every article it caches, not just titles, so you can search for a phrase you half-remember from three weeks ago.
- **OPML import/export** — bring your existing subscriptions in from any other reader, or export your list to move away, with no lock-in either direction.

feedwell deliberately does not try to be a social network, a recommendation engine, or a read-it-later service. It reads feeds, tracks what you've seen, and lets you search what it's cached. That's the whole job.

## Installation from source

feedwell is a Python WSGI application with no required external services beyond a database. It's tested on Python 3.10+.

```bash
git clone https://example.com/feedwell/feedwell.git
cd feedwell
python3 -m venv venv
source venv/bin/activate
pip install -r requirements.txt
```

If you plan to use PostgreSQL instead of the SQLite default, also install the Postgres extra:

```bash
pip install -r requirements-postgres.txt
```

Copy the example config and adjust it for your environment:

```bash
cp config.example.toml config.toml
```

At minimum, set `secret_key` to a random value (feedwell uses it to sign session cookies) and confirm the `database.url` matches your intended backend. See the Database section below for the exact connection string format for each backend.

Initialize the schema:

```bash
python -m feedwell.db init
```

## First-run setup

The first time feedwell starts with an empty database, visiting the web UI redirects you to `/setup`, a one-time page that creates the initial admin account. You'll be asked for an email address, a password, and a display name. Once this account is created, `/setup` disables itself — further accounts (if you enable multi-user mode in `config.toml`) are created from the admin panel, not this route.

Feedwell does not send any email during setup or normal operation by default; password resets, if enabled, require configuring an SMTP relay under `[mail]` in `config.toml`.

To run feedwell directly for local testing, without a production WSGI server:

```bash
python -m feedwell.wsgi --dev
```

This binds to `127.0.0.1:8000` and auto-reloads on code changes. It is not meant to be exposed to the network — for anything beyond your own laptop, run it behind a real WSGI server as described below.

## Running behind a WSGI server

feedwell exposes a standard WSGI callable at `feedwell.wsgi:application`, so it works with any WSGI server. Two common setups:

**gunicorn**, fronted by nginx or Caddy for TLS termination:

```bash
gunicorn feedwell.wsgi:application --workers 4 --bind unix:/run/feedwell.sock
```

**uWSGI**, if you're already standardized on it:

```bash
uwsgi --module feedwell.wsgi:application --socket /run/feedwell.sock --processes 4
```

Either way, terminate TLS at your reverse proxy and forward to the socket or a local port. feedwell trusts the `X-Forwarded-For` and `X-Forwarded-Proto` headers only when `trusted_proxies` is set in `config.toml`, so configure that to match your proxy's address before relying on it for logging or rate limiting.

## Database backends

feedwell uses SQLite by default — a single file, zero configuration, and enough for the overwhelming majority of self-hosted, single- or few-user installs. The default `database.url` is:

```
sqlite:///data/feedwell.db
```

For larger installs, multi-user deployments, or if you want the database on separate storage from the app, PostgreSQL is fully supported:

```
postgresql://feedwell:yourpassword@localhost:5432/feedwell
```

Switching backends after initial setup requires a fresh `db init` against the new URL; feedwell does not migrate data between backends automatically. If you need to move an existing SQLite install to Postgres, use `python -m feedwell.db export` and `import` to dump and reload articles, feeds, and read-state.

## Scheduling feed polling

feedwell does not poll feeds on its own in the background — polling is a separate command intended to be run on a schedule, keeping the web process itself lightweight and stateless:

```bash
python -m feedwell.poll
```

A typical cron entry, polling every fifteen minutes:

```
*/15 * * * * cd /opt/feedwell && venv/bin/python -m feedwell.poll >> /var/log/feedwell-poll.log 2>&1
```

The poll command respects each feed's `<ttl>` hint and any `Cache-Control` headers from the last fetch, so setting cron more aggressively than fifteen minutes rarely pulls fresher content — it mostly just adds load on the feeds you're polling.
