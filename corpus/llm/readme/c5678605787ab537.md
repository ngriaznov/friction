# backupctl

A small collection of bash scripts that automate nightly backups of a LAMP stack server. `backupctl` dumps every MySQL database, rsyncs the web root to a backup directory, rotates old archives, and provides a restore script that reverses the whole process.

## What it backs up

- **MySQL**: a `mysqldump` of every database the configured user can see, one `.sql.gz` file per database.
- **Web root**: an `rsync -a --delete` mirror of your document root into a dated archive directory.
- **Rotation**: anything older than the configured retention window is deleted automatically after each successful run.

## Required environment variables

Set these in `/etc/backupctl/backupctl.env` (root-readable only, `chmod 600`):

```bash
DB_HOST=localhost
DB_USER=backup_user
DB_PASSWORD=change_me
WEB_ROOT=/var/www/html
BACKUP_DIR=/var/backups/backupctl
RETENTION_DAYS=14
```

`DB_USER` needs `SELECT`, `LOCK TABLES`, and `SHOW VIEW` privileges at minimum on every database you want dumped.

## Installing the cron entry

Copy `backupctl.sh` to `/usr/local/sbin/backupctl.sh`, make it executable, then add:

```cron
0 2 * * * root /usr/local/sbin/backupctl.sh >> /var/log/backupctl.log 2>&1
```

This runs the full backup at 2 AM daily. Logs go to `/var/log/backupctl.log`; check there first if a scheduled run doesn't produce the archives you expect.

## Where backups live

Each run creates a timestamped subdirectory under `BACKUP_DIR`:

```
/var/backups/backupctl/
  2024-06-01T02:00/
    databases/
      app_production.sql.gz
      analytics.sql.gz
    webroot/
      ... mirrored web root ...
```

Retention is enforced by deleting any subdirectory older than `RETENTION_DAYS`, checked at the end of every run — so a broken cron schedule won't cause storage to grow unbounded once it starts working again, but it also means a very long gap between runs can leave you with fewer backups than expected.

## Restoring from a backup

`restore.sh` takes a timestamp directory name and reverses the process:

```bash
sudo ./restore.sh 2024-06-01T02:00
```

This will:

1. Prompt for confirmation before touching anything (pass `--force` to skip in scripted contexts).
2. Restore each `.sql.gz` file into its matching database via `gunzip | mysql`.
3. Rsync the archived web root back over `WEB_ROOT`, again with `--delete`, so files removed since the backup are also removed on restore.

Run it on a test server before you ever need it on a production one — `restore.sh` is destructive by design, and the whole point of `--delete` mirroring is that it makes the target match the archive exactly.

## Requirements

`bash`, `mysqldump` and `mysql` clients, `rsync`, and `gzip`. Tested on Debian and Ubuntu; should work anywhere those tools are present.
