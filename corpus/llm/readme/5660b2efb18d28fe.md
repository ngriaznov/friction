# feedwell

A self-hosted RSS and Atom reader with a small web UI. It runs behind any WSGI server, keeps its state in a database you control, and does not phone home.

feedwell exists because most hosted readers eventually change their pricing, their layout, or their shutdown date. This one is about 4,000 lines of Python, has no JavaScript build step, and will keep working as long as you keep the process running.

## Features

- **Folder organization.** Feeds live in nested folders. Drag them around in the UI or edit the tree from the subscriptions page.
- **Read/unread tracking.** Per-article state, with keyboard navigation (`j`/`k` to move, `m` to toggle read, `o` to open the original link).
- **Full-text search.** Article bodies are cached at fetch time and indexed, so search covers the text of everything you've ever pulled down — including articles the publisher has since deleted or edited.
- **OPML import/export.** Bring your subscriptions in from whatever you're leaving, and take them with you if you leave this.
- **Starred items** with their own view, and a per-feed "keep everything" flag that exempts a feed from retention pruning.

## Requirements

- Python 3.10 or newer
- A WSGI server (gunicorn, uWSGI, Waitress — anything)
- SQLite (bundled with Python) or PostgreSQL 13+

## Installation from source

```
git clone https://github.com/example/feedwell.git
cd feedwell
python3 -m venv .venv
source .venv/bin/activate
pip install -e .
```

For PostgreSQL support, install the optional extra:

```
pip install -e ".[postgres]"
```

Copy the sample configuration and edit it:

```
cp feedwell.example.toml feedwell.toml
```

The two settings that matter on a fresh install are `database_url` and `secret_key`. Generate a key with `python -m feedwell genkey` and paste the result in.

## First run

Initialize the schema and create the first account:

```
feedwell db init
feedwell createadmin
```

`createadmin` prompts for a username and password interactively. It refuses to run if an admin account already exists — use `feedwell passwd <username>` to reset a password instead.

Then start it. For a quick look:

```
feedwell serve --host 127.0.0.1 --port 8080
```

The built-in `serve` command uses Waitress and is fine for a handful of users on a home network. For anything exposed to the internet, run it under gunicorn behind a reverse proxy that terminates TLS:

```
gunicorn -w 4 -b 127.0.0.1:8080 feedwell.wsgi:application
```

The WSGI callable reads `FEEDWELL_CONFIG` from the environment to find `feedwell.toml`. If unset, it looks in the current directory and then `/etc/feedwell/`.

## Database backends

SQLite is the default and is the right choice for a single-user instance. The database file lives wherever `database_url` points:

```toml
database_url = "sqlite:///var/lib/feedwell/feedwell.db"
```

Full-text search on SQLite uses FTS5, which is compiled into most distribution Python builds. If `feedwell db init` reports that FTS5 is unavailable, search will fall back to a slower `LIKE` scan; everything else works.

PostgreSQL is worth it if you have more than a few users, or more than roughly 50,000 cached articles, where the FTS5 index starts to feel it:

```toml
database_url = "postgresql://feedwell:secret@localhost/feedwell"
```

Search on Postgres uses `tsvector` with a GIN index, and handles stemming better than the SQLite path. Migrating between backends is a `feedwell db dump` followed by `feedwell db load` against the new URL; article state and folder structure carry over, cached bodies included.

## Scheduling feed polling

feedwell does not run its own scheduler. Polling is a separate command that fetches every feed whose interval has elapsed, and it is safe to run more often than any individual feed's interval:

```
feedwell poll
```

Install a cron entry as the user that owns the database:

```
*/15 * * * * /opt/feedwell/.venv/bin/feedwell poll --quiet >> /var/log/feedwell/poll.log 2>&1
```

Every fifteen minutes is a reasonable default. Per-feed intervals are set in the UI (default 60 minutes) and `poll` respects them, so a tighter cron schedule only means feeds get picked up closer to when they're actually due, not that publishers get hammered.

`poll` honors HTTP caching — `ETag` and `Last-Modified` are stored per feed and sent on subsequent requests, so a feed that hasn't changed costs one 304 response. It also backs off automatically: a feed that errors gets its effective interval doubled, up to a cap of 24 hours, and reset on the first success. Persistent failures show as a warning badge on the subscriptions page rather than silently disappearing.

Add `--feed <id>` to poll a single feed, which is useful when debugging a specific publisher's malformed XML.

## Retention

By default, articles are pruned 180 days after publication unless starred or belonging to a feed marked keep-everything. Change it with `retention_days` in the config, or set it to `0` to keep everything forever. Pruning happens during `poll`, so it needs no separate cron entry.
