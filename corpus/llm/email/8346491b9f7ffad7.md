**To:** platform-api@  
**Cc:** mobile-eng@, dana.okonkwo@ (PM, Discovery)

Hi all,

I'm building the redesigned catalog search screen for the 4.2 mobile release and I need a new endpoint. The existing `/v2/catalog/search` doesn't fit the new design — details below — and rather than pile more query parameters onto it, I think a `/v3` endpoint is the cleaner path. I've tried to write this up in enough detail that you can size it without a meeting, but I'm happy to do a working session if that's faster.

## What we're building

The new screen replaces the current three-tab search (Products / Sellers / Collections) with a single scrolling result list over products only, plus a filter sheet and a sort control. Sellers and collections move to a separate discovery surface, so this endpoint only needs to return products.

The list is infinite-scroll with a page size of 24. Users can change filters and sort without leaving the screen, which means we re-query frequently and need responses fast enough that the list doesn't feel like it's reloading from scratch. Design is targeting a perceived response under 400 ms on a warm connection.

## Why the existing endpoint doesn't work

Three things:

1. **Offset pagination.** `/v2/catalog/search` takes `page` and `per_page`. Our catalog changes constantly — items go out of stock, new listings land — and with offset paging users see duplicates and skipped items while scrolling. QA filed this twice against 4.0 and we closed both as won't-fix because the fix was this endpoint.

2. **No combined filters.** v2 accepts a single `category` and a single `price_max`. The new filter sheet lets users combine category, price range, condition, shipping speed, and seller rating in one query.

3. **Response weight.** v2 returns the full product object, including the description body and the complete image array. For a 24-item list where we render a thumbnail, title, price, and two badges, we're pulling roughly 40 KB per page that we throw away. On the low-end Android devices in our top-five markets this is a real cost.

## Proposed request shape

```
GET /v3/catalog/search
```

Query parameters:

| Param | Type | Required | Notes |
| --- | --- | --- | --- |
| `q` | string | no | Free-text query. Absent means "browse everything matching the filters." |
| `cursor` | string | no | Opaque. Absent means first page. |
| `limit` | int | no | Default 24, max 50. |
| `sort` | enum | no | See below. Default `relevance`. |
| `category_ids` | repeated int | no | OR within the parameter. |
| `price_min`, `price_max` | int (minor units) | no | Inclusive. |
| `condition` | repeated enum | no | `new`, `like_new`, `used`, `refurbished`. |
| `ships_within_days` | int | no | Matches listings whose stated handling + transit is at or under this. |
| `seller_rating_min` | float | no | 0.0–5.0, one decimal. |

Sort options we need, in priority order:

- `relevance` (default; ignored when `q` is absent, in which case treat as `newest`)
- `price_asc`
- `price_desc`
- `newest`
- `rating_desc`

If `rating_desc` is expensive to support I can drop it from 4.2 — design has it behind a "more" disclosure and we could ship without it. The other four are load-bearing.

**One request:** please make `sort` and the filter set part of the cursor's encoded state, and reject a request that supplies a `cursor` alongside a different filter set with a 400 rather than silently re-anchoring. We got burned by a silently-reset cursor on the orders endpoint last year and spent a day on it.

## Proposed response shape

```json
{
  "results": [
    {
      "id": "prod_8812f",
      "title": "Cast iron skillet, 10 inch",
      "price": { "amount": 3400, "currency": "USD" },
      "compare_at_price": { "amount": 4200, "currency": "USD" },
      "thumbnail": {
        "url": "https://cdn.example.com/p/8812f_400.webp",
        "width": 400,
        "height": 400,
        "blurhash": "L6PZfSjE.AyE_3t7t7R**0o#DgR4"
      },
      "condition": "used",
      "seller": { "id": "sel_31a", "name": "Harbor Goods", "rating": 4.7 },
      "badges": ["free_shipping", "ships_today"],
      "in_stock": true
    }
  ],
  "next_cursor": "eyJvIjoxMjA...",
  "total_estimate": 1840,
  "facets": {
    "category": [ { "id": 44, "label": "Cookware", "count": 210 } ],
    "condition": [ { "value": "used", "count": 903 } ]
  }
}
```

Notes on the shape, in case any of it is contentious:

- **`next_cursor` null means end of results.** Please don't return an empty string or omit the key — both make the client logic ambiguous.
- **`total_estimate` is explicitly an estimate.** Design shows "About 1,800 results" and is fine with imprecision. If an exact count is cheap, great, but don't add latency for it.
- **`blurhash` on the thumbnail** lets us show a placeholder while images load. This matters a lot on the scroll experience. If blurhash isn't practical, a dominant-color hex string is an acceptable substitute.
- **`facets`** drive the counts next to each filter option in the sheet. If facet computation is the expensive part of this endpoint, I'd rather have it behind a `include_facets=true` flag that we only send when the user opens the filter sheet, than have it slow down every scroll page.
- **Prices as integer minor units**, please, not decimal strings or floats.

## Error handling

Standard envelope is fine. The specific cases I need to distinguish:

- Invalid or expired cursor → 400 with code `cursor_invalid` so we can silently restart the list from the top rather than showing an error.
- Rate limited → 429 with `Retry-After`.
- Backend degraded → 503, and if there's a partial-results mode where search falls back to a simpler ranking, a `degraded: true` field in the response would let us suppress the "no results" empty state incorrectly firing.
