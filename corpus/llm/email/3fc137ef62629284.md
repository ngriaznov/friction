Subject: Incident summary — analytics dashboard showed stale data for three days (Aug 12–15)

Hi all,

Below is the summary for the incident where the daily analytics dashboard displayed stale numbers for three consecutive days before it was caught. This affected the customer-facing usage dashboard only; billing and internal reporting pipelines were not affected, since they run through a separate ingestion path. I want to walk through the timeline in some detail because the way this was discovered says as much about the gap in our monitoring as the root cause does, and I'd rather we all see that clearly than get the short version.

## Summary

For three days, the daily aggregation job that populates the usage dashboard silently failed to run, and the dashboard continued displaying the last successfully computed totals without any indication that the data was stale. No alert fired, because no alert existed for this specific failure mode. The issue was discovered on the third day when a customer emailed support asking why their reported usage hadn't changed since the previous week, despite their team actively using the product. Support escalated to engineering, who traced it to a data pipeline task that had been failing quietly since day one.

## Timeline

**Day 1, 2:15 AM UTC** — The daily Airflow DAG that aggregates raw event data into the usage summary table kicked off on schedule, as it does every night. The task responsible for pulling the prior day's raw events from the event store failed partway through, due to a schema change in an upstream event table (a new nullable column was added by an unrelated team's deploy earlier that day) that the task's SQL query wasn't written to tolerate. The failure was a Python exception inside a try/except block that had originally been added months earlier to handle a different, transient, and since-resolved issue — a retryable connection timeout to the event store. That except block logged the exception at INFO level and then allowed the DAG to proceed to its next task and ultimately report success, rather than re-raising and failing the DAG.

**Day 1, through Day 3** — The aggregation job "succeeded" each night by this same path, three nights running, each time failing to update the usage summary table and each time reporting green. The dashboard, which reads directly from that summary table, kept showing the numbers from the last real successful run, two nights before day 1. Nothing in our alerting stack flagged this, because our existing DAG monitoring only tracks task and DAG success/failure status, and this DAG was reporting success throughout.

**Day 3, 11:40 AM UTC** — A customer emailed support asking why their team's usage numbers hadn't moved in what looked like over a week, despite daily active use. Support could not explain the discrepancy from the dashboard itself and opened an internal ticket.

**Day 3, 1:05 PM UTC** — An engineer on the data platform team picked up the ticket, queried the underlying summary table directly, and confirmed its `updated_at` timestamp hadn't advanced in three days, despite the DAG runs for those three days showing as successful in the Airflow UI.

**Day 3, 1:50 PM UTC** — The engineer traced the stale timestamp to the raw event pull task, found the swallowed exception in the logs (which had been quietly accumulating there the whole time, just never surfaced anywhere anyone was looking), and identified the schema change as the trigger.

**Day 3, 3:30 PM UTC** — A patch was deployed to the task's query to explicitly select the columns it needs rather than relying on `SELECT *`, which both fixes the immediate breakage and removes the class of bug where an unrelated upstream schema change breaks this task silently in the future.

**Day 3, 4:15 PM UTC** — The DAG was manually triggered and completed successfully, backfilling three days of aggregation in one run. The dashboard reflected correct, current numbers by 5:00 PM UTC that day.

## Root cause

The proximate cause was a schema change to an upstream table that broke a `SELECT *` query the aggregation task depended on. But the reason this went undetected for three days, rather than being caught and fixed the same night it started, is the real root cause: a broad exception handler in the task swallowed the failure and let the DAG report success, and our monitoring only checks DAG-level success/failure, not whether the DAG's actual output — the summary table — was updated as expected. A DAG can be "green" while doing nothing useful, and we had no independent check catching that.

## Customer impact

The usage dashboard showed data current only through the night before day 1 for the full three-day window. No other customer-facing systems were affected: billing calculations, usage-based alerting for customers near their plan limits, and the API all read from a different, unaffected pipeline. One customer contacted support directly; we don't have visibility into how many others noticed without reaching out, so we're treating the reported case as a lower bound rather than the full extent.

## Fix and follow-up actions

The immediate fix — rewriting the query to select explicit columns instead of `SELECT *` — is already deployed, and the affected days have been backfilled with correct data.

Beyond that, we're making the following changes:

1. **Remove the broad exception handler**, or narrow it to catch only the specific transient connection error it was originally written for, so that any other failure inside this task causes the DAG to fail loudly. Owner: data platform team. Due: this Friday.
2. **Add a freshness check as a separate monitored step**, independent of the DAG's own success reporting, that verifies the summary table's `updated_at` timestamp has advanced within the expected window after each run, and pages on-call if it hasn't. This is the check that would have caught this within hours instead of days. Owner: data platform team. Due: next Friday.
3. **Audit other DAGs for similarly broad exception handlers** that could mask a failure as a success, since we suspect this pattern isn't unique to this one task. Owner: data platform team, with support from whoever owns each DAG found. Due: two weeks out.
4. **Add a lightweight cross-team notice for schema changes to shared event tables**, so that teams consuming those tables get a heads-up before a column is added or changed, rather than discovering it via a downstream failure. Owner: data platform team, in coordination with the events infrastructure team. Due: three weeks out, since this involves agreeing on a process with another team.

Happy to answer questions, and I'll post an update here once the freshness-check work lands.
