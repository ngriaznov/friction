Hi all,

Writing up yesterday's outage while it's fresh. Short version: our public website and checkout flow were unreachable for 40 minutes because the TLS certificate on the edge load balancer expired. Automated renewal had been failing quietly for eleven days and nobody saw it. No data was lost or exposed. This is a process failure, not a security incident.

## Timeline (all times UTC)

- **14:00** — Certificate for `www.example-retail.com` and `checkout.example-retail.com` reaches its notAfter time. Browsers begin showing interstitial warnings. API clients using strict verification start failing handshakes.
- **14:03** — First customer report arrives in support chat. Support initially triages it as a single-user browser problem, which is reasonable given how it looked from the ticket.
- **14:09** — Synthetic checks in the external monitor flip to failing. This did page, but to the on-call rotation for the checkout service rather than platform, because the check is registered under that service's ownership.
- **14:11** — Checkout on-call acknowledges, sees healthy application metrics, and escalates.
- **14:18** — Platform on-call joins and identifies the expired certificate from the load balancer's TLS status endpoint.
- **14:26** — A replacement certificate is issued manually from the CA's web console.
- **14:34** — Certificate installed on both edge nodes, config reloaded.
- **14:40** — Synthetics green. Manual verification of checkout completes at 14:44.

Total customer impact: 40 minutes of failed page loads and API handshakes. Support logged 61 tickets. Finance estimates roughly 340 abandoned checkouts based on the same weekday-hour comparison we've used for previous incidents.

## Why automated renewal failed

We renew through an ACME client running as a scheduled job on the edge nodes. It uses the DNS-01 challenge, which requires writing a TXT record to our zone via the DNS provider's API.

On 3 October, as part of a routine credential rotation, the DNS provider API token used by the ACME client was replaced. The new token was scoped correctly for the zones we manage, but the rotation script updated the token in our secrets store without restarting the ACME client's systemd unit — the client had the old token cached in memory and in its own on-disk config, which it reads only at startup.

From 3 October onward, every renewal attempt failed at the DNS challenge step with a 401 from the provider. The client logged this at `WARN` and exited non-zero. The systemd timer was configured with `OnFailure=` pointing at a unit that was removed during an unrelated cleanup in August, so the failure notification went nowhere. Nothing else was watching.

Two more layers should have caught this and didn't:

1. **Certificate expiry monitoring.** We have a check for this. It alerts at 14 days remaining. The certificate had a 90-day lifetime and renewal normally happens at 30 days out, so the check fired on 22 October — into a Slack channel (`#platform-noise`) that the team muted last quarter when a different alert became chatty. The message is in the scrollback. Nobody read it.
2. **Ownership of the synthetic check.** The check that would have caught this fastest was routed to the wrong on-call, costing us about nine minutes.

## What we're changing

Owner and date on each; all tracked under INC-2214 in the platform board.

- **Rotation runbooks must include a service-restart step.** Any credential rotation now requires listing every consumer of that credential and how it picks up changes. The DNS token rotation runbook has already been updated. *(Priya, done)*
- **ACME client reads its token from the secrets store on every run**, not at startup. Removes the class of failure entirely for this client. *(Marcus, 14 Nov)*
- **Certificate expiry alerts become pages, not chat messages.** Two thresholds: a ticket at 21 days, a page at 7 days. Routed to platform on-call. *(Dana, 8 Nov)*
- **Audit every `OnFailure=` target in our systemd units.** We found three more units pointing at the removed handler. *(Marcus, 21 Nov)*
- **Review synthetic check ownership across all services.** Roughly 40 checks to go through; we'll do it in one sitting rather than trickling it out. *(Dana, 28 Nov)*
- **Muted-channel audit.** If an alert is noisy enough to mute, it's either not an alert or it needs fixing. We'll go through the muted channels and decide which per alert. *(Priya, 5 Dec)*
