**Subject:** Home lab rebuild: pfSense box, IoT VLAN, and two evenings lost to an MTU mismatch

Hi all,

Long one, sorry. I finished the rebuild I'd been threatening to do since spring and figured the NAS problem at the end is worth writing up, because I went down two wrong paths before finding the actual cause and I suspect at least one of you has the same trap set in your rack right now.

**The new router**

I retired the consumer router that had been holding everything together. It had been rebooting itself roughly every ten days and no amount of firmware fiddling fixed it.

The replacement is a small four-port fanless box — Celeron N5105, 8 GB RAM, four 2.5 GbE Intel NICs — running pfSense. About £190 including a used SSD I had in a drawer. It's overkill for a 500/75 line, but the whole point was to stop treating the router as an appliance and start treating it as a machine I can actually inspect.

Install was uneventful. WAN on the first port, LAN on the second, the other two currently unused but earmarked for a second AP run and eventually a link to the garage. Everything downstream is a managed 8-port switch doing 802.1Q.

The immediate wins were unglamorous and enormous: real DHCP static mappings that survive reboots, a resolver I control, and — the thing I didn't expect to care about as much as I do — actual state table and per-interface traffic graphs. Turns out one of my "idle" devices was doing 40 GB a month. It's a robot vacuum. I have no idea what it's saying and that's precisely why the next section exists.

**VLAN segmentation**

Four VLANs now:

- 10 — trusted (laptops, phones, desktop)
- 20 — IoT (vacuum, TV, thermostat, plugs, the doorbell)
- 30 — servers (Proxmox cluster, NAS)
- 40 — guest

The IoT rules are the strict ones. VLAN 20 can reach the internet and nothing else. No access to 10, no access to 30, no access to the router's web UI, and DNS forced to the pfSense resolver with an outbound NAT rule so the devices that hard-code 8.8.8.8 get quietly redirected instead of bypassing me.

Two things bit me here that are obvious in hindsight. First, mDNS doesn't cross VLANs, so the TV vanished from casting on my phone. I installed the Avahi package on pfSense and repeated mDNS between 10 and 20, which brings back discovery without opening general traffic. Second, my printer is technically an IoT device but I actually want to print from VLAN 10, so it got a single allow rule to port 9100 and 631 from trusted only. Purity lost to practicality about four minutes into real use, as it always does.

Rule of thumb I'd pass on: build the block rules first, then add the narrow allows as things break. Doing it the other way round means you never find out what was silently permitted.

**The NAS problem**

Here's the part worth the email.

The NAS and the three-node Proxmox cluster both moved to VLAN 30. Proxmox mounts a couple of NFS shares off the NAS for VM disks and backups. After the migration, the mounts hung. Not failed cleanly — hung, then eventually timed out with `mount.nfs: Connection timed out`.

Basic checks all passed. Ping from a Proxmox node to the NAS: fine, sub-millisecond. `showmount -e` against the NAS: returned the export list correctly. `nc -zv nas 2049`: open. Every diagnostic said the path was healthy, and yet nothing would mount.

First wrong theory: pfSense firewall. I spent an evening staring at rules and reading the state table, convinced something was being dropped. It wasn't — both hosts are on the same VLAN, so that traffic never touches the router at all. I'd built a mental model where pfSense was in the path and then debugged the model instead of the network. Embarrassing, and I'd guess common.

Second wrong theory: NFS version negotiation. I forced `vers=3`, then `vers=4.1`, tried `tcp` explicitly, disabled and re-enabled the export. Same hang each time. What I should have noticed sooner was the *shape* of the failure: the small stuff worked and the big stuff didn't. Ping worked. RPC portmapper queries worked. The actual mount, which pushes larger frames, didn't.

That's an MTU problem, and once I'd thought the words the test was thirty seconds:

```
ping -M do -s 1472 nas   # ok
ping -M do -s 8972 nas   # 100% loss
```

The NAS and the Proxmox NICs were both configured for jumbo frames, MTU 9000, carried over from the old flat network where they'd been on a dedicated switch that supported it. The new managed switch was happily passing tagged traffic but was still at its default 1500 on the ports in question — I'd configured VLANs on it and never touched the frame size settings, which live on a completely different page of its interface.

So: both endpoints believed they could send 9000-byte frames, the switch silently discarded them, and small packets sailed through the whole time to reassure me that everything was connected.

The fix was to raise the switch's maximum frame size to 9216 (it wants the value including headers, which is its own little gotcha — 9000 wasn't enough and produced exactly the same failure) and reboot it. Mounts came up instantly.

If you don't need jumbo frames — and honestly at 1 GbE with modern offload you probably don't — the easier fix is to set everything back to 1500 and stop thinking about it. I kept 9000 because the backup window genuinely shortened, from about 50 minutes to 34 for the nightly run. But I've now written the MTU value on a label stuck to the switch, because future me will absolutely not remember this.
