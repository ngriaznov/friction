Subject: Incident Summary: Three Days of Stale Analytics Dashboard Data

Team,

I want to walk through what happened with the analytics dashboard over the past week, since this one stayed hidden longer than any of us are comfortable with, and I think there are real lessons in how it went unnoticed.

**Summary**

Between Monday and Wednesday of last week, the daily analytics dashboard displayed stale data — specifically, numbers frozen at Sunday night's values, not reflecting three full days of actual activity. The dashboard itself never went down or threw errors; it simply kept showing old, increasingly wrong numbers as if nothing were wrong, which is part of why this took as long as it did to catch.

**How it was discovered**

We did not catch this internally. A customer on our analytics team's mid-market tier reached out to support on Wednesday afternoon, noting that their week-over-week totals looked "flat in a way that doesn't match what we're seeing in our own systems." Support initially treated this as a possible confusion about time zones or reporting periods, which is a common and reasonable first read on this kind of ticket. It was only when a second, unrelated customer flagged something similar later that same afternoon that support escalated to the data platform team, at which point one of our engineers pulled up the dashboard, compared it against raw event counts in the underlying data warehouse, and immediately saw the mismatch — the dashboard's daily totals hadn't moved in three days, while the raw event volume in the warehouse had continued growing normally.

I want to be direct about this: the fact that two paying customers noticed a problem in our own systems before we did is not acceptable, and it's the primary reason the follow-up section below is as extensive as it is.

**Root cause**

The dashboard is populated by a nightly Airflow DAG that aggregates the previous day's raw events into summary tables. Investigation traced the failure to a single task within that DAG — the `aggregate_daily_events` task — which had begun silently failing three days earlier, coinciding with a schema change deployed to one of the upstream event tables. The schema change added a new nullable column; a downstream transformation step in the task performed a strict column-count validation that hadn't been updated to account for the new column, causing the task to raise an exception and fail.

Here is the part that made this genuinely hard to catch: the DAG was configured with `retries: 0` and, critically, had no failure alerting configured on this particular task. Airflow marked the task as failed in its own UI, which almost nobody was actively watching, but no Slack alert, no PagerDuty page, and no email fired to notify anyone. Because the task failure didn't cascade to any downstream process that customers or internal teams actively monitor — the dashboard simply kept serving the last successfully computed data, rather than showing an error or a "data unavailable" state — there was no forcing function that would have surfaced this to a human before a customer did.

We've since confirmed this task has existed in something close to its current form for over a year, and as far as we can tell, it has never had failure alerting configured, meaning this exact failure mode has been possible the entire time and we simply got unlucky that a schema change happened to trigger it now rather than something else doing so earlier.

**The fix**

Once identified, remediation had two parts:

1. **Immediate fix**: We patched the `aggregate_daily_events` task to handle the new nullable column correctly, removing the strict column-count check in favor of an explicit schema validation that fails loudly and specifically if columns are missing, rather than silently passing or crashing on an unrelated assertion.

2. **Backfill**: We re-ran the aggregation for all three affected days against the correct source data. This required a manual trigger since the DAG's default scheduling window had already moved past those dates, and we validated the backfilled numbers against raw warehouse counts before restoring the dashboard, to make sure we weren't just replacing one wrong number with another. The dashboard was showing fully correct, current data again by Thursday morning, roughly 18 hours after the customer report came in.

We reached out proactively to both customers who reported the issue, along with three other accounts on the same tier who we determined had likely viewed the stale dashboard during the affected window, to explain what happened and confirm the data is now correct. We think this kind of direct outreach matters more than a blanket status page note for an issue that specifically affected data customers were actively relying on for decision-making.

**New monitoring being added**

The core problem here wasn't really the schema change or even the task failure — task failures happen, and always will. The core problem is that a critical task failed silently for three days with no alerting whatsoever. We're addressing that at a few levels:

1. **Task-level alerting**: All tasks in the daily aggregation DAG now have failure alerting configured to page the data platform on-call channel immediately on failure, not just log to the Airflow UI. This is being extended to every production DAG this team owns, not just this one — owner: Data Platform (Yusuf), due end of this week.

2. **Freshness monitoring on the dashboard itself**: We're adding an independent freshness check that compares the dashboard's most recent data timestamp against the current date and fires an alert — and eventually shows a visible "data may be stale" banner on the dashboard itself — if the gap exceeds a defined threshold. This gives us a safety net even if a future failure mode doesn't trip task-level alerting for some reason we haven't anticipated — owner: Data Platform (Yusuf), due in two weeks.

3. **DAG audit**: We're auditing every production DAG in the data platform for missing failure alerting, since this task is very unlikely to have been the only one in this state. Initial audit is roughly 40% complete as of this writing and has already turned up two other DAGs with the same gap, which we're prioritizing separately — owner: Data Platform (Priya), due in three weeks.

4. **Schema change process**: We're introducing a lightweight review step for schema changes to upstream event tables that flags downstream consumers, so a change like the one that triggered this doesn't land without at least a heads-up to teams with dependent pipelines — owner: Data Engineering (Marcus), due in three weeks.

I'll post an update in this thread once the alerting work lands, and we'll do a short retro in next week's data platform sync to make sure the DAG audit findings get properly triaged rather than sitting in a backlog. Apologies for the impact here, and thank you to everyone who jumped on the investigation and backfill quickly once we knew what we were looking at.

— Data Platform Team
