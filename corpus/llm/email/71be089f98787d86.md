Subject: Incident Summary: Payment API Outage (2 hours) — [date]

Team,

Below is a summary of yesterday's payment processing API outage.

**Timeline**

- 2:14 PM — Deploy of payment-service v4.12 completed, including an updated connection pool configuration.
- 2:19 PM — Error rate alerts fire for payment-service; on-call engineer acknowledges within 3 minutes.
- 2:31 PM — Root cause identified as connection pool exhaustion; the new config set max pool size to 10, down from the previous 100, due to a misapplied environment variable during the deploy.
- 2:52 PM — Rollback to v4.11 initiated.
- 3:40 PM — Rollback completes; error rates begin recovering but remain elevated due to a backlog of queued requests.
- 4:16 PM — Error rates return to baseline; incident declared resolved.

Total duration: approximately 2 hours from first alert to full recovery.

**Root cause**

The v4.12 deploy included a connection pool configuration change intended for our staging environment. Due to a misconfigured deployment template, this staging value (max pool size of 10) was applied in production instead of the intended production value (max pool size of 100). Under normal production load, a pool of 10 connections was quickly exhausted, causing new payment requests to queue and time out.

**Customer impact**

Approximately 2 hours of degraded to unavailable payment processing. Roughly 6% of payment attempts during the window failed outright and were shown an error; the majority of remaining attempts succeeded but with elevated latency (several seconds to tens of seconds). No customer payment data was lost or duplicated — failed transactions were not charged.

**Follow-up actions**

1. Add environment-specific validation to the deploy pipeline to catch mismatched config values before rollout — owner: Infra team (Raj), due in 1 week.
2. Add an alert on connection pool utilization to catch exhaustion before it causes customer-facing errors — owner: Payments team (Lin), due in 1 week.
3. Require a second reviewer on any deploy touching connection pool or resource-limit configuration — owner: Payments team (Lin), due in 3 days.
4. Post-incident review of the deployment template system to identify other configs at similar risk — owner: Infra team (Raj), due in 2 weeks.

We'll follow up in the incident channel once each action item is closed. Thanks to everyone who jumped on this quickly.

— On-call incident commander
