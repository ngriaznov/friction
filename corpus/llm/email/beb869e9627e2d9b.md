Subject: Incident Summary: Payment Processing API Outage (2 hours, resolved)

Hi all,

Below is a summary of today's payment processing API outage. The service is fully restored and processing transactions normally. Details follow.

**Impact**

Between 10:14 AM and 12:09 PM UTC, the payment processing API returned elevated error rates, peaking at roughly 78% of requests failing with connection timeouts. Any customer attempting to complete a checkout or subscription renewal during that window was likely affected. We estimate approximately 6,400 transaction attempts failed outright; a subset of those customers retried successfully once the service recovered, but we cannot confirm how many gave up before then.

**Timeline**

- 10:14 AM — Deploy of payment-api v2.41.0 completes, rolling out a change to database connection handling.
- 10:19 AM — Automated alerts fire for elevated 5xx rates on the payment-api service.
- 10:26 AM — On-call engineer acknowledges the page and begins investigating; connection pool exhaustion is identified in service logs.
- 10:52 AM — Root cause confirmed: the new deploy set the connection pool's max size lower than the service's peak concurrency needs, causing requests to queue and time out under normal traffic.
- 11:15 AM — Rollback to v2.40.2 initiated.
- 11:48 AM — Rollback completes across all instances; error rates begin dropping.
- 12:09 PM — Error rates return to baseline; incident declared resolved.

**Root cause**

The v2.41.0 deploy changed how the service configures its database connection pool. A default value was applied that was appropriate for staging traffic levels but well below what production concurrency requires, causing connections to be exhausted almost immediately after rollout.

**Follow-up actions**

- Add a pre-deploy check that fails the pipeline if pool size configuration falls below a documented production floor. Owner: Priya, due Friday.
- Add an alert on connection pool saturation specifically, rather than relying solely on downstream 5xx rate. Owner: Marcus, due next Wednesday.
- Update the deploy runbook to require an explicit config diff review for any change touching connection pool settings. Owner: Priya, due Friday.
