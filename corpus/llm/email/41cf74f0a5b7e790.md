**Subject:** Incident summary — Payments API degradation, Nov 14 (INC-2291)

All,

Between 13:42 and 15:38 UTC yesterday, the Payments API returned elevated 5xx errors. Roughly 31% of authorization requests failed during that window. This is the summary; the full postmortem doc is linked at the bottom and the review is Thursday at 10:00.

**Timeline (UTC)**

- **13:35** — Release `payments-api v4.18.0` finishes rolling out across all three regions.
- **13:42** — Error rate crosses 5%. Automated page fires to payments-oncall.
- **13:49** — Priya acknowledges and opens the bridge. Initial suspicion is the upstream processor, since latency to it is also elevated.
- **14:20** — Processor confirms no issues on their side. Attention shifts to our own service.
- **14:55** — Marcus notices `pool_wait_ms` p99 at 8,400ms and connection acquisition timeouts in the logs.
- **15:11** — Decision to roll back to v4.17.3.
- **15:38** — Rollback complete in all regions. Error rate returns to baseline.

**Root cause**

v4.18.0 included a refactor of our database configuration loading. A change to how defaults are merged caused the per-instance connection pool maximum to fall back to 10 instead of the configured 60. Under normal traffic each instance needs 40–50 connections; requests queued waiting for a free connection, hit the 5s acquisition timeout, and returned 500s. The value is not asserted in any test and is not exposed in a health check, so nothing caught it before or after deploy.

**Customer impact**

Approximately 47,000 failed authorization attempts across 1,900 merchants. No incorrect charges, no data loss, no double-captures. Support has the affected merchant list and is sending notifications today.

**Action items**

1. Add a startup assertion that fails the boot if pool max is below a floor value — *Marcus, Nov 21*
2. Expose pool configuration in `/health/detail` and add a dashboard panel — *Priya, Nov 25*
3. Alert on `pool_wait_ms` p99 above 500ms — *Dana, Nov 25*
4. Config-merge regression tests covering default fallback paths — *Marcus, Dec 2*
5. Add pool saturation to the standard post-deploy check in the release runbook — *Jules, Nov 28*
